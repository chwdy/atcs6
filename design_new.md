# ATCS6 Desired Design Model

This document defines the target refactor contracts and changed cross-component behavior for the current ATCS6 codebase.
It is intended to guide an engineer refactoring the existing implementation, not to replace the code as a complete standalone implementation spec.
Unchanged entity-local fields, helper internals, and serialization details continue to follow the current code unless this document states otherwise.
If current code conflicts with a changed contract stated here, this document wins.

Implementation note: use `design_new_implementation_index.md` as the compact working map during coding. This file remains the authoritative source for changed contracts.


## Scope

Primary files reviewed:

- `simulation.py`
- `train.py`
- `train_controller.py`
- `train_physics.py`
- `block.py`
- `block_manager.py`
- `path.py`
- `path_dispatcher.py`
- `route_executor.py`
- `train_route.py`
- `track.py`
- `switch.py`
- `network.py`
- `speed_profile.py`
- `block_power.py`

Terminology:

- `path`: a dispatcher-managed reserved movement authority between blocks.
- `route`: a higher-level travel plan made of stop / `pass_through` waypoints that ultimately resolve to concrete block targets.
- `route run`: the per-train runtime instance of an assigned route. It references one shared `Route` definition but owns that train's mutable execution state: waypoint cursors, the current resolved target scratch value, dwell timing, and active-path correlation. Current-code implementation may still keep the class name `RouteExecutionState`, but the canonical concept is `RouteRun`.
- `block`: an occupancy and reservation unit.
- `track tile`: physical rail geometry on the grid.
- `platform`: the concrete physical stopping place on the track. Dispatcher targets are always expressed against a concrete block traversal frame, never against a logical station group; when a waypoint resolves through station/platform data, the platform supplies the linked blocks and traversal context used to derive that block target.
- `station`: a logical grouping of one or more platforms used only for route-level stop selection. When a route targets a station-level stop, `RouteExecutor` must first resolve one concrete platform for that attempt and then derive the dispatcher request contract from that resolved platform.

## Design Direction

**Ownership split**

- `TrainController` should own live operational state: ATC/ATO/manual mode, handle position, future manual `power_percent`-mode inputs, and the canonical live lookahead data series. "Target speed" and "speed-limit reason" should not be stored as standalone fields anywhere; they should be the value and reason metadata at position 0 of the lookahead series.
- `TrainController` should also own live power/cab state: `power_on`, active cab selection, and any live direction-selection inputs tied to that active cab. After the runtime 1:1 `Train` <-> `TrainController` pairing is established, those values are not re-synced from `Train` on every tick.
- `Train` should own persistent/configuration state only: identity, consist, schedule/route assignment, and non-live train configuration. Initial live placement is set by the train-addition API flow: `SimulationController.add_train(...)` is the canonical owner of this API call, invoked from the frontend/client layer when a new train is introduced into the running simulation. This is an ownership change, not a new public request-shape requirement: the existing train-create payload shape (`id`, optional `position: {x, y}`, `direction`, `max_speed`, `length`, and other train configuration fields already accepted by the repo API) remains the frontend/API input unless separately changed by implementation. `SimulationController.add_train(...)` must create the `Train`, create or obtain the `TrainController`, derive the initial span from that placement/configuration payload, and write the initial `TrainController.current_span` before the first simulation tick. If legacy persistence supplies placement during bootstrap, bootstrap should route that placement through the same `SimulationController.add_train(...)` / span-initialization path rather than teaching `TrainController` construction or `_update_train()` to read a live `Train` position field. Live position/span, live speed, ATO/ATC/path-runtime state, power/cab state, and operational state should not be mirrored on `Train`.
- `manual_target_speed` should be removed entirely. With the new handle plus power-percentage manual model there is no per-train target speed to store, so no compatibility shim is needed.
- Manual control should have two controller-owned submodes:
  - `simulation`: user drives with handle notches; the handle command flows to `TrainPhysics`, which integrates it into speed change over time.
  - `power_percent`: user drives with percentage power; the controller passes raw percentage power to `TrainPhysics`, which immediately converts it via train/profile calibration data such as `SpeedProfile.power_speed_curve` into both track voltage and the calibrated current speed when no braking override is active.
- `TrainPhysics` and `BlockPowerController` should not decide manual-mode policy. They should execute whichever command the controller produces and perform command-to-speed conversion and voltage emission.
- Percentage-power mapping data should live in `SpeedProfile.power_speed_curve` as part of train calibration and be read by physics.

## Layered Architecture

**Layered responsibilities**

- `PathDispatcher` should execute the route plan by acquiring future blocks, locking future switches, and managing movement authority. It should plan for the controller by providing the dispatcher-owned authority geometry and current authority-end block; the controller projects the actual braking target from that boundary using its safety-margin policy.
- `PathDispatcher` should remain the sole owner of dispatcher path records. `TrainController.received_path_plan` is only a pushed view of the currently active authority, not the source of truth.
- `PathDispatcher` should keep each path record keyed by `path_id` in a dispatcher-owned registry such as `paths_by_id[path_id]`.
- `PathDispatcher` should also keep a single active-authority index such as `active_path_id_by_train[train_id]`. Each train has at most one active authority path at a time, and the controller inbox mirrors only that newest active path.
- Cancelled or completed paths may remain in `paths_by_id[path_id]` for history after controller authority has been cleared, but they are not active authority and are never mirrored into `TrainController.received_path_plan`. In v1 there is no path-owned deferred-release flag. `PathDispatcher` owns only future authority resources: blocks and switches the train has not yet entered. When the train head enters a resource, that future reservation/lock is consumed and physical occupancy becomes resource-local physical state through dispatcher-mediated writes. Cancellation and completion release only not-yet-entered dispatcher-owned reservations and locks, clear controller authority, clear `active_path_id_by_train[train_id]`, and transition `Path.status` synchronously. Physical train motion after completion/cancellation is not blocked by retained path rows: `TrainPhysics` keeps moving the train according to live network geometry/state, and physical `occupied_by` state is cleared only by later controller-reported tail-vacate release events. `PathDispatcher.create_path(...)` must reject a same-train request as its first step when that train already has an `ACTIVE` path, with no path ID allocation, switch acquisition, block reservation, path push, or switch-state mutation. Once the old path is no longer active, later creation is governed only by ordinary live resource conflicts.
- Controller progress reports identify the moving train by `train_id` only; they do not carry a caller-supplied `path_id`. `TrainController` owns the canonical stored span and speed. `TrainPhysics.tick()` computes the next physical span/speed plus the tile-level delta for that movement, then calls `TrainController.on_physics_updated(event_time, span_update)` once per crossed resource boundary and once more for the final non-boundary span/speed update when span or speed changed. `span_update` carries the new `TrainSpan`, the new `current_speed_kmh`, ordered `added_tiles`, ordered `removed_tiles`, and the traversal frame used for each added/removed tile. `TrainController.on_physics_updated(event_time, span_update)` atomically applies the new span/speed to controller-owned storage, interprets the tile delta against `TrainController.received_path_plan.resource_sequence` when authority exists plus canonical lookahead, and sends one ordered `PathDispatcher.on_controller_progress(report)` call. `PathDispatcher` resolves any active path from `active_path_id_by_train[train_id]`, decides whether reported resources belong to that path, and then commits active progress. After authority has been cleared, later physical release must not depend on a retained path row surviving: block release is driven by `block_id` plus `direction` through `BlockManager`, and switch release is driven by the vacated switch resource's train-owned physical occupancy/protection state.
- `TrainController` should execute the path plan by calculating ATC safety limits, ATO/manual commands, and an active handle or future power command. It should plan for physics by producing the active control command for the current mode.
- `TrainPhysics` should remain an executor only; it should not decide manual-mode policy.
- `PathDispatcher` should pass the full target contract to the controller whenever a path is created or extended: the requested target (`requested_destination_block_id`, `requested_destination_direction`) plus the current authorized target (`authority_end_block_id`). The controller should brake to the current authority boundary using its canonical safety margin, while `RouteExecutor` may compare requested vs authorized block targets to see whether the live authority already reaches the current requested target carried by that path. The controller should derive speed restrictions from lookahead over the network and dispatcher authority structure, not receive per-block speed limits as separate pushed data.
- The dispatcher-owned path record should be the single source of truth for controller authority while it is active. Cancelling or replacing a path in `PathDispatcher` should be sufficient to give the controller a clean slate.

## Core Runtime Loop

**Phase structure**

### Phase 1 - Setup (top-down planning)

1. Advance `simulation_time`.
2. Run `RouteExecutor.update(delta_seconds)`. This decides which waypoint/path is active for each train and calls `PathDispatcher.create_path()` when a new path is needed. A route-managed train should already have its 1:1 `TrainController` by this point; `RouteExecutor` must ensure the controller exists before it reads controller state or asks `PathDispatcher` to push authority.
3. After path creation, `PathDispatcher` should call `controller.receive_path_plan(path_plan)` directly on that assigned train's existing `TrainController`. The pushed payload must follow the canonical **received_path_plan schema**, and its nested authority geometry must follow the canonical **resource_sequence entry schema** and **path_tile entry schema**, so controller/UI consumers have complete geometry and ordering after train-side path mirrors are removed and do not have to infer the traversal frame later.

### Phase 2 + Phase 3 - Per-train transactional Execute + Feedback

- Phase 2 and Phase 3 are interleaved per train, not as two separate world-wide passes. The simulation loop iterates trains and runs the full `_update_train(train, delta_seconds)` transaction for one train — controller tick, physics tick, controller progress report, dispatcher commit, route callbacks — to completion before starting the next train. This treats each train's tick like a database transaction: one train's physics callbacks finish committing dispatcher/resource state changes before the next train's controller reads any shared state. Cross-train iteration order within a tick is route-priority based (descending owning-route `Route.priority` for route-managed trains). Non-route trains use the same default scheduling priority as a route that omits `Route.priority` (`5` in v1). Stable existing train order is the tie-break for equal priorities.
- For each train in that order:
  1. Tick `TrainController`. This includes the pre-physics stop-completion evaluation for the active authority and may send a no-tile-delta controller progress report to `PathDispatcher.on_controller_progress(report)` when `stop_complete == true`.
  2. Tick `TrainPhysics`. Within `TrainPhysics.tick(delta_seconds)`, compute the next span/speed and tile-level span delta for the train physics owns.
  3. After movement for that train is reconciled, `TrainPhysics.tick(delta_seconds)` calls `TrainController.on_physics_updated(event_time, span_update)` (one call per resource boundary crossed, in physical order, plus the final no-boundary span/speed update when needed; see the controller-mediated progress contract).
  4. `TrainController.on_physics_updated(event_time, span_update)` writes controller-owned `current_span` / `current_speed_kmh`, builds a controller progress report from the tile delta, canonical lookahead, and `received_path_plan.resource_sequence` when live authority exists, then calls `PathDispatcher.on_controller_progress(report)`.
  5. `PathDispatcher.on_controller_progress(report)` commits dispatcher/resource state: head-entry progress, tail-vacate release, path cancellation, path completion, and route callbacks. If the report carries `stop_complete == true`, dispatcher accepts that controller stop-complete report and commits completion only when the active `Path.authority_end_block_id` has reached `Path.requested_destination_block_id`; dispatcher does not infer completion from precise train position on its own. Path completion must not force-unlock a block or switch that is still physically occupied by the train.
- After all trains have completed their per-train transactions, update signals from blocks once for the tick.

**`SimulationController.update()` calls**

- `self.route_executor.update(delta_seconds)` remains the setup entry point.
- `self._update_train(train, delta_seconds)` remains the per-train execute step.
- `SimulationController` should stay an orchestrator only: advance time, call `RouteExecutor.update(delta_seconds)`, call `_update_train(train, delta_seconds)` for each train, and then update signals. It should not forward resource-entry or tail-vacate events itself.
- `SimulationController` should own one shared `PathDispatcher` instance for all trains. `TrainPhysics.tick(delta_seconds)` should compute the next span/speed plus tile delta and invoke `TrainController.on_physics_updated(event_time, span_update)` for that train. `TrainController.on_physics_updated(event_time, span_update)` applies the update to controller-owned span/speed and sends ordered resource-entry, typed tail-vacate, and deviation observations to that shared dispatcher through `PathDispatcher.on_controller_progress(report)`. Stop-completion reports are emitted by the pre-physics `TrainController.tick(...)` predicate described in the **Active-path completion procedure**, not by `TrainController.on_physics_updated(...)`. `PathDispatcher` resolves active authority from its own registries while resolving post-authority physical release from the resource itself rather than by reading stale controller inbox state.
- `self.network.update_signals_from_blocks()` should run after dispatcher feedback so signals reflect all block-state changes, including path completion.
- Remove `self.path_dispatcher.get_and_clear_completion_events()` and the loop that calls `route_executor.handle_path_completion()`. Completion should be synchronous inside `PathDispatcher.on_controller_progress(report)` when the accepted report carries `stop_complete == true`.

**SimulationController runtime surface**

- `SimulationController` is the registered runtime surface shared by `TrainController`, `PathDispatcher`, `RouteExecutor`, and `TrainPhysics` whenever any simulation runtime is active. It is the canonical home for runtime services and is the only owner of the public `add_train(...)` API surface. When a `SimulationController` instance exists for a network, it must finish initializing and registering this surface before any `TrainController` instance is constructed.
- `SimulationController` is optional in editor mode. Pure map-editor sessions (geometry placement, connectivity wiring, static field edits that do not affect runtime occupancy or locks) run with no `SimulationController`, no `BlockManager` runtime, no dispatcher, and no controllers; entities that hold a reference to `SimulationController` MUST type it as `Optional[SimulationController]` and tolerate `None`. An editor session that wants live track/switch testing MAY instantiate a lightweight `SimulationController` (with `BlockManager` wired but no runtime route/dispatcher trains) so that switch state changes route through the canonical mutation workflow normally. The choice is binary at the editor session level — there is no partial wiring.
- The v1 surface exposes exactly the shared services and registries needed by those components: `network`, `block_manager`, `path_dispatcher`, `route_executor`, the controller registry keyed by `train_id`, the physics registry keyed by `train_id`, `get_train(train_id)`, `get_or_create_controller(train_id)`, `get_or_create_physics(train_id)`, and the public train-addition API `add_train(...)`. `add_train(...)` is owned by `SimulationController` because the train-addition API is invoked from the frontend/client layer to introduce a new train into the running simulation; it constructs the `Train`, ensures the controller exists, and writes the initial `TrainController.current_span` from placement input before any simulation tick.
- When a `SimulationController` instance is created for a runtime session, it is the first runtime object initialized for that network run. `SimulationController.__init__` constructs/registers `BlockManager`, `PathDispatcher`, and `RouteExecutor`, wires them and every already-loaded network entity (including each `Switch`) to the same `SimulationController` reference so that cross-entity callbacks such as `Switch` → `BlockManager.on_switch_state_changed(switch_id)` resolve through `self.simulation_controller.block_manager` rather than requiring direct injected back-references, and only then allows `SimulationController.get_or_create_controller(train_id)` to create a `TrainController`. Any later-created or later-loaded entity must be registered with this same `SimulationController` before it is allowed to mutate cross-entity runtime state. If that surface is not registered yet, `SimulationController.get_or_create_controller(...)` must fail rather than constructing a partially wired controller.
- Every `TrainController` stores only a reference to `SimulationController`, not separate dispatcher or route-executor references. Controller-owned release/removal commands use that runtime surface in a fixed order: call `SimulationController.path_dispatcher.cancel_path(...)` for the active path while the train's `RouteRun` is still registered, then call a route-executor removal entry point such as `RouteExecutor.remove_train_route_run(train_id, reason)` through `SimulationController.route_executor`, then finish controller-local state cleanup.
- `PathDispatcher` and `RouteExecutor` also resolve controllers through `SimulationController.get_or_create_controller(train_id)` and must not keep private controller registries or construct controllers directly.

**Canonical runtime procedures**

These named procedures are the canonical home for ordering-sensitive cross-component workflows. Later sections may restate local consequences, but they should cross-reference these procedures rather than inventing a second order.

- **Physical progress / deviation procedure**:
  1. `TrainPhysics.tick(...)` emits one ordered `PhysicsSpanUpdate` per crossed resource boundary, plus a final no-boundary update when span or speed changed.
  2. `TrainController.on_physics_updated(event_time, span_update)` writes the new controller-owned span/speed, converts the tile delta into typed resource observations, and calls `PathDispatcher.on_controller_progress(report)`.
  3. `PathDispatcher.on_controller_progress(report)` handles entered resources before any path bookkeeping. For each entered block it calls `BlockManager.occupy_blocks([block_id], train_id)`; for each entered switch it first compares the incoming `train_id` with the current `Switch.occupied_by`, and only on a clean entry does it set `Switch.occupied_by = train_id` and convert applicable same-path switch/flank locks into train-owned physical protection. Physical occupancy is the top-priority truth: if a train physically enters a resource and recording that entry would not overwrite another owner's live claim, the resource state must record it even if the software authority state is already wrong.
  4. If recording that physical entry would overwrite another train's current physical/reservation owner, `PathDispatcher` enters the canonical fatal physical-entry conflict procedure below immediately, leaves the prior owner intact, and stops processing the report.
  5. If `report.deviation == true`, dispatcher cancels the active path with `PathCancellationKind.ROUTE_DEVIATION` after recording clean physical entries. It does not run normal `Path.current_resource_index` advancement or `RouteExecutor.handle_train_advanced(...)` for that report. `RouteExecutor.handle_path_cancellation(...)` still runs immediately on that same tick for route-owned cleanup, but it records any `deviation_kind` / `passed_requested_target` recovery context on the matching `RouteRun` and defers `RouteExecutor._skip_waypoint(...)` plus any next-target planning until the train has reached the fresh stopped no-authority or post-EB recovery point. There is no reroute-on-the-fly while the train is still braking under the cancelled authority.
  6. If `report.deviation == false`, dispatcher applies ordinary active-path head progress and route head-advance callbacks.
  7. Dispatcher processes `tail_vacated_resources` after all entered-resource handling above.
- **Active-path completion procedure**:
  1. Stop-completion evaluation runs in `TrainController.tick(...)` before that tick's physics movement, using the stable controller span/speed written by the previous physics update and the current tick's lookahead. `TrainController.on_physics_updated(...)` updates span/speed and resource observations only; it does not report `stop_complete`.
  2. When the usable-authority stop predicate is true, `TrainController.tick(...)` sends a stop-complete-only `PathDispatcher.on_controller_progress(report)` with empty `entered_resources` and `tail_vacated_resources`.
  3. `PathDispatcher` accepts completion only when the active path exists, the report has `stop_complete == true`, and `Path.authority_end_block_id == Path.requested_destination_block_id`. Dispatcher does not require the train head to physically occupy the requested destination block; the controller safety margin / ATC stop boundary is the higher-priority stopping rule.
  4. On accepted completion, `PathDispatcher` first clears controller authority by calling `TrainController.receive_path_plan(None)`, then calls `TrainController.on_path_complete()` so the controller transitions to the state-machine-derived stopped ready state.
  5. `PathDispatcher` transitions `Path.status` to `COMPLETED`, clears `active_path_id_by_train[train_id]`, releases not-yet-entered block reservations and switch/flank locks, and then calls `RouteExecutor.handle_path_completion(...)`.
  6. `RouteExecutor.handle_path_completion(...)` advances route-owned stop progress/bookkeeping for a matching `RouteRun`, records the arrival time for dwell, and clears the route-owned active-path correlation. It does not call `TrainController.enter_station_dwell()` in the completion callback.
  7. On the next `RouteExecutor.update(...)` tick, a run with a recorded stop arrival enters dwell before any new departure/path planning for the next leg. This prevents the stopped ready state between completion and dwell entry from being misread as a fresh departure opportunity.
- **Power-off procedure**:
  1. `TrainController.power_off_cmd()` first validates that the train is stopped.
  2. If an active dispatcher path exists, it calls `PathDispatcher.cancel_path(active_path_id, cancellation_kind=PathCancellationKind.POWER_OFF, reason="power off")` while the train's `RouteRun` is still registered, so the ordinary cancellation callback can clear route-owned correlation.
  3. It then calls `RouteExecutor.remove_train_route_run(train_id, reason="power_off")` through `SimulationController.route_executor`.
  4. Finally it performs controller-local OFF cleanup: transition to `OFF`, clear the active cab selection, clear any EB latch, clear `post_eb_restart_pending`, clear `departure_ready_path_id`, and set `ato_running = False`.
- **Fatal physical-entry conflict procedure**:
  1. `SimulationController` owns the unrecoverable failed-runtime flag and fatal diagnostic payload.
  2. `PathDispatcher` or `BlockManager` sets that flag when a physical entry would overwrite another train's `occupied_by`, another train's `reserved_for_train`, or another train's `Switch.occupied_by`.
  3. The current simulation transaction aborts immediately after recording the diagnostic and running a clean cancellation-style teardown for the incoming train and any identifiable prior-owner train: cancel any live path through `PathDispatcher.cancel_path(..., cancellation_kind=PathCancellationKind.REVOKED, reason="fatal physical-entry conflict")`, clear controller authority, remove matching `RouteRun` entries, and then freeze the runtime. This cleanup uses the ordinary cancellation entry point for consistency, but it is not a recoverable reroute path while the failed-runtime flag remains set. Unrelated trains and resources remain frozen at their current state.
  4. `SimulationController.update(...)` refuses further simulation advancement while the failed-runtime flag is set. V1 defines no automatic software resume; a manual/admin cleanup path must clear the failed-runtime flag and repair resource state before simulation can run again.

**Path completion notification flow**

- Remove `_complete_path_on_head_arrival()` and replace normal runtime completion with the canonical **Active-path completion procedure** above. This is not a rename: the trigger changes (head-arrival or head-tile-equals-last-path-tile -> controller-reported usable-authority stop on the next pre-physics controller tick), the notification chain changes (event-queue append -> synchronous direct calls through `PathDispatcher.on_controller_progress(report)`), and the method body changes accordingly.
- `PathDispatcher.on_controller_progress(report)` should commit completion only when the active-path report has `stop_complete == true` and the active path's authority end has reached the path's requested target. Completion ordering is exactly the **Active-path completion procedure**: clear controller authority, call `TrainController.on_path_complete()`, transition the path to `COMPLETED`, release not-yet-entered resources, then call `RouteExecutor.handle_path_completion(...)` using the canonical completion payload from the **route path-event callback schema**. Completion release may drop not-yet-entered reservation ownership and may force-clear `CAUTION` for matching still-reserved blocks, but it must not force-clear any `OCCUPIED` resource the train still physically occupies.
- `PathDispatcher` should hold a reference to `RouteExecutor`, and it should resolve `TrainController` instances through a shared controller registry keyed by `train_id`. The registry is owned by `SimulationController` and exposed through a public train-ID-based accessor such as `SimulationController.get_or_create_controller(train_id)`; `PathDispatcher`, `RouteExecutor`, and other layers go through that accessor rather than passing whole `Train` entities around just to find a controller or keeping private `_get_or_create_controller` helpers or circular back-references.
- Wiring pattern: `SimulationController` is initialized first and is the canonical shared runtime owner. It then constructs `PathDispatcher` and `RouteExecutor` with a reference to itself so both components can use the same controller registry and shared runtime services through `SimulationController`. They may still hold direct references to each other after construction, but `SimulationController` is the common home and is created before either of them.
- `TrainController` instances are created on demand through `SimulationController.get_or_create_controller(train_id)`, which runs only after the **SimulationController runtime surface** above is fully registered. Every new `TrainController` is constructed with a reference to `SimulationController`, and controller-owned release/removal commands (e.g. `TrainController.power_off_cmd()`) reach `PathDispatcher` and `RouteExecutor` through that registered surface rather than through independent direct references or a global lookup. This keeps `SimulationController` the single registry of shared runtime components and removes any temporal concern about `TrainController` being constructed before `PathDispatcher` / `RouteExecutor`.
- Remove `_record_completion_event()`, `completed_path_events`, and `get_and_clear_completion_events()` from `PathDispatcher`.
- Path completion should only be recognized from a controller stop-complete report after the train is fully stopped at the usable authority stop boundary and the live authority reaches the requested destination block. The controller safety margin is a braking/diagnostic target used by lookahead and is higher priority than trying to force the head to the physical edge or physical interior of the requested destination block. No completion callback should run while the train is still braking or creeping toward that usable authority stop.
- After dispatcher-owned completion release, route-level waypoint and dwell logic should follow the **Active-path completion procedure**: the completion callback records route-owned arrival/progress, and the next `RouteExecutor.update(...)` tick decides whether the train enters dwell (`RUNNING_AT_STATION`) or remains in the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected).

**`_update_train()` flow**

1. Get or create a `TrainController`.
2. Get or create a `TrainPhysics`.
3. On first pairing only, initialize any controller-owned bootstrap values that still come from persisted train data, then establish the runtime 1:1 `Train` <-> `TrainController` pairing for that `train_id`.
4. Tick controller.
5. Tick physics.
6. Sync only train-owned persistent/configuration state back to `Train`. Do not sync live position/span, speed, path authority, power/cab state, or operational state back to `Train`.
7. Do not add a separate simulation-owned dispatcher feedback pass. `TrainPhysics.tick()` should compute a `span_update` and call `TrainController.on_physics_updated(event_time, span_update)`, and that controller method should apply the controller-owned span/speed update and report progress plus typed tail-vacate observations to `PathDispatcher.on_controller_progress(report)`.

**`_update_train()` calls**

- Keep `get_or_create_controller(train_id)` (the public `SimulationController` accessor that owns the controller registry), `_get_or_create_physics(train)`, `controller.tick(delta_seconds)`, and `physics.tick(delta_seconds)`. `RouteExecutor` and `PathDispatcher` both reach the registry through the same public train-ID-based accessor rather than keeping private `_get_or_create_controller` helpers.
- A newly created controller may bind only to train-owned persistent/configuration data needed for that 1:1 pairing. It does NOT seed `TrainController.current_span` itself; initial span placement is owned by the application train-addition path. The API `add_train()` flow must create or obtain the controller and write `TrainController.current_span` before any simulation tick. In the desired model `Train` does not carry live runtime authority or live position/span fields, so this constructor path must not seed `received_path_plan` from `Train` directly, and the derived reads `assigned_path_id`, `ato_path_id`, and `ato_destination_block_id` are never written directly on the controller — they only surface when `PathDispatcher` pushes a live plan. If persisted data implies an active authority, bootstrap re-establishes it through the ordinary v1 flow: route-managed trains let `RouteExecutor` create the path in Phase 1 through `PathDispatcher.create_path(train_id=..., ...)`, and non-route trains use the same `PathDispatcher.create_path(train_id=..., ...)` entry point (treated as a standalone dispatcher-authority path with `train_id` always set). `PathDispatcher` then pushes `received_path_plan` via `controller.receive_path_plan(...)` exactly as it does for runtime-created paths. For route-managed trains, `RouteExecutor` should already have ensured the controller exists before any Phase 1 authority push; `get_or_create_controller(train_id)` in `_update_train()` remains a fallback for non-route flows and recovery.
- In v1 there is no late-controller recovery hook. Controller existence is a hard precondition for authority assignment: `RouteExecutor` or any other caller must ensure `SimulationController.get_or_create_controller(train_id)` has already established the 1:1 `train_id -> controller` binding before `PathDispatcher.create_path(...)`, `PathDispatcher.extend_path(...)`, or any `controller.receive_path_plan(...)` push occurs. If persisted/bootstrap train data is needed to initialize that controller, `SimulationController` resolves the `Train` entity internally from `train_id`; callers still use the train-ID-based accessor. Controller bootstrap must not recreate authority from train-side runtime mirrors, and `PathDispatcher` does not expose `on_controller_available(train_id)` or repush authority after a late bind.
- Stop writing `train.target_speed`, `train.speed_limit_reason`, `train.ato_destination_block_id`, and `train.state` here. Consumers that want live target-speed data should read controller lookahead at distance 0 instead; consumers that want live operational state should read `TrainController.state` directly.
- Do not re-sync live power/cab state from `Train` on every tick. If compatibility/bootstrap persistence still stores those values on `Train`, they may be imported once when the controller is first created; after that point `TrainController` is the live owner.
- Replace block-only feedback with controller progress reports triggered by `TrainPhysics.tick()`, so dispatcher updates can consume both blocks and switches in `resource_sequence` order.
- In the same controller-mediated reporting path, emit typed tail-vacated resource-release observations so `PathDispatcher` can release a vacated resource according to its resource type (`block` vs `switch`).

**Dispatcher progress/completion flow**

- `PathDispatcher.on_controller_progress(report)` is the normal runtime progress API. Old physics-named dispatcher progress APIs are removed from the target model. The report payload carries exactly `train_id`, `event_time`, `entered_resources`, `tail_vacated_resources`, `current_head_sequence_index`, `deviation`, `deviation_kind`, `deviation_reason`, `passed_requested_target`, and `stop_complete`. It does not carry `path_id`; `PathDispatcher` resolves the active path from `active_path_id_by_train[train_id]`. `current_head_sequence_index` is the index of the train head's current position in the active `resource_sequence`, or `None` when the controller cannot map the head to the active resource sequence. When live authority exists and the controller cannot map the head to that active `resource_sequence`, the report must set `deviation = true`, `deviation_kind = "out_of_sequence"`, `current_head_sequence_index = None`, and `stop_complete = false`; dispatcher treats that report as deviation/cancellation input rather than as ordinary active-path progress. `deviation_kind` is the branchable enum (`"out_of_sequence"`, `"beyond_authority"`, or `"beyond_requested_target"`); `deviation_reason` is optional plain-text diagnostics only and must not be used for branching. `passed_requested_target` is the branchable boolean telling route recovery whether the deviation proves the train head has passed beyond the active path's requested target. Each resource event in `entered_resources` and `tail_vacated_resources` carries `sequence_index` when known, `resource_type`, and `resource_id`; block tail-vacate events additionally carry `direction`. For a single report, `PathDispatcher.on_controller_progress(report)` follows the **Physical progress / deviation procedure**: entered physical resources are recorded first, deviation cancellation is handled after clean physical entry, and tail-vacated resources are processed last.
- The branchable deviation predicates are:

  | `deviation_kind` | Predicate | `passed_requested_target` |
  | --- | --- | --- |
  | `"out_of_sequence"` | Live authority exists, but the train head cannot be mapped to the active `received_path_plan.resource_sequence`, or maps to a resource that is not the current/next legal head resource for that active path. | `False` unless the same observation also proves the head is past the requested target terminal frame. |
  | `"beyond_authority"` | The head is physically beyond `Path.authority_end_block_id` in the path's directed traversal frame while the active path remains truncated short of `Path.requested_destination_block_id`. | `False` unless the head is also beyond the requested target terminal frame. |
  | `"beyond_requested_target"` | The head is physically beyond `Path.requested_destination_block_id` in the stored directed traversal frame for that requested target. This is an overshoot of the pending route target, not an ATC safety-margin stop before the target. | `True`. |

- `TrainController` owns progress interpretation and canonical span storage. It applies the `span_update` from `TrainPhysics`, converts ordered `added_tiles` and `removed_tiles` into entered/tail-vacated block and switch resource observations, and compares the updated `current_span` with `received_path_plan.resource_sequence` when live authority exists. Stop completion is evaluated separately on the next pre-physics `TrainController.tick(...)` from the stable stored span/speed and current lookahead. When no live authority exists, the report may still carry physical entry/release observations but `current_head_sequence_index` is `None` and no active-path progress can be inferred by the controller. `PathDispatcher` still owns `Path.current_resource_index`, path status, reservation/lock consumption, resource release, path cancellation/completion, and route callbacks.
- For entered resources, `PathDispatcher.on_controller_progress(report)` should resolve the relevant dispatcher-owned path record for that train and update `path.current_resource_index` from the reported `sequence_index` when the train head enters a resource in `path.resource_sequence`. The globally-unique-ID-namespace alternative is not adopted.
- After the dispatcher-owned path record has updated `path.current_resource_index` for the entered resource, `PathDispatcher.on_controller_progress(report)` must call the single route-facing head-advance callback `RouteExecutor.handle_train_advanced(train_id, path_id, resource_type, resource_id)` for the path's active route execution, if any. The `path_id` argument is the dispatcher-resolved active path ID, not a value supplied by the controller report. This is the canonical notification chain for head-based route-progress events; `RouteExecutor` must not poll `controller.get_current_span()` or `controller.get_lookahead()` inside `RouteExecutor.update(...)` to discover that the train head has entered a new resource. `Waypoint.kind == "pass_through"` uses the same resolved target contract as `Waypoint.kind == "stop"` (`ResolvedWaypointTarget` with block and direction), but its completion trigger is head entry into the resolved target block rather than stop completion. When the entered resource is a block whose `resource_id` matches the resolved target block of the next `Waypoint.kind == "pass_through"` on the active planning chain, `RouteExecutor.handle_train_advanced(...)` applies the route-owned pass-through completion update, leaves dispatcher authority intact, and does not call `TrainController.enter_station_dwell()` or set `arrived_at_platform_time`. The callback resolves the next `pass_through` target on demand from the current route definition and current physical progress rather than relying on a persistent per-waypoint target cache. If that callback-time resolution fails, the callback is a no-op for route progress on that tick and later ticks retry normally; it must not synthesize skip, cancellation, or stale-target adoption from that callback alone. This head-entry route progress is not gated by `departure_ready_path_id`: if the head enters the resolved `pass_through` block before departure acceptance, the callback still consumes that waypoint. Switch entries and non-matching block entries are no-ops on the route side.
- When the entered resource is a block, that same dispatcher-owned entry handoff must call `BlockManager.occupy_blocks([block_id], train_id)`. In the desired model this is the only normal runtime path that marks a block physically `OCCUPIED`, and it consumes any same-train dispatcher reservation for that block because the resource has moved from future authority into train-owned physical occupancy.
- When the entered resource is a switch, the same dispatcher-owned entry handoff should first verify that the switch is not already physically occupied by another train. On clean entry it sets `Switch.occupied_by = train_id` for that `switch_id`, consumes the path-owned main switch lock for the entered switch, and converts any required flank protection for that occupied switch into train-owned physical protection that will be cleared on tail-vacate. If another train already owns `Switch.occupied_by`, the hard-failure rule below applies and the handoff must not overwrite it. Switch physical occupancy is separate from future reservation/lock ownership.
- Physical occupancy updates still happen even when no `ACTIVE` path remains for that train. If `active_path_id_by_train[train_id]` is already clear because the old authority was completed or cancelled, `PathDispatcher.on_controller_progress(report)` must still apply the resource-typed physical entry update (`BlockManager.occupy_blocks(...)` or `Switch.occupied_by = train_id`) and simply skip path-progress / completion bookkeeping because there is no active authority row left to update. Clean physical entry records the reported block or switch as occupied by this `train_id` and consumes same-train future claims. A conflicting physical entry is not a normal workflow: if the target block's prior `occupied_by` is another train, or its `reserved_for_train` is another train, or the target switch's prior `Switch.occupied_by` is another train, the dispatcher/manager must enter one canonical unrecoverable hard-failure path: emit a fatal conflict diagnostic identifying the resource, the incoming `train_id`, and the prior owner; stop further simulation advancement immediately; leave unrelated trains and resources frozen in their current state; clear authority for the incoming train and any identifiable prior-owner train by cancelling their live paths / controller authority when present; cancel/remove those trains' `RouteRun` records when present; and require manual operator/admin cleanup before simulation may be restarted. V1 defines no automatic in-software resume workflow after this failed state. It must not silently overwrite the prior `occupied_by` / `Switch.occupied_by`, must not treat the conflict as recoverable cancellation, and must not continue route or dispatcher bookkeeping as though the entry succeeded. In practice this conflict should be unreachable: controller lookahead/ATC produces no valid positive forward ATC speed for any occupied/conflicting resource ahead, so the head should never reach a conflicting resource while live authority exists.
- In the desired model there should be no separate `CLEARING` lifecycle state. A live dispatcher-owned authority path stays `ACTIVE` until it is either `COMPLETED` or `CANCELLED`; entering the final block/resource only updates progress and completion predicates.
- Tail-vacate release remains resource-local and dispatcher-mediated. `TrainController.on_physics_updated(event_time, span_update)` reports vacated resources in `tail_vacated_resources`, and `PathDispatcher.on_controller_progress(report)` releases each vacated resource according to type after it has processed any `entered_resources` in that same report. `direction` is required for `resource_type == "block"` and ignored for switches. Active progress continues to resolve through `PathDispatcher`'s registries rather than from `TrainController.received_path_plan`, but tail-release logic after authority release must resolve from the resource itself so it still works after the controller inbox has been cleared:
  - if `resource_type == "block"`, dispatcher should route the release through `BlockManager.on_block_tail_vacated(block_id, train_id, direction)`
  - if `resource_type == "switch"`, dispatcher should clear `Switch.occupied_by` and clear any train-owned physical protection for that switch; neighbour flank protection associated with the vacated switch is released by the same tail-vacate operation, not by a retained path claim
- `PathDispatcher.on_controller_progress(report)` is not a deferred-release hook. Once a path is no longer `ACTIVE`, any later physical release is resource-local and triggered by controller-reported tail-vacate observations.
- Explicit local/manual reposition authorities that do not cross a new resource, if retained, do not introduce a route-authored centimeter target. The controller uses the same safety-margin authority-boundary logic as every other stop, and completion still comes only through the pre-physics `TrainController.tick(...)` stop-complete report into `PathDispatcher.on_controller_progress(report)`. Dispatcher must not run a separate precise-position detector for those stationary local moves.
- Switch release should be driven by tail-vacate detection in `TrainPhysics`, not by dispatcher tile-index checks.
- Implementation note: every old physics-named dispatcher progress or tail-release caller must be migrated to `TrainController.on_physics_updated(event_time, span_update)` plus `PathDispatcher.on_controller_progress(report)`. Active progress commit belongs to `PathDispatcher`, but delayed release of a resource that is still physically occupied after authority release must resolve from the resource itself (`BlockManager` for blocks, `Switch.occupied_by` plus train-owned protection for switches) rather than requiring a retained path row just to rediscover ownership.

**Controller/train sync**

- `TrainController.tick(delta_seconds)` should continue to own ATC, ATO, and manual-control runtime calculations, but target speed and speed-limit reason should move into the canonical controller lookahead payload instead of standalone scalars.
- `Train` should keep only persistent/configuration state in sync from the simulation loop.
- `PathDispatcher.create_path()` should push a path plan directly into the controller, and path cancellation or completion should clear that controller inbox through `PathDispatcher` as its sole writer rather than through train-side mirrors or controller self-mutation.

**Tick-order dependency**

- Phase 1 must run before Phase 2 because the controller should read path tiles that already exist.
- Phase 2 must run before Phase 3 because the dispatcher should read positions that physics has just produced.
- Physics progress and route-level reactions are synchronous within the same per-train transaction: a boundary crossing reported through `TrainController.on_physics_updated(event_time, span_update)` is committed by `PathDispatcher.on_controller_progress(report)` and any route callback before the next train's transaction starts.

## Units

**Units contract**

- The unit-mixing hazard between `Train.max_braking_rate` (`m/s^2`) and `SpeedProfile.deceleration_rate` (`km/h/s`) persists in the desired model. Resolve it at exactly one boundary: `TrainPhysics` performs the `m/s^2` ↔ `km/h/s` conversion when it reads profile rates, so all controller-facing deceleration math stays in a single unit system. No other layer reinterprets the raw fields.
- The desired model uses one canonical stopped predicate everywhere: `TrainController.is_stopped()` with `STOPPED_SPEED_THRESHOLD_KMH = 0.1`, reading controller-owned `current_speed_kmh`. `STOPPED_SPEED_THRESHOLD_KMH` is the global "considered stopped" speed threshold; it is distinct from any ATC zero-speed limit. The "ATC limit" mentioned elsewhere in this document means the ATC-derived speed cap at distance 0 in the canonical lookahead — when that cap is `0` the ATC is granting no clearance distance. Controller-reported stop completion, `RUNNING_WAITING` entry, `TrainController.power_off_cmd()`, `TrainController.set_cab()`, `TrainController.set_mode()`, and `TrainController.release_emergency_cmd()` must all use this same `STOPPED_SPEED_THRESHOLD_KMH` helper instead of introducing layer-specific stop thresholds. Same-block or zero-movement movement, if retained for explicit local/manual repositioning, may complete only when the pre-physics `TrainController.tick(...)` stop-complete predicate reports `stop_complete == true`; dispatcher must not add a separate position-based completion predicate.

**Safety margin globals**

- The controller safety margin is two distinct global values, not a single tunable. Both are owned by `TrainController` lookahead computation and are not authored on routes, paths, or per-block fields.
  - `TRACK_END_SAFETY_MARGIN_CM`: applied when the authority-end block is bounded by a track-end / dead-end / non-station authority terminus.
  - `PLATFORM_SAFETY_MARGIN_CM`: applied when the authority-end block is the resolved terminal block of a platform stop.
- `TrainController` lookahead is the single computation site for these margins. When building the authority-boundary projection in `get_lookahead()`, the controller finds the terminal block entry for `authority_end_block_id`, projects the authority-end block's forward boundary in that directed terminal frame, and counts back from that edge by the selected safety margin to build the ATC/ATO speed curve. ATC is intentionally not trying to drive the train all the way to the physical edge of the cleared/authorized block. This projection is a braking and diagnostics calculation only; it is not route-authored stop-position data and is not a route completion tolerance. Other layers (dispatcher, route, physics, signals) must not re-derive or duplicate this margin; they consume the lookahead-projected boundary instead.

## TrackSegment

**Path locking**

- Remove `TrackSegment.locked_by_path`, `locked_state`, and the single-owner lock methods once switch locking is owned entirely by the `Switch` entity.
- Remove `path_direction` from `TrackSegment` in the desired model. Temporary reservation direction belongs at the block/path-plan level: `Block.reserved_direction` is the dispatcher-owned block reservation direction, and `Path.resource_sequence[*].entry_edge` / `exit_edge` plus nested `path_tiles[*].entry_edge` / `exit_edge` carry the canonical per-resource and per-tile traversal direction. `TrackSegment` should not store a second live routing-direction field.
- Replace the single-owner track lock model with the multi-owner `Switch.locks` model described below.
- `TrackSegment` keeps static geometry, classification, and `switch_id`, but it is not the authoritative store for the active switch state. If the segment is a switch, callers resolve the active segment from the owning `Switch.state` in `network.switches` via `switch_id`. `_switch_state` on `TrackSegment` is removed. The old single-owner track-level path lock is not migrated — per-resource `Block.reserved_by_path` / `Block.reserved_for_train` and multi-owner `Switch.locks` play the equivalent role, so there is no transitional phase.

**Track-segment role and traversal**

- The retained `TrackSegment` schema in v1 is explicit:
  - persistent fields kept on `TrackSegment`: `x`, `y`, `track_bits`, `dead_end_ports`, `signal_ids`, `station_id`, `block_section_id`, `switch_id`, `length`, `curve_radius`, `wear_level`, `last_maintenance`, `maintenance_count`
  - computed read kept on `TrackSegment`: `track_type`
  - removed live runtime fields: `_switch_state`, `occupied_by`, `reserved_by`, `locked_by_path`, `locked_state`, `path_direction`
- `TrackSegment` does not carry static or temporary traffic-direction policy in v1. Static allowed travel direction is block-owned, through `Block.allowed_travel_directions`; route/requested travel direction is route-owned, through `RouteExecutor` resolving `Waypoint.requested_direction` into `ResolvedWaypointTarget.requested_destination_direction`; temporary reservation direction is dispatcher-owned, through `Block.reserved_direction`; and finer-grained traversal frame data lives on `Path.resource_sequence[*]` and nested `path_tiles[*]`.
- `TrackSegment.station_id` remains a legacy field name in the current codebase, but the canonical desired-model meaning of that field is concrete physical platform membership on the tile. Elsewhere in the desired model, use `platform_id` for that physical identifier and reserve `station_id` for logical multi-platform station groups only.
- `TrackSegment` is not the authoritative store for live switch state or switch locks. Remove `_switch_state`, `locked_by_path`, and `locked_state` outright; the desired model does not keep them. Switch state ownership lives on `Switch`, and lock ownership is expressed through `Switch.locks` (for switches) and `Block.reserved_by_path` / `Block.reserved_for_train` (for blocks).
- If the segment classification says the tile is a switch, `TrackSegment.switch_id` should point to the authoritative `Switch` entity in the network entity database. Live switch state and switch lock ownership should live only on that `Switch` entity.
- Split planning-time traversal enumeration from live-state traversal reads.
- Live traversal helpers in the desired model:
  - `TrackSegment.get_active_exits(entry_edge, resolver) -> List[str]`
  - `TrackSegment.get_active_entry_for_exit(exit_edge, resolver) -> Optional[str]`
  where `resolver` is the network or an equivalent switch-state resolver that can read `Switch.state` via `switch_id`.
- Planning-time helper in the desired model:
  - `TrackSegment.enumerate_traversals(entry_edge) -> List[(exit_edge, required_switch_state)]`
  This helper enumerates every legal geometric traversal through the tile independent of the switch's current live state. For an ordinary non-switch tile, it yields the one legal `(exit_edge, None)` pair. For a switch tile, it yields the legal `(exit_edge, required_switch_state)` pairs that dispatcher path search may acquire.
- `TrackSegment.get_active_exits(...)` and `TrackSegment.get_active_entry_for_exit(...)` map one edge through the currently active segment selected by `Switch.state`. `TrackSegment.enumerate_traversals(...)` is the planner-facing geometry contract and must not consult live switch alignment.
- For Y-shape switch geometry in v1, branch-to-branch traversal is invalid. `TrackSegment.enumerate_traversals(...)` must not yield branch-to-branch options.
- `PathDispatcher` path construction/extension and BFS switch derivation use `TrackSegment.enumerate_traversals(...)`. `TrainPhysics._advance_end()`, tail tracing, and other live movement readers use the active-state helpers. Switch traversal never reads track-stored live state.

**Track-segment invariants**

- Switch-integrity while a train spans a switch: in the desired model, the combination of `Switch.occupied_by` plus the still-held `Switch.locks` entries prevents a switch from flipping out from under the spanning train. A global path lock is no longer required for this guarantee.
- Tail tracing still uses the live-state entry/exit helper, but it now resolves through the live `Switch.state` per the directed resolver contract in **Track-segment role and traversal** rather than through a separately persisted track-tile field.

## Switch Entity

**Switch entity**

- `Switch` should become a first-class resource entity at the same level as a block.
- The retained `Switch` schema in v1 is explicit:
  - identity/location: `switch_id`, `x`, `y`
  - retained physical/configuration fields from current code: `main_length_cm`, `diverge_length_cm`, `main_radius_cm`, `diverge_radius_cm`, `switch_type`, `name`, `notes`
  - new authoritative live/runtime fields: `state`, `occupied_by`, `locks`, `flank_protection`, `train_protection_claims`
  - reserved future physical field: `length_cm = 0.0`
  - removed single-owner lock fields: `locked_by_path`, `locked_state`
- Add `state: int` as the authoritative physical switch state. In the desired model the code-defined values are retained explicitly: `0 = MAIN`, `1 = DIVERGE`. When traversal code needs the active switch segment, it should resolve that state from the `Switch` entity rather than keeping a second authoritative live state copy on `TrackSegment`.
- Add `occupied_by: Optional[str]` as the switch resource's physical-occupancy field. `occupied_by` means a train is physically spanning the switch tile right now; it is set on switch-resource entry and cleared on tail-vacate. Reservation/lock ownership remains separate.
- Replace single-owner `locked_by_path` / `locked_state` fields with future-authority `locks`, keyed canonically by `(path_id, claim_role, source_switch_id)`. In v1:
  - a main-usage claim uses `claim_role == "main"` and `source_switch_id = None`
  - a flank-protection claim uses `claim_role == "flank"` and stores the main switch that created it in `source_switch_id`
  Each future-authority lock claim stores exactly `path_id`, `claim_role`, `train_id`, and `locked_state`. When `claim_role == "flank"`, the claim also stores `source_switch_id`, the main switch whose acquisition created that flank-protection claim. Path locks do not carry a deferred-release flag in v1.
- `train_protection_claims` is the train-owned physical protection set used after the train head has entered a switch and consumed the path lock. Each claim stores exactly `train_id`, `source_switch_id`, and `locked_state`; it blocks conflicting switch state changes until the source switch tail-vacate event clears it.
- `acquire_lock(path_id, claim_role, train_id, state, source_switch_id=None)` must first check `Switch.locks`, `Switch.occupied_by`, and `Switch.train_protection_claims`. Compatible future switch locks may be shared only when no switch throw is required: if `Switch.state` already equals `state` and all existing future locks / train-owned protection are compatible with `state`, `acquire_lock(...)` may record another future lock claim without moving the switch. If the current state differs, `acquire_lock(...)` may throw the switch only when no physical occupancy or train-owned protection exists and no future lock requires another state. Physically occupied switches are not acquirable for future authority except for same-train already-covered span entries that are seeded into `Path.resource_sequence` and are not newly locked.
- Every successful `Switch.state` mutation path, whether it came from dispatcher lock acquisition or from a manual/API switch-state command, must use the same canonical mutation workflow: validate that no future lock, physical occupancy, or train-owned protection requires a different state; write `Switch.state`; then notify `BlockManager.on_switch_state_changed(switch_id)`. `Switch.simulation_controller` is `Optional[SimulationController]` and is required for any runtime mutation: `Switch.acquire_lock(...)`, `Switch.release_lock(...)`, and any `Switch.state` change that must notify `BlockManager` MUST raise `RuntimeError("Switch runtime operations require a SimulationController")` when `simulation_controller is None`. When the runtime surface is wired, `Switch` reaches `BlockManager` via `self.simulation_controller.block_manager` rather than being constructed with a direct `BlockManager` back-reference. `Switch` remains the owner of the state mutation itself; `BlockManager` owns the downstream CAUTION reevaluation. Pure geometric editor writes (placement, connectivity wiring, static field edits that do not affect occupancy or locks) do not invoke these runtime methods and remain safe with `simulation_controller is None`.
- A non-dispatcher/manual/API switch-state command follows that same canonical workflow and may change `Switch.state` only when no lock, physical occupancy, or train-owned protection blocks the requested state. If any such claim exists, the state-change request must fail rather than bypassing the workflow. Such a manual/API command is a runtime mutation and therefore also requires `simulation_controller` to be wired; it must raise in pure editor mode and is available only when the editor session has instantiated a runtime surface.
- `acquire_lock(path_id, claim_role, train_id, state, source_switch_id=None)` should be idempotent only for an already-recorded claim on that same canonical claim key with the same `locked_state`, and succeed immediately in that case.
- `acquire_lock(path_id, claim_role, train_id, state)` should allow multiple paths to hold future lock claims on the same switch when those claims all require the same physical `state` and the switch is already in that state.
- `acquire_lock(path_id, claim_role, train_id, state)` must fail if any existing future lock or train-owned protection on that switch requires a different physical `state`, or if satisfying the request would require throwing a physically occupied switch.
- When the train head enters a switch, `PathDispatcher.on_controller_progress(report)` consumes that path's main switch lock for the entered switch and consumes any path-owned flank locks sourced from that main switch by converting them into `train_protection_claims`. From that point onward the occupied switch and its active flank protection are train-owned physical state, not path-owned cleanup.
- `release_lock(path_id, claim_role, source_switch_id=None)` removes that future-authority claim immediately. It must not inspect train physical occupancy or set a pending flag; an occupied switch is protected by `Switch.occupied_by` and any `train_protection_claims`, not by a retained path lock.
- Releasing or rolling back a switch lock claim does **not** restore a previous physical `Switch.state` in v1. `Switch.state` stays at the last successfully written alignment; a later compatible or conflicting path acquisition sets it again if needed.
- Add `release_train_protection_from(source_switch_id, train_id)` on `Switch` for neighbour-side tail-vacate cleanup. It removes only train-owned physical protection claims where `claim.train_id == train_id` and `claim.source_switch_id == source_switch_id`. This helper manages train-protection claims only; it does not read or mutate `occupied_by`. It is called when the source switch's tail-vacate event clears `Switch.occupied_by`; it is not a path-release trigger.
- Tail-vacate switch release must compare the releasing `train_id` with the current `Switch.occupied_by` before clearing anything. If they match, clear `Switch.occupied_by` and then release neighbour-side train protection sourced from that switch. If they do not match, leave switch occupancy and train protection unchanged and emit a diagnostic such as `switch <switch_id> release for train <train_id> skipped: currently occupied by <other_train_id>`.
- In the desired model, `Switch.locks` is a multi-owner lock collection, but physical occupancy remains single-owner: only one train may have `Switch.occupied_by` at a time.
- Add `flank_protection: List[Tuple[str, int]]` on the switch entity and reserve `length_cm: float = 0.0` for future physical switch length. In v1 each tuple is exactly `(neighbour_switch_id, blocking_state)`, where `blocking_state` is the neighbour state that would create the flank conflict if that neighbour were set toward this switch.
- Migrate call sites from `track.lock_for_path()` / `track.unlock_for_path()` and `track.is_locked_by_path()` to switch-entity lock methods.

**Switch invariants**

- `is_locked()` and `can_lock(state)` should check the canonical `(path_id, claim_role, source_switch_id)`-keyed future lock collection plus train-owned physical protection, not a single field. `can_lock(state)` means "is there a compatible lock/protection state for this switch right now," not "is there only one owner." Train-owned protection continues to block a conflicting acquisition until the later tail-vacate callback removes it.
- Once `Switch.locks` is the sole authority, `TrackSegment` lock fields should be removed rather than "kept in sync".

## Flank Protection Computation

**Flank protection computation**

- Compute flank-protection relationships at the network level and store them on each switch entity instead of on individual paths.
- Use one canonical global setting `FLANK_PROTECTION_DISTANCE_CM = 5.0` when searching for nearby switches that require mutual locking.
- At switch placement time, search the network graph outward from the switch tile, determine which neighbour states would create a flank conflict, and append `(neighbour_switch_id, blocking_state)` to `flank_protection`.
- Recompute nearby flank-protection relationships whenever topology changes.
- In v1, future flank protection uses the same `Switch.locks` compatibility rule as ordinary future switch use: multiple paths may hold compatible same-state lock claims, but physical occupancy is still single-owner and no lock or protection set may demand conflicting physical states. Future flank-protection claims follow the same `(path_id, claim_role, train_id, locked_state)` contract as primary switch claims, using `claim_role = "flank"` instead of `"main"`, and each flank claim additionally stores `source_switch_id`, the main switch whose acquisition created that claim. When the train head enters the source switch, those future flank claims are consumed into `train_protection_claims` until source-switch tail-vacate clears them. Stored flank-protection data remains `(neighbour_switch_id, blocking_state)`; the acquisition-time `safe_state` is derived from it as `1 - blocking_state` because v1 switches are binary.

## Block

**Block model**

- Replace the stored `state: BlockState` field with the following underlying primitive fields and make `state` a computed read-only property:
  - `occupied_by: Optional[str]` — physical train presence (non-None means a train is in the block).
  - `_is_caution: bool` — physical safety-margin flag (True when a train just vacated and the next block ahead is still occupied).
  - `reserved_by_path: Optional[str]` — dispatcher reservation ownership for the one active path that currently holds the block reservation.
  - `reserved_direction: Optional[str]` — direction reserved by the dispatcher through the block (N/E/S/W).
  - `reserved_for_train: Optional[str]` — the train ID the reservation is intended for; separate from `occupied_by` (physical presence) so that `BlockManager.occupy_blocks()`'s RESERVED-entry safety check stays effective after `occupied_by` is removed from the RESERVED state.
  - `caution_direction: Optional[str]` — direction of the departing train that triggered `CAUTION` (N/E/S/W). Cleared when `_is_caution` is cleared, either by `_reevaluate_caution_blocks()` during normal state-machine progression, or force-cleared by `release_path_block_reservations(completed=True)` on path completion with train stopped.
  - `allowed_travel_directions: Set["forward", "reverse"]` — static block-level travel policy for this block. Defaults to both directions allowed. This is not a reservation field and is not stored on `TrackSegment`; `Block.reserved_direction` remains only the temporary dispatcher reservation direction for one path.
- The computed `state` property should use priority order: OCCUPIED > CAUTION > RESERVED > FREE.
  - Return `OCCUPIED` if `occupied_by is not None`.
  - Return `CAUTION` if `_is_caution is True`.
  - Return `RESERVED` if `reserved_by_path is not None`.
  - Return `FREE` otherwise.
- The intended computed-state table is:
  - physical `occupied_by is not None` -> `OCCUPIED`
  - physically free + `_is_caution is True` -> `CAUTION`
  - physically free + not caution + `reserved_by_path is not None` -> `RESERVED`
  - physically free + not caution + not reserved -> `FREE`
- This makes composite physical+reservation states directly representable without contradictions:
  - OCCUPIED + `reserved_by_path` set (start-block scenario): `state` reads `OCCUPIED`; reservation is visible and clearable as a plain field write with no state check.
  - CAUTION + `reserved_by_path` set (path holds block through safety margin): `state` reads `CAUTION`; reservation is likewise clearable unconditionally.
- Treat `reserved_by_path` as the dispatcher's resource lock and `occupied_by` as physical train presence only.
- `occupied_by` should always be `None` in `RESERVED` and `CAUTION`; the dispatcher sets `reserved_by_path`, not `occupied_by`, to claim a block.
- Every `Block` must also expose one canonical block-local traversal order over its member geometry as a public ordered field such as `Block.ordered_tiles`. `Block` owns that order and owns the static allowed-direction policy for that order through `Block.allowed_travel_directions`. The list index is the canonical block-local traversal index. It is initialized directly from the tile list supplied to backend block-creation/edit logic, preserved through block edits, and never rewritten by runtime switching or path acquisition. Backend validation must verify that the supplied list is already one connected switch-free walk in that exact order; it must not reorder, reverse, or silently renormalize the caller-supplied sequence. This is a backend canonical-order contract, not a requirement to finalize a new public API shape in v1. Block editing must only insert or remove member geometry before or after the current sequence while preserving the surviving relative order, then reindex so the smallest block-local index is `0`. An edit that would require a middle insertion, reorder, or reversal of that preserved block-local order is invalid in v1 and must be rejected by backend edit validation. For a direct block target, `requested_destination_direction == "forward"` means movement in the increasing direction of that block-local order, and `"reverse"` means movement in the decreasing direction of that same order. Before `RouteExecutor` or `PathDispatcher` accepts that request, the concrete `"forward"` or `"reverse"` value must be present in the target block's `allowed_travel_directions`; otherwise the target/traversal candidate is rejected. There is no legacy unordered-position migration fallback in v1: the refactor must update current block creation/edit code so it supplies and preserves this canonical order directly.
- Because acquisition decisions need to check all blocks at once, `BlockManager` should be the sole mutator and `Block` should remain a data container.

**`CAUTION` vs reservation independence**

- `CAUTION` is an independent safety state indicating the block ahead (in the departing train's direction) is still occupied; it is orthogonal to path reservation.
- A block can be simultaneously `CAUTION` and `reserved_by_path` (path still holds it for a future or in-progress train), or `CAUTION` with no reservation (train has passed and path is done). With the computed-state model both combinations are natively representable — the `state` property returns `CAUTION` in both cases, and `reserved_by_path` can be cleared by a plain field write with no state guard.
- `CAUTION` by itself does not make a block unreservable. Its operational effect is that `TrainController` lookahead applies `CAUTION_SPEED_LIMIT_KMH` when it samples the block. `BlockManager.reserve_blocks_for_path(...)` must still allow a `CAUTION` block when the primitive reservation predicate below is satisfied.
- The `OCCUPIED → CAUTION → FREE` lifecycle is driven purely by physical train movement through `BlockManager`; it does not depend on whether a path reservation exists.
- Path reservation (`reserved_by_path`) is consumed by the dispatcher/manager on train-head entry into that block, or released by the dispatcher on path completion/cancellation if the block was never entered. This is separate from the occupancy state machine.
- `CAUTION` is directional: `caution_direction` records the direction the departing train was moving. The `CAUTION → FREE` check must only look at the adjacent block in `caution_direction`, not at all neighbours. Without this constraint a following train entering the block immediately behind would incorrectly prevent a `CAUTION` block from clearing, because the `OCCUPIED` neighbour check would match the follower rather than the train ahead that triggered the caution.

**Block methods**

- Remove `Block.can_enter()` from the physical-occupancy path. In the desired model, path reservation checks and physical occupancy are separate concerns: reservation eligibility is checked during `PathDispatcher` / `BlockManager.reserve_blocks_for_path(...)`, while `BlockManager.occupy_blocks([block_id], train_id)` records physical train entry only (single-block calls go through the same atomic helper with a one-item list).
- Remove `Block.occupy()`. With `BlockManager` as the sole mutator, `Block.occupy()` is dead code — `BlockManager.occupy_blocks(...)` writes `block.occupied_by` directly for every block in its list. Keeping `Block.occupy()` would leave a parallel write path that bypasses `BlockManager`'s serialization guarantee.
- Remove `Block.set_to_caution()`. In the new design all `OCCUPIED → CAUTION` transitions are owned by `BlockManager`; callers use `block_manager.on_block_tail_vacated()`. A `Block`-level method that changes occupancy state bypasses the manager's single-serialization guarantee.
- `reserve_for_path(train_id, direction)` (signature changed: `path_id` is removed from the block-level method, both `train_id` and `direction` are required) should stop storing `train_id` in `occupied_by` and instead store it in `reserved_for_train`. `occupied_by` is physical train presence only and must remain `None` while in `RESERVED`. Path membership is recorded separately by `BlockManager.reserve_blocks_for_path(...)` writing `block.reserved_by_path` directly; the block-level reservation field write does not carry `path_id`. Because this method is now a plain field write with no state check, it naturally handles the occupied-start-block case if one is still represented during bootstrap: setting `reserved_by_path` (by `BlockManager`) and `reserved_for_train` (by this method) is additive and does not change `occupied_by`. During normal runtime, same-train reservations are consumed on head entry and do not remain as path-owned cleanup for occupied resources.
- `release_path_reservation()` should clear `reserved_by_path`, `reserved_direction`, and `reserved_for_train` only, with no state guard. It must NOT touch `caution_direction` or `_is_caution` — those are physical-lifecycle fields owned exclusively by `BlockManager`. In the computed-state model the method is just a plain field clear, so it works regardless of the current physical state (`OCCUPIED`, `CAUTION`, `RESERVED`, or `FREE`). The old `state == RESERVED` guard is removed because it was the reason OCCUPIED+reserved and CAUTION+reserved blocks had no callable release path.
- `Block.reserve_for_path()` and `Block.release_path_reservation()` are **internal helpers** only; all callers go through `BlockManager.reserve_blocks_for_path()` and `BlockManager.release_path_block_reservations()`. They are not part of the public `Block` API.

**Block invariants**

- Remove `Block.occupy()` entirely — dead code with `BlockManager` as sole mutator.
- Remove `Block.set_to_caution()` and `Block.clear()` entirely; those physical transitions are owned by `BlockManager`.
- Remove `Block.can_enter()` outright. It is not kept for reservation-read use either; callers that need to check whether a block is reservable go through `BlockManager.reserve_blocks_for_path(...)` and let the acquisition result report failure.
- Remove `Block.is_available_for_path()` outright. Path-acquisition validation lives in `BlockManager.reserve_blocks_for_path(...)`; there is no per-block predicate method in the desired API.
- `Block.reserve_for_path()` and `Block.release_path_reservation()` are kept as internal helpers called only through `BlockManager` methods, not by any other caller.
- Remove the `occupied_by`-while-`RESERVED` behavior from `Block.reserve_for_path()`; use `reserved_for_train` instead.
- `BlockManager.occupy_blocks(block_ids, train_id)` is the sole physical-entry writer; there is no separate `occupy_block(block_id, train_id)` method. Single-block physical entry calls the same helper with a one-item list. Its RESERVED-entry path (applied per block inside the atomic call) reads `block.reserved_for_train` rather than `block.occupied_by`, because `occupied_by` is `None` in `RESERVED` in the new model. Clean physical entry is accepted as reported: `occupy_blocks(...)` sets `block.occupied_by = train_id`, clears `block._is_caution = False` plus `block.caution_direction = None`, and consumes any same-train reservation by clearing `reserved_by_path`, `reserved_direction`, and `reserved_for_train` for that block in the same atomic write. If a target block is already occupied by another train or reserved for another train, `occupy_blocks(...)` must invoke the same canonical unrecoverable hard-failure path defined above: emit a fatal conflict diagnostic identifying the block, incoming `train_id`, and prior owner; stop further simulation advancement immediately; clear authority for the incoming and prior-owner trains when identifiable; cancel/remove those trains' `RouteRun` records when present; leave unrelated trains and resources frozen in their current state; and require manual operator/admin cleanup before simulation may be restarted. It must not silently overwrite the prior owner, and it is not a recoverable cancellation or EB workflow. `OCCUPIED` overrides `CAUTION` on clean entry, and stale caution metadata must not survive an intervening clean physical entry.

## BlockManager

**Block-manager model**

- `BlockManager` should become the database-style lock manager for block resources and the single serialization point for atomic block acquisition, whether the dispatcher is attempting a full-route all-or-nothing reservation or a best-effort prefix reservation.
- Keep `occupy_blocks(block_ids, train_id)` as the existing atomic occupy helper.
- Add `reserve_blocks_for_path(block_ids, path_id, train_id, directions)` to replace one-by-one block reservation with atomic reservation.
- `directions` in `reserve_blocks_for_path(block_ids, path_id, train_id, directions)` should be a mapping keyed by `block_id`; each value must provide both the reserved block's forward `exit_edge` direction (`N`/`E`/`S`/`W`) in the chosen `resource_sequence` traversal order and the block-relative traversal direction (`"forward"` or `"reverse"`) derived from `Block.ordered_tiles`. `PathDispatcher` owns building that mapping from the chosen path geometry before calling `BlockManager`. The `exit_edge` value is written to `Block.reserved_direction`; the block-relative value is used only for `Block.allowed_travel_directions` validation.
- `reserve_blocks_for_path(...)` must first check eligibility for every future block in the candidate block set before writing any fields. Blocks already physically occupied by the train may appear in `Path.resource_sequence` for geometry/progress, but they are not included in the future reservation candidate set. A candidate future block is eligible when `block.occupied_by is None`, `block.reserved_by_path is None or block.reserved_by_path == path_id`, and the candidate's block-relative traversal direction is present in `block.allowed_travel_directions`. `block._is_caution == True` is not an eligibility failure by itself; `CAUTION` affects the following train through `TrainController.CAUTION_SPEED_LIMIT_KMH`, not by blocking an otherwise legal reservation. If any block in that candidate set fails eligibility the entire call is rejected and no state changes are made. `PathDispatcher` owns choosing whether that candidate set is the full requested route (`all_or_nothing`) or the longest best-effort prefix it wants to attempt atomically. This removes the `Block.is_available_for_path()` predicate entirely; its responsibilities are absorbed into this manager-level eligibility check.
- `reserve_blocks_for_path(...)` should set `block.reserved_by_path` directly (the `path_id` stays at the manager level, not in the block-method signature) and set `block.reserved_direction` and `block.reserved_for_train` for each future block by calling `Block.reserve_for_path(train_id, reserved_exit_edge)` with the mapping value's `exit_edge`. It must not create path-owned reservations for blocks the train already physically occupies; those resources are train-owned physical occupancy and are represented only in `resource_sequence` / `current_resource_index` for path progress.
- Add `release_path_block_reservations(block_ids, path_id, completed=False)` to release not-yet-entered reservation ownership; it replaces scattered direct `block.release()` calls during completion and cancellation without modifying physical occupancy state. This manager method must clear only blocks that both belong to that path's dispatcher-owned future reservation set and currently satisfy `block.reserved_by_path == path_id`; a mismatched block is ignored and must emit a warning/diagnostic message such as `release <block_id> but it's not reserved for <path_id>` rather than being treated as a hard release failure. Because `Block.release_path_reservation()` is now a plain field clear with no state guard, this method can call it for each matching owned block regardless of whether the block is currently `CAUTION` or `RESERVED`; normal head-entry consumption means occupied resources should no longer be path-owned future reservations. When `completed=True` (path completed with train fully stopped at terminal), it additionally force-clears `_is_caution` and `caution_direction` on any still-CAUTION matching owned blocks. When `completed=False` (path cancelled mid-flight), physical CAUTION state is left untouched — the train is still moving and the safety margin must be preserved.
- Remove `set_block_to_caution()` and replace it with `on_block_tail_vacated(block_id, train_id, direction)`: this method clears `block.occupied_by`, sets `block._is_caution = True`, records `block.caution_direction = direction`, then calls `_reevaluate_caution_blocks()` to cascade any blocks that can already advance to `FREE`.
- Treat `on_block_tail_vacated()` as the only normal train-vacated physical transition entry point.
- Keep `release_path_block_reservations(...)` as future-reservation release for path completion and cancellation. Head-entry consumption of a block reservation happens through the physical-entry path, not this path-release path.
- Keep `release_block()` as a manual/admin reservation-cleanup path only: it may clear `reserved_by_path`, `reserved_direction`, and `reserved_for_train`, but it must not touch `occupied_by`, `_is_caution`, or `caution_direction`. Remove `clear_block()` from the desired model. Manual/admin cleanup must not be part of the routine path-completion flow.
- `BlockManager` should hold a reference to the owning `RailwayNetwork` entity layer rather than maintaining its own copied block/switch registries. `RailwayNetwork` remains the canonical home of the block registry, switch registry, and topology graph/traversal helpers. `BlockManager` reads `network.blocks`, `network.switches`, and one shared network-topology adjacency helper from there; it must not rescan unrelated entity lists or invent a second topology cache of its own.

**`on_block_tail_vacated()` behaviour (directional CAUTION evaluation)**

- Legacy direct `TrainPhysics -> BlockManager.on_block_tail_vacated(...)` calls must be removed in the desired model. `TrainController.on_physics_updated(event_time, span_update)` reports normal tail-vacated block resources through `PathDispatcher.on_controller_progress(report)`, and `PathDispatcher` is the only normal runtime caller that invokes `BlockManager.on_block_tail_vacated(block_id, train_id, direction)` for block resources. `BlockManager` replaces `set_block_to_caution()` with this method.
- `BlockManager` does not independently decide that a block resource should be released; that instruction comes from `PathDispatcher.on_controller_progress(report)` after a controller-reported tail-vacate observation. `train_id` is passed through for bookkeeping/history and optional diagnostics, not as a second ownership gate that can block the normal physical `OCCUPIED -> CAUTION -> FREE` transition once release has already been instructed.
- `on_block_tail_vacated()` clears `block.occupied_by`, sets `block._is_caution = True`, and sets `block.caution_direction = direction`. With the computed-state model the block's `state` property now returns `CAUTION`.
- After updating the vacated block, `BlockManager` should call `_reevaluate_caution_blocks()` to cascade any blocks that can already advance to `FREE`.
- `_reevaluate_caution_blocks()` iterates all blocks currently in `CAUTION`. In the normal reevaluation path, a `CAUTION` block should advance to `FREE` only while it can still resolve a reachable forward protection chain in `block.caution_direction` and the first forward block on that reachable chain is NOT `OCCUPIED`. `BlockManager` owns this walk, but it performs it through the shared `RailwayNetwork` topology graph / neighbour-traversal helper rather than by scanning the full entity lists. "Forward block" is defined precisely: start from the vacated block's exit edge for `block.caution_direction`, inspect the neighbouring resource in network connectivity, and keep following live tile connectivity through any intervening switch tile using the current `Switch.state` until the next block resource is reached. That next reachable block resource is the only occupancy check used for the `CAUTION -> FREE` decision; blocks behind the vacated block or off the currently selected switch branch are ignored. This prevents a following train (entering from behind) from incorrectly keeping a caution block alive, and it also means a later switch throw can invalidate the old protected chain.
- If `_reevaluate_caution_blocks()` cannot resolve any reachable forward-adjacent block in `block.caution_direction`, or if live connectivity no longer reaches the block that was previously being protected, there is nothing ahead left to protect. In that case it should clear `_is_caution` and `caution_direction` immediately, so the computed state becomes `RESERVED` if `reserved_by_path` is still set, otherwise `FREE`.
- When a CAUTION block clears, set `block._is_caution = False` and `block.caution_direction = None`. The block's computed `state` then re-evaluates to `RESERVED` if `reserved_by_path` is still set, or `FREE` if it is not.
- Reevaluation is triggered by manager-owned connectivity changes, not by a periodic scan: at minimum `BlockManager.on_block_tail_vacated()` must call `_reevaluate_caution_blocks()`, and every successful `BlockManager.on_switch_state_changed(switch_id)` call must also trigger `_reevaluate_caution_blocks()`. `Switch` does not independently clear block caution state; it only changes connectivity, and `BlockManager` remains the sole owner of the actual `CAUTION -> FREE` decision.
- `reserved_by_path` is NOT checked as a condition for `CAUTION → FREE`. The physical safety margin and the dispatcher reservation are independent: a block can become physically clear of `CAUTION` while still holding a `reserved_by_path` value. In that case the computed `state` becomes `RESERVED`, not `FREE`, until the dispatcher separately clears the reservation via `release_path_block_reservations()`.
- Explicit exception: `BlockManager.release_path_block_reservations(..., completed=True)` may force-clear `_is_caution` and `caution_direction` during terminal completion release for owned blocks. That is a completion-time release rule, not part of the normal neighbour-based reevaluation path.

## Path And PathDispatcher

**Path model**

- Reduce the persisted dispatcher path lifecycle to three states only: `ACTIVE`, `COMPLETED`, and `CANCELLED`. The current lifecycle value is stored on `Path` as `status: PathStatus`, where `PathStatus` is the enum `{ACTIVE, COMPLETED, CANCELLED}`. `status` is initialized to `ACTIVE` on successful `create_path(...)` and is the field transitioned by completion and cancellation.
- Keep the core identity / routing fields on `Path`: `path_id`, `status`, `requested_destination_block_id`, `requested_destination_direction`, `authority_end_block_id`, `train_id`, and `path_tiles`.
- `RouteExecutor` owns route scheduling priority through `Route.priority`. Dispatcher path records do not carry a second copied `priority` field in v1; scheduling stays route-owned rather than becoming path-owned metadata.
- `path_tiles` should remain the ordered physical tile list for the authority, and its default order is train tail -> current authority end. `Path.path_tiles` and every `resource_sequence[*].path_tiles` slice use the canonical **path_tile entry schema** below; shared contracts must not use bare `(x, y)` tuples.
- Remove `PENDING`, `SETTING`, `SET`, and `CLEARING` from the desired model. Resource acquisition is synchronous inside `create_path()`, and terminal-approach behavior should be represented by progress/completion predicates rather than a second live status.
- Replace `block_sequence` and `switch_positions` with `resource_sequence`, an ordered list of path-step records interleaving blocks and switches in traversal order. The per-entry schema is defined canonically in the **resource_sequence entry schema** subsection immediately below and must not be restated divergently elsewhere.
- `RouteExecutor` platform-end resolution, `PathDispatcher.create_path(...)` start-side selection, and `PathDispatcher.extend_path(...)` suffix search must all use the same shared backend pathfinding home/helper. The implementation may extend the existing backend pathfinding code in `PathDispatcher.find_paths()` / `PathDispatcher._bfs_find_paths(...)` or extract that code into a `RailwayPathfinder` class, but it must not create a second disconnected pathfinder with different comparison or direction rules. That shared helper must be callable before any live `Path.resource_sequence` exists, must return the ordered candidate walk it used for comparison, and must be the single source for candidate-length comparison, direction filtering, current-span end selection, and tie-breaking rather than letting different layers reimplement those rules independently.

**Path field schema**

This is the single canonical field set for the dispatcher-owned `Path` entity in v1.

| Field | Type | Meaning |
| --- | --- | --- |
| `path_id` | `str` | Unique dispatcher path identifier |
| `status` | `PathStatus` | One of `ACTIVE`, `COMPLETED`, `CANCELLED` |
| `train_id` | `str` | Assigned train |
| `path_tiles` | `List[path_tile]` | Full ordered train-tail -> authority-end geometry |
| `resource_sequence` | `List[resource_sequence entry]` | Ordered interleaved block/switch resources |
| `current_resource_index` | `int` | `sequence_index` of the resource where the head currently is |
| `requested_destination_block_id` | `str` | Caller's current requested block target carried by this live path |
| `requested_destination_direction` | `str` | Resolved block-relative traversal constraint at the requested target (`"forward"` or `"reverse"` only); used for compatibility/filtering, not exact terminal-frame geometry |
| `authority_end_block_id` | `str` | Current live authority end block |
| `last_status_updated_time` | `float` | System-time Unix timestamp when `status` last changed |

- `Path` is the entity name for the dispatcher-owned resource-sequence authority record itself. Shared contracts must refer back to this table instead of rediscovering the field set from scattered prose.

**Path status state machine**

This is the single canonical state-machine contract for `Path.status` in v1. `status` is the lifecycle enum. Shared contracts must not invent extra path lifecycle states or path-owned pending cleanup flags.

| From `status` | Trigger | To `status` | Notes |
| --- | --- | --- | --- |
| (none) | `PathDispatcher.create_path(...)` succeeds | `ACTIVE` | Path record is inserted into `paths_by_id` and indexed as the train's active authority. |
| `ACTIVE` | `PathDispatcher.on_controller_progress(report)` accepts `stop_complete == true` from the pre-physics controller tick and the active path's live authority reaches the path's requested target | `COMPLETED` | The **Active-path completion procedure** owns ordering. Dispatcher commits the controller stop-complete report plus the path-owned requested-target check; it does not infer completion from precise train position or require physical head occupancy in the requested block. |
| `ACTIVE` | `PathDispatcher.cancel_path(path_id, cancellation_kind, reason=None)` | `CANCELLED` | Not-yet-entered authority resources are released synchronously; controller authority is cleared; `active_path_id_by_train[train_id]` is cleared; `RouteExecutor.handle_path_cancellation(...)` is notified. |
| `COMPLETED` | any | `COMPLETED` | Terminal. `cancel_path(...)` on a `COMPLETED` path fails with reason `"already completed"`. |
| `CANCELLED` | any | `CANCELLED` | Terminal. `cancel_path(...)` on a `CANCELLED` path fails with reason `"already cancelled"`. |

- `status` is set once per lifecycle transition by the originating synchronous call. No later stopped cleanup pass re-transitions status or writes a pending field.
- Physical `occupied_by` (block or switch) is outside this state machine. It is cleared only by controller-reported tail-vacate observations committed through `PathDispatcher.on_controller_progress(report)` and never by `status` transitions.
- A train may have at most one `ACTIVE` path at a time; retained `COMPLETED` / `CANCELLED` rows do not block a fresh `create_path(...)`.
- In a stored live path, `resource_sequence[-1]` must always be a `block` entry. A v1 path may contain switch resources internally, but its live authority end is always expressed by `authority_end_block_id` on a block resource, never on a terminal switch.

**path_tile entry schema**

This is the single canonical definition of one tile step inside `Path.path_tiles` and inside each `resource_sequence[*].path_tiles` slice.

- Each `path_tile` entry carries exactly:
  - `x`
  - `y`
  - `entry_edge`
  - `exit_edge`
  - `resource_sequence_index` — the parent `Path.resource_sequence[*].sequence_index`.
- `entry_edge` and `exit_edge` are required on every tile entry; shared contracts must not infer them later from neighboring coordinates.
- For same-block / same-tile synthetic movement, tile-entry `entry_edge` and `exit_edge` follow the train's intended forward cab direction for that move. If the move stays inside a single tile and no cab is selected, dispatcher must reject the request rather than inventing a traversal frame.

**resource_sequence entry schema**

This is the single canonical definition of a `resource_sequence` entry. Every site that describes the controller path plan, dispatcher/UI authority projections, the `to_dict()` exports, or any other projection of authority geometry refers back to this schema by name rather than restating it.

- Each `resource_sequence` entry carries exactly:
  - `sequence_index` — position of the entry in the path's train-tail -> authority-end traversal order.
  - `resource_type` — `"block"` or `"switch"`.
  - `resource_id` — stable network resource ID for the block or switch.
  - `path_tiles` — the contiguous ordered slice of canonical `path_tile` entries belonging to that resource, in train-tail -> authority-end traversal order. Every nested tile entry in this slice has `resource_sequence_index == sequence_index`.
  - `entry_edge` — the directed traversal-frame entry edge for that resource in train-tail -> authority-end traversal order.
  - `exit_edge` — the directed traversal-frame exit edge for that resource in train-tail -> authority-end traversal order.
- No other fields are required in v1.
- Ordered tiles alone are not enough for same-block / same-tile movement because a single tile can be traversed in either direction and the stop frame changes with the chosen entry side; `entry_edge` and `exit_edge` are required fields on every entry.
- `entry_edge` must equal the first nested `path_tiles[0].entry_edge`, and `exit_edge` must equal the last nested `path_tiles[-1].exit_edge`; they are stored redundantly so resource-level consumers can read the traversal frame without unpacking the whole tile slice.
- For switch resources, the required switch state is not stored as a fixed field on the entry. It is derived at acquisition time from the planner-facing `TrackSegment.enumerate_traversals(entry_edge)` contract on the switch tile, using the `(entry_edge, exit_edge)` pair selected for that resource's `path_tiles` slice. This derivation replaces storing `switch_positions` as a separate dict on the path.
- These per-resource tile slices plus explicit resource/tile entry-exit edges are the geometry contract for controller/UI consumers after `Train.current_path` is removed.
- Replace `current_block_index` with `current_resource_index`, which should track the `sequence_index` of the resource where the train head is currently located, not the first matching raw resource ID.
- Remove `blocks_cleared`; the desired model does not need a stored `resources_cleared` replacement in v1.
- Remove `flank_protection_switches` from `Path`; flank protection should live on the switch entity and be acquired automatically when the switch is locked.
- Add the requested target fields on `Path`: `requested_destination_block_id` and `requested_destination_direction`. `requested_destination_direction` is the caller's already-resolved block-relative traversal constraint for the requested target and is always `"forward"` or `"reverse"` by the time dispatcher stores it. It is used to filter compatible terminal candidates and to choose a legal terminal traversal frame, but no stop-centimeter field is stored on the path.
- Add the current authorized target field on `Path`: `authority_end_block_id`. This is the live authority end block whose forward boundary the controller brakes toward using its safety-margin policy.
- The live terminal frame still comes from explicit directed geometry on the relevant terminal `resource_sequence` block entry (`path_tiles`, `entry_edge`, `exit_edge`). For a same-block / same-tile synthetic authority, that traversal frame must still be explicit in the path contract; the spec must not rely on readers inferring direction from tile coordinates alone or from `requested_destination_direction` alone.
- When the live authority already reaches the requested destination, `authority_end_block_id == requested_destination_block_id`. When the live authority is a best-effort truncated prefix, the requested target fields remain unchanged while `authority_end_block_id` describes the temporary current authority boundary.
- Remove overlap / approach-lock data from `Path` in the desired model; they are not part of the new design and must not be retained for old approach-lock policy, cancellation gating, or history in v1. Do not add a path-owned pending cleanup field. Physical `occupied_by` state and train-owned switch protection change only through controller-reported resource entry/tail-vacate observations committed by `PathDispatcher.on_controller_progress(report)`.
- `PathDispatcher` should treat each `Path` record as the authoritative dispatcher-owned database entry, keyed by `path_id` in `paths_by_id[path_id]`, with `active_path_id_by_train[train_id]` holding the one active authority path for that train. The controller inbox is only a pushed projection of that current authority.
- Dispatcher-owned path records should remain available while active and, after termination, as retained `CANCELLED` or `COMPLETED` records for history/inspection. In v1, retain that history indefinitely rather than aging it out. Update `last_status_updated_time` on every `status` transition for recordkeeping, but authority release must not depend on the controller inbox surviving.
- `PathDispatcher`'s retained path database should be the authoritative historical store for every path it has created. After `active_path_id_by_train[train_id]` has been cleared, controller progress reports resolve active authority only against the new active authority, while delayed release or occupancy reporting for a block or switch that remains under the train resolves from the resource itself (`BlockManager` state for blocks, `Switch.occupied_by` / `Switch.train_protection_claims` for switches). `PathDispatcher.create_path(...)` must reject while that train still has an `ACTIVE` path, but once the old path is no longer active retained history rows do not by themselves block creation; only ordinary live resource conflicts remain.
- In the desired model, `train_id` is mandatory for every dispatcher authority path, including route-driven and manually requested paths. Frontend/API callers must be updated to supply it; anonymous authority paths are out of scope for this model. Future authority on reserved resources is tracked through `Block.reserved_by_path` (written by `BlockManager.reserve_blocks_for_path(...)`) and `Switch.locks` (keyed by `(path_id, claim_role, source_switch_id)`, where main claims use `source_switch_id = None`, and each claim stores `path_id`, `claim_role`, `train_id`, and `locked_state`); the block-level `Block.reserve_for_path(train_id, direction)` method itself no longer takes `path_id`.
- There is no v1 compatibility adapter for legacy path-request payloads. Repo callers, REST handlers, and UI/API layers must migrate directly to the new `create_path(...)` / `extend_path(...)` contract rather than expecting dispatcher to reinterpret old request shapes.

**Path API migration**

- Remove the legacy path-request contract entirely in v1. Do not keep or shim old caller payloads that were built around caller-supplied start/end fields, legacy result wrappers, or anonymous/manual complete-path flows.
- The canonical replacement write interfaces are `PathDispatcher.create_path(requested_destination_block_id, train_id, requested_destination_direction, acquisition_mode=...)`, `PathDispatcher.extend_path(path_id, requested_destination_block_id, requested_destination_direction, acquisition_mode=...)`, and `PathDispatcher.cancel_path(path_id, cancellation_kind, reason=None)`. `extend_path(...)` is the same request contract as `create_path(...)` plus the leading `path_id` that identifies which live path is being grown in place. `reason` is optional diagnostic text only; callers branch on `cancellation_kind`, not on reason text.
- The canonical replacement read interfaces are the controller-owned `received_path_plan` projection for active authority geometry, `TrainController.get_current_span()` for current physical span, `TrainController.get_lookahead()` for live speed/limit diagnostics, and a dispatcher-owned progress projection such as `PathDispatcher.get_active_path_progress(train_id) -> {path_id, status, current_resource_index}` when UI/debug consumers need live `current_resource_index`. That projection is resolved from dispatcher-owned path registries (for example `active_path_id_by_train` plus `paths_by_id`) and returns the currently active path bound to that `train_id`; it does not read train/controller mirror fields.
- Route-managed planning remains point-to-point per call. `RouteExecutor` never asks dispatcher/pathfinder to solve a whole multi-waypoint route in one search. Each `create_path(...)` or `extend_path(...)` request targets exactly one currently resolved waypoint block at a time, and longer waypoint chains are formed by concatenating repeated successful point-to-point segments onto the same live path.

**`create_path()` flow**

1. Before candidate search or any side effect, `PathDispatcher.create_path(...)` must reject the request if `active_path_id_by_train[train_id]` already references an `ACTIVE` path. A train can have only one active authority plan at a time. This failure happens with no path ID allocation, switch acquisition, block reservation, path push, switch-state mutation, or `paths_by_id` record insertion. Callers must use `PathDispatcher.extend_path(...)` to grow that same live path, or wait until the old path has transitioned out of `ACTIVE` before calling `PathDispatcher.create_path(...)` again.
1. Candidate search should enumerate direction-compatible resource sequences from the train's current occupied span to `requested_destination_block_id`, reject any candidate that uses repeated resources, reject any candidate whose traversal violates a block's `Block.allowed_travel_directions`, reject any candidate that reaches the terminal block in a way that does not satisfy `requested_destination_direction`, and then attempt acquisition in candidate order under the chosen `acquisition_mode`.
1. Dispatcher must build and store the exact directed terminal frame for the requested target (`path_tiles`, `entry_edge`, `exit_edge`) as part of the terminal `resource_sequence` block entry. For an ordinary live path, dispatcher derives that frame from the chosen terminal block traversal. For same-block / same-tile normalization, dispatcher derives the needed local frame from the `train_id`'s current occupied blocks and, when the move stays inside a single tile, the currently selected cab direction. When the requested target was resolved from a multi-block platform, `RouteExecutor` must already have resolved one concrete terminal block for that run before calling dispatcher, and the terminal frame uses that already-resolved terminal block directly; dispatcher does not choose between platform blocks itself.
1. `PathDispatcher.create_path(...)` should take `requested_destination_block_id`, `train_id`, `requested_destination_direction`, and `acquisition_mode`; it should not require a caller-supplied `start_block_id`, a stop-centimeter value, or a second opaque waypoint/platform stop-context payload. Dispatcher derives the forward planning side from `SimulationController.get_or_create_controller(train_id).get_current_span()` by calling the same shared global pathfinder/helper that `RouteExecutor` uses: compare both physical ends of the train against the requested target, use the shorter successful result as the forward/head side for pathfinding toward the target, and then seed the stored authority from the full already-occupied span behind that forward side. If one physical end is currently on a switch resource, map that end to the one occupied block inward from that end of the current span before running the candidate comparison; if no such inward occupied block exists for that end, that end is not a valid start-side candidate. The canonical comparison order is: first lower candidate `tile_count`, then lower candidate `walk_length_cm`; if candidates still tie across the two physical train ends, prefer the `end_a` candidate over the `end_b` candidate; otherwise keep the stable candidate order returned by that shared helper and do not add a layer-local ad hoc tie-break.
1. `PathDispatcher.create_path(...)` should also take an explicit `acquisition_mode` parameter of type `PathDispatcher.AcquisitionMode`, an enum owned by `PathDispatcher` with v1 values `all_or_nothing` and `best_effort`.
1. Candidate search must become direction-aware. The shared ordered-walk entry point (named `RailwayPathfinder.find_ordered_walk(...)` in this document if the implementation extracts a class from the existing dispatcher search) must reject candidates whose traversal violates `Block.allowed_travel_directions` and candidates whose terminal traversal does not satisfy `requested_destination_direction`, and same-block / same-tile synthetic path construction must use `requested_destination_direction` only as a constraint while dispatcher still derives the exact local terminal frame from explicit geometry. For a direct `block_id` target, `requested_destination_direction` is interpreted against that block's immutable internal traversal order: `"forward"` means the increasing direction of that block-local order and `"reverse"` means the decreasing direction. `RouteExecutor` must resolve any waypoint-authored `"either"` into one concrete block-relative `"forward"` or `"reverse"` before calling `create_path(...)` or `extend_path(...)`; dispatcher never receives `"either"` in the v1 path contract. If dispatcher still cannot build one unique terminal frame for the chosen move, path creation must fail rather than guessing.
1. Stop-position centimeter inputs are not part of `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)` in v1. The controller computes the braking target from the authority boundary and its canonical safety margin.
1. Allow `create_path(...)` for same-block repositioning when the train's current occupied span already includes `requested_destination_block_id`, but treat that as a dispatcher capability for explicit local-reposition/manual callers rather than as the normal route-side handling for an already covered stop waypoint. Argument naming is consistent throughout the desired model: `requested_destination_block_id` is the caller's current requested target passed into `create_path(...)` / `extend_path(...)`, and `authority_end_block_id` is the current live-authority end stored on the `Path`.
1. For an explicit same-block repositioning request, `PathDispatcher.create_path(...)` owns deciding what tiles/resources must be assigned based on the train's current occupied span and the requested destination block/direction. It does not accept or store a separate centimeter stop target for that local move; the controller uses the ordinary safety-margin stop logic. If the required movement stays on ordinary track tiles inside one block, dispatcher may build a synthetic local path with one block resource whose `path_tiles` slice covers the local movement. If that movement stays inside a single tile, dispatcher must still use `requested_destination_direction` plus the train's currently selected cab direction to validate and disambiguate the local traversal frame. If those disagree, or if no cab is selected for this same-tile edge case, dispatcher must reject the request with a defined failure reason such as `"same-tile synthetic movement requires a selected cab direction"` rather than guessing.
1. In `all_or_nothing` mode, if the full requested candidate path cannot be acquired, roll back and return failure; no live path is created.
1. In `best_effort` mode, if the full requested candidate cannot be acquired, `PathDispatcher` should truncate the authority to the furthest forward resource prefix it can acquire on that candidate and still create one live path. That truncated live path keeps the same `path_id`, preserves the requested target fields, and sets `authority_end_block_id` to the last acquired block in the current authority. The controller does not need a special "you are already at your authority end" branch: it enters the ordinary running flow, and ATC/lookahead handles the geometry using the current authority boundary plus safety margin. `create_path(...)` succeeds whenever it creates a brand-new path record with a non-empty live `resource_sequence`, even if that live sequence is only the newly created path entity's seeded already-covered span and no newly acquirable forward resource was added beyond the train's current coverage. In that covered-span-only case, the head is always inside a block (the head-on-switch case is rejected separately below), so `authority_end_block_id` is that head-side block.
    - Special case: if the furthest acquirable prefix ends on a `switch` resource, dispatcher must truncate again to the previous `block` resource before storing the live path, so the stored live authority is always block-terminated.
    - If the train's covered span itself is empty so no non-empty live `resource_sequence` can be formed for the new path, `PathDispatcher.create_path(..., acquisition_mode=best_effort)` must fail.
    - Exception: if the train head is currently on a switch resource and no forward block beyond that switch can be acquired, `PathDispatcher.create_path(..., acquisition_mode=best_effort)` must fail rather than storing a head-on-switch holding authority. A natural-language failure reason such as `"cannot create best-effort authority while head is on a switch"` is sufficient in v1.
1. Allocate the new `path_id` before switch acquisition so `Switch.locks` and flank-protection claims can be keyed by that same path ID. Once the chosen acquisition result succeeds, create the dispatcher-owned path record directly in `ACTIVE` state and push the controller path plan immediately. There should be no persisted intermediate `SET` state in the desired model.
1. `PathDispatcher.create_path(...)` seeds `resource_sequence` from the train's already-occupied resource span for every occupied-start case, not only the one-resource synthetic case. The canonical start-side rule is: read the current span from `TrainController.get_current_span()`, collect the current block at each physical end of the train, and if one end is currently on a switch resource use the one occupied block inward from that end as its start-side comparison block. Then run the shared helper/pathfinder from each valid end block toward `requested_destination_block_id` and compare the resulting candidate metrics in the canonical order `tile_count`, then `walk_length_cm`, then the helper's own stable candidate order. The shorter successful result identifies the forward/head side for the new move. If the train remains entirely within one block, that same block is both ends and there is no ambiguity. If only one end can produce a valid candidate, use that end as the forward/head side. If a candidate from a switch-side end would require traversing through the current switch area in a way that is not reachable under the live switch states, that end's candidate simply fails. If both ends fail, path creation fails. After that forward/head-side choice, build the stored sequence in traversal order as: already-occupied resources from the tail-most occupied resource through the current head side, then the forward candidate from that head side toward the requested target. The already-occupied backward portion is included because the train already owns it physically, but it is not re-reserved as future path authority; only the forward suffix beyond the current head side is subject to ordinary acquisition conflict handling and therefore to `all_or_nothing` vs `best_effort`. After the full sequence is assembled, set `current_resource_index` to the resource where the train head is currently located. On each seeded entry, the side toward the path direction is `exit_edge` while the side the train came from is `entry_edge`. As a worked example: for an explicit same-block repositioning request, if dispatcher builds that one-resource synthetic move, initialize both the sequence and the head index to that sole resource. `RouteExecutor` v1 does not use this same-block path flow for a stop waypoint whose resolved target block is already physically covered by the current train span; route-side covered-waypoint normalization skips that stop instead. If the train's current span or required movement would still include another resource (for example a switch that the train continues to cover), `PathDispatcher.create_path(...)` should expand the assigned tiles/resources itself and build a normal multi-resource authority from the train's current occupied span to the target; `RouteExecutor` does not compute or pass those tiles directly.
1. Build `resource_sequence` in traversal order so both blocks and switches are tracked in one sequence.
1. Store both target contracts on the `Path`: the resolved requested target (`requested_destination_block_id`, `requested_destination_direction`) and the current authorized target (`authority_end_block_id`).
1. The active-path guard has already run before acquisition. A retained `CANCELLED` / `COMPLETED` row or retained history row does not by itself block `PathDispatcher.create_path(...)`; only ordinary resource conflicts still apply.
1. Store the new dispatcher-owned path record in `paths_by_id[path_id]` and set `active_path_id_by_train[train_id] = path_id`.
1. Do not copy reserved-block state onto `Train`; future reservations remain dispatcher-owned on resources and in the controller-facing authority projection until head-entry consumes them.
1. Push the canonical **received_path_plan schema** to the controller after successful creation. Its nested authority geometry must follow the canonical **resource_sequence entry schema** and **path_tile entry schema**.
1. The pushed plan must preserve an explicit traversal frame for every block and switch entry; readers must not try to recover that frame later from tile coordinates alone.

**`create_path()` / `extend_path()` return contract**

- `PathDispatcher.create_path(...)` and `PathDispatcher.extend_path(...)` return a small result object with exactly `success: bool`, `path_id: Optional[str]`, `resource_sequence: Optional[List[resource_sequence entry]]`, `requested_destination_block_id: Optional[str]`, `requested_destination_direction: Optional[str]`, `authority_end_block_id: Optional[str]`, and `reason: Optional[str]`.
- On success, `path_id`, `resource_sequence`, `requested_destination_block_id`, `requested_destination_direction`, and `authority_end_block_id` are required; `reason = None`; and `resource_sequence` is the full current live `resource_sequence` after that create/extend operation completes. `RouteExecutor` may inspect these returned target fields and geometry to see whether the armed pending-waypoint target is already contained in the live path, but it does not advance any route waypoint index from this return payload alone.
- Success means that `PathDispatcher.create_path(...)` created a new path record with a non-empty live `resource_sequence`, or that `PathDispatcher.extend_path(...)` appended at least one new resource to the existing live `resource_sequence`. A create-path call may therefore succeed with a non-empty seeded covered-span authority even when no newly acquirable forward resource was added, but an extend-path call that appends nothing is still a failure in v1 rather than a successful no-op.
- On failure, `success = False`, `path_id = None`, `resource_sequence = None`, all target fields are `None`, and `reason` is required.
- `reason` is human-readable diagnostic text for create/extend failures. Callers may display or log it, but they must not branch on exact string equality in v1.

**`cancel_path()` return contract**

- Define `PathCancellationKind` as the branchable cancellation enum with v1 values `OPERATOR_CANCELLED`, `REVOKED`, `EB`, `ROUTE_DEVIATION`, and `POWER_OFF`.
- `PathDispatcher.cancel_path(path_id, cancellation_kind, reason=None)` returns a small result object with exactly `success: bool`, `path_id: Optional[str]`, `new_status: Optional[PathStatus]`, `cancellation_kind: Optional[PathCancellationKind]`, and `reason: Optional[str]`.
- On success, `success = True`, `path_id` is required, `new_status = CANCELLED`, `cancellation_kind` is the enum value applied to that path, and `reason` is optional plain-text diagnostic context.
- On failure, `success = False`, `path_id = None`, `new_status = None`, `cancellation_kind = None`, and `reason` is required.
- Failure cases are explicit in v1:
  - missing path -> failure with a plain-text reason such as `"path not found"`
  - already `COMPLETED` path -> failure with reason `"already completed"`
  - already `CANCELLED` path -> failure with reason `"already cancelled"`
- When the path is currently `ACTIVE`, `cancel_path(...)` performs the normal cancellation flow described below and returns success. Callers may display or log `reason`, but they must never branch on exact reason text.

**Resource acquisition**

- Acquire switches first, then blocks, so switch conflicts fail before any blocks are reserved.
- For each switch in path order, call `switch.acquire_lock(path_id, "main", train_id, required_state)` and immediately acquire any `switch.flank_protection` locks. Each `flank_protection` entry `(neighbour_switch_id, blocking_state)` is acquired as `neighbour_switch.acquire_lock(path_id, "flank", train_id, safe_state)`, where `safe_state` is the neighbour's state whose active segment does **not** point toward the primary switch's track — i.e. the state that keeps the neighbour's diverging path aimed away, preventing a head-on approach. `safe_state` is computable from switch geometry: it is the neighbour state whose selected branch exit edge is not the edge facing the primary switch. In v1, because switches are binary, `safe_state` is simply the opposite of the neighbour's `blocking_state` recorded at placement time. Every acquired flank claim must store `source_switch_id = switch.switch_id` so later switch head-entry can convert only the flank claims sourced from that main switch into train-owned protection.
- Acquire blocks atomically through `BlockManager.reserve_blocks_for_path(...)`.
- Resource acquisition should write `Block.reserved_direction` through `BlockManager.reserve_blocks_for_path(...)` for every reserved block. Tile-level traversal direction is carried by `resource_sequence[*].entry_edge` / `exit_edge` and nested `path_tiles[*].entry_edge` / `exit_edge`; there is no separate `TrackSegment.path_direction` field in the desired model.
- Distinguish retained geometry, static allowed travel, and temporary reservation direction: v1 does not define a track-level `traffic_direction_policy` field. Static allowed travel direction lives on `Block.allowed_travel_directions`; `Block.reserved_direction` is only the dispatcher-owned temporary reservation direction for one path; and the path plan geometry carries the finer-grained per-tile traversal frame inside that block.
- On failure, roll back in reverse acquisition order, including switch locks and block reservations. There is no separate tile-level `path_direction` assignment to clear.
- That rollback releases the acquired claims/reservations only; it does not restore an earlier physical `Switch.state`. The live switch alignment remains at the last successfully written value until some later switch command or path acquisition changes it again.
- Replace direct `block.release()` calls in completion and cancellation with `BlockManager.release_path_block_reservations(...)`.
- In v1, block reservations remain single-train/single-path resources even though `Switch.locks` can have multiple compatible owners. `Block.reserved_direction` therefore has at most one active value per reserved block and should be cleared when that block reservation is released.
- `create_path(..., acquisition_mode: PathDispatcher.AcquisitionMode)` and `extend_path(..., acquisition_mode: PathDispatcher.AcquisitionMode)` must share the same `PathDispatcher.AcquisitionMode` enum, with two v1 behaviors:
  - `AcquisitionMode.all_or_nothing`: dispatcher acquires only the full requested authority or returns failure after full rollback
  - `AcquisitionMode.best_effort`: dispatcher may truncate to the furthest forward acquirable resource prefix, but the acquisition of that chosen prefix is still atomic
- In `best_effort` mode, `PathDispatcher.create_path(...)` may report success without acquiring any new future resource only when it still creates a new path record with a non-empty seeded `resource_sequence` from the train's already-covered span. This create-only exception exists so explicit same-block / local movement authorities can work. A create with an empty `resource_sequence` still fails. `PathDispatcher.extend_path(...)` has no matching no-op success rule: an extend that appends no new resource to the existing live path fails and leaves the existing path unchanged.
- The special head-on-switch case remains a failure because v1 does not allow storing a head-on-switch live authority end.
- In all acquisition modes, the stored live authority end must be block-terminated. A same-tick acquisition result that reaches a switch but no following block is not a valid stored live authority in v1; dispatcher must roll that trailing switch/flank acquisition back before storing or pushing the path.

**Controller-mediated progress**

- `TrainPhysics.tick(...)` should compute the next `TrainSpan`, next `current_speed_kmh`, and the ordered tile-level delta for that movement, then call `TrainController.on_physics_updated(event_time, span_update)`. `TrainPhysics` does not call dispatcher progress, completion, or release APIs directly and does not own the stored span.
- `TrainController.on_physics_updated(event_time, span_update)` should atomically write `span_update.new_span` and `span_update.current_speed_kmh` into controller-owned storage, then detect newly entered blocks, newly entered switches, tail-vacated blocks, and tail-vacated switches by converting `span_update.added_tiles` and `span_update.removed_tiles` through network tile/resource lookup, `received_path_plan.resource_sequence` when authority exists, and current traversal context. It then sends one ordered `PathDispatcher.on_controller_progress(report)` call. Stop completion is not reported from this method; it is evaluated on the next pre-physics `TrainController.tick(...)`.
- The controller progress report payload carries exactly `train_id`, `event_time`, `entered_resources`, `tail_vacated_resources`, `current_head_sequence_index`, `deviation`, `deviation_kind`, `deviation_reason`, `passed_requested_target`, and `stop_complete`. It does not carry `path_id`; `PathDispatcher` resolves active authority from `active_path_id_by_train[train_id]`. `current_head_sequence_index` is the index of the train head's current position in `received_path_plan.resource_sequence`, or `None` when no active resource-sequence mapping is available. When live authority exists and the controller cannot map the head to that active `resource_sequence`, the report must set `deviation = true`, `deviation_kind = "out_of_sequence"`, `current_head_sequence_index = None`, and `stop_complete = false`; dispatcher treats that report as deviation/cancellation input rather than as ordinary active-path progress. `deviation_kind` is the branchable enum (`"out_of_sequence"`, `"beyond_authority"`, or `"beyond_requested_target"`), `passed_requested_target` is the branchable boolean used by route recovery, and `deviation_reason` is diagnostic plain text only. Each resource event in `entered_resources` and `tail_vacated_resources` carries `sequence_index` when known, `resource_type`, and `resource_id`; block tail-vacate events additionally carry `direction`. For a single report, dispatcher processing order is always entered resources first, then tail-vacated resources.
- When physical movement crosses multiple resource boundaries within one simulation tick, `TrainPhysics` must fire multiple sequential `TrainController.on_physics_updated(event_time, span_update)` calls — one per resource boundary crossed, in physical traversal order — rather than batching them into a single multi-resource report. `TrainPhysics` computes each incremental `span_update` up to the next boundary, samples `time.time()` for that boundary event, calls `TrainController.on_physics_updated(event_time, span_update)` with that system-time Unix timestamp, lets `TrainController.on_physics_updated(event_time, span_update)` and `PathDispatcher.on_controller_progress(report)` commit that step's state changes, then computes the next boundary update and repeats. After the last boundary in that tick, or on a tick with no boundary crossing, `TrainPhysics` must still emit one final `span_update` when the integrated span or `current_speed_kmh` changed; that final update carries `added_tiles=[]` and `removed_tiles=[]` when no resource boundary was crossed. A pure speed change with no span movement still emits this no-boundary update so `TrainController.current_speed_kmh` cannot go stale. This guarantees that downstream side effects (lock consumption, tail-vacate release, route head-advance callbacks, switch state notifications) happen in the same physical order as the boundary crossings, while controller-owned span/speed storage is still refreshed on ordinary non-boundary motion. Within any single `TrainController.on_physics_updated(event_time, span_update)` call, `entered_resources` and `tail_vacated_resources` therefore typically carry one entry each at most; if a single call legitimately needs to carry more (for example simultaneous head entry and tail vacate at the same boundary), events within each list must still be ordered by physical traversal / vacate order, and dispatcher still processes the entered list before the vacated list.
- Entry ownership is resource-typed and dispatcher-mediated:
  - on block entry, `PathDispatcher.on_controller_progress(report)` calls `BlockManager.occupy_blocks([block_id], train_id)`; this is the only normal runtime path that writes `Block.occupied_by`
  - on clean switch entry, `PathDispatcher.on_controller_progress(report)` sets `Switch.occupied_by = train_id`, consumes the path-owned main switch lock, and converts applicable flank locks into train-owned protection; if another train already occupies the switch, this is the hard-failure conflict case and must not overwrite the prior owner
- Dispatcher progress should update `Path.current_resource_index` using the reported path-step `sequence_index`, not by searching for the first matching raw `resource_id`. `Path.current_resource_index` is head-based progress only; it advances when the train head enters a new resource and does not wait for the later tail-based release of earlier resources.
- A live path should remain `ACTIVE` after creation, through intermediate resources, and after entering the final block/resource. Entering the terminal resource should not change lifecycle state by itself.
- `stop_complete == true` is controller-reported only from the pre-physics `TrainController.tick(...)` stop-complete check. It may be set only when all of the following are true: the controller has live authority, the current authority has been accepted for departure (`departure_ready_path_id == received_path_plan.path_id`), the selected cab/travel frame is heading in the active authority frame toward the current authority end, `TrainController.is_stopped()` is true, `TrainController.eb_active == False`, and the distance-0 lookahead has `atc_limit == 0` with `atc_limit_reason_code == "authority_stop"`. The controller may satisfy that authority-stop predicate either because the train has physically progressed through the final `resource_sequence` entry or because the remaining projected authority distance is too short to grant additional positive clearance after applying the controller safety margin (for example, a very short terminal block is smaller than the margin, so ATC cannot safely command entry all the way to that block edge). It does not require a route-authored centimeter stop target, physical head occupancy in the requested destination block, a requested-destination block comparison, or a second exact-position check. `PathDispatcher.on_controller_progress(report)` owns the path-level acceptance check: a controller `stop_complete` report becomes path completion only when the active `Path.authority_end_block_id == Path.requested_destination_block_id`; otherwise the path remains live and route-side extension/retry logic continues. `departure_ready_path_id` is the single canonical depart-acceptance gate for route/API departure and for stop-completion eligibility; it is set only by a successful `TrainController.depart()` acceptance for the current `received_path_plan.path_id` and is cleared whenever the current authority is replaced, completed, cancelled, EB-latched, or powered off. Manual driving input may still command motion before `departure_ready_path_id` is set, but such movement is protected by the same ATC lookahead limits and cannot produce a dispatcher path-completion report until `TrainController.depart()` has accepted that authority. This depart gate applies only to stop-completion eligibility. Head-entry route progress, including `Waypoint.kind == "pass_through"` consumption through `RouteExecutor.handle_train_advanced(...)`, is not depart gated. This unifies stop completion across ATO, manual, and any explicit dispatcher-owned same-block / stationary repositioning move: any train that has been told to depart and has stopped at the end of usable authority may report usable-authority stop; only dispatcher may convert that report into path completion. A train that never departed (cab selected but never told to go) cannot.
- Raw `atc_limit == 0` is not enough for stop completion. No-cab, no-authority, EB, obstruction/conflict, wrong-direction cab, and truncated best-effort authority are not stop completion, even if the distance-0 ATC limit is zero.
- For a stop waypoint whose live authority already reaches its requested target, a controller stop-complete report at the safety-margin-adjusted usable authority stop completes the path normally. The head may be short of the physical requested block when the safety margin/ATC boundary requires that; ATC remains the higher-priority rule and there is no "go back and try again" prompt for a within-block or before-block safety-margin stop.
- EB activation cancels the path through `PathDispatcher.cancel_path(..., cancellation_kind=PathCancellationKind.EB, reason=...)`. While EB is latched, `TrainController.tick(...)` must not report `stop_complete == true`; after EB release any route continuation uses a fresh path request.
- `PathCancellationKind.ROUTE_DEVIATION` means any controller-reported out-of-sequence resource, beyond-authority resource, or beyond-requested-terminal overshoot. When `PathDispatcher.on_controller_progress(report)` sees `deviation == true` for the active path, dispatcher cancels that path with `cancellation_kind=PathCancellationKind.ROUTE_DEVIATION` and carries `deviation_kind`, `passed_requested_target`, and diagnostic `deviation_reason` into the cancellation context. Cancellation wins over stop completion if both are present in the same faulty report. `RouteExecutor.handle_path_cancellation(...)` records that context immediately on the matching `RouteRun`, but route skip/recovery planning still waits until the train has reached the fresh stopped no-authority or post-EB recovery point. `RouteExecutor` must branch only on `cancellation_kind`, `deviation_kind`, and `passed_requested_target`; `reason` / `deviation_reason` strings are for logs and UI only.
- A best-effort truncated path must not complete just because the train has stopped at the current authority boundary while the current authorized target is still short of the requested target. In that case the same path remains `ACTIVE`, the controller may enter `RUNNING_WAITING` under the still-live authority, and `RouteExecutor` should keep trying `PathDispatcher.extend_path()` on that same `path_id`.
- Completed paths should release only not-yet-entered block reservations through `BlockManager.release_path_block_reservations(..., completed=True)`, because reservations for already-entered blocks were consumed on head entry. That reservation release may force-clear terminal `CAUTION` only for matching still-reserved owned blocks, but it must not force-clear any physical `OCCUPIED` block early. On this `ACTIVE -> COMPLETED` transition, dispatcher follows the **Active-path completion procedure** ordering. The retained record may remain in `paths_by_id` for history, but physical release of a switch or block still under the train resolves from the resource itself. When a later tail-vacate resource event arrives through `PathDispatcher.on_controller_progress(report)`, it clears `Switch.occupied_by` / block occupancy and any train-owned switch protection through the resource-specific release path. `RouteExecutor` treats the dispatcher callback as authoritative completion and does not re-check safety-margin projection itself.
- Remove `_record_completion_event()`, `completed_path_events`, and `get_and_clear_completion_events()`.
- When creating or extending a path, resolve and store the requested target contract first, then set the current authorized target contract and include both in the controller path plan:
  - if the live authority already reaches the requested target, set `authority_end_block_id == requested_destination_block_id`
  - if the live authority is still truncated, keep the requested target unchanged and set `authority_end_block_id` to the current temporary end of `resource_sequence`
- Drive resource release from controller-reported tail-vacate observations. `PathDispatcher.on_controller_progress(report)` should inspect `resource_type` and release it accordingly:
  - vacated blocks go through `BlockManager.on_block_tail_vacated(block_id, train_id, direction)`
  - vacated switches go through the `Switch` entity after `PathDispatcher` resolves the vacating `train_id` for that `switch_id` from switch state (`clear Switch.occupied_by`, then clear train-owned protection for that source switch through `Switch.release_train_protection_from(source_switch_id=switch_id, train_id=train_id)` on each protected neighbour)
- Route any normal block release through `BlockManager.on_block_tail_vacated()` so `OCCUPIED -> CAUTION -> FREE` remains a single-manager state machine. Manual/admin cleanup stays out of the routine completion flow; in the desired model that cleanup uses `release_block()` only because `clear_block()` is removed.

**Path extension**

- Keep forward-only extension.
- When the path model switches to `resource_sequence`, append new tiles and new resources while skipping duplicated connection/start entries.
- Reject any extension that would cause a resource to appear twice in the combined path.
- `PathDispatcher.extend_path(...)` should take the same argument contract as `create_path(...)`, except that it identifies the existing live path by `path_id`: `path_id`, `requested_destination_block_id`, `requested_destination_direction`, and `acquisition_mode`. The live path identified by `path_id` is the fixed already-acquired prefix; `extend_path(...)` grows that existing path forward from its current authority end toward the caller-supplied requested target for this extend attempt. Dispatcher does not run a separate shared-walk prefix-compatibility test. If the requested extension cannot continue forward from the existing live path without revisiting an already-held resource or otherwise violating the ordinary path rules, `extend_path(...)` fails and leaves the existing path unchanged.
- The only difference between `extend_path(...)` and `create_path(...)` in v1 is that `extend_path(...)` requires a live `path_id` and the newly appended suffix must continue forward from that live path's current authority-end edge in the same travel direction the existing prefix was built in. The caller-supplied `requested_destination_direction` applies only to the new terminal block `requested_destination_block_id`; it is not a license to reverse at the current authority end. A `requested_destination_direction` that would require the train to reverse 180 degrees at the current authority end (for example, the requested new terminal block lies behind the current authority-end edge on the existing prefix's travel frame, or reaching it would require exiting the authority-end block backward out of its current `exit_edge`) is invalid for `extend_path(...)` and must be rejected with `success = False` and a `reason` such as `"extend would reverse at authority end"`. The existing live path must remain unchanged in that rejection. Callers that actually need the train to turn back at the current terminal must cancel the existing path and issue a fresh `create_path(...)` from the train's current span instead.
- `PathDispatcher.extend_path(...)` must return `success=False` with a required `reason` when `path_id` does not exist or when the referenced path is not currently `ACTIVE`.
- In `all_or_nothing` mode, `extend_path(...)` should either acquire the full requested suffix to `requested_destination_block_id` or leave the existing path unchanged.
- In `best_effort` mode, `extend_path(...)` should keep the same `path_id` and append the furthest forward acquirable suffix it can add to the current path. The `resource_sequence` therefore grows in place on the same live path instead of creating a new path. On a successful extend attempt, update the stored requested target fields on that same `Path` to the caller-supplied contract for that attempt, even if the live authority remains truncated short of it. If the extend attempt cannot add any new resource at all, it is a failure result and the existing stored requested target remains unchanged.
- While the path is still truncated short of the caller's current requested target, set `authority_end_block_id` to the current last acquired block.
- On every successful `PathDispatcher.extend_path(...)` that appends at least one resource, update the dispatcher-owned `Path` record and repush the refreshed path plan through `TrainController.receive_path_plan(...)` if that path is still the train's active authority, even when best-effort authority remains short of the current requested target. Once `extend_path(...)` finally reaches the current requested target block carried by that path, additionally set `authority_end_block_id = requested_destination_block_id` before that same repush.
- In `best_effort` mode, if an extension attempt cannot add any new resource at all on that tick, it is a failure result rather than a successful no-op. The existing live path remains in place, but the return contract reports `success = False`.

**Cancellation**

- `PathDispatcher.cancel_path(path_id, cancellation_kind, reason=None)` is the single canonical cancellation entry point in v1. `cancellation_kind` is the branchable enum carried through release and route-side recovery. `reason` is plain-text diagnostic context for logs/UI only and must not be used for condition branching.
- Release owned blocks through `BlockManager.release_path_block_reservations(...)` instead of direct `block.release()` calls. In the desired v1 model, cancellation release clears future reservation ownership only; it never clears physical occupancy.
- Path cancellation or revocation effects are owned entirely by `PathDispatcher`. `RouteExecutor` or `TrainController` may initiate cancellation only by calling `PathDispatcher.cancel_path(...)`; they must not clear authority or release resources themselves. Cancelling a live path should clear controller authority by calling `controller.receive_path_plan(None)`.
- Power-off uses this same dispatcher cancellation workflow. `TrainController.power_off_cmd()` is the canonical initiator and must follow the **Power-off procedure**: validate stopped, cancel any active path through `PathDispatcher.cancel_path(active_path_id, cancellation_kind=PathCancellationKind.POWER_OFF, reason="power off")` while the train's `RouteRun` is still registered, let the ordinary cancellation callback path run (including `RouteExecutor.handle_path_cancellation(...)` with `cancellation_kind=PathCancellationKind.POWER_OFF`), then call `RouteExecutor.remove_train_route_run(train_id, reason="power_off")`, and only after route/dispatcher teardown perform controller-local OFF cleanup such as clearing cab, EB latch, `post_eb_restart_pending`, `departure_ready_path_id`, and `ato_running`. If `active_path_id_by_train[train_id]` is empty when power-off runs, the `PathDispatcher.cancel_path(...)` step is skipped and `TrainController.power_off_cmd()` proceeds straight to `RouteExecutor.remove_train_route_run(train_id, reason="power_off")`; the listed cancellation step is a comprehensive description of the workflow when a live path exists, not a requirement that one must exist. It must not invent a separate OFF-specific release path.
- On the `ACTIVE -> CANCELLED` transition, `PathDispatcher.cancel_path(...)` runs synchronously and must transition the path to `CANCELLED`, clear not-yet-entered block reservation ownership, clear not-yet-entered switch/flank locks, clear controller authority, and clear `active_path_id_by_train[train_id]` before returning success. Cancellation clears future reservation/authority only; it never clears `Block.occupied_by`, `Block._is_caution`, `Block.caution_direction`, `Switch.occupied_by`, or train-owned switch protection. A block reservation may be cleared even when the train still physically occupies that block because reservation ownership and physical occupancy are independent, but in normal flow same-train reservations for entered blocks have already been consumed on head entry. A same-train new path is allowed once the old path is no longer `ACTIVE`, subject to ordinary live resource conflicts and train-owned physical protection.
- Reservation / physical state ownership in v1 should be read literally:
  - dispatcher-owned future reservation state: `Block.reserved_by_path`, `Block.reserved_for_train`, `Block.reserved_direction`, `Switch.locks`, flank-protection lock ownership for resources the train has not entered yet
  - block physical state owned by `BlockManager` and mutated only through `BlockManager` entry/tail-vacate APIs invoked by `PathDispatcher` on controller-reported observations: `Block.occupied_by`, `Block._is_caution`, `Block.caution_direction`
  - dispatcher-mediated switch physical state, written by `PathDispatcher` on controller-reported resource-entry / tail-vacate observations rather than directly by `TrainPhysics`: `Switch.occupied_by` and `Switch.train_protection_claims`
  - a block or switch has at most one physical `occupied_by` train at a time (single-train physical ownership). A single train may hold multiple path records layered over that physical ownership; path membership is tracked separately by `PathDispatcher` on `Path` records, not by duplicating `occupied_by` per path.
  - cancellation / completion release clears only future block reservations and future switch locks that have not already been consumed by head entry
  - only controller-reported physical entry / tail-vacate observations may clear or set `BlockManager`-owned block physical state or dispatcher-mediated switch physical state
  - once a resource is physically occupied, later tail-vacate clears physical occupancy and train-owned protection rather than path-owned residue
- Once `received_path_plan` is cleared while the train is moving, the essential event is "authority removed." `PathDispatcher` does not set EB directly. On the next `TrainController.tick()` after authority was cleared — which, when cancellation ran inside the current tick's Phase 1, is the same tick's Phase 2 controller tick — the controller rebuilds lookahead with no live authority and therefore extends it only to the occupied block boundary. The controller must command ordinary braking toward zero at that boundary using the no-authority ATC limit derived from that rebuilt lookahead. If the no-authority braking / overspeed check determines service braking is insufficient to keep the train within that current block, it escalates into EB. If ordinary braking succeeds and the train reaches a full stop with `eb_active == False`, `TrainController.tick()` transitions it to the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected); that stopped controller state is the "fresh stopped no-authority state" that `RouteExecutor` waits for before retrying the waypoint. This is distinct from ordinary `RUNNING_WAITING`, which requires the same path to still exist while clearance inside that live authority has dropped to zero. While the train is braking under this no-authority condition, `TrainPhysics` still advances it according to speed and the current live network state. Any later block/switch occupancy or release observations are still reported through `TrainController.on_physics_updated(event_time, span_update)`, but cancellation does not authorize a physically occupied switch to drop its lock early.
- After cancelling a live path, `PathDispatcher` should notify `RouteExecutor.handle_path_cancellation(train_id, path_id, cancellation_kind, deviation_kind=None, passed_requested_target=None, reason=None)`. This notification is mandatory and runs immediately for route-owned cleanup, but the free-form `reason` string is informational only. `RouteExecutor` should inspect whether that cancelled path actually affects its current waypoint / assigned route state, must not treat the old path as finished, and must defer any skip/replan decision until the stopped no-authority or post-EB recovery point. The branchable enum values are:
  - `PathCancellationKind.OPERATOR_CANCELLED` for ordinary operator/requested cancellation
  - `PathCancellationKind.REVOKED` for dispatcher/resource-loss revocation
  - `PathCancellationKind.EB` for emergency-brake cancellation
  - `PathCancellationKind.ROUTE_DEVIATION` for any controller-reported out-of-sequence resource, beyond-authority resource, or beyond-requested-terminal overshoot
  - `PathCancellationKind.POWER_OFF` for the train-power-off release case initiated by `TrainController.power_off_cmd()`

**Path invariants**

- In the desired model, old `PENDING` and `SETTING` disappear entirely because acquisition is synchronous inside `create_path()`, and old `SET`, old `ACTIVE`, and old `CLEARING` collapse into a single live dispatcher state: `ACTIVE`. Whether the train has started moving, entered the terminal resource, or is stopped at the stop point should be represented by controller state, `current_resource_index`, and explicit completion predicates, not by separate path lifecycle values.
- `resource_sequence` replaces both `block_sequence` and `switch_positions`, so existing callers iterating those fields need updating.
- `current_resource_index` should track `sequence_index`, not the first occurrence of a raw resource ID.
- For v1, repeated resources in a single path are invalid and should be rejected during both `create_path()` and `extend_path()`.
- Switch resources contribute `0 cm` to forward-distance accumulation. Any helper that sums per-resource physical length should therefore add `0` for `resource_type == "switch"` and continue the cumulative axis across the surrounding block geometry.
- `FLANK_PROTECTION_DISTANCE_CM` should be a global config, not a per-path setting.
- In v1, switch locks are a multi-owner compatibility set: multiple paths may hold compatible same-state lock claims on the same switch, but conflicting required states are not allowed and physical occupancy stays single-owner.
- Remove `PathDispatcher._release_blocks_behind_train()` in the desired model. Once block release is fully owned by `BlockManager.on_block_tail_vacated()` triggered from physics, the dispatcher no longer needs a separate behind-train sweep.

## Route And RouteExecutor

**Route data**

| Field | Type | Meaning |
| --- | --- | --- |
| `route_id` | `str` | Unique route identifier |
| `name` | `str` | Display name |
| `waypoints` | `List[Waypoint]` | Ordered route definition |
| `mode` | `RouteMode` | One of `ONE_OFF`, `CIRCULAR`, `ROUND_TRIP` |
| `assigned_train_ids` | `List[str]` | Trains assigned to the route |
| `is_active` | `bool` | Route execution enabled |
| `started_at` | `Optional[float]` | System-time Unix timestamp when activated |
| `priority` | `int` | Route-executor scheduling priority (default `5`) |
| `default_departure_mode` | `"auto" \| "manual"` | Ordinary departure policy (default `"auto"`) |
| `auto_depart_after_eb` | `bool` | Post-EB restart override |
| `acquisition_mode` | `PathDispatcher.AcquisitionMode` | Default route path-acquisition policy (default `AcquisitionMode.best_effort`) |

**Canonical ownership split**

- `Route` is the shared plan definition only: ordered waypoints plus route-level policy such as mode, departure defaults, and acquisition mode. It does not own per-train mutable execution cursors.
- A route may be assigned to multiple trains in v1, but each train may execute at most one route task at a time. Each assigned train owns exactly one `RouteRun`, keyed by `train_id`; the run's `route_id` field identifies which shared `Route` definition that train is currently executing. That `RouteRun` is the per-train runtime instance of the shared plan and therefore owns its own waypoint cursor, current traversal direction, active path correlation key, dwell timing, and current resolved target scratch value. Shared route execution state across trains is not allowed.
- Because multi-train assignment is supported, `RouteRun` is the only canonical runtime progress store. Remove route-level runtime summary fields such as `Route.current_waypoint_index` and `Route.direction` from the target model for now; the future UI summary shape is intentionally left open rather than being baked into the refactor contract.
- Per-train route/path errors belong to `RouteRun.last_error` and `RouteRun.error_time`; `Route` does not keep a shared last-writer-wins error summary in v1.
- Add `default_departure_mode` with two v1 values: `auto` and `manual`, defaulting to `auto` when omitted. This is the ordinary route-level default for whether `RouteExecutor` automatically issues `controller.depart()` once authority exists and the next leg is ready.
- Add `auto_depart_after_eb: bool = False` at route level. This is a separate override for post-EB recovery only: when a train returns to the stopped ready state (`IDLE` or `STANDBY`) after `TrainController.release_emergency_cmd()`, `auto_depart_after_eb = False` suppresses automatic departure even if the ordinary departure mode is `auto`. In v1, this gate applies to the fresh post-EB path recreation flow, not to retained-authority reuse.
- Add `acquisition_mode` at route level as the policy for how this route wants dispatcher authority to be acquired (`all_or_nothing` or `best_effort`), with default `AcquisitionMode.best_effort` when the route definition omits it. In v1, `RouteExecutor` reads that field directly for both `create_path(...)` and later `extend_path(...)` retries on the same planning chain; no second per-train acquisition-mode runtime field is introduced.
- Add `priority` at route level as the canonical route-executor scheduling priority, with default `5`. `RouteExecutor` sorts runnable route runs by the owning route's `priority`; dispatcher paths and route runs do not carry a second independent copied priority field in v1.
- Define one route-owned transient structure, `ResolvedWaypointTarget`, carrying exactly `requested_destination_block_id` and `requested_destination_direction`. `requested_destination_direction` in this structure is always the block-relative direction for `requested_destination_block_id`. `Platform` has no direction field, no platform-frame direction, and no direction-conversion helper in v1; station/platform resolution chooses a concrete platform-end block, then derives the resolved direction from `Block.ordered_tiles`, validates it against `Block.allowed_travel_directions`, and stores that block-relative result. There is no persistent per-waypoint resolved-target cache in v1: every new path attempt resolves the target again from the current route definition, platform availability, train span, and waypoint policy. If `create_path(...)` / `extend_path(...)` fails before authority is created or grown, the next retry re-runs resolution. If the path request succeeds, the path record's `requested_destination_block_id`, `requested_destination_direction`, and `authority_end_block_id` become the live authority's stored target contract, while `RouteRun.current_route_status` may retain the route-owned meaning of that current immediate target for callbacks and deferred recovery. Platform reselection is route-owned and occurs only during a fresh route-side target-resolution attempt after failure, cancellation, replan, or route edit; a successfully created/grown path does not reselect its target while it remains live.

**Canonical Next-Target Helper**

- `RouteExecutor._find_next_waypoint_target(route, current_waypoint_index, direction) -> Optional[NextWaypointTarget]` is the single canonical home for route-mode progression in v1. `NextWaypointTarget` carries exactly `waypoint_index`, `waypoint`, and `direction`. Returning `None` means there is no next waypoint on this directed route walk and the current leg is terminal. Other route-executor flows should call this helper rather than open-coding `RouteMode` branches inline.
- Every route-executor site that needs "the next waypoint" must call this helper or use a `NextWaypointTarget` that was previously returned by it. Callers store `target_waypoint_index = target.waypoint_index` and `direction = target.direction` when arming that target, but they must not infer the next waypoint through raw numeric `+1` / `-1` index arithmetic or by reading `Route.waypoints[target_waypoint_index]` without using the helper's returned `waypoint`.
- `Route.mode` is consumed through that helper only:
  - `RouteMode.ONE_OFF`: if no next waypoint exists on the current directed route walk, the current leg is terminal and ordinary route completion/unassignment follows the final completed stop or any explicit terminal skip that leaves no next waypoint. The train remains where it is in the state-machine-derived stopped ready state.
  - `RouteMode.CIRCULAR`: the helper wraps from the last waypoint to the first waypoint
  - `RouteMode.ROUND_TRIP`: the helper reflects at the route ends and returns the reversed traversal direction together with the next waypoint
- Leg arming, post-arrival advance, overshoot skipping, and route-edit reconciliation should all reuse this same helper so the route-mode semantics stay in one place.
- The canonical `ROUND_TRIP` truth table for a three-waypoint route `[A, B, C]` is:
  - `(-1, forward) -> (0, forward)`
  - `(0, forward) -> (1, forward)`
  - `(1, forward) -> (2, forward)`
  - `(2, forward) -> (1, reverse)`
  - `(1, reverse) -> (0, reverse)`
  - `(0, reverse) -> (1, forward)`

**Waypoint data**

Retained current-code enums used by waypoint/route data:

- `RouteMode`: `ONE_OFF`, `CIRCULAR`, `ROUND_TRIP`

This is the canonical field set for `Waypoint` in v1.
| Field | Type | Applies | Meaning |
| --- | --- | --- | --- |
| `kind` | `"stop" \| "pass_through"` | all | Required waypoint behavior discriminator |
| `station_id` | `Optional[str]` | primarily `stop` | Logical station-group target when route planning stops by station |
| `platform_id` | `Optional[str]` | primarily `stop` | Preferred or fixed concrete platform target |
| `block_id` | `Optional[str]` | all | Direct concrete block target when this waypoint does not resolve through a platform |
| `dwell_time_sec` | `float` | `stop` | Planned dwell time; use `0` for a terminal stop with no dwell |
| `flexible_platform` | `bool` | `stop` | Allow compatible platform substitution |
| `requested_direction` | `Optional["forward" \| "reverse" \| "either"]` | all | Route-specified block-relative traversal preference resolved by `RouteExecutor`; for platform/station targets it filters candidate terminal traversals on the candidate end block; defaults to `"either"` when omitted |
| `target_time` | `Optional[float]` | `stop` | Optional absolute system-time Unix departure timestamp |
| `departure_mode` | `Optional["auto" \| "manual"]` | usually `stop` | Optional departure override |

- Split the current overloaded waypoint concept into two explicit kinds in the target model: `Waypoint.kind == "pass_through"` and `Waypoint.kind == "stop"`.
- `Waypoint.kind` is required at creation/update time. Route/waypoint validation must reject a waypoint with missing, null, or unrecognized `kind` before it can be stored; there is no default kind inferred later by `RouteExecutor`.
- A `pass_through` waypoint is still a live route/planning target, but it is not a dwell/stop target. It may be traversed at speed, does not define a stop window, and does not invoke arrival/dwell logic.
- A terminal waypoint must not be `pass_through`. If the train must stop and reverse immediately with no dwell, that terminal waypoint is still `Waypoint.kind == "stop"` with `dwell_time_sec = 0`.
- A `stop` waypoint is the current platform-stop concept. The arrival, same-block repositioning, controller stop-complete, and dwell rules in this section apply only to `Waypoint.kind == "stop"`.
- For target resolution and path acquisition, `Waypoint.kind == "stop"` and `Waypoint.kind == "pass_through"` use the same resolution chain and the same dispatcher target contract. Both kinds resolve to a concrete `ResolvedWaypointTarget` and are considered served only when that resolved target is actually reached by live authority/physical progress. The difference is behavioral: `stop` completion is dispatcher completion caused by a controller `stop_complete` report for the resolved terminal block followed by dwell entry, while `pass_through` completion is head entry into the resolved target block followed by immediate route-progress bookkeeping with no dwell, no `arrived_at_platform_time`, and no `TrainController.enter_station_dwell()`.
- Station/platform distinction is explicit in the desired model:
  - `Station` is a logical grouping of platforms used by route planning and platform selection.
  - `Platform` is the concrete physical stop. When a waypoint resolves through station/platform data, dispatcher path requests, block IDs, and directions are always derived from one resolved concrete platform, never from a station group directly.
  - The current attempt may resolve one concrete `platform_id` when resolution goes through a platform. For a direct block-target waypoint, no platform resolution is needed.
- Define one canonical ordered block list for every concrete `Platform`, exposed as a public field such as `Platform.ordered_blocks`. This order is only the physical ordered extent of the platform, used to identify the two platform-end blocks and preserve edit stability. `Platform` carries no direction, no platform-local forward/reverse semantics, no per-block alignment mapping, and no user-facing directional option in v1. It is initialized directly from the block order supplied to backend platform-creation/edit logic. Backend validation must verify that the supplied block list is already one connected switch-free walk in that exact order; it must not reorder, reverse, or silently renormalize the caller-supplied sequence. This is a backend canonical-order contract, not a requirement to finalize a new public API shape in v1. `Platform.ordered_blocks` is preserved forever through runtime operation and changed only by block-edit operations that insert or remove linked blocks before or after the current sequence while preserving the surviving relative order, then reindex so the smallest platform-local index is `0`. An edit that would require a middle insertion, reorder, or reversal of the preserved physical order is invalid in v1 and must be rejected by backend edit validation. There is no legacy unordered-position migration fallback in v1: the refactor must update current platform creation/edit code so it supplies and preserves this canonical order directly.
- Remove platform-direction helpers from the target model. Do not add `Platform.block_direction_matches_platform`, `Platform.get_block_direction_from_platform()`, `required_platform_side`, or any equivalent platform-side direction contract. If a platform should serve only one direction, the user must configure the underlying end block's `Block.allowed_travel_directions` so only that traversal is allowed.
- `requested_destination_direction` is the resolved traversal constraint at the requested target. Waypoint authors still express the route-level preference as `forward`, `reverse`, or `either` on `Waypoint.requested_direction`, but those values are block-relative preferences, not platform-relative preferences. By the time `RouteExecutor` builds `ResolvedWaypointTarget`, it must have resolved that preference into one concrete block-relative `"forward"` or `"reverse"` for the chosen `requested_destination_block_id`. For a waypoint that resolves through a concrete platform, the candidate comparison defined in the platform resolution subsection below evaluates terminal traversals through the platform end block(s); `Waypoint.requested_direction == "forward"` or `"reverse"` filters out candidates whose terminal traversal does not match that authored block-relative direction or is not allowed by `Block.allowed_travel_directions`. `Waypoint.requested_direction == "either"` applies no route-authored direction filter, but every candidate must still satisfy `Block.allowed_travel_directions`, and `RouteExecutor` still stores the chosen block-relative concrete direction. When a waypoint targets a direct block, `"forward"` / `"reverse"` are interpreted directly in that block's immutable internal traversal order, and `"either"` means `RouteExecutor` picks whichever block-relative direction is reachable under the same current-span comparison and allowed by `Block.allowed_travel_directions`. Dispatcher never receives `"either"` in the v1 path contract; route resolution must always eliminate it before calling `create_path(...)` or `extend_path(...)`.
- Define the exact dispatcher terminal frame separately. The terminal frame is the explicit directed geometry used for controller braking and diagnostics: `path_tiles`, `entry_edge`, and `exit_edge` for the relevant terminal block. When a live path exists, dispatcher derives that frame from the chosen terminal `resource_sequence` block entry. Boundary/safety-margin projection must never infer that frame from `requested_destination_direction` alone.
- Resolve waypoint targets through one canonical chain: `station -> platform -> block`. If the waypoint already specifies a concrete `platform_id`, resolution starts at `platform`. If it specifies a direct `block_id`, resolution skips station/platform lookup and targets that block directly.
- When a route/waypoint targets a logical station rather than a fixed platform, `RouteExecutor` must resolve one concrete platform before path creation. In v1, platform availability is evaluated relative to the train for this route attempt. A platform is unavailable when any linked block is held by another train's physical occupancy or another train/path's live reservation. `CAUTION` by itself does not make a platform unavailable: a caution block may still be reserved/acquired when ordinary reservation rules allow it, and the caution state is consumed by `TrainController` lookahead as a lower ATC speed cap. The current train's own physical occupancy or current live authority must not make that platform unavailable to itself; same-train coverage is handled by covered-waypoint normalization and same-train path conflicts are handled by the shared pathfinder/acquisition rules. Deterministic tie-breaking is required and follows the canonical candidate-order rule below.
- Flexible platform selection in v1 is:
  - if the waypoint names no preferred `platform_id`, choose any compatible available platform in the station group
  - if the waypoint names a preferred `platform_id` and it is compatible and available, use it
  - if the waypoint names a preferred `platform_id`, it is not available, and `flexible_platform == True`, choose any other compatible available platform in the same station group
  - if the waypoint names a preferred `platform_id`, it is not available, and `flexible_platform == False`, fail the waypoint attempt rather than silently substituting another platform
- Flexible platform substitution preserves the route-specified `requested_direction` literally as a block-relative traversal preference. If the waypoint specified `forward` or `reverse`, substitute platforms are compatible only when at least one available platform-end candidate has a terminal traversal satisfying that direction under the candidate block's `Block.allowed_travel_directions`. If the waypoint specified `either` (or omitted the field, which is treated as `either`), any `Block.allowed_travel_directions`-compatible terminal traversal may be used.
- Later retries follow that same route-side platform-selection policy. A fixed platform retry keeps the same platform. A station/flexible-platform retry may re-resolve to a different compatible platform only when the route definition allows that substitution. If no concrete platform can be resolved for the retry under that policy, `RouteExecutor` fails target resolution for that retry and must not treat it as an `extend_path(...)`-side retarget problem.
- For already-covered normalization and subsequent waypoint service on the current directed route walk, a station/platform waypoint with flexible substitution counts as satisfied when the train covers or serves any compatible concrete platform in that waypoint's allowed station/platform set. When that happens, `RouteExecutor` must use the actually served platform/block as the served target for route bookkeeping; it must not force resolution to some other platform and it must not depend on a persistent per-waypoint cache to remember that choice later.
- After a concrete platform is resolved, `RouteExecutor` must gather the terminal candidate block at each end of that platform and resolve one terminal target block for this attempt by calling the same shared current-span/target helper that `PathDispatcher.create_path(...)` uses. For a multi-block platform, the candidate end blocks are the first and last entries of `Platform.ordered_blocks`, so the comparison has four start/target pairs: two physical train ends times two platform-end blocks. For a single-block platform, both platform ends collapse to the same block, so the comparison has only two start/target pairs: two physical train ends times that one block; do not create duplicate first-end/last-end candidates for the same block. Each candidate pathfinder result carries the terminal block-relative direction derived from the candidate terminal traversal through `Block.ordered_tiles`; that direction must pass the waypoint direction filter and `Block.allowed_travel_directions`. Pick the shortest successful candidate using the canonical deterministic tie-break order from the shared pathfinding helper: first lower `tile_count`, then lower `walk_length_cm`; if candidates still tie across the two physical train ends, prefer the `end_a` candidate over the `end_b` candidate; if they still tie, prefer the earlier platform-end block in `Platform.ordered_blocks`; if they still tie, keep the stable candidate order returned by the shared helper. The chosen block becomes `requested_destination_block_id`, and the chosen block-relative direction becomes `requested_destination_direction`. This is how waypoint-authored `"either"` is converted into a concrete `"forward"` or `"reverse"` for that platform waypoint. If a physical train end is currently on a switch resource, map it to the one occupied block inward from that end of the current span before running the comparison; if no such inward occupied block exists, that end is dropped from the comparison set. If no candidate succeeds, fail the waypoint attempt. The chosen block is the dispatcher-facing target block for both `stop` and `pass_through` waypoints that resolve through that platform.
- For a waypoint-authored `requested_direction == "forward"` or `"reverse"`, the same candidate comparison is used, but pairs whose resulting block-relative direction does not match the authored direction are dropped from the comparison before selection. For `requested_direction == "either"`, no route-authored direction filter is applied and the shortest allowed candidate wins.
- After that resolution, `RouteExecutor` derives the per-attempt `ResolvedWaypointTarget` (`requested_destination_block_id`, block-relative `requested_destination_direction`) for the current waypoint and passes only that transient route-owned request contract into `PathDispatcher`. There is no platform-frame direction to convert. Later planning retries may resolve again from the route definition, current platform availability, and current physical progress, but callbacks read the route-owned `RouteRun.current_route_status` scratch rather than performing fresh target resolution.
- In v1, every waypoint must provide exactly one concrete targeting field among `block_id`, `platform_id`, and `station_id`. Supplying more than one is a route-definition error; supplying none is also a route-definition error. No extra type-discriminator field is needed because the mutually exclusive field set is itself the discriminator.
- A `Waypoint.kind == "stop"` may therefore target either:
  - a fixed concrete `platform_id`, or
  - a logical `station_id`, in which case `RouteExecutor` resolves a concrete `platform_id` for the current attempt before path creation
  - a direct concrete `block_id`, in which case no platform resolution is required
  If more than one of `block_id`, `platform_id`, or `station_id` is present, the route definition is invalid. If none of them is present for a stop waypoint, the route definition is invalid.
- Keep platform targeting, dwell/timing rules, platform-selection flexibility, and block-relative direction policy.
- Remove platform-side direction constraints from the target model in v1. Compatibility depends only on block-level `Block.allowed_travel_directions` plus current availability; there is no separate `required_platform_side`, platform-direction field, platform-side helper, or fallback rule.
- Add explicit stop-policy data used by route arrival and same-block repositioning for `Waypoint.kind == "stop"`:
  - the resolved destination block for the waypoint attempt
  - the block-relative traversal direction for that attempt
- Add an explicit route-owned traversal-constraint field, `requested_destination_direction`, on the per-attempt `ResolvedWaypointTarget` for every waypoint. Same-block / same-tile repositioning must not guess direction from geometry alone; before path creation, `RouteExecutor` must resolve the waypoint-authored `requested_direction` into one concrete block-relative `"forward"` or `"reverse"` for `requested_destination_block_id` and store that value on `ResolvedWaypointTarget`. Dispatcher still derives the exact terminal frame from explicit terminal geometry, but it does so after route resolution has already eliminated `"either"` from the request contract.
- If the waypoint targets a logical `station_id` or concrete `platform_id`, `requested_destination_block_id` is resolved only after `RouteExecutor` has picked a concrete platform for that train's current attempt and then applied the canonical shorter-path platform-end selection rule above. If the waypoint targets a direct `block_id`, that block becomes `requested_destination_block_id` directly. In all cases, the stored `requested_destination_direction` is the block-relative direction for that resolved block; there is no raw platform-level direction token in the route definition or resolved runtime state.
- Add optional `departure_mode` as a per-waypoint override of `Route.default_departure_mode`. When unset, the waypoint inherits the route default.
- Do not define a separate stop-window tolerance or route-authored stop-position field in v1. The controller safety margin is used by controller lookahead and ATO braking to shape the train's stop, but route completion does not manually verify a centimeter tolerance around any route value.
- For `Waypoint.kind == "stop"`, waypoint arrival / completion is not simply "the train is in the waypoint block", but it is also not gated by an exact-stop tolerance check in v1. A stop waypoint is reached only by dispatcher completion caused by a controller `stop_complete` report for the active authority that reaches the resolved target. `Waypoint.kind == "pass_through"` is reached by train-head entry into its resolved block. `PathCancellationKind.ROUTE_DEVIATION` covers any controller-reported out-of-sequence resource, beyond-authority resource, or beyond-requested-terminal overshoot.
- Add one shared boundary projection helper such as `RailwayNetwork.project_authority_boundary_delta(head_tile, head_entry_edge, head_distance_cm, authority_end_block_id, terminal_frame, safety_margin_cm) -> delta_cm`. Here `terminal_frame` is the exact directed terminal frame (`path_tiles`, `entry_edge`, `exit_edge`) for the authority-end block. It uses tile lengths and traversal geometry to project the live train head and the safety-margin-adjusted authority boundary onto the same forward axis, then returns their signed separation in centimeters on that shared axis: positive means the train head is past the safety-margin boundary in the forward axis, negative means it is still short of it, and zero is on-target. In v1 this helper is for braking/diagnostic projection only; it is not the authoritative path-completion gate, and `RouteExecutor` must not compare live train position against it itself.

**Waypoint time semantics**

- Remove `TimingMode` entirely in v1. All stored route/waypoint timestamps use system-time Unix seconds.
- `Waypoint.target_time`, when present, is the absolute system-time Unix departure timestamp for that stop. If the train arrives late (`current_time_sec >= target_time` at dwell entry), `Waypoint.should_depart(...)` returns `True` immediately with no extra wait.
- `Waypoint.should_depart(arrived_at_time_sec, current_time_sec)` should use only system-time Unix seconds in v1:
  - if `target_time` is present, depart when `current_time_sec >= target_time`
  - otherwise, depart when `current_time_sec - arrived_at_time_sec >= dwell_time_sec`
- `dwell_time_sec = 0` is valid. It still enters the normal stop-waypoint dwell path, but `Waypoint.should_depart(...)` should return `True` immediately so the route may leave without any extra waiting interval.

**Route-definition validation**

- A valid route definition must contain at least two `Waypoint.kind == "stop"` waypoints in total.
- Every waypoint must provide `kind` explicitly as either `"stop"` or `"pass_through"`. Missing `kind`, null `kind`, or any other value is a validation error at waypoint creation/update time.
- A route made only of `pass_through` waypoints is invalid.
- The stored route/schedule waypoint list must end in `Waypoint.kind == "stop"` before a `RouteRun` may be created. The schedule editor/API must validate that terminal stop requirement before sending the route to route-run activation. `RouteMode.CIRCULAR` changes how the stored waypoint list is interpreted during execution, but it does not remove the requirement that the authored list itself ends at a stop.
- A bulb loop or other turnaround that returns to the same stop must be modeled explicitly in the waypoint list (for example `A(stop) -> bulb(pass_through) -> A(stop)`). `RouteMode.ROUND_TRIP` does not infer that geometry from one terminal stop.
- Every `Waypoint.kind == "stop"` must identify a valid stop target: either a concrete `block_id`, a concrete `platform_id`, or a logical `station_id` that can be resolved to a platform at runtime.
- `RouteExecutor` should reject or refuse to activate any route definition that violates these rules rather than trying to infer missing stop semantics at runtime.

**Route-run state**

This is the canonical field set for `RouteRun` in v1. `RouteExecutor.execution_states[train_id]` is a `Dict[str, RouteRun]` that stores at most one `RouteRun` for each train, with exactly the fields below. A single `Route` can still have many `RouteRun` instances because many trains may be assigned to the same shared route definition. Throughout the rest of this section the name `exec_state` is used as a short alias for the `RouteRun` belonging to the current `train_id` (i.e. `RouteExecutor.execution_states[train_id]`).

| Field | Type | Meaning |
| --- | --- | --- |
| `train_id` | `str` | The train this run belongs to. Also the key used in `RouteExecutor.execution_states`. |
| `route_id` | `str` | The shared `Route` definition this run is executing. The run itself is keyed by `train_id` because one train can execute only one route task at a time in v1. |
| `current_waypoint_index` | `int` | Physical-progress cursor: index in `Route.waypoints` of the last waypoint the train has actually finished (stop-completed, pass-through-consumed, or explicitly skipped). Initialized to `-1` before the first completed waypoint; `-1` is a sentinel, never a Python negative index. |
| `target_waypoint_index` | `int` | Planning cursor: index of the waypoint the current live planning chain is presently targeting for the next point-to-point create/extend step on the current directed route walk. May be numerically greater than `current_waypoint_index` on forward legs or numerically smaller on reverse-round-trip legs. Equal to `current_waypoint_index` when no next waypoint on the current directed route walk is armed. |
| `direction` | `"forward" \| "reverse"` | Effective traversal direction for the current directed route walk. Initialized to `"forward"`; reversible round-trip behavior comes from this field plus `RouteExecutor._find_next_waypoint_target(...)`. All route-walk code reads and writes this field as the literal `"forward"` / `"reverse"` string — no numeric `+1` / `-1` encoding is used in v1. |
| `arrived_at_platform_time` | `Optional[float]` | System-time Unix seconds at which `RouteExecutor._enter_waypoint_arrival(...)` recorded the latest dispatcher-committed stop arrival. It is set before dwell entry, remains set through `RUNNING_AT_STATION`, and is used by `Waypoint.should_depart(...)` to compute dwell elapsed time. `None` when no recorded stop arrival is pending or dwelling. |
| `waiting_for_path` | `bool` | Pre-departure create-path failure flag only. Set when pre-departure platform lookup, current-block lookup, or dispatcher `create_path(...)` fails before any authority exists; cleared on successful path creation, authoritative path completion, and on `handle_path_cancellation(...)` for this run's current live path. It must not be used for a live best-effort truncated path. |
| `last_error` | `Optional[str]` | Most recent route/path error text for this train's run (per-train; `Route` does not carry a shared last-writer-wins error summary in v1). |
| `error_time` | `Optional[float]` | System-time Unix timestamp of `last_error`. |
| `last_waypoint_platform_id` | `Optional[str]` | Concrete `platform_id` of the last completed stop when that stop was platform-derived; `None` when the last completed stop resolved through a direct `block_id` or when no stop has completed yet. |
| `active_path_id` | `Optional[str]` | Route-owned correlation key for the current live dispatcher path this run is using. Written from the `path_id` returned by a successful `PathDispatcher.create_path(...)`; unchanged across later `extend_path(...)` on that same live path; cleared by `handle_path_completion(...)`, by `handle_path_cancellation(...)`, and on route-run removal. In steady state `received_path_plan is None ↔ active_path_id is None`, and otherwise `received_path_plan.path_id == active_path_id`. |
| `current_route_status` | `Optional[RouteRunStatus]` | Route-owned live status scratch for this run. It records what the current active or just-cancelled planning chain means at the route layer: the immediate live waypoint target being served by `active_path_id` (the exact `NextWaypointTarget`, the paired `ResolvedWaypointTarget`, and concrete `platform_id` when any) plus any deferred cancellation-recovery context. It is updated by route planning, head-advance/completion callbacks, and cancellation cleanup, and is cleared on route-run removal. |

- `RouteRun` is the canonical per-train runtime object for one assigned route. Current-code implementation may still name the class `RouteExecutionState`, but every changed contract in this section refers to that object as the train's `RouteRun`.
- Keep `current_waypoint_index`, add `target_waypoint_index`, and keep `direction`, `arrived_at_platform_time`, and `last_waypoint_platform_id`.
- `RouteRun.current_route_status` is route-owned scratch, not a shared route-definition cache. In v1 it must at minimum retain the exact immediate `NextWaypointTarget`, the paired `ResolvedWaypointTarget`, the concrete `platform_id` when that target is platform-derived, and deferred cancellation-recovery values `pending_cancellation_kind`, `pending_deviation_kind`, and `pending_passed_requested_target`. `RouteExecutor.handle_train_advanced(...)` and `RouteExecutor.handle_path_completion(...)` read this field instead of doing fresh target resolution after dispatcher state has already changed.
- `RouteExecutor` owns a scheduling registry over these `RouteRun` entries. On each Phase 1 tick it iterates runnable runs in descending owning-route `Route.priority` order rather than arbitrary per-train order. Among equal priorities, stable existing iteration order is acceptable in v1.
- Add `RouteExecutor.remove_train_route_run(train_id, reason)` as the canonical route-owned removal entry point used by controller power-off and other train-removal flows. It unassigns the train from any active route, removes `RouteExecutor.execution_states[train_id]`, clears route-owned scratch planning state for that run, and does not cancel dispatcher authority itself; any live authority cancellation must already have run through `PathDispatcher.cancel_path(...)` while the `RouteRun` still existed.
- Add `RouteExecutor.continue_route_run_after_eb(train_id) -> bool` as the canonical EB-release continuation hook. It is called by `TrainController.release_emergency_cmd()` after EB has been cleared and the controller has returned to `IDLE` or `STANDBY`. If `RouteExecutor.execution_states[train_id]` has no current `RouteRun`, it returns `False`. If a `RouteRun` exists, it keeps that run registered, clears stale active-path correlation, preserves `current_waypoint_index` as the physical progress cursor, and returns `True` so the controller can latch `post_eb_restart_pending`. The next `RouteExecutor._execute_route_for_train(...)` tick then runs the ordinary planning kernel from the current physical position, re-resolves any concrete platform/target for the pending waypoint from current state, and creates fresh authority; this hook does not reuse or complete the cancelled pre-EB path.
- Initialize both waypoint cursors to `-1` before the first completed waypoint. There is no invariant that `target_waypoint_index` must be numerically greater than or equal to `current_waypoint_index`; on reverse round-trip legs the armed target may be numerically smaller than the last completed waypoint.
- `current_waypoint_index` is the route-progress cursor: it always marks the last waypoint the train has actually finished.
- `target_waypoint_index` is the pending-planning cursor: it marks the waypoint the current live planning chain is presently targeting for the next point-to-point create/extend step on the current directed route walk. It may be numerically greater than `current_waypoint_index` on forward legs or numerically less on reverse legs. When no next waypoint on the current directed route walk is armed beyond current progress, `target_waypoint_index == current_waypoint_index`.
- `-1` is a sentinel only. It means "no waypoint has been completed yet" and must never be used as a Python-style negative index into `Route.waypoints`.
- The initial `RouteRun.direction` is `"forward"` through the stored route order. The route plan remains an ordered list in v1. Reversible round-trip behavior comes only from `RouteRun.direction` flipping between `"forward"` and `"reverse"` plus `RouteExecutor._find_next_waypoint_target(...)`, not from building a second linked or reversed route structure.
- When a new leg is armed, `RouteExecutor` calls that helper and stores `target_waypoint_index = target.waypoint_index` and `direction = target.direction` from the returned `NextWaypointTarget` atomically on the run state. The returned `target.waypoint` is the canonical waypoint object for that planning decision; route planning must not skip beyond it in one pathfinder request.
- RouteExecutor still resolves concrete platform and `ResolvedWaypointTarget` on demand during planning, but once that planning result is adopted for the active or pending chain it writes the immediate target scratch into `RouteRun.current_route_status` rather than leaving callbacks to re-resolve it later. This scratch is route-owned only; it is not a shared per-waypoint cache and may be rewritten on later retries, reconciliation, or retargeting. Once `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)` succeeds, the live `Path.requested_destination_block_id`, `Path.requested_destination_direction`, and `Path.authority_end_block_id` remain the dispatcher-owned stored target contract for that authority, while `RouteRun.current_route_status` remains the route-owned meaning of that authority for callbacks and later recovery. If the next planning attempt cannot currently resolve a concrete target, that failure occurs in route planning before any callback-time route progress commit. If an active planning chain later fails before arrival, `RouteExecutor` must roll `target_waypoint_index` back to the earliest waypoint index known to have failed on that chain; if the exact failed index is unknown, recompute the rollback point by calling `RouteExecutor._find_next_waypoint_target(route, current_waypoint_index, direction)` from the still-recorded physical progress cursor. If that helper returns `None`, leave `target_waypoint_index == current_waypoint_index`; otherwise store `target_waypoint_index = target.waypoint_index` and `direction = target.direction`. Later planning attempts then resolve fresh concrete platform/target data for that pending waypoint and rewrite `RouteRun.current_route_status` accordingly.
- Add `active_path_id: Optional[str]` as the route-owned correlation key for the current live dispatcher path being used by this route execution. It is set when `RouteExecutor` adopts a newly created path, stays unchanged across `extend_path(...)` on that same live path, and is cleared when that path completes for this route, is cancelled for this route, or route execution is torn down. A single live path may span multiple concatenated waypoint segments, including chained `pass_through` waypoints and any later stop that the current planning chain has already appended.
- Keep a pre-departure retry flag such as `waiting_for_path` only for "path request failed before movement began" handling.
- Set `waiting_for_path = True` only when pre-departure platform lookup, current-block lookup, or dispatcher path creation fails before any authority exists.
- Do not use `waiting_for_path` for a live best-effort truncated path. That case still has active authority; the route should keep the same path alive and retry `extend_path()` on it rather than dropping into the pre-authority failure bucket.
- Clear `waiting_for_path` on successful path creation, on authoritative path completion, and when `RouteExecutor.handle_path_cancellation(...)` consumes a cancellation notification for the route's current live path.
- Do not add a separate controller operational sub-state for cancellation recovery in v1. When a live path is cancelled, `PathDispatcher` still clears controller authority and the controller still enters the no-authority braking path against the current occupied-block boundary. The only deferred recovery scratch is route-owned on `RouteRun.current_route_status`: `RouteExecutor.handle_path_cancellation(...)` records the cancellation/deviation context immediately, but `RouteExecutor._skip_waypoint(...)`, next-target selection, and fresh path planning wait until the train reaches the fresh stopped no-authority state. If that no-authority stop escalates into EB, the train remains blocked until a manual `TrainController.release_emergency_cmd()` transitions it to the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected) and latches a controller-owned `post_eb_restart_pending` flag; only after that stopped recovery point should ordinary `RouteExecutor` reachability + departure logic for the same waypoint run again.
- Add one route-owned covered-waypoint normalization helper such as `RouteExecutor._advance_past_covered_waypoints(train, route, exec_state)`. It must call `SimulationController.get_or_create_controller(train_id).get_current_span()` and repeatedly call `RouteExecutor._find_next_waypoint_target(...)` from the current confirmed progress cursor / direction pair to inspect the next waypoint on the current directed route walk. With the initial sentinel state `current_waypoint_index == -1` and forward initial direction, that first helper call yields waypoint `0`. For a station/platform waypoint it must first resolve the current attempt's concrete target block before applying the coverage test, except that a station/platform waypoint with flexible substitution is already satisfied when the train currently covers any compatible concrete platform/block in that waypoint's allowed station/platform set. In that flexible-covered case, `RouteExecutor` must use the actually covered compatible platform/block as the served target for this normalization step; it must not force resolution to some other uncovered platform or rely on a persistent per-waypoint cache. If the resolved target block is already physically covered by the train's current span, the waypoint is treated as already missed/skipped and `RouteExecutor._advance_past_covered_waypoints(...)` advances past it by calling `RouteExecutor._skip_waypoint(...)` immediately without dwell and without requesting a same-block `create_path(...)`. This same skip rule applies to both `Waypoint.kind == "pass_through"` and `Waypoint.kind == "stop"`; the only difference is that a skipped stop still counts as no-dwell route progress rather than arrival. After each such skip, the helper calls the canonical next-target helper again from the updated progress cursor and direction rather than incrementing the waypoint index numerically. This helper runs whenever route progress advances and before `target_waypoint_index` is armed, so the next pending target is always the first waypoint on the current directed route walk whose resolved target block is not already covered under these rules.

**Canonical Route-Progress Events**

- `current_waypoint_index` may advance only from these route-owned events in v1:
  - head-based `Waypoint.kind == "pass_through"` consumption
  - dispatcher-committed completion from a controller `stop_complete` report for `Waypoint.kind == "stop"`
  - explicit skip handling such as already-covered normalization or `PathCancellationKind.ROUTE_DEVIATION`
  - route edit / reconciliation that explicitly declares one or more pending waypoints skipped
- Head-based `Waypoint.kind == "pass_through"` consumption is a route-owned in-motion progress event, not a dispatcher stop-completion event. The canonical trigger is the progress chain `TrainPhysics.tick(...)` -> `TrainController.on_physics_updated(event_time, span_update)` -> `PathDispatcher.on_controller_progress(report)` -> `RouteExecutor.handle_train_advanced(...)`. `RouteExecutor.handle_train_advanced(train_id, path_id, resource_type, resource_id)` must first compare `path_id` with `RouteRun.active_path_id`; stale callbacks are ignored. If `resource_type != "block"`, the route side does no waypoint completion. For a block entry, `RouteExecutor` reads `RouteRun.current_route_status` for that live planning chain. Callback-time pass-through handling does not perform fresh station/platform/block target resolution. If that status scratch is absent or its immediate live waypoint is not a `pass_through`, the callback is a route-owned no-op other than optional diagnostics. If the immediate live waypoint is a `pass_through` and `resource_id` matches its stored `ResolvedWaypointTarget.requested_destination_block_id`, consume the waypoint. The pass-through completion update mirrors the stop-waypoint progress update for the served waypoint (`current_waypoint_index = ...`, direction/bookkeeping from the stored target), except it does not stop the train, does not clear dispatcher authority or `active_path_id`, does not set `arrived_at_platform_time`, and does not call `TrainController.enter_station_dwell()`. If a later waypoint is already armed on the same live path, `RouteExecutor` updates `RouteRun.current_route_status` to the next immediate live target already represented by that planning chain; otherwise it clears the consumed immediate-target scratch and lets the next `RouteExecutor.update(...)` tick populate the next one. `RouteExecutor.update(...)` must not re-derive pass-through consumption by polling controller span/lookahead state.
- `RouteExecutor._skip_waypoint(train, route, exec_state, target: NextWaypointTarget, reason)` is the single route-owned skip helper for already-covered normalization, route-deviation overshoot, route edit/reconciliation, and explicit operator skip. It records physical route progress without dwell: set `exec_state.current_waypoint_index = target.waypoint_index`, set `exec_state.direction = target.direction`, clear `exec_state.arrived_at_platform_time`, do not call `TrainController.enter_station_dwell()`, do not update `exec_state.last_waypoint_platform_id`, and do not synthesize dispatcher completion. It then calls `RouteExecutor._find_next_waypoint_target(route, exec_state.current_waypoint_index, exec_state.direction)`. If a next target exists, store its `waypoint_index` and `direction` atomically as the new `target_waypoint_index` / `direction`; if none exists, leave `target_waypoint_index == current_waypoint_index`. It also rewrites `exec_state.current_route_status` for the newly pending target or clears the immediate-target scratch when no next target exists. If the skip was caused by a live-path cancellation, `exec_state.active_path_id` has already been cleared by `RouteExecutor.handle_path_cancellation(...)`; if the skip happens during covered-waypoint normalization before any authority exists, it must not create or cancel dispatcher authority. For `PathCancellationKind.ROUTE_DEVIATION`, `RouteExecutor.handle_path_cancellation(...)` records the deferred recovery context immediately, but it does not call this helper until the train has first reached the stopped recovery point. If no next target exists after the skip and the owning route mode treats that directed walk as terminal, the next route update handles ordinary route completion and the train remains where it is in the state-machine-derived stopped ready state.
- `target_waypoint_index` is only a planning cursor. It may advance when a new `NextWaypointTarget` is armed, when route reconciliation retargets the run, or after a successful `PathDispatcher.create_path(...)` / `PathDispatcher.extend_path(...)` refresh proves that live authority has reached the currently armed waypoint target. "Reached the currently armed waypoint target" means the returned or pushed live plan for the same `path_id` has `authority_end_block_id` equal to the current attempt's resolved `requested_destination_block_id` for that request. No additional stop-position tolerance window is applied by `RouteExecutor`; a best-effort create/extend that grows `resource_sequence` but leaves the live authority end short of that reached-target predicate must keep the same `target_waypoint_index` and retry the same target later. `target_waypoint_index` never proves physical progress by itself.

**Route-executor state reads**

- `RouteExecutor` should read live operational state from `TrainController`, not from mirrored runtime fields on `Train`.
- Departure, retry, arrival, dwell, and waiting decisions should use controller state as the operational source of truth.
- `Train` may still expose persisted or UI-facing state, but route-control decisions should not depend on it being a live mirror.
- In the desired model, manual driving is `control_mode == manual`, not a separate operational state. A route-managed manual train still uses ordinary `STANDBY` / `IDLE` / `RUNNING_*` states and dispatcher authority; the difference from ATO is how movement begins and is driven, not whether `RouteExecutor` owns the waypoint plan. In particular, manual `IDLE`/`STANDBY` must not block route-side path creation. It changes only what `depart()` means after authority exists.

**Planning Kernel**

- One route-planning pass has four canonical steps in v1:
  1. normalize already-covered waypoints through `RouteExecutor._advance_past_covered_waypoints(...)`
  2. arm the next pending waypoint through `RouteExecutor._find_next_waypoint_target(...)` when no next waypoint on the current directed route walk is already armed
  3. resolve exactly one waypoint into one transient route-owned `ResolvedWaypointTarget`
  4. call `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)` for that one resolved waypoint only
- `RouteExecutor` never asks dispatcher/pathfinder to solve a whole multi-waypoint route in one search. Longer authorities are formed only by repeated point-to-point segments appended onto the same live path identified by `path_id`.
- In normal route-managed execution, a live path whose current terminal waypoint is `Waypoint.kind == "pass_through"` should get one immediate opportunity to grow past that pass-through boundary. After a successful create/extend that actually reaches the current pass-through waypoint target, `RouteExecutor` may immediately arm the next waypoint and attempt at most one additional point-to-point concatenation on the same tick, continuing from the current authority end along the current directed route walk. It must not loop repeatedly until the next stop waypoint is appended.
- A successful create/extend may therefore immediately advance only the planning cursor and attempt at most one further concatenation beyond the immediate next waypoint on that same tick. In practical terms, from the current physical progress cursor on the directed route walk, `RouteExecutor` may reach at most the immediate next waypoint and, if that waypoint is a `pass_through` whose target is already reached by the refreshed live authority, one additional waypoint beyond it. No separate used-attempt flag is stored. If successful best-effort growth remains short of the immediate armed target, the planning cursor must not advance. If that additional concatenation succeeds but the refreshed live authority still terminates at another `Waypoint.kind == "pass_through"`, or if the extra concatenation fails/truncates, the live authority remains as-is and later ticks use the ordinary best-effort extension/retry rules. Physical route progress still advances only through the canonical route-progress events above.
- A pass-through-terminated authority after that one extra attempt is a degraded but valid v1 authority boundary. If the train later brakes there, that is a safety stop caused by lack of further authority, not a planned stop for the pass-through waypoint itself.
- `Waypoint.kind == "stop"` versus `Waypoint.kind == "pass_through"` changes only what happens when the resolved target is reached: `stop` enters dwell through dispatcher-committed completion from a controller `stop_complete` report, while `pass_through` advances immediately without dwell. It does not change the dispatcher path API shape.

**Route Edit And Reconciliation**

- If the shared `Route` definition changes while a `RouteRun` is active, the train stays at its current physical position. Route edits must not teleport the train, synthesize path completion, or mark intermediate waypoints finished just because the definition changed.
- Reconciliation is route-owned. Starting from the current physical progress cursor, `RouteExecutor` must discard any in-flight concrete platform/target resolution for the affected planning attempt, then recompute `target_waypoint_index` through the canonical next-target helper or through the explicit operator-selected target when one exists. "First affected waypoint" means the earliest waypoint index on the still-pending directed route walk whose target fields, order, kind, station/platform membership, direction constraint, or predecessor/successor relationship changed.
- If the active live path still matches the reconciled planning chain and can continue forward from its current authority end toward the reconciled target, `RouteExecutor` may keep it and continue extending it. Otherwise it must cancel that live path through `PathDispatcher`, wait for the ordinary no-authority stop / EB recovery point when applicable, and then replan from the train's current position under the new route definition.
- Skip-to-waypoint or operator retargeting is the same reconciliation rule in a narrower form: move only the planning cursor, clear route-owned scratch target state for the affected attempt, and replan from the train's current physical position without synthetic progress jumps.

**Concrete `RouteExecutor.update(delta_time)` calls**

- `update(delta_time)` should continue to increment `RouteExecutor.simulation_time` for simulation bookkeeping, scan active route/train pairs, order the runnable `RouteRun` registry by descending owning-route `Route.priority`, and call `_execute_route_for_train(train, route)` in that order. Stored route/run timestamps such as `Route.started_at`, `RouteRun.arrived_at_platform_time`, `RouteRun.error_time`, and `Waypoint.target_time` use system-time Unix seconds.
- `_execute_route_for_train()` should continue to create or reuse the train's `RouteRun` (current-code class may still be named `RouteExecutionState`). When `target_waypoint_index == current_waypoint_index`, it should arm the next planning target by calling the canonical mode-aware next-waypoint helper, storing `target.waypoint_index` and `target.direction` from the returned `NextWaypointTarget` on `exec_state`, and resolving `target.waypoint` through the canonical `station -> platform -> block` chain when needed.
- When `_execute_route_for_train()` resolves the immediate pending waypoint for create/extend purposes, it must also refresh `exec_state.current_route_status` for that same immediate live target before any create/extend decision.
- If a distinct pending waypoint is already armed (`target_waypoint_index != current_waypoint_index`), `_execute_route_for_train()` must re-resolve that same already-armed waypoint through the same canonical `station -> platform -> block` chain before any create/extend decision and rewrite `exec_state.current_route_status` for that pending waypoint. Later ticks do not rely on stale callback-time target resolution. If that route-side re-resolution yields no legal concrete platform/block target under the waypoint's fixed/flexible platform policy, the retry fails at target resolution and `RouteExecutor` must not call `PathDispatcher.extend_path(...)` for that tick.
- Before any create/extend decision, the current attempt's resolved target is the route-owned request contract for `target_waypoint_index`: the waypoint target block and the route-owned `requested_destination_direction` constraint. It must not resolve or pass any stop-position centimeter field. Dispatcher and controller use the chosen terminal frame plus controller safety margin for braking/boundary projection.
- Route-managed path building is always segment-by-segment along the current directed route walk. On each create/extend attempt, the current transient resolved target represents exactly one resolved waypoint target, never a bundled multi-waypoint search request. After one segment is successfully created or appended and the live authority reaches a `Waypoint.kind == "pass_through"` target, `RouteExecutor` may resolve the next waypoint and attempt at most one additional concatenation on the same live path during that tick. That means at most one waypoint beyond the immediate next waypoint on the current directed route walk; no separate used-attempt flag is stored. It must not keep resolving/concatenating repeatedly until a `Waypoint.kind == "stop"` is reached; if that extra attempt still leaves a pass-through terminal or a truncated authority, normal later-tick extension/retry handles it.
- `_execute_route_for_train()` should ensure the train's `TrainController` exists before it reads controller state or calls `PathDispatcher.create_path(...)`. In the desired model a route-managed train should already have a controller by the time authority is assigned in Phase 1. `SimulationController` owns only the 1:1 binding between `train_id` and `TrainController`; it does not construct or push path plans.
- Before arming a new pending waypoint or retrying the current one, `_execute_route_for_train()` should normalize current progress through `RouteExecutor._advance_past_covered_waypoints(...)` so the route does not keep targeting a waypoint the train already physically covers.
- The operational state checks inside `_execute_route_for_train()` should read controller state rather than `train.state`.
- If controller state is `OFF`, `_execute_route_for_train()` must treat that train as unavailable for route execution on this tick. It must not create, extend, or rely on dispatcher authority for that train, must not auto-power-on the train, and should record that error on `RouteRun.last_error` / `RouteRun.error_time` (for example `"train is powered off"`). The canonical power-off release/removal order is owned by `TrainController.power_off_cmd()`: inside that command, the controller first tells `PathDispatcher` to cancel the train's active path and run the ordinary cancellation workflow while route execution is still registered, then calls `RouteExecutor.remove_train_route_run(train_id, reason="power_off")`, and then clears any remaining route-owned bookkeeping for that train. `_execute_route_for_train()` may defensively ignore any stale leftover assignment, but it is not the canonical owner of the power-off sequence. `TrainPhysics` continues to run independently; power-off kills the onboard controller, not world physics.
- If `exec_state.arrived_at_platform_time is not None` and controller state is `IDLE` or `STANDBY`, `_execute_route_for_train()` must call `TrainController.enter_station_dwell()` before any departure/path planning. This is the next-tick dwell-entry half of dispatcher-committed stop arrival.
- If controller state is `STANDBY` or `IDLE` and there is no pending recorded arrival, `_execute_route_for_train()` should call `_try_depart_to_waypoint(train, route, exec_state)`. Path creation/retry is allowed from either state. The difference is only departure execution after authority exists: ATO may auto-select/start, while manual mode leaves actual movement to the driver.
- If controller state is `RUNNING_MOVING`, `RouteExecutor._execute_route_for_train()` should not poll for stop-waypoint arrival; normal stop-waypoint arrival now comes only from dispatcher-committed path completion after a controller `stop_complete` report. `Waypoint.kind == "pass_through"` consumption is also not polled inside `RouteExecutor._execute_route_for_train()`; it is driven by the head-advance callback chain `TrainPhysics.tick(...)` -> `TrainController.on_physics_updated(event_time, span_update)` -> `PathDispatcher.on_controller_progress(report)` -> `RouteExecutor.handle_train_advanced(...)`. `RouteExecutor.handle_train_advanced(...)` reads the matching `RouteRun.current_route_status`, compares the entered block against the stored immediate `pass_through` target for that live path, and applies the route-owned cursor advance when they match. Callback-time pass-through handling must not do fresh target resolution. In that match case it does not require a stop, does not set `arrived_at_platform_time`, and does not call `TrainController.enter_station_dwell()`. Pass-through consumption is head-based route progress only; the later physical release of earlier path resources still waits for tail-vacate callbacks. `RouteExecutor` does not perform a second direction check at pass-through consumption time; directional correctness is established when the block-direction target is resolved and the shared pathfinder builds authority through that target. `RouteExecutor._execute_route_for_train()` in `RUNNING_MOVING` is therefore limited to best-effort `PathDispatcher.extend_path(...)` retries toward the currently armed target; it does not re-implement head-entry detection.
- If controller state is `RUNNING_AT_STATION`, `_execute_route_for_train()` should call `_check_dwell_complete(train, route, exec_state)`.
- If controller state is `RUNNING_WAITING`, `_execute_route_for_train()` should treat the route as on hold and should not request a brand-new path while `received_path_plan` is still present. If that still-live path's authorized target (`authority_end_block_id`) is still short of its requested target (`requested_destination_block_id`), `_execute_route_for_train()` should keep retrying `PathDispatcher.extend_path(...)` on that same path using a fresh re-resolution of the same pending waypoint's current requested target contract on each retry.
- More generally, dynamic best-effort extension is allowed in any controller state except `OFF`. `RUNNING_WAITING` is the common zero-clearance retry case, but if a still-live path remains short of its requested target while the train is still moving or otherwise stopped under authority, `_execute_route_for_train()` may proactively retry `extend_path(...)` on later ticks without waiting for a state change, as long as it does not create a second live path.
- `RouteExecutor` does not call any stop-position resolver and does not pass stop centimeters into dispatcher. Route callers pass only the resolved block/direction request contract.
- `_try_depart_to_waypoint()` is the route executor's normal "make progress toward the current waypoint" entry point. The same function should be used for the initial departure attempt and for retries after `PathDispatcher` has cancelled/revoked the previous path once the train has reached a fresh stopped no-authority state. If the cancellation stop escalated into EB, that retry point occurs only after `TrainController.release_emergency_cmd()` has returned the controller to `IDLE` or `STANDBY` according to cab selection; active-path completion still comes back from `PathDispatcher`, not from `_execute_route_for_train()` polling for end-of-path.
- `RouteExecutor` should resolve one effective departure policy for the current waypoint each time it considers departure:
  - start from `Route.default_departure_mode`
  - override with `Waypoint.departure_mode` when present
  - if `TrainController.post_eb_restart_pending` is true, apply `Route.auto_depart_after_eb` as the separate final gate
- If `TrainController.post_eb_restart_pending` is true, the EB-interrupted path has already been cancelled by the EB activation flow. `RouteExecutor` must wait for EB release, then make a fresh `create_path(...)` or `extend_path(...)` decision from the current route state; it must not try to reuse that cancelled path.

- **Departure-to-waypoint flow**

- `RouteExecutor` owns waypoint targeting and departure policy; `PathDispatcher` owns authority acquisition and terminal authority geometry; `TrainController` owns stop/braking behavior from that authority geometry using the controller safety margin. The departure flow is: resolve waypoint block/direction, request or extend dispatcher authority as needed, and only then decide whether to call `TrainController.depart()`.
- The stop, same-block, and dwell-entry rules in this subsection apply only to `Waypoint.kind == "stop"`. `Waypoint.kind == "pass_through"` does not call arrival/dwell helpers; it constrains route geometry only.
- `Waypoint.kind == "pass_through"` uses the same block/direction resolution rules and the same point-to-point create/extend contract as a stop waypoint. The difference is route behavior only: when that waypoint target is reached, `RouteExecutor` advances immediately without dwell, resolves the next waypoint, and tries to concatenate the next point-to-point segment onto the same live path.
- A longer multi-waypoint route is therefore implemented as repeated point-to-point concatenation. A pathfinder call never receives "go through all remaining waypoints"; instead, after one waypoint target has been resolved and live authority actually reaches that target, the planning cursor may advance and the next `create_path(...)` / `extend_path(...)` request is made from the end of the last resolved waypoint segment to the next resolved waypoint. Physical route progress still waits for pass-through head entry or stop completion.
- `RouteExecutor` owns waypoint-chain progression on the route side. `PathDispatcher` grows authority geometry; it does not own waypoint progression. A pass-through waypoint is consumed only when the train head first enters that waypoint's resolved block. Live `resource_sequence` coverage may be inspected for diagnostics or extension planning, but coverage alone does not advance `current_waypoint_index` and does not retarget dispatcher authority away from the currently armed waypoint. Tail-based resource release remains a separate physical-lifecycle concern owned by controller-reported tail-vacate observations and dispatcher-mediated resource release.
- For a train departing from rest under route control, if the live path's current terminal waypoint is `Waypoint.kind == "pass_through"` and a next waypoint is available on the active planning chain, `RouteExecutor` should attempt one additional same-path `extend_path(...)` before issuing `TrainController.depart()`. This is the same rule as the planning kernel: from the current physical progress cursor, the route may reach at most the immediate next waypoint and, if that waypoint is a `pass_through` already reached by the live authority, one additional waypoint beyond it. No separate used-attempt flag is stored. After that one extra attempt, the current live authority is route-ready for v1 if departure policy otherwise allows it, even if the terminal boundary is still pass-through or best-effort truncated. Later ticks continue ordinary extension/retry.
- There is a route-side already-covered skip in v1. If the resolved target block for the current waypoint is already physically covered by the train's current span, `RouteExecutor` treats that waypoint as already missed/skipped, does not request a same-block `create_path(...)`, and immediately advances route planning toward the next waypoint on the current directed route walk without dwell for the skipped stop. Any explicit same-block repositioning flow remains a dispatcher capability for non-route/manual callers only.
- `RouteExecutor` should not resolve or compare stop-position targets at all. For any stop that still needs authority, it passes only `requested_destination_block_id` and `requested_destination_direction`. Dispatcher stores authority geometry and the controller owns safety-margin braking from that geometry. The route/waypoint resolution step must still provide `requested_destination_direction` as a route-level constraint; dispatcher must not guess it from same-block geometry, and must not treat it as the exact terminal frame by itself.
- `RouteExecutor` should use `Route.acquisition_mode` for both `create_path(...)` and any later `extend_path(...)` retries while it is still pursuing that same planning chain. `AcquisitionMode.best_effort` is therefore a route policy choice, not a one-off branch invented mid-chain.
- For a `pass_through` waypoint, the create/extend chain is still block-based: the current per-attempt resolved target still carries `requested_destination_block_id` and `requested_destination_direction` just like a stop waypoint. The difference is not the path API shape; the difference is that once the train head enters that waypoint block, `RouteExecutor` consumes the waypoint immediately, advances the route cursor, and uses the next create/extend step to concatenate authority toward the next resolved waypoint.
- The canonical create-vs-extend decision for `RouteExecutor` is driven by `TrainController.received_path_plan` presence, not by any route-side re-evaluation of whether the current waypoint is reachable on an empty map. For the currently armed waypoint:
  - if `controller.received_path_plan is None`, the train has no live authority, so `RouteExecutor` must call `PathDispatcher.create_path(train_id=..., ...)` and then copy the returned `path_id` into `exec_state.active_path_id`
  - if `controller.received_path_plan is not None`, the train is already on a live path, so `RouteExecutor` must call `PathDispatcher.extend_path(path_id=received_path_plan.path_id, ...)` on that same `path_id` rather than synthesizing a second path
  Because `PathDispatcher` is the sole writer of `received_path_plan` and clears it to `None` on cancellation, revocation, and completion release, this rule is well-defined in v1: a cancelled/completed path does not remain on the controller inbox, so the next planning tick after cancellation naturally falls into the `create_path(...)` branch. A pass-through waypoint at which the train happens to be stopped with no live plan is therefore a `create_path(...)` case, not an `extend_path(...)` case.
- `exec_state.active_path_id` is the route-owned correlation key for this same live path. On a successful `create_path(...)`, `RouteExecutor` writes the returned `path_id` into `exec_state.active_path_id`, and `PathDispatcher` concurrently pushes the canonical **received_path_plan schema** so the two stay equal. On ordinary cancellation, EB recovery, or completion release, `PathDispatcher` clears `received_path_plan` and the cancellation/completion callback clears `exec_state.active_path_id`. In steady state the invariant is: `received_path_plan is None` ↔ `exec_state.active_path_id is None`, and otherwise `received_path_plan.path_id == exec_state.active_path_id`.
- If `TrainController.received_path_plan is None` while `exec_state.active_path_id` still holds a value, treat that route-side `active_path_id` as stale bookkeeping, clear it immediately, and continue with the ordinary no-live-authority `create_path(...)` branch for the current pending waypoint. No additional recovery workflow is needed beyond clearing the stale route-run correlation key.
- If `TrainController.received_path_plan` already exists and `received_path_plan.path_id == exec_state.active_path_id`, `_try_depart_to_waypoint()` must treat that live authority as the current route path for this attempt and must not request a second `create_path(...)` on top of it. If the next route decision wants a subsequent waypoint target on the current directed route walk, `RouteExecutor` may present that new target on the next `extend_path(...)` for the same `path_id`. If dispatcher cannot continue the existing live path from its current authority end toward that requested target, `RouteExecutor` must cancel the old live path, wait for the no-authority stop / recovery point, and only then request a fresh path.
- If `TrainController.received_path_plan` exists but `received_path_plan.path_id != exec_state.active_path_id`, that is a route-executor / dispatcher invariant violation, not an expected best-effort case. In v1 the controller-pushed `path_id` is defined as whatever the return value of the most recent successful `PathDispatcher.create_path(...)` / `extend_path(...)` call wrote into `exec_state.active_path_id`, so a live plan with a different `path_id` indicates that either (a) a dispatcher path was created for this train outside the route-executor request that is tracking this run, or (b) route-owned bookkeeping fell out of sync with dispatcher state. `RouteExecutor` must treat this as an error: record it on `exec_state.last_error` / `exec_state.error_time`, cancel both the live `received_path_plan.path_id` and any still-recorded `exec_state.active_path_id` through `PathDispatcher.cancel_path(..., cancellation_kind=PathCancellationKind.REVOKED, reason=...)`, clear `exec_state.active_path_id`, wait for the ordinary no-authority / EB recovery point, and then restart the whole waypoint-path flow from the current `current_waypoint_index` through normal planning (`_advance_past_covered_waypoints(...)` → `_find_next_waypoint_target(...)` → target resolution → fresh `create_path(...)`). `RouteExecutor` must not silently adopt the unknown `path_id` as its own active path, and must not try to reuse the mismatched live plan as an `extend_path(...)` target.
- If `create_path(..., acquisition_mode=best_effort)` returns a live path whose current authorized target is still short of the route's current planning target, that is not a failure. It is a degraded but valid live authority: let the controller treat it as normal movement authority toward the current authorized end, and let `RouteExecutor` keep retrying `extend_path()` on the same `path_id` toward that same pending waypoint, re-resolving its current request contract on each retry, on later ticks in any controller state except `OFF`. A best-effort create request counts as success whenever it creates one new path record with a non-empty live `resource_sequence`; a best-effort extend request only counts as success when the returned `resource_sequence` actually grew.
- Once such a live path exists, `RouteExecutor` should still apply the ordinary departure policy by calling `TrainController.depart()` when this leg is otherwise route-ready. Any immediate zero-clearance hold or `RUNNING_WAITING` outcome is controller-owned and comes from lookahead/ATC against that live authority rather than from a special route-side suppression rule.
- On successful path, do not write train-side path cache fields from `RouteExecutor`. `PathDispatcher` owns the authoritative path-progress view; any controller/UI-facing path tiles or path-progress reads should be pushed/read as a projection of dispatcher state rather than as a train mirror.
- Do not set destination-block fields directly on `Train` or `TrainController` from `RouteExecutor`; controller authority comes only from the pushed path plan.
- `PathDispatcher` owns `controller.received_path_plan`; `controller.assigned_path_id` should be only a derived read of `received_path_plan.path_id`, so `RouteExecutor` does not write that field.
- On successful path creation or extension, `RouteExecutor` should update both `exec_state.active_path_id` and `exec_state.current_route_status` for the immediate live target carried by that path. Later planning retries or reconciliation may re-resolve and rewrite that route-owned scratch from route state and current physical progress, but callback handling should read the stored route-run status rather than trying to rediscover the path's route meaning after dispatcher state has already changed. A successful `PathDispatcher.create_path(...)` / `PathDispatcher.extend_path(...)` for the currently armed waypoint may advance the planning cursor to the next waypoint and trigger an immediate attempt to concatenate one more point-to-point segment only when the live authority actually reaches that armed waypoint target. Returned `resource_sequence` geometry alone does not advance `current_waypoint_index`, which remains physical route progress.
- After any successful `PathDispatcher.extend_path(...)` that returns a grown `resource_sequence`, `RouteExecutor` may advance `target_waypoint_index` to the next waypoint only if the refreshed live authority now reaches the currently armed waypoint target. If the grown path is still short of that target, `RouteExecutor` keeps the same `target_waypoint_index` and re-resolves that same pending target later. The result payload by itself does not advance physical route progress; `current_waypoint_index` still advances only when the train actually reaches/consumes that waypoint.
- Deliver the canonical **received_path_plan schema** inside the controller path plan pushed by `PathDispatcher`. Its nested authority geometry must follow the canonical **resource_sequence entry schema** and **path_tile entry schema**.
- Keep `TrainController.depart()` as the route/controller departure command once a valid path plan exists. In ATO it may begin movement immediately; in manual mode it marks the current authority ready to go and movement still begins through later driver input.
- When `RouteExecutor` calls `TrainController.depart()` and receives `success == False`, it must treat that as a failed departure handoff, not as movement. Leave the train in its current stopped controller state, record the diagnostic `reason` on `RouteRun.last_error` / `RouteRun.error_time`, and let the next planning tick re-evaluate from current controller state and `received_path_plan` presence. If authority was cleared before the call, the normal create-path branch handles recovery on that later tick; if EB or power/state made departure invalid, the existing EB/power/stopped-state rules decide when retry is allowed.
- Ordinary departure policy (`auto` vs `manual`) controls whether `RouteExecutor` issues `controller.depart()` automatically after authority exists. In ATO, that can immediately start movement. In manual mode, the same call marks the current authority ready to go and actual movement still waits for driver input. `Route.auto_depart_after_eb` separately controls the post-EB fresh-path restart case and defaults to `false`.

**Concrete departure calls**

- Every `RouteExecutor` access to a train's controller goes through `SimulationController.get_or_create_controller(train.train_id)` (the shared public accessor) rather than a private `_get_controller` helper or any direct dictionary lookup.
- If the resolved target block is already physically covered by the train's current span, `_try_depart_to_waypoint()` must not call `path_dispatcher.create_path(...)` for that waypoint. It treats that waypoint as already missed/skipped under the same covered-waypoint normalization rule used elsewhere and continues planning toward the next waypoint on the current directed route walk instead.
- For any stop that still needs authority, `RouteExecutor` does not compute or compare a centimeter-level local stopping target. It passes only the waypoint's `requested_destination_block_id` and `requested_destination_direction` into `PathDispatcher.create_path(...)`.
- Explicit same-block/zero-movement authorities may still exist as dispatcher-owned local/manual reposition behavior outside route-managed covered-stop skipping, but they do not carry a separate target-position field; the controller uses the standard safety-margin stop logic. Route-managed stop execution in v1 does not use that flow for a waypoint whose resolved block is already covered.
- When the current attempt uses `AcquisitionMode.best_effort`, compare the live path's current authorized target against the live path's stored requested target each tick (`Path.authority_end_block_id` versus `Path.requested_destination_block_id`). If the live path is still short of that requested target, keep calling `path_dispatcher.extend_path(...)` on that same `path_id` using the newly re-resolved request contract for the same pending waypoint; do not synthesize a new path.
- If `_try_depart_to_waypoint()` sees current live authority already present on the controller for `exec_state.active_path_id`, do not call `path_dispatcher.create_path(...)` again. Branch only on departure policy:
  - if that live authority still terminates at a `Waypoint.kind == "pass_through"` and a subsequent waypoint remains on the active planning chain, attempt at most one additional `extend_path(...)` toward that next waypoint before departure; this is the same immediate-next-waypoint plus at-most-one-further-waypoint rule used by the planning kernel, and no separate used-attempt flag is stored
  - if auto departure is allowed for this case, call `controller.depart()` after that one extra attempt or immediately when no pass-through extra attempt applies; in ATO that may start movement immediately, while in manual mode it only marks the authority/route as ready and still leaves motion to the driver
  - if manual confirmation is required, leave the train in `STANDBY` or `IDLE` with the current live authority intact
- Remove the train-side `current_path` / `path_index` write from `RouteExecutor`; `PathDispatcher` should own the authoritative path-progress view and expose any controller/UI-facing path tiles or path-progress display as a pushed/read-only projection.
- Remove the `train.assigned_path_id` write from `RouteExecutor`; `controller.assigned_path_id` should be derived from the path plan that `PathDispatcher` pushes.
- Do not set `controller.ato_path_id` or any destination field directly from `RouteExecutor`.
- Let `PathDispatcher` push the canonical **received_path_plan schema** to the controller as part of the path plan. Its nested authority geometry must follow the canonical **resource_sequence entry schema** and **path_tile entry schema**.
- Remove the route-controlled fallback where `controller.depart()` is called directly without dispatcher authority; route-driven movement should require a dispatcher path plan.
- Remove the route-facing `TrainController.wait_for_path(reason)` command in the desired model. The controller should infer "no path authority" from an empty `received_path_plan`; higher layers do not need a separate command to tell it that the path is gone.
- If initial path creation fails before departure in `all_or_nothing` mode, `RouteExecutor` should record that route/path error on `exec_state.last_error` / `exec_state.error_time`, set `exec_state.waiting_for_path = True`, and keep the train in `STANDBY` or `IDLE`; the train never had authority, so no special controller waiting command is needed.
- In `best_effort` mode, only "no authority at all could be created" is a creation failure. A truncated but live path is not a failure path; the train may run under that current authority and later wait at the current authority boundary while `RouteExecutor` keeps retrying `extend_path()` on the same `path_id`.
- If `PathDispatcher` cancels/revokes a live path mid-run, it should clear controller authority by calling `controller.receive_path_plan(None)`, forcing the controller into no-authority braking against the current occupied-block boundary.
- After the cancellation-driven no-authority stop has finished, ordinary `_try_depart_to_waypoint()` logic for the same waypoint should run again. If that stop escalated into EB, this retry point is only after `TrainController.release_emergency_cmd()` has returned the controller to `IDLE` or `STANDBY` according to cab selection:
  - if `cancellation_kind` was ordinary revocation/cancellation and the waypoint should still be attempted, let `PathDispatcher` acquire a fresh path
  - if `cancellation_kind == PathCancellationKind.EB`, treat it as ordinary restart-after-EB recovery after `TrainController.release_emergency_cmd()` returns the controller to `IDLE` or `STANDBY`; the EB path has already been cancelled, so replan the same pending waypoint with a fresh path request
  - if `cancellation_kind == PathCancellationKind.ROUTE_DEVIATION`, branch on the structured deviation context after the no-authority / EB recovery point. `RouteExecutor.handle_path_cancellation(...)` records that context immediately, but it does not reroute or skip on the fly while the train is still braking. If `passed_requested_target == True`, the controller has proven an overshoot beyond the pending requested target, so route logic applies `RouteExecutor._skip_waypoint(...)` only after the stopped recovery point and then replans toward the next target on the directed route walk. If `passed_requested_target != True`, including out-of-sequence entry into a resource that is not on the plan, keep the same pending waypoint armed, clear stale planning state, and replan toward that same target after the stopped recovery point. `deviation_kind` is branchable only to distinguish these recovery classes; `reason` remains logs/UI text only.
  - if unreachable or path creation fails, use the ordinary pre-departure route/path error path instead of introducing a separate recovery-only state machine

**Arrival detection**

- Stop using `RouteExecutor._is_train_at_platform()` as the normal arrival gate after dispatcher-owned path completion. In the desired model, the pre-physics `TrainController.tick(...)` predicate owns stop-complete observation and `PathDispatcher.on_controller_progress(report)` owns the completion commit; dispatcher-committed completion is the authoritative arrival trigger for that stop.
- Delete `RouteExecutor._check_waypoint_arrival()` from the desired model and replace it with one route-owned arrival-entry helper with signature `RouteExecutor._enter_waypoint_arrival(train, route, exec_state, served_target: NextWaypointTarget, served_platform_id, arrival_time)`. `arrival_time` is a required system-time Unix seconds timestamp supplied by the caller; it is the canonical value written into `exec_state.arrived_at_platform_time`. `served_target` is the exact next-target helper result for the stop that just completed, and `served_platform_id` is the concrete platform used for that stop or `None` for direct block targets. Callers sourced from `RouteExecutor.handle_path_completion(...)` pass the callback `event_time`; any other caller passes the current system time (e.g. `time.time()`) since `RouteExecutor` runs in the same clock frame as the rest of the runtime.
- Remove `TrainController.arrive_at_station()` in the desired model and implement a new route-executor-facing `TrainController.enter_station_dwell()` command instead. This is not a rename: route-level dwell entry should happen only after dispatcher-committed stopped arrival from a controller `stop_complete` report. Despite the legacy name, `TrainController.enter_station_dwell()` is the universal dwell-entry command for any `Waypoint.kind == "stop"` (direct block stop, platform stop, or station-resolved stop) and should be valid from the dispatcher-completed stopped ready state (`IDLE` or `STANDBY`). ATO movement itself still requires a dispatcher path.
- On first arrival from dispatcher-committed completion for a `Waypoint.kind == "stop"`, `RouteExecutor._enter_waypoint_arrival(train, route, exec_state, served_target: NextWaypointTarget, served_platform_id, arrival_time)` should set `exec_state.arrived_at_platform_time = arrival_time`, set `exec_state.current_waypoint_index = served_target.waypoint_index`, set `exec_state.direction = served_target.direction`, and, if another waypoint exists, call the canonical mode-aware next-waypoint helper once and store `target.waypoint_index` and `target.direction` from the returned `NextWaypointTarget` on the run state atomically (otherwise leave `target_waypoint_index == current_waypoint_index`). It then sets `exec_state.last_waypoint_platform_id = served_platform_id`, clears `exec_state.waiting_for_path`, clears `exec_state.active_path_id`, and rewrites or clears `exec_state.current_route_status` for the next leg's immediate target scratch. It does not call `TrainController.enter_station_dwell()` in the completion callback. `arrival_time` is a system-time Unix timestamp: when the caller is `RouteExecutor.handle_path_completion(...)`, it is the callback `event_time`; otherwise it is the current system time. This arrival-recording path applies to both ATO and manual trains; the manual/ATO difference is departure behavior only. The helper must assume dispatcher completion as the only normal arrival trigger for a stop waypoint.
- On the next `RouteExecutor.update(...)` after `_enter_waypoint_arrival(...)` records `exec_state.arrived_at_platform_time`, `_execute_route_for_train()` must handle that pending arrival before any new path creation, extension, departure, or covered-waypoint normalization. If the controller is in the dispatcher-completed stopped ready state (`IDLE` or `STANDBY`), `RouteExecutor` calls `TrainController.enter_station_dwell()` to transition into `RUNNING_AT_STATION`. If the controller is already `RUNNING_AT_STATION`, route logic proceeds to `_check_dwell_complete(...)`. A stop waypoint with `dwell_time_sec = 0` still enters this same dwell state first; `Waypoint.should_depart(...)` may then return `True` immediately on the dwell-check pass.
- `_check_dwell_complete()` runs only after dwell has been entered and calls `waypoint.should_depart(exec_state.arrived_at_platform_time, current_time_sec)`, where both timestamps are system-time Unix seconds.
- If dwell/timing says depart, `_check_dwell_complete()` calls `_advance_to_next_waypoint(route, exec_state)`.
- `_advance_to_next_waypoint()` does not mark arrival; that already happened in `_enter_waypoint_arrival(...)`. It also does not apply a second round-trip/circular direction update. Instead it prepares the next leg by keeping `exec_state.direction` on the already-armed next-leg direction returned earlier by the canonical next-waypoint helper, keeping `exec_state.target_waypoint_index` on the already-armed next waypoint when one was set at arrival time (otherwise leaving it equal to `current_waypoint_index`), and clearing `exec_state.arrived_at_platform_time` so the next leg will resolve a fresh planning target on the following tick.
- If another waypoint remains, `_check_dwell_complete()` calls `SimulationController.get_or_create_controller(train.train_id).finish_dwell()`.
- If no waypoint remains, `_check_dwell_complete()` calls `_handle_route_complete_for_train(train, route, exec_state)`.
- `_handle_route_complete_for_train()` resolves the controller through `SimulationController.get_or_create_controller(train.train_id)`, calls `route.unassign_train(train.train_id)`, clears `train.assigned_route_id` when it matches, removes `execution_states[train.train_id]`, calls `controller.finish_dwell()` for any route-managed train still in dwell (including manual trains), and calls `route.deactivate()` for completed one-off routes with no assigned trains. It does not force a custom completion state; once route bookkeeping is removed, the train remains in the state-machine-derived stopped ready state (`STANDBY` with a cab selected, `IDLE` otherwise).
- `finish_dwell()` is a **dwell-exit state-transition command only**, named `finish_dwell` rather than `depart_from_station` because it does not start movement. It transitions the controller out of `RUNNING_AT_STATION` to the state-machine-derived stopped ready state. `RouteExecutor` is still responsible for deciding whether more route work remains, clearing route assignment when complete, and removing the execution-state entry; those are route-level bookkeeping, not controller state.
  `TrainController.finish_dwell()` must not touch `received_path_plan` (only `PathDispatcher` writes it; authority for the completed leg was already cleared by `PathDispatcher.on_controller_progress(report)` before dwell began), must not call `TrainController.depart()` / `TrainController.ato_go()`, and must not initiate physics movement. The next leg's route-side restart happens on the following tick through `RouteExecutor._try_depart_to_waypoint()` -> `PathDispatcher.create_path()` and then, if departure policy allows, `TrainController.depart()`. In ATO that can begin movement immediately. In manual mode the route remains armed but stopped until the operator selects a cab if needed and applies manual driving input; `TrainController.depart()` marks the current authority ready to go but does not start physics movement by itself.

**Dispatcher completion handling**

**route path-event callback schema**

- This is the single canonical callback contract for `PathDispatcher -> RouteExecutor` path-terminal notifications.
- The callback payloads are exactly:
  - completion context: `train_id`, `path_id`, `authority_end_block_id`, `event_time`
  - cancellation context: `train_id`, `path_id`, `cancellation_kind`, `deviation_kind`, `passed_requested_target`, `reason`
  `RouteExecutor` uses `exec_state.active_path_id` as its route-owned correlation key for these callbacks and must not rediscover path identity from torn-down controller state.
- In that completion context:
  - `event_time` is the system-time Unix timestamp recorded at that same instant and is used as the dwell-entry arrival time
- In that cancellation context:
  - `cancellation_kind` is the `PathCancellationKind` enum used for route-side branching in v1
  - `deviation_kind` is populated only for `PathCancellationKind.ROUTE_DEVIATION` and carries the branchable controller deviation enum (`"out_of_sequence"`, `"beyond_authority"`, or `"beyond_requested_target"`)
  - `passed_requested_target` is populated only for `PathCancellationKind.ROUTE_DEVIATION` and tells route recovery whether the train head has passed beyond the pending requested target
  - `reason` is optional plain-text diagnostic context only and must not be used for branching
- `PathDispatcher.on_controller_progress(report)` should follow the **Active-path completion procedure** when it accepts `stop_complete == true` plus the active path requested-target check: clear controller authority by calling `TrainController.receive_path_plan(None)`, call `TrainController.on_path_complete()`, transition the `Path` to `COMPLETED`, clear `active_path_id_by_train[train_id]`, release not-yet-entered dispatcher resources, and then call `RouteExecutor.handle_path_completion(...)` directly using the canonical completion payload from this schema.
- `handle_path_completion()` should treat dispatcher completion as authoritative and should not perform a second exact-stop or live-controller-state check. It should first compare the callback `path_id` against `exec_state.active_path_id`; if they differ, the callback is stale for this route and should be ignored.
- If no `RouteRun` exists for `train_id`, `RouteExecutor.handle_path_completion(...)` is a no-op other than optional diagnostics. Non-route dispatcher paths complete at the dispatcher/controller layer; route waypoint, dwell, and assignment bookkeeping run only when a matching `RouteRun` exists.
- It should clear only route-executor-owned bookkeeping such as `exec_state.waiting_for_path`. Active path tiles, reserved resources, and other authority residue should not be stored or cleared on `Train` by `RouteExecutor` in the desired model. It should no longer clear `train.ato_destination_block_id` (that field should be removed), `train.assigned_path_id` (that field moves to the controller and is cleared by `PathDispatcher`), or `train.reserved_blocks` (reserved resource ownership stays dispatcher-owned).
- `PathDispatcher` clears controller authority by calling `controller.receive_path_plan(None)` as part of path release before `controller.on_path_complete()` and before calling `handle_path_completion()`. The derived reads `controller.assigned_path_id`, `controller.ato_path_id`, and `controller.ato_destination_block_id` then disappear automatically.
- `controller.transition_to_standby()` should be removed from `handle_path_completion()`. `TrainController.on_path_complete()` owns the post-path stop transition and should leave the train in the state-machine-derived stopped ready state; `RouteExecutor` then records whether the completed stop should enter dwell on the next route update.
- Controller destination-block/path release should remain dispatcher-owned through `controller.receive_path_plan(None)`; `TrainController.on_path_complete()` reacts to that completion while `RouteExecutor` remains responsible for deciding whether the completed stop becomes station dwell (`RUNNING_AT_STATION`) on the next route update or remains in the non-dwell stopped ready state.
- `handle_path_completion()` must not need to query live train/controller path state after dispatcher release. It should use the completion context passed in by `PathDispatcher` plus route-executor-owned state only.
- `RouteExecutor.handle_path_completion()` must not read `PathDispatcher.paths_by_id[path_id]` or any other dispatcher path record. After the `path_id` correlation check passes, it uses only the completion context and `exec_state.current_route_status`; it must not perform fresh target resolution in the completion callback.
- If that route-owned status scratch is missing, or if its immediate live waypoint is not a `Waypoint.kind == "stop"`, or if its stored `ResolvedWaypointTarget.requested_destination_block_id` does not equal `authority_end_block_id`, treat the callback as a route/dispatcher invariant violation or degraded safety-stop event: clear only route-owned correlation/bookkeeping for that path, keep physical progress unchanged, record diagnostics, and let ordinary planning request or extend authority again later from the current progress cursor.
- If the immediate live waypoint in `exec_state.current_route_status` is a `Waypoint.kind == "stop"` and its stored `ResolvedWaypointTarget.requested_destination_block_id` equals `authority_end_block_id`, call `RouteExecutor._enter_waypoint_arrival(..., served_target=exec_state.current_route_status.immediate_target, served_platform_id=exec_state.current_route_status.immediate_platform_id, arrival_time=event_time)` immediately to record route progress and dwell timing, but do not call `TrainController.enter_station_dwell()` from the completion callback. The next `RouteExecutor.update(...)` must process that recorded arrival before any new departure/path planning, so there is no route-owned chance to misread the bare stopped ready state as a fresh departure opportunity.
- If the immediate live waypoint in `exec_state.current_route_status` is a `Waypoint.kind == "pass_through"`, that waypoint must already have been consumed earlier by the route-owned head-entry progress rule. A later stop completion at or beyond that pass-through boundary is a safety-stop/truncated-authority event, not pass-through arrival. In that case, `RouteExecutor.handle_path_completion()` must not advance `current_waypoint_index` from the stop-completion event itself. It clears only route-owned bookkeeping for the completed path and lets ordinary replanning continue from whatever route progress has already been recorded. In all cases, dispatcher-committed completion plus the passed completion context are authoritative; `RouteExecutor` does not re-check safety-margin projection from live train/controller state.
- Add `RouteExecutor.handle_path_cancellation(train_id, path_id, cancellation_kind, deviation_kind=None, passed_requested_target=None, reason=None)` as the cancellation-side counterpart. It should first compare the callback `path_id` against `exec_state.active_path_id`; if they differ, the callback is stale for this route and should be ignored. For the matching live path, it should clear `exec_state.waiting_for_path`, clear `exec_state.active_path_id`, record route/path error context on `exec_state.last_error` / `exec_state.error_time` when relevant, and update `exec_state.current_route_status` with deferred cancellation-recovery context for that just-cancelled planning chain. It must NOT advance the waypoint, synthesize arrival, or choose the next waypoint at cancellation time while the train is still braking.
  - `PathCancellationKind.OPERATOR_CANCELLED` or `PathCancellationKind.REVOKED`: keep `exec_state.current_waypoint_index` unchanged, keep the same pending waypoint in route-owned scratch, and let ordinary retry logic re-resolve and replan that same pending waypoint only after the stopped recovery point
  - `PathCancellationKind.EB`: treat it as post-EB recovery rather than route deviation. Keep `exec_state.current_waypoint_index` unchanged, keep the same pending waypoint in route-owned scratch, and let the later restart workflow request a fresh path after `TrainController.release_emergency_cmd()`
  - `PathCancellationKind.ROUTE_DEVIATION`: branch on `passed_requested_target`. When `passed_requested_target == True`, record deferred skip-after-stop context for the pending waypoint. When `passed_requested_target != True`, including out-of-sequence entry into a resource not on the live plan, record deferred retry-after-stop context for that same pending waypoint. In both cases, no reroute, retarget, or `RouteExecutor._skip_waypoint()` call occurs until the stopped recovery point. `deviation_kind` is branchable only together with `passed_requested_target`; `reason` is recorded for logging/UI only. There is no operator retry-vs-continue prompt in v1 for this case.
  - `PathCancellationKind.POWER_OFF`: the train has been powered off through `TrainController.power_off_cmd()`. `RouteExecutor.handle_path_cancellation(...)` runs the ordinary cancellation bookkeeping (clear `active_path_id`) but must not retry the waypoint. The subsequent `RouteExecutor.remove_train_route_run(train_id, reason="power_off")` call from `power_off_cmd()` removes the `RouteRun` entirely; `handle_path_cancellation(...)` does not itself remove the run and does not record a `last_error`, because power-off is an operator-directed removal, not a route/path error.
- Route edit / reconciliation uses this same scratch-clear model. When the route definition or operator-selected planning target changes, `RouteExecutor` must clear route-owned scratch target state for the affected attempt, preserve only physical progress that has actually happened, and then restart ordinary planning from the train's current position under the reconciled target chain.
- Completion handling may observe a train still physically occupying the terminal block or switch footprint. That is not a contradiction: `RouteExecutor` treats dispatcher completion as authoritative arrival, while physical resource release still waits for the later tail-vacate callbacks.

## Train Entity

**Train ownership**

- Remove live position/span and live speed from `Train`. In v1, `Train` is the persistent/configuration entity, not the runtime physical-location store.
- `TrainController` owns the live physical span object for its train, such as `current_span`, together with the live `current_speed_kmh` value. `TrainPhysics` computes movement and sends `span_update` deltas to the controller; the controller applies those updates to its own storage. `TrainPhysics` does not make `Train` the storage owner.
- Remove train-side mirrors for `target_speed` and `speed_limit_reason`; those should become reads from controller lookahead at distance 0.
- Remove `manual_target_speed` entirely; the new manual model should not keep a per-train target speed field.
- Remove `train.state`; operational state lives entirely on `TrainController.state` and must not be mirrored on `Train`. Every consumer that wants operational state should read `controller.state` directly.
- Move live power/cab ownership to `TrainController`. If train serialization still keeps compatibility/bootstrap copies of power or cab fields, those are persistence/bootstrap inputs only; they are not the live runtime source of truth after the controller is created.
- Move live placement/span fields such as `position`, `occupied_tiles`, `occupied_blocks`, end locators, and per-end in-tile distances out of `Train` and into the controller-owned span. `SimulationController.get_or_create_controller(train_id)` does NOT seed `TrainController.current_span` from persisted data; its job is only "make sure a controller object exists and is registered for this `train_id`." Initial placement of `TrainController.current_span` is owned by the API `add_train()` flow, which constructs the train, builds its initial physical span from placement input, obtains the controller, and writes the span directly into `TrainController.current_span` before any simulation tick runs. After that initial placement, `TrainPhysics` is the only normal producer of movement `span_update` values and `TrainController.on_physics_updated(event_time, span_update)` is the normal writer for `TrainController.current_span`; live movement updates never write back to `Train`.
- Remove `train.assigned_path_id`; the controller-side derived read `TrainController.assigned_path_id` (from `received_path_plan.path_id`) is the only runtime source.
- Remove `train.ato_destination_block_id`; destination and authority-end blocks should travel inside the controller path plan pushed by `PathDispatcher`.
- Remove train-side `current_path` and `path_index`; active path tiles and path-progress reads should come from a controller/UI projection owned by `PathDispatcher` instead of a train mirror written by `RouteExecutor`.
- Remove `train.reserved_blocks` as runtime authority residue in the desired model; reserved block/resource ownership should stay on dispatcher path records and controller-facing projections, not on `Train`.
- Keep `Train` focused on persistent/configuration data only, and move live physical span, speed, authority, and operational diagnostics to `TrainController`.

**Review anchor**

- `TrainController` remains the source of truth for operational transitions. The rationale inverts: controller is source of truth because train-side operational mirrors (`target_speed`, `speed_limit_reason`, `ato_destination_block_id`, etc.) are removed and nothing overwrites the controller from train fields. The conclusion is the same in both models; the supporting mechanism is different.

## TrainController

**Controller state**

- `TrainController` owns live power/cab state in the desired model: `power_on`, active cab selection, and the live direction selection implied by that cab. These are not re-synced from `Train` on every tick.
- `TrainController` owns the train's live physical span and speed in the desired model. `TrainPhysics` advances movement by mutating this controller-owned state, but `Train` itself does not store live position/span.
- Add `manual_mode_type`, such as `simulation` or `power_percent`.
- Add `manual_power_percent` for `power_percent`-mode manual control. In v1 this is an integer `0..100` voltage-style command rather than a signed traction/brake command.
- Add `post_eb_restart_pending: bool` as a latched flag that marks "the last transition into the stopped ready state came from an emergency-brake release and the next departure decision is the special post-EB restart case." EB activation always cancels the live path if one exists. On EB release, `TrainController.release_emergency_cmd()` must not inspect route target state itself; it asks the route owner by calling `RouteExecutor.continue_route_run_after_eb(train_id)` through the registered `SimulationController` surface. If that route-executor call finds an existing `RouteRun` and keeps it active for fresh replanning, it returns `True` and the controller latches `post_eb_restart_pending = True`. If no `RouteRun` exists, it returns `False` and the flag stays cleared. The flag is cleared by `TrainController.depart()` after a successful restart acceptance; `RouteExecutor` decides route-run continuation but does not write the controller flag directly.
- Define the `IDLE` / `STANDBY` trigger explicitly: `IDLE` is the controller's state when the train is powered on but no cab is selected. In `IDLE`, the train has no manually selected forward/backward direction because no cab is active. A controller enters `IDLE` from `OFF` when power is turned on with no cab selected. Selecting a cab transitions the controller immediately to `STANDBY`. Route authority may still be assigned while the controller is `IDLE`, and `RouteExecutor` must not treat `IDLE` as a blocker for `create_path(...)`. In ATO mode, `depart()` / `ato_go()` may auto-select the cab from the directed authority geometry carried by `received_path_plan.resource_sequence` and then begin movement. In manual mode, assigning authority while `IDLE` is allowed, but `depart()` only marks that current authority ready to go; it must not auto-select a cab or begin physics movement. Manual motion begins only after a cab is selected and the human driver applies input, and it is always constrained by ATC lookahead: with live authority, ATC protects the authority boundary; with no live authority, ATC protects only the current occupied-block boundary. Manual input may therefore move the train even before `departure_ready_path_id` is set, but such movement cannot satisfy path stop-completion until `TrainController.depart()` has accepted that authority. Such pre-depart manual movement may still produce head-entry route progress such as `Waypoint.kind == "pass_through"` consumption; only stop-completion remains depart gated. The unsupported exception is same-tile synthetic movement with no cab selected: dispatcher rejects that request before any authority is pushed.
- Keep manual driving as `control_mode == manual`; do not keep a separate `MANUAL` operational state in the desired model.
- Add `assigned_path_id: Optional[str]` only as a computed read-only property derived from `received_path_plan.path_id`. It replaces `train.assigned_path_id` as the controller-facing runtime read, but it should not be stored or written independently.
- Add `received_path_plan` as the controller inbox for the active path plan pushed by `PathDispatcher`.
- `received_path_plan` is a projection written only by `PathDispatcher`; it is not the source of truth for dispatcher path ownership, and `TrainController` should not mutate it directly.
- `TrainController` is also the canonical query and storage home for the train's current occupied span. The live span is produced by `TrainPhysics` and written into `TrainController.current_span`; block/switch resources still carry their own physical `occupied_by` ownership, but tile-level ends and ordered occupied tiles live on the controller span rather than on `Train`. `RouteExecutor` and `PathDispatcher` ask the controller for one cab-independent physical span read instead of deriving it independently from `Train`. That span read must expose the ordered occupied span in physical order (`occupied_resources`, `occupied_blocks`, and `occupied_tiles`) plus the two explicit physical end locators needed for later ordering comparisons. The occupancy list is the block/resource-level ownership view; the end locators are the tile-level precise geometry view. It does not depend on a currently selected cab.
- Exception: same-tile synthetic movement without a selected cab remains unsupported in v1. `PathDispatcher.create_path(...)` should reject that request before a plan is pushed; `TrainController` does not infer or invent the cab direction for that case after the fact.

**Controller state machine**

| State | Meaning | Canonical entry triggers | Canonical exits |
| --- | --- | --- | --- |
| `OFF` | Power off | `TrainController.power_off_cmd()` from a stopped powered state; startup default | `TrainController.power_on_cmd()` |
| `IDLE` | Powered on, no cab selected | `TrainController.power_on_cmd()` with no cab; `TrainController.set_cab(None)` from a stopped state; `TrainController.release_emergency_cmd()`, `TrainController.on_path_complete()`, or stopped no-authority recovery when no cab is selected | `TrainController.set_cab("A" or "B")`; `TrainController.depart()` may auto-select a cab in ATO with live authority |
| `STANDBY` | Stopped, cab selected, not dwelling, not waiting | cab selection while stopped; post-path `TrainController.on_path_complete()` when a cab is selected; successful no-authority stop after cancellation/revocation when a cab is selected; `TrainController.release_emergency_cmd()` when a cab is selected; `TrainController.finish_dwell()` | ATO `TrainController.depart()` / movement start; manual driver input under live authority; `TrainController.enter_station_dwell()`; `TrainController.set_cab(None)`; `TrainController.power_off_cmd()` |
| `RUNNING_MOVING` | Moving or actively commanded under authority/manual driving | successful ATO `TrainController.depart()` / movement start; manual driver input under live authority | `RUNNING_WAITING` when stopped under the same live authority with zero clearance; state-machine-derived stopped ready state on post-path completion or no-authority stop; `RUNNING_AT_STATION` only through route-owned dwell entry after confirmed arrival |
| `RUNNING_WAITING` | Stopped while the same live authority still exists but current clearance inside that authority is zero | `TrainController.tick()` when the train is stopped, `received_path_plan` is still present, and the distance-0 ATC limit is at or below the stopped threshold | back to `RUNNING_MOVING` when distance-0 clearance becomes positive again under the same authority; authority loss follows the no-authority braking path instead of staying in `RUNNING_WAITING` |
| `RUNNING_AT_STATION` | Route-managed dwell at a confirmed stop waypoint | `TrainController.enter_station_dwell()` after dispatcher-committed completion from a controller `stop_complete` report | `TrainController.finish_dwell()` |

- The state machine above is the single canonical operational-state contract. Shared logic must not introduce additional live route/runtime state enums for path completion or cancellation recovery in v1.
- Stopped-only operator commands (`power_off_cmd()`, `set_cab(...)`, and `set_mode(...)`) may be issued from any physically stopped controller state. In v1 they disengage any active ATO run and land in the command-defined stopped target state (`OFF`, `IDLE`, or `STANDBY`); they do not cause automatic movement just because clearance later returns or dwell later finishes.
- Stopped recovery commands must not hard-code `STANDBY`. When a stopped recovery needs the ordinary powered, non-dwell, non-waiting state, `TrainController` derives it from the table: powered with no cab selected becomes `IDLE`; powered with a cab selected becomes `STANDBY`; powered off remains `OFF`.

**`ato_running` meaning and lifecycle**

- `ato_running` means "an ATO run is currently in progress": the train has been commanded to move under ATO via `TrainController.depart()` / `TrainController.ato_go()`, and that run has not yet been ended by arrival-at-dwell, path completion, authority clear, EB, or any stopped-state command (power / cab / mode). It is a **run-active** flag, not a **mode** flag. The mode flag is `control_mode` (`ato` vs `manual`), which says "what kind of driving the controller is configured for"; `ato_running` says "is an ATO run currently driving the train." A train in ATO mode is not necessarily `ato_running`: before the first `depart()`, between runs, during dwell, and after any run-ending event, `control_mode == ato` but `ato_running == False`. The one nuance is `RUNNING_WAITING`: the train is stopped with zero clearance but the same live authority still exists, so the run has not ended — `ato_running` stays `True` so the controller auto-resumes when clearance returns. A train in manual mode is never `ato_running`.
- `ato_running = True` is set in exactly one place in v1: `TrainController.ato_go()`, which is called only from a successful `TrainController.depart()` acceptance path when `control_mode == ato` and `received_path_plan is not None`. No other command, tick handler, or callback flips this flag to `True`. In particular, `TrainController.set_cab(...)`, `TrainController.set_mode(...)`, `TrainController.release_emergency_cmd()`, `TrainController.on_path_complete()`, `TrainController.enter_station_dwell()`, `TrainController.finish_dwell()`, and `TrainController.receive_path_plan(...)` never set `ato_running = True`.
- `ato_running` has exactly one writer: `TrainController`. Neither `RouteExecutor` nor `PathDispatcher` nor any train-side mirror writes this flag directly; train-running state is not a route executor's concern. `ato_running = False` is set by `TrainController` on every canonical run-ending event, all of which it owns: successful start of dwell (`enter_station_dwell()`), controller path completion (`on_path_complete()`), any authority clear (`receive_path_plan(None)`), EB activation (inside the controller's EB entry path), `power_off_cmd()`, `set_cab(...)`, and `set_mode(...)`. Resuming ATO after any of these events requires another `depart()` / `ato_go()` acceptance. Dispatcher-driven path cancellation reaches this flag only indirectly: `PathDispatcher.cancel_path(...)` clears the controller inbox through `controller.receive_path_plan(None)`, and it is that controller call — not dispatcher code — that drops `ato_running`.
- `RUNNING_WAITING` does not by itself clear `ato_running`. `RUNNING_WAITING` is a temporary zero-clearance hold under the same live authority; the flag stays `True` so that when the distance-0 ATC limit becomes positive again the controller resumes forward motion without a fresh departure decision. Only the run-ending events listed above (path completion, dwell entry, EB, authority clear, power/cab/mode changes) toggle `ato_running` back to `False`.
- Manual mode never sets `ato_running`. In manual, `TrainController.depart()` marks the current authority ready to go and does not call `ato_go()`; `ato_running` stays `False` throughout manual driving.

**Power/cab/mode command contracts**

- `TrainController.power_on_cmd()` is the explicit `OFF -> powered` transition. It is valid only when power is currently off. If no cab is selected it transitions to `IDLE`; if a cab is already selected it transitions directly to `STANDBY`.
- `TrainController.power_off_cmd()` is valid only while the train is stopped. It is the canonical owner of route/dispatcher release and must follow the **Power-off procedure** in one explicit order: first cancel the train's active path through `PathDispatcher` and let the ordinary cancellation workflow notify `RouteExecutor` while the route execution is still registered, then call `RouteExecutor.remove_train_route_run(train_id, reason="power_off")`, and only then transition the controller to `OFF`, clear the active cab selection, clear any EB latch, clear controller-owned restart-related state such as `post_eb_restart_pending`, clear `departure_ready_path_id`, and disengage any active ATO run (`ato_running = False`). The controller turning off does not stop `TrainPhysics`; world physics continues to run.
- `TrainController.set_cab(cab)` is valid only while the train is stopped. It disengages any active ATO run (`ato_running = False`) but does not create motion or clear any currently assigned dispatcher authority. Setting `cab` to `"A"` or `"B"` transitions the controller to `STANDBY`; setting `cab = None` transitions the controller to `IDLE`. If the selected cab points away from the current live authority, the controller must not rewrite that authority. Instead it rebuilds lookahead in the selected travel frame; if that frame has no forward authority, the distance-0 ATC limit becomes `0`, so ATC prevents wrong-direction movement under the mismatched cab choice.
- `TrainController.set_mode(mode)` is valid only while the train is stopped. It switches between `ato` and `manual`, disengages any active ATO run (`ato_running = False`), clears `departure_ready_path_id` because the previous departure acceptance was mode-specific, and does not create or clear dispatcher authority. `manual` is a control mode, not a separate operational state in the desired model: after a stopped mode switch the controller remains `STANDBY` when a cab is selected, otherwise `IDLE`.
- There is no separate `TrainController.set_travel_direction(...)` command in v1. Manual direction selection is only by cab selection through `TrainController.set_cab(...)`.

**received_path_plan schema**

- This is the single canonical schema for the controller's active path-plan payload. Every producer/consumer should refer back to this subsection by name instead of restating the field list elsewhere.
- `received_path_plan` carries exactly `path_id`, `resource_sequence`, `requested_destination_block_id`, `requested_destination_direction`, and `authority_end_block_id` in v1. It is the controller's only active path-plan payload. `resource_sequence` uses the canonical **resource_sequence entry schema**, and each nested `path_tiles` slice uses the canonical **path_tile entry schema**, so the controller can extend lookahead along the actual geometry without reading `Train.current_path` and without inferring terminal-frame direction from tile coordinates alone. `requested_destination_direction` is already the resolved block-relative target traversal constraint for `requested_destination_block_id` and is always `"forward"` or `"reverse"` in this payload; the terminal frame still comes from explicit directed geometry on the relevant terminal `resource_sequence` entry.
- When the live authority already reaches the current requested target carried by the path, `authority_end_block_id == requested_destination_block_id`; when the path is a best-effort truncated authority, `authority_end_block_id` is the temporary current boundary while the requested target fields remain unchanged.
- `received_path_plan` does not carry a separate cab or head-side field. The ordered `resource_sequence` is the combined already-occupied physical span plus forward path authority in tail-to-authority order. "Tail" means the physical end of the current span farther from `authority_end_block_id` / `requested_destination_block_id`; "authority side" means the physical end closer to the destination and pointing into the path authority. When `TrainController.depart()` is asked to run in ATO with no cab selected, it derives the cab by comparing `TrainSpan.end_a` and `TrainSpan.end_b` against that ordered seeded span and chooses the cab whose physical end is on the authority side. If that comparison is tied between physical ends, v1 prefers `end_a`.
- Treat `assigned_path_id`, `ato_path_id`, and `ato_destination_block_id` as computed reads derived from `received_path_plan`, not as independently written runtime fields. The alias mapping is explicit in v1:
  - `assigned_path_id := received_path_plan.path_id`
  - `ato_path_id := received_path_plan.path_id`
  - `ato_destination_block_id := received_path_plan.authority_end_block_id`
  When `PathDispatcher` clears authority by calling `controller.receive_path_plan(None)`, all three disappear automatically.
- Keep `lookahead`, but make it the canonical cached series used by ATC, ATO, UI, and monitor consumers.
- Remove standalone scalar fields such as `target_speed` and `effective_limit` once those values are represented through lookahead-at-distance-0 reads. Keep the top-level exported `speed_limit_reason` only as a compatibility projection for current UI/monitor consumers; its canonical source remains the distance-0 lookahead speed-curve metadata.

**canonical lookahead payload**

- `TrainController.get_lookahead()` is the single canonical exported lookahead payload for ATC, ATO, UI, and monitor consumers. Every producer/consumer should refer back to this subsection by name instead of restating the field list elsewhere.
- In v1, `get_lookahead()` carries exactly:
  - top level: `train_id`, `head_tile`, `head_distance_cm`, `travel_direction`, `cab`, `speed_limit_reason`, `lookahead`
  - nested `lookahead`: `blocks`, `signals`, `switches`, `stations`, `clearance_cm`, `safety_margin_cm`, `authority_boundary_delta_cm`, `speed_curves`
- `head_tile` is the current train head tile coordinate or `None` when unavailable. `head_distance_cm`, `clearance_cm`, `safety_margin_cm`, and `authority_boundary_delta_cm` are centimeters. `travel_direction` is the train's current forward travel direction in the same frame used by movement/traversal. `cab` is the currently selected cab or `None`.
- `blocks`, `signals`, `switches`, and `stations` are ordered forward projections for UI/debug consumers. They are informational read models only; control decisions come from the same payload's clearance and speed-curve data.
- `lookahead.stations` keeps the current compatibility payload name in v1, but each entry refers to a concrete physical platform ahead on the track, not to a logical multi-platform station group.
- Each `lookahead.blocks` entry carries exactly:
  - `id`
  - `name`
  - `state`
  - `start_cm`
  - `end_cm`
  - `length_cm`
  - `tile_count`
  - `speed_limit_kmh`
- Each `lookahead.signals` entry carries exactly:
  - `id`
  - `name`
  - `state`
  - `distance_cm`
- Each `lookahead.switches` entry carries exactly:
  - `x`
  - `y`
  - `name`
  - `position`
  - `distance_cm`
  - `locked`
  where `position` is `"main"` or `"diverging"` for the live switch alignment at that tile, and `locked` is the exported boolean monitor view of whether that switch currently has any future lock claim or train-owned protection claim that blocks conflicting acquisition.
- Each `lookahead.stations` entry carries exactly:
  - `platform_id`
  - `station_id`
  - `name`
  - `distance_cm`
  - `length_cm`
  - `tile_count`
  - `top_speed_kmh`
- `platform_id` in this compatibility payload is the concrete physical platform identifier on the track.
- `station_id` in this compatibility payload is the logical station-group identifier that owns that platform, or `None` when no station group exists. `station_id` must not be reused as the physical platform identifier anywhere in the desired model.
- Each `lookahead.speed_curves` entry carries exactly:
  - `distance_cm`
  - `atc_limit`
  - `operational_limit`
  - optional `atc_limit_reason_code`
  - optional `atc_limit_reason_detail`
  The limit fields are in `km/h`.
- `atc_limit_reason_code == "authority_stop"` is the canonical reason code for the zero-speed restriction at the active stop/end-of-authority boundary. The controller stop-completion predicate must key on this code, not on arbitrary reason strings.
- `authority_boundary_delta_cm` is the live signed separation from the train head to the safety-margin-adjusted authority boundary in the same forward distance axis as the `speed_curves[*].distance_cm` samples and the authority-boundary projection helper. With a live path it is derived from `authority_end_block_id` plus the terminal frame; without a live path it is derived from the current occupied-block boundary. It is diagnostic/control lookahead data, not a route-authored stop-position field.
- Consumers asking "what is the target speed right now?" sample `lookahead.speed_curves` at distance `0`: `operational_limit` at distance `0` is the controller target speed, and `atc_limit` plus its reason metadata at distance `0` is the controller ATC limit/reason. The top-level `speed_limit_reason` field remains part of the exported v1 payload shape for compatibility with current monitor/UI consumers.
- The empty/no-cab/no-train form must preserve this same top-level and nested key shape, with empty lists and zero distances instead of returning a different payload shape. If a compatibility producer cannot compute one of the nested boundary/safety fields on an empty payload, it should still emit the key with `0.0` rather than omitting it.

**Controller tick order**

1. If no train, return immediately.
2. If power is off, set controller to `OFF` and return.
3. If emergency brake is active:
  - Set handle to `EB`, clear `departure_ready_path_id`, cancel any live dispatcher path through `PathDispatcher.cancel_path(..., cancellation_kind=PathCancellationKind.EB, reason=...)`, and early-exit the tick while EB remains latched.
  - Stay in the early-exit loop until the train has stopped.
  - Require explicit `release_emergency_cmd()` to clear `eb_active`.
  - While `eb_active == True`, `TrainController.tick()` does not perform post-EB restart logic. `TrainController.release_emergency_cmd()` owns the transition to the state-machine-derived stopped ready state (`IDLE` when powered with no cab selected, or `STANDBY` when powered with a cab selected) and the immediate call to `RouteExecutor.continue_route_run_after_eb(train_id)`; the next tick simply observes the released state.
4. Mark cached lookahead data stale for the new tick.
5. If no cab is selected, force ATC limit to zero and return the canonical empty lookahead payload for that tick.
6. Otherwise ensure the canonical lookahead payload is available:
  - With a received path plan, lookahead should extend along the path to the current `authority_end_block_id` boundary adjusted by the controller safety margin.
  - Without a path plan, lookahead should extend only through the forward boundary of the current occupied block in the train's current travel frame. For a train spanning multiple blocks, "forward" means the side where the train/path would continue next, not the trailing side.
7. Build ATC state from the cached lookahead payload, including structured reason metadata.
8. Apply ATC overspeed logic.
9. Calculate ATO info.
10. In ATO mode:
  - If `ato_running`, calculate handle with `_ato_calculate_handle()`.
  - If not running and live authority still exists, choose braking handle toward zero and transition to the state-machine-derived stopped ready state once stopped. If live authority has been cleared while rolling, the no-authority braking and possible EB escalation branch in step 19 owns the behavior instead of this generic not-running branch.
11. In manual mode, write a controller-owned command and let physics convert it to speed:
  - In `simulation` submode, store the driver's handle notch in `handle_position` and allow ATC to override with braking.
  - In `power_percent` submode, store the driver's percentage power in `manual_power_percent` as an integer `0..100` and let physics map it through `SpeedProfile.power_speed_curve` when no braking override is active. This value is positive only and represents absolute applied track/motor voltage and its calibrated immediate running speed rather than signed traction vs brake effort.
  - At any given tick there is only one effective propulsion/brake command for the active mode. In ATO and manual `simulation` mode, the controller/physics speed solution is authoritative and `power_percent` / `track_voltage` are derived from that operating point. In manual `power_percent` mode, `manual_power_percent` is authoritative only while no safety braking override is active; it maps to track voltage and the calibrated absolute speed for that same movement update, so the normal acceleration/deceleration-rate fields do not shape that manual-power command. Raising it immediately commands the higher calibrated voltage/speed point, lowering it immediately commands the lower calibrated voltage/speed point, and holding it steady holds the same commanded power/speed point. If ATC, service braking, or EB intervenes, the controller uses the current handle-based braking flow (`handle_position` for service braking or `EB`) and the positive power-percent command is ignored for that tick. There are no negative power-percent values.
12. Stop computing standalone `effective_limit` and `target_speed` scalars; consumers should read controller lookahead at distance 0 instead.
13. Remove controller-side path completion mutations such as standalone path completion or path-backed completion helpers. Before physics movement for the tick, `TrainController.tick()` may interpret the stable span/speed from the previous physics update plus the current lookahead and report `stop_complete`, but it must not mutate `Path` records, release resources, clear authority, or call route callbacks itself.
14. Let waiting decisions come from controller lookahead and let path completion commits come only from `PathDispatcher.on_controller_progress(report)` after the pre-physics `TrainController.tick(...)` stop-complete report is accepted by dispatcher. `SimulationController` must not add a separate forwarding pass.
15. `RUNNING_WAITING` is controller-owned only. To enter it: the ATC limit derived from the canonical lookahead payload (at distance 0) is at or below the stopped-speed threshold, the train has fully stopped, and `received_path_plan` is still present. In the desired model `RUNNING_WAITING` means "stopped while the same path still exists, but current clearance inside that path is zero."
16. Do not enter `RUNNING_WAITING` solely because the driver manually stopped the train or because EB brought the speed to zero. A driver-commanded manual stop under live authority should remain in `RUNNING_MOVING`; zero speed alone does not change the operational state. Those cases become waiting only if the controller recomputes the same live authority and still finds zero-speed clearance at distance 0.
17. `TrainController.tick()` is also the only component that clears `RUNNING_WAITING`: when the same authority still exists and the lookahead-derived allowed speed at distance 0 becomes positive again, the controller may return to `RUNNING_MOVING` according to mode-specific restart logic.
18. A best-effort truncated path stopping at its current authority boundary is a normal source of `RUNNING_WAITING`, not completion. In that case the same `received_path_plan.path_id` remains live while `RouteExecutor` keeps retrying `extend_path()` on it.
19. Do not enter `RUNNING_WAITING` for an EB-caused stop. If `received_path_plan` is cleared while the train is moving, treat that as path-authority loss rather than ordinary waiting. The essential event is "authority removed": `PathDispatcher` clears `received_path_plan(None)`, then on the next `TrainController.tick()` after that clear — which, when the cancellation ran inside the current tick's Phase 1, is the same tick's Phase 2 controller tick — the controller rebuilds lookahead with no live authority and therefore only to the occupied block boundary. The controller must command ordinary braking toward zero at that current-block boundary using the no-authority ATC limit derived from that rebuilt lookahead. If the no-authority braking / overspeed check determines service braking is insufficient to keep the train within that current block, it escalates to EB. If ordinary braking succeeds and the train reaches a full stop with `eb_active == False`, transition to the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected). This is the cancellation/revocation path, not `RUNNING_WAITING`, and it subsumes the generic ATO not-running branch for no-authority rolling trains.
20. After `TrainController.release_emergency_cmd()`, transition to the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected). EB activation has already cancelled any live path, so restart requires a fresh path-creation plus fresh departure decision rather than automatic controller self-resume.

**ATC speed limit**

- Stop reading signal state directly for ATC restriction selection. In the desired model, CAUTION restriction should come from a single controller-owned global cap such as `CAUTION_SPEED_LIMIT_KMH`, applied when `TrainController` samples a block whose computed `Block.state` is `CAUTION`; signals remain display state derived from blocks rather than an independent ATC input.
- In manual mode with a received path plan, include `_calculate_authority_boundary_limit()` so the effective ATC limit enforces the current authority end correctly: brake to the `authority_end_block_id` boundary in the current live authority frame using the controller safety margin.
- Treat ATC reason reporting as structured metadata on the lookahead/curve payload, not only as a free-form controller string.

**ATO handle calculation**

- Stop rebuilding monitor lookahead inside `_ato_calculate_handle()` and read the canonical cached controller lookahead payload instead.
- If the sampled operational speed curve at distance `0` is already at or below the stop threshold, calculate a direct braking notch immediately.
- Replace the current multi-handle forward simulation wording with a two-point sampling approach:
  - sample the operational speed curve at distance `0`
  - sample one future point at a delta-scaled horizon such as `speed_cm_s * self._tick_delta * LOOKAHEAD_TICKS`
  - combine those samples with the active ATC and block caps to choose power, coast, or brake
- Once the two-point horizon is in place, remove the old fixed-horizon wording and any special near-stop fast-path that only exists to compensate for the old horizon logic.

**Speed curves**

- Build a unified restriction set for the full clearance/authority area and take the minimum of all relevant curves and local limits at each sample point.
- Carry source metadata on each `lookahead.speed_curves` datapoint, such as `atc_limit_reason_code` and `atc_limit_reason_detail`.
- Preserve metadata for which restriction category produced the current minimum ATC limit so monitor/debug UI can explain the displayed number.

**Driver/operator inputs**

- Keep `TrainController.set_handle()` as the active manual-driving command for `simulation` submode manual control. The command may be accepted while manual mode is active, the train is powered, a cab is selected, and EB is not latched; the effective command is still clamped by ATC lookahead before physics receives it.
- Add `TrainController.set_manual_power_percent()` as the active driver input for `power_percent` submode manual control, and add the matching API endpoint/client method plus train/editor UI control so operator input reaches the controller-owned field through the same route as other manual commands. Like handle input, the command may be accepted before `departure_ready_path_id` exists, but ATC remains authoritative and can override with braking.
- `TrainController.depart()` is invoked either by `RouteExecutor` according to route departure policy or by a direct API/UI departure button for an operator-managed train. No other component should synthesize departure acceptance by writing `departure_ready_path_id` directly.

**Dispatcher/route-executor inputs**

- Add `receive_path_plan(path_plan)`, called by `PathDispatcher` after successful `create_path()`, after any `extend_path()` that appends one or more new resources to the live authority on the same `path_id`, and with `None` on cancellation or completion release. `received_path_plan` should mirror only the active authority path referenced by `active_path_id_by_train[train_id]`.
- `path_plan` must follow the canonical **received_path_plan schema**. Its nested authority geometry must follow the canonical **resource_sequence entry schema** and **path_tile entry schema**; the controller must not be asked to recover terminal-frame direction later from tile coordinates alone.
- In v1, the controller path plan always carries both requested and authorized block targets. The live stop the controller should brake to on this tick is derived from `authority_end_block_id`, the terminal frame in `resource_sequence`, and the controller safety margin.
- `path_plan` should not carry a second lifecycle status enum in the desired model. For the controller, movement authority is binary: `received_path_plan is not None` means there is live authority, and `received_path_plan is None` means there is not.
- Add `on_physics_updated(event_time, span_update)`, called by `TrainPhysics.tick(...)` after it computes the next span/speed and tile delta. `TrainController.on_physics_updated(event_time, span_update)` applies the update to controller-owned `current_span` / `current_speed_kmh`, then builds the canonical progress report from the tile delta, canonical lookahead, and `received_path_plan.resource_sequence` when live authority exists, then calls `PathDispatcher.on_controller_progress(report)`. This method owns span storage and progress interpretation only; it does not mutate dispatcher path records or route state directly.
- Add `on_path_complete()`, called by `PathDispatcher.on_controller_progress(report)` when dispatcher accepts a controller `stop_complete` report and commits completion. `TrainController.on_path_complete()` should transition the controller into the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected), but it must NOT clear `received_path_plan` itself. `PathDispatcher`, as the sole owner/writer of the pushed path plan, clears authority immediately before the callback by calling `controller.receive_path_plan(None)`. `TrainController.on_path_complete()` must not enter station dwell by itself; `RouteExecutor.handle_path_completion()` records whether the completed stop should become dwell on the next route update. `TrainController.on_path_complete()` is not called while EB is still latched; EB activation cancels the path, and post-EB continuation always uses fresh authority.
- Remove `arrive_at_station()` in the desired model and replace it with a new route-executor-facing `enter_station_dwell()` command, used only after a confirmed stopped arrival from dispatcher-committed completion on a path. `TrainController.enter_station_dwell()` must accept dispatcher-completed stopped ready state (`IDLE` or `STANDBY`) in the desired model.
- Remove `wait_for_path(reason)` from the desired controller API. Missing path authority is represented entirely by `received_path_plan is None`.
- Keep `TrainController.depart()`, `TrainController.enter_station_dwell()`, and `TrainController.finish_dwell()` as route-executor-facing controller commands. `TrainController.finish_dwell()` is the end-of-dwell state transition (see the Route-executor section for full semantics); it lands in the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected), does not clear `received_path_plan`, and does not start movement. Cab selection is preserved across route completion.
- Manual trains should also enter dwell through `TrainController.enter_station_dwell()` on the route update after confirmed arrival is recorded. The difference from ATO is departure behavior only: in manual mode `TrainController.depart()` records that the current authority has been accepted and the train is ready to go, but it does not itself start movement or call `TrainController.ato_go()`.
- `PathDispatcher` should call `RouteExecutor.handle_path_cancellation(train_id, path_id, cancellation_kind, deviation_kind=None, passed_requested_target=None, reason=None)` whenever a live path is cancelled or revoked. That callback runs immediately for route-owned cleanup and records any deferred recovery context on `RouteRun.current_route_status` right away, but it does not retarget or reroute while the train is still braking. After controller authority is cleared and the train has reached a fresh stopped no-authority state, `RouteExecutor` uses that stored context plus ordinary reachability + path-request logic for recovery. If the no-authority stop escalated into EB, this recovery point is only after a manual `TrainController.release_emergency_cmd()` has returned the controller to `IDLE` or `STANDBY` according to cab selection. `PathCancellationKind.ROUTE_DEVIATION` has two branchable route outcomes at that recovery point: if `passed_requested_target == True`, treat the pending waypoint as missed/skipped and move planning to the next target; otherwise, including out-of-sequence resources not on the plan, keep targeting the same pending waypoint. `reason` remains diagnostic only and must not gate route progression.
- `RouteExecutor` should not set controller path or destination fields directly; controller authority should be derived entirely from `receive_path_plan(...)`.
- Replace `transition_to_standby()` and `arrive_at_station()` as completion hooks with `on_path_complete()` plus route-owned dwell-entry once completion release is dispatcher-owned and the controller reacts through callbacks only.
- `TrainController.release_emergency_cmd()` should only clear EB when the train is already stopped and powered. It transitions the controller to the state-machine-derived stopped ready state: `IDLE` if no cab is selected, or `STANDBY` if a cab is selected. Because EB activation already cancelled the live path, `release_emergency_cmd()` never evaluates a stale path completion predicate. `TrainController` owns the `post_eb_restart_pending` latch, but it does not inspect route target state directly. Instead it calls `RouteExecutor.continue_route_run_after_eb(train_id)` through `SimulationController.route_executor`; that route-owned hook decides whether an existing `RouteRun` continues and returns the boolean used to latch `post_eb_restart_pending`. Otherwise `post_eb_restart_pending` stays cleared.
- After any EB stop, the old active path must not be reused. EB activation cancels the active path through `PathDispatcher.cancel_path(path_id, cancellation_kind=PathCancellationKind.EB, reason=...)`; `TrainController.release_emergency_cmd()` only clears the EB latch and transitions to the stopped ready state. A successful new departure decision after fresh authority clears `post_eb_restart_pending`. There is no station/terminal exception to retain or complete the pre-EB path; normal route covered-waypoint normalization and replanning handle the train's stopped position after EB release.

**route/dispatcher command contracts**

- `TrainController.receive_path_plan(path_plan)` is an atomic full replacement of the controller's active authority projection. `PathDispatcher` uses it both to push a brand-new path and to refresh the same `path_id` after extension; `None` clears the projection immediately. It is valid while the train is stopped or moving because it is a projection update, not a physics state transition. If `path_plan is None` or `path_plan.path_id` differs from the current `received_path_plan.path_id`, `TrainController.receive_path_plan(...)` must clear `departure_ready_path_id`; a same-`path_id` extension refresh may keep the ready marker.
- `TrainController.depart()` is the route/controller departure command for an existing authority/mode decision; it does not create dispatcher authority itself. `TrainController.depart()` returns `(success: bool, reason: Optional[str])` and accepts only when `received_path_plan is not None`, `power_on == True`, `eb_active == False`, and the state-machine-derived state is `IDLE` or `STANDBY`. The `reason` string on failure is diagnostic only, not a branchable API contract. All failure branches leave controller state unchanged, do not clear `post_eb_restart_pending`, do not call `TrainController.ato_go()`, do not set `ato_running`, and do not change `departure_ready_path_id`. On success, `TrainController.depart()` returns `(True, None)` and writes `departure_ready_path_id = received_path_plan.path_id` in both ATO and manual modes; this is the single canonical depart-acceptance gate that downstream stop-completion logic keys on, replacing any earlier mixed `ato_running` / depart-flag predicate. The same successful acceptance clears `post_eb_restart_pending` in both ATO and manual modes, because the post-EB gate applies to "the next fresh departure decision" regardless of control mode. In ATO, a successful acceptance also calls `TrainController.ato_go()`, which is the single setter of `ato_running = True`; cab/end choice and the exact handoff into controller-driven motion remain controller-internal behavior. In manual mode, a successful acceptance does not call `TrainController.ato_go()` and does not start physics movement by itself; the train remains in the stopped ready state with the current authority accepted, and the human driver must still move the train through the normal manual input path. `departure_ready_path_id` is controller-owned live state scoped to the current authority and is cleared when `received_path_plan` is replaced with `None`, replaced by a different `path_id`, completed, cancelled, EB-latched, or powered off. (Same-`path_id` extension refresh keeps it.)
- `TrainController.on_path_complete()` is valid only after `PathDispatcher.on_controller_progress(report)` accepts `stop_complete == true`, verifies the active path requested-target check, and commits path completion. It transitions the controller to the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected), must not clear `received_path_plan`, and must not enter dwell itself.
- `TrainController.enter_station_dwell()` is valid only after confirmed stopped arrival from dispatcher-committed path completion for any `Waypoint.kind == "stop"`. Despite the legacy name, it is the universal stop-waypoint dwell-entry command in v1. It accepts either dispatcher-completed stopped ready state (`IDLE` or `STANDBY`), transitions the controller to `RUNNING_AT_STATION`, and must not create movement or mutate `received_path_plan`.
- `TrainController.finish_dwell()` is valid only from `RUNNING_AT_STATION`. It transitions back to the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected), preserves cab selection, does not call `TrainController.depart()`, and does not mutate `received_path_plan`.

**Read accessors**

- Add `get_lookahead()` as the canonical accessor for UI and debug consumers. Any consumer asking for target speed or speed-limit reason should sample this payload at distance `0`.
- Add `get_current_span()` as the canonical controller accessor for occupied-span queries. It reads `TrainController.current_span`, the v1 storage home for live physical occupancy and end locators. Keep the payload general and geometry-first: at minimum it must expose `occupied_resources`, `occupied_blocks`, and `occupied_tiles` in physical span order from one physical end of the train to the other, plus explicit end locators for both physical ends. The ordered occupancy is the block/resource-level ownership view; the end locators are the tile-level precise geometry view. Each end locator must carry the end's current `tile`, the current `block_id` when that end is inside a block, the current `resource_id` / `resource_type`, and optional precise in-tile position when available. Convenience reads such as `end_a_resource_id`, `end_b_resource_id`, `end_a_block_id`, `end_b_block_id`, `end_a_tile`, and `end_b_tile` may be exposed as derived fields from that span. `end_a` and `end_b` are the train's two **physical** ends and are cab-independent: they are stable geometric labels for the two ends of the consist and do NOT imply head/tail. The "head" end is whichever physical end corresponds to the currently selected cab in the controller's travel frame; without a selected cab, `current_span` still carries both physical ends but no head/tail labeling. `RouteExecutor` and `PathDispatcher` consumers that need head-side reasoning derive it from controller cab/travel state plus the span; they must not assume `end_a == head`. `TrainPhysics` is the only normal producer of movement `span_update` values, while `TrainController` is the only normal writer of `TrainController.current_span`; `RouteExecutor` / `PathDispatcher` must use `TrainController.get_current_span()` whenever they need the train's current span or physical ends.

**TrainSpan schema**

This is the canonical v1 shape of `TrainController.current_span` and the payload returned by `TrainController.get_current_span()`.

| Field | Type | Meaning |
| --- | --- | --- |
| `end_a` | `SpanEndLocator` | Stable physical end A of the consist. It is cab-independent and does not imply head/tail. |
| `end_b` | `SpanEndLocator` | Stable physical end B of the consist. It is cab-independent and does not imply head/tail. |
| `occupied_tiles` | `List[SpanTile]` | Tile-level coverage in physical order from `end_a` to `end_b`. |
| `occupied_resources` | `List[SpanResourceInterval]` | Contiguous resource coverage intervals in the same `end_a` -> `end_b` physical order. Blocks and switches are both represented. |
| `occupied_blocks` | `List[str]` | Unique block IDs currently covered by the train, in first-seen `end_a` -> `end_b` order. Switch resources are excluded. |

`SpanEndLocator` carries exactly:

- `end_id` — `"A"` or `"B"`
- `tile` — current tile coordinate for that physical end
- `resource_type` — `"block"` or `"switch"` when the end is on a known resource, otherwise `None`
- `resource_id` — block ID or switch ID for that resource, otherwise `None`
- `block_id` — current block ID when the end is inside a block, otherwise `None`
- `entry_edge` — edge used as the end's current in-tile distance frame, when known
- `distance_cm_from_entry` — precise in-tile distance from `entry_edge`, in centimeters, when known

`SpanTile` carries exactly:

- `tile`
- `resource_type`
- `resource_id`
- `block_id`
- `entry_edge`
- `exit_edge`
- optional `start_distance_cm_from_entry`
- optional `end_distance_cm_from_entry`

`SpanResourceInterval` carries exactly:

- `resource_type`
- `resource_id`
- `block_id` for block resources, otherwise `None`
- `start_tile_index` into `occupied_tiles`
- `end_tile_index` into `occupied_tiles`, inclusive

The `occupied_resources` list contains one entry per contiguous physical interval. If a resource ever appears in two disconnected intervals, that is represented as two intervals rather than silently merging them. Consumers that need the forward/head side derive it from selected cab/travel state plus `end_a` / `end_b`; `TrainSpan` itself never relabels `end_a` or `end_b` as head/tail.

`PhysicsSpanUpdate` is the canonical payload from `TrainPhysics.tick(...)` into `TrainController.on_physics_updated(event_time, span_update)`. It carries exactly:

- `new_span: TrainSpan`
- `current_speed_kmh: float`
- `added_tiles: List[SpanTile]` in physical traversal order for tiles newly covered by the updated span
- `removed_tiles: List[SpanTile]` in physical vacate order for tiles no longer covered by the updated span
- traversal-frame metadata on each added/removed tile sufficient for `TrainController` to derive block tail-vacate `direction`

`TrainPhysics` computes this delta by comparing the previous controller-owned span it read at the start of the movement step with the newly integrated span. `TrainController` is the only normal writer of the stored `current_span`: it applies `span_update.new_span`, derives resource entry/release observations from `added_tiles` / `removed_tiles`, and then reports those observations through `PathDispatcher.on_controller_progress(report)`.

`TrainPhysics.tick(...)` must emit a `PhysicsSpanUpdate` even when `added_tiles` and `removed_tiles` are both empty if the integrated `new_span` or `current_speed_kmh` differs from controller-owned storage. This no-boundary update is how `TrainController.current_span` and `TrainController.current_speed_kmh` stay canonical during ordinary in-block movement or pure speed changes.

- Add one shared neighbor/edge helper such as `RailwayNetwork.get_connection_edges(tile_a, tile_b) -> Optional[Tuple[str, str]]`, which answers two questions at once: are the two tiles neighbors, and if so, which edge on each tile connects to the other. `TrainPhysics` and traversal helpers should use this instead of re-deriving neighbor-edge pairs ad hoc.
- Add one shared backend pathfinding / walk-metrics helper in the common network/pathfinding home, such as `RailwayPathfinder.find_ordered_walk(...) -> CandidateWalk` if the current dispatcher search is extracted into a class. If the implementation keeps the helper on `PathDispatcher` or another existing backend pathfinding module, it must expose the same contract and remain the only operational pathfinding home. `CandidateWalk` carries the ordered walk plus canonical comparison metrics `tile_count` and `walk_length_cm`, and every comparable locator resolves to block, tile, and optional precise in-tile position. A companion projection helper such as `measure_along_walk(ordered_walk, locator_a, locator_b) -> float` may be used when a caller needs an in-walk distance after the candidate has already been chosen. `RouteExecutor` platform-end selection and dispatcher start-side / prefix-compatibility checks must all use this same helper/home instead of inventing separate block/tile/precision comparisons.

**Pathfinding-home migration**

- The current operational backend path search lives in `PathDispatcher.find_paths(start_block_id, end_block_id, train_id=None) -> List[PathSegment]` / `PathDispatcher._bfs_find_paths(...)`. That contract is insufficient for the v1 contracts above because it is block-to-block and distance-sorted only; it does not support direction-aware terminal rejection, locator-level (tile-precise) start positions, the canonical `tile_count` then `walk_length_cm` then stable-order tie-break comparison metric, single-block/two-candidate platform selection, multi-block/four-candidate platform selection, or measure-along-walk projection. The refactor must extend or extract that existing backend pathfinding home so it exposes at least:
  - `find_ordered_walk(start_locator, end_locator, *, requested_destination_direction=None, exclude_resources=None, ...) -> Optional[CandidateWalk]` — direction-aware ordered-walk search that accepts tile-precise start and end locators (not just block IDs), rejects candidates whose terminal traversal does not satisfy `requested_destination_direction` or `Block.allowed_travel_directions`, and returns a `CandidateWalk` carrying `ordered_walk`, `tile_count`, and `walk_length_cm`. Tie-break order is fixed: lower `tile_count`, then lower `walk_length_cm`, then the stable internal candidate order; layer-local ad hoc tie-breaks are not allowed.
  - `measure_along_walk(ordered_walk, locator_a, locator_b) -> float` — in-walk centimeter distance projection between two locators on an already-chosen walk, used by lookahead and platform-end pair comparison.
  - `CandidateWalk` payload carrying the ordered walk plus canonical comparison metrics, locator resolution to (block, tile, optional in-tile position), and the terminal block-relative traversal direction used for `requested_destination_direction`.
- Once that shared pathfinding home is in place, every layer that needs pathfinding migrates to it: `RouteExecutor` platform-end selection, `PathDispatcher.create_path(...)` start-side and forward candidate selection, `PathDispatcher.extend_path(...)` suffix selection, and the boundary-projection helpers all share this single home. The legacy block-to-block `PathDispatcher.find_paths(...)` contract is removed or made a thin adapter over the new ordered-walk helper in v1; it must not remain as a parallel source of operational path choices.

**Manual mode and movement-authority boundary**

- In `simulation` submode, the driver should call `set_handle()`, the controller should store `handle_position`, and `TrainPhysics` should integrate it into speed while ATC can still override with braking.
- In `power_percent` submode, the driver should call `TrainController.set_manual_power_percent()`, the controller should store `manual_power_percent`, and `TrainPhysics` should convert it through `SpeedProfile.power_speed_curve` in the same tick whenever no braking override is active.
- In that same `power_percent` submode, the converted power-percent command is the absolute voltage/speed command and overrides the normal acceleration/deceleration-rate fields while no safety braking override is active. `TrainPhysics.tick(...)` must set the `span_update.current_speed_kmh` for that tick to the calibrated speed implied by `manual_power_percent`; the model assumes negligible momentum under direct voltage control, so there is no service-rate ramp between manual power-percent settings. Service braking and EB still use the existing handle-based braking flow: when controller safety logic requests braking, `handle_position` / `EB` wins and `manual_power_percent` is ignored for that tick; there is no signed negative power-percent command.
- Remove `manual_target_speed` entirely; no hidden shim or compatibility field should remain.
- In manual mode with a received path plan, add `_calculate_authority_boundary_limit()` so the controller brakes to the current authority end boundary using the controller safety margin.
- Without a received path plan, the current-block boundary should remain the fallback authority limit.

**Completion ownership and timing**

- Make `TrainController` the sole owner of stop-complete interpretation and `PathDispatcher` the sole owner of path completion commit. The controller reports `stop_complete`; dispatcher decides whether that report applies to the active path and then mutates path/resource/route state.
- Let `TrainController` react to dispatcher-committed completion through `on_path_complete()`, but stop letting the controller decide independently that a path-backed run is complete.
- Keep `PathDispatcher` as the sole writer of `TrainController.received_path_plan`; `on_path_complete()` is a reaction hook, not an inbox-mutating hook.
- Remove helper logic such as `path_backed_run_active` / `_is_standalone_path_complete()` once controller-reported, dispatcher-committed completion is authoritative.
- Tighten the invariant so path completion is emitted only after the pre-physics `TrainController.tick(...)` predicate reports `stop_complete == true` under the canonical usable-authority stop predicate and `PathDispatcher.on_controller_progress(report)` accepts it for the active path by verifying that `Path.authority_end_block_id == Path.requested_destination_block_id`. The controller safety margin remains a braking/diagnostic target; it is not a separate centimeter-tolerance completion gate.

**Controller invariants**

- There should be no `self.target_speed` field once lookahead-at-distance-0 becomes the canonical source of target speed.
- Controller-owned live control/physical state and train-owned persistent/configuration state should be cleanly separated.
- Remove the runtime fallback read `self.ato_destination_block_id or getattr(train, "ato_destination_block_id", None)` from controller ATO logic; in the new model destination state comes exclusively from `received_path_plan`.
- `SimulationController.get_or_create_controller(train_id)` should preserve the 1:1 train/controller pairing without recreating authority from train-side runtime mirrors. Its job is only "make sure a controller object exists and is registered for this `train_id`." In v1, controller existence is a hard precondition for any dispatcher authority push: callers must ensure the controller exists before `create_path(...)`, `extend_path(...)`, or any `receive_path_plan(...)` write. `SimulationController` must not construct or write the plan payload itself, and there is no late-bind recovery hook such as `PathDispatcher.on_controller_available(train_id)`.

## TrainPhysics

**Movement-authority input in `TrainPhysics`**

- `TrainPhysics` should continue to execute physical integration (speed update, span/end-locator update, occupancy tracing, and tail tracing), but the canonical live storage is `TrainController.current_span` and `TrainController.current_speed_kmh`. `TrainPhysics.tick(...)` computes each `span_update` (`new_span`, `current_speed_kmh`, ordered `added_tiles`, ordered `removed_tiles`, and traversal frame metadata) and passes it to `TrainController.on_physics_updated(event_time, span_update)`, which applies the controller-owned storage write. `TrainPhysics` should not own path identity, dispatcher authority state, progress interpretation, completion, or a separate canonical position store on `Train`.
- To choose exits on ambiguous geometry, `TrainPhysics` normally needs a controller-provided, read-only authority-geometry projection derived from `TrainController.received_path_plan.resource_sequence`. The minimum movement data is the ordered `resource_sequence` / `path_tiles` geometry from that active plan, plus enough local direction context to choose the correct next edge through the current tile.
- `TrainPhysics` does **not** need dispatcher ownership fields such as `path_id` to step the train, and it does not need requested/authorized centimeter stop targets for physical integration. Centimeter stop-target fields are not part of the v1 path/controller contract; controller braking logic uses authority-boundary geometry plus the controller safety margin.
- `TrainPhysics` should obtain that geometry projection from `TrainController.received_path_plan` rather than from a separate `TrainController.get_path_tiles()` API. `Train.current_path` should not remain a movement input in the desired model.
- `TrainPhysics` should read the current live position through the controller-owned span and should write movement only by sending `span_update` to `TrainController.on_physics_updated(event_time, span_update)`, not through any train-entity position field. Initial placement is established by the API `add_train()` flow writing `TrainController.current_span` before the first tick. If legacy save data contains placement data, it is bootstrap compatibility only and must be routed through that same span-initialization path; it must not remain a runtime `Train` field after that controller span has been initialized.
- Exception for cancellation/revocation braking: if `PathDispatcher` has already cleared `received_path_plan` to revoke authority while the train is still rolling, `TrainPhysics` must still keep moving the train according to speed and the current live network state. That post-revocation movement relies on the physical `Switch.state` / live track geometry that exists in the network at that moment, not on retained authority locks or a second copy of path ownership surviving in the controller inbox.
- Once live switch state ownership moves to `Switch`, `TrainPhysics._advance_end()` and tail tracing must call the updated `TrackSegment` traversal helpers using the resolver input defined by the `TrackSegment` helper contract above.

**Block occupancy**

- Route normal tail-vacated transitions through `TrainController.on_physics_updated(event_time, span_update)` and `PathDispatcher.on_controller_progress(report)`, which routes block releases through `BlockManager.on_block_tail_vacated()` so `OCCUPIED -> CAUTION -> FREE` stays in one state machine.
- `TrainPhysics` must not write `Block` fields directly and must not call block-state mutators for normal occupancy, CAUTION, or release. It computes movement `span_update` values, and the controller/dispatcher feedback chain performs all block writes through `BlockManager`.
- `TrainController.on_physics_updated(event_time, span_update)` must not include a block in `tail_vacated_resources` just because the tail left one tile of that block. `PathDispatcher` may call `BlockManager.on_block_tail_vacated()` only after the controller report proves the train no longer occupies **any** tile in that block.
- Replace direct `clear_block()` calls for normal CAUTION clearing with the cascade inside `on_block_tail_vacated()` via `_reevaluate_caution_blocks()`, not a separate `release_block()` step.

**Tail-vacate flow in `TrainPhysics`**

- Remove direct calls to `block_manager.set_block_to_caution()` and `block_manager.clear_block()` for normal vacate transitions.
- On tail-vacate, `TrainController.on_physics_updated(event_time, span_update)` includes a typed resource-release observation in `tail_vacated_resources` and sends it through `PathDispatcher.on_controller_progress(report)`. For blocks, the controller must report the vacate only after the updated `current_span` proves the train no longer occupies any tile in that block; tile-level vacate is not enough. For switches, tile-level vacate of the switch resource is sufficient. The resource event obtains `resource_id` from the same tile-lookup mechanism already used for entry detection: `track.block_section_id` for blocks, `track.switch_id` for switch tiles (both fields are on `TrackSegment` and available from `network.tracks.get(tile)`). The controller report carries block tail-vacate `direction` derived from the movement basis used for that vacated traversal. `PathDispatcher` routes the release according to `resource_type`: blocks go through `BlockManager.on_block_tail_vacated(block_id, train_id, direction)` so `OCCUPIED -> CAUTION -> FREE` stays in one state machine; switches go through the `Switch` entity by clearing `Switch.occupied_by` and then clearing train-owned protection sourced from that vacated switch.
- `_caution_blocks` tracking in `TrainPhysics` becomes unnecessary once `BlockManager` handles the full release lifecycle internally; remove that legacy field and its associated maintenance logic in the desired model.

**Voltage behavior**

- Stop reading `controller.target_speed` and `train.manual_target_speed` once those standalone fields are removed.
- Keep the terminology explicit and simple: `track_voltage`, `power_percent`, and `speed_kmh` are three different values in the desired model.
- `TrainPhysics` should pass the current `track_voltage` value to `BlockPowerController` as the software-to-hardware output layer for block voltage emission.
- The active mode determines which value is authoritative. In ATO and manual `simulation` mode, `speed_kmh` is the controller/physics source of truth and `power_percent` / `track_voltage` are derived from that current operating point. In manual `power_percent` mode, `manual_power_percent` is the source of truth and `speed_kmh` / `track_voltage` are derived from that commanded power level in the same movement update; the manual power command sets the absolute calibrated voltage/speed point instead of being integrated through the normal service acceleration/deceleration rates.
- In manual `power_percent` mode, that authority applies only while no controller braking override is active. If ATC/service braking or EB is active, `TrainPhysics` must follow the current handle-based braking command instead of the positive power-percent input for that tick.
- In `power_percent` manual mode, `TrainPhysics` should use the profile's voltage/power/speed calibration directly rather than reading removed scalar target-speed fields or applying the service acceleration/deceleration rates to the manual-power command. The calibration must be usable in both directions so physics can convert between the authoritative value for the active mode and the derived outputs it needs to maintain. These mappings are owned by `SpeedProfile` and should be documented exactly this way:
  - `track_voltage <-> power_percent`
  - `power_percent <-> speed_kmh`
- When `TrainPhysics` needs `track_voltage`, it derives it from the current authoritative mode input: `speed_kmh -> power_percent -> track_voltage` in ATO and manual `simulation` mode, or `manual_power_percent -> track_voltage` plus the calibrated absolute `speed_kmh` command in manual `power_percent` mode. In manual `power_percent` mode without a braking override, that calibrated `speed_kmh` is written into the same `PhysicsSpanUpdate.current_speed_kmh` that carries the movement result.
- Do not introduce extra names for these concepts in the desired model. Keep the doc wording in terms of voltage, power percent, and speed, and keep the mappings distinct.

**Physics invariants**

- `TrainPhysics` should not own manual-mode policy; it should execute controller commands and maintain physical state only.
- `TrainPhysics` no longer relies on a separate track-level path-lock field. The future-authority role is now played by `Block.reserved_by_path` / `Block.reserved_for_train` on the block side and `Switch.locks` on the switch side. Movement remains geometry-driven; once the train enters a resource, switch integrity during traversal is enforced by `Switch.occupied_by` plus any `Switch.train_protection_claims` rather than by a global track-level path lock or retained path claim. This is not a transitional/migrated version of the old field — the mechanism is different, so no transitional phase is needed.

## SpeedProfile

`SpeedProfile` carries motion-rate data plus per-train calibration in the vocabulary the rest of the system should use directly: voltage, power percent, and speed. The calibration defines bidirectional mappings between `track_voltage` and `power_percent`, and between `power_percent` and calibrated `speed_kmh`. Keep those mappings explicit in the doc instead of introducing extra terminology.

- Keep these fields on `SpeedProfile`:
  - `profile_id`: unique profile identifier.
  - `name`: display name for UI/debug/profile selection.
  - `startup_voltage`: minimum `track_voltage` that produces movement. Below this threshold the train remains stopped.
  - `max_voltage`: top of the usable `track_voltage` range for the first mapping stage.
  - `power_speed_curve`: stored calibration mapping `(power_percent, speed_kmh)` for the second stage.
  - `lighting_voltage`: voltage used for stopped lit states.
  - `acceleration_rate`: service acceleration rate in `km/h/s`.
  - `deceleration_rate`: service braking rate in `km/h/s`.
  - `emergency_brake_rate`: emergency-brake deceleration rate in `km/h/s`.
  - `friction_rate`: passive/coasting deceleration rate in `km/h/s`.
  - `operational_decel_ratio`: comfort-braking fraction used when ATO builds operational braking curves.
  - `air_resistance_enabled`: whether the drag model is active.
  - `drag_coefficient`: drag strength used by the drag model.
  - `reference_speed_kmh`: reference speed used to scale the drag model.
- Remove `speed_voltage_curve` and `min_start_voltage` from the desired model. They belong to the old one-stage speed-to-voltage design and must not remain in the target schema.

**SpeedProfile constraint**

- `SpeedProfile` is still not a speed limit object under the desired model. It expresses motion-rate data and per-train calibration (`startup_voltage`, `max_voltage`, `power_speed_curve`), not any form of speed ceiling. Train maximum speed and block maximum speed remain separate, independently enforced constraints.

**Speed-profile addition**

- Keep the desired-model calibration wording in three explicit values: `track_voltage`, `power_percent`, and `speed_kmh`.
- The calibration has two bidirectional mappings and both should be stated directly in the doc:
  1. `track_voltage <-> power_percent`
  2. `power_percent <-> speed_kmh`
- `startup_voltage` and `max_voltage` define the voltage range used by the first mapping. Below `startup_voltage`, the train does not move. `max_voltage` is the top of the usable range. In v1, `track_voltage <-> power_percent` is linear across that usable range, so reversing from `power_percent` back to `track_voltage` uses the same linear interpolation.
- `power_speed_curve` is the stored `(power_percent, speed_kmh)` mapping used by the second step. `power_percent` is the intermediate normalized control value between voltage and speed; it is not a second name for either of them. In v1 this may be linear by default, but it is still stored explicitly as profile calibration data rather than inferred ad hoc elsewhere. Reverse lookup from `speed_kmh` to `power_percent` uses the inverse interpolation of this same stored curve.
- In manual `power_percent` mode, the speed implied by `power_speed_curve` is the commanded absolute speed while no safety braking override is active; the controller/physics update applies that speed immediately because the model train is voltage-driven and treated as having negligible momentum for this manual command. The service `acceleration_rate` / `deceleration_rate` fields do not shape that manual-power response. Those motion-rate fields still govern ATO, manual `simulation` handle integration, service braking, emergency braking, and coasting behavior outside the manual-power command.
- Every train should have a default `SpeedProfile` carrying these calibration fields so the `power_percent` manual mode always has a defined voltage/power/speed mapping, even before per-train tuning is customized.

## Signals

**Signals**

- Signals remain display-only in the desired model. CAUTION handling moves to `TrainController.CAUTION_SPEED_LIMIT_KMH` (enforced via the lookahead / ATC path), not to signal aspects. `RailwayNetwork.update_signals_from_blocks()` still produces aspect values for the UI, but no controller or physics layer consumes them as a speed restriction.

## Power

**Power-controller role**

- Keep `BlockPowerController` focused on the software-to-hardware boundary only: it accepts a voltage number and applies it to block outputs.
- `TrainPhysics` computes `track_voltage` from the current authoritative operating input for the active mode: `speed_kmh -> power_percent -> track_voltage` in ATO and manual `simulation` mode, or `manual_power_percent -> track_voltage` plus the calibrated absolute `speed_kmh` command in manual `power_percent` mode. In manual `power_percent` mode without a braking override, the calibrated speed is effective immediately in `PhysicsSpanUpdate.current_speed_kmh`. `BlockPowerController` applies that already-computed voltage to the hardware-facing block outputs.
- Do not let it own manual-mode state or read `manual_target_speed`.

## Data Flow To UI

**API payload ownership**

- Each runtime/entity owner should expose its own API payload through its own `to_dict()` (or equivalent read-model method) rather than merging changed live fields back into another entity's payload. `Train.to_dict()` owns persistent/configuration train data. `TrainController.to_dict()` owns live onboard/control/physical diagnostics. Dispatcher-owned path progress is exposed through a dispatcher-owned read model such as `PathDispatcher.get_active_path_progress(...)`.
- API responses that need both persistent train data and live controller data should include them as separate entity payloads (for example a `trains` collection plus a `controllers_by_train_id` collection, or a train-detail response with separate `train` and `controller` objects). They must not make `Train.to_dict()` a compatibility dumping ground for controller-owned or dispatcher-owned live state.

**`Train.to_dict()` payload**

- `to_dict()` should expose all canonical fields owned by the `Train` entity for convenience.
- Export only persistent/configuration train state from `Train.to_dict()`, because those are the fields owned by `Train`.
- Remove `position`, `current_speed`, `state`, `target_speed`, `speed_limit_reason`, `assigned_path_id`, `ato_destination_block_id`, `current_path`, `path_index`, ATO info, lookahead data, and other live physical/control diagnostics from `Train.to_dict()` when those values are no longer canonical `Train` fields in the refactor.
- Read live operational diagnostics from `TrainController.to_dict()` instead.

**`TrainController.to_dict()` payload**

- `to_dict()` should expose all canonical fields owned by the `TrainController` entity for convenience.
- Export all live operational state, including `handle_position`, `manual_mode_type`, `manual_power_percent`, and `departure_ready_path_id`.
- Export live physical state from the controller-owned storage, including `current_span` and `current_speed_kmh`, for UI/debug consumers that previously read position or occupied tiles from `Train.to_dict()`.
- Export ATO state using `ato_destination_block_id` derived from `received_path_plan.authority_end_block_id`.
- Export `received_path_plan` when present using the canonical **received_path_plan schema**. This is the sole controller/UI source of truth for the active path plan, and its nested authority geometry must continue to follow the canonical **resource_sequence entry schema** and **path_tile entry schema**.
- Do not make `TrainController.to_dict()` the owner of live path-progress state in v1. `PathDispatcher` remains the sole owner of `current_resource_index`; if UI needs that progress projection, expose it through a dispatcher-owned read model such as `PathDispatcher.get_active_path_progress(train_id) -> {path_id, status, current_resource_index}`, resolved from the dispatcher's own active-path registry for that `train_id`, rather than copying ownership into `TrainController` or pushing per-tick sequence-index writes into the controller.
- Do not keep `TrainController.get_path_tiles()` in v1. UI/debug consumers that need active authority geometry should read `received_path_plan.resource_sequence`; consumers that need current physical occupancy should read `TrainController.get_current_span()`.
- Expose the full canonical lookahead payload as the single source of truth for current target speed, ATC limit, speed-limit reason, and forward curve rendering.

**UI data-flow anchor**

- Treat controller payload as the source of truth for live operational/manual/physical state, and train payload as the source for persistent/configuration state.
- A UI asking "what is the train's target speed right now?" should call `controller.get_lookahead()` and sample at distance `0`.

## End-To-End ATO Path Run

**End-to-end path-authority handoff**

- `PathDispatcher` should push the canonical **received_path_plan schema** via the controller path plan. Its nested authority geometry must follow the canonical **resource_sequence entry schema** and **path_tile entry schema**. `controller.assigned_path_id` should be only a derived read of that plan's `path_id`.
- `RouteExecutor` should ensure the train's `TrainController` exists before this path-authority handoff happens in Phase 1.
- `RouteExecutor` should not write `assigned_path_id` or `ato_destination_block_id` directly in the desired model.

**End-to-end ATO run**

1. Route is active and assigned to the train.
2. In Phase 1 setup, `RouteExecutor` first normalizes already-covered waypoints, then arms the next pending waypoint through the canonical mode-aware next-waypoint helper, and then resolves exactly one concrete waypoint target through the canonical `station -> platform -> block` chain (or directly from `block_id`), together with the route-owned `requested_destination_direction` constraint for serving that target.
3. If that currently armed waypoint's resolved target block is not already physically covered by the train's current span, `RouteExecutor` calls `PathDispatcher.create_path()` for that one waypoint target only after first ensuring `SimulationController.get_or_create_controller(train_id)` has established the controller object for that train. It passes `requested_destination_block_id`, `train_id`, and `requested_destination_direction`, chooses `acquisition_mode=route.acquisition_mode`, and lets the controller use the resulting authority boundary plus safety margin for braking.
4. If that currently armed waypoint's resolved target block is already physically covered by the train's current span, covered-waypoint normalization treats that waypoint as already missed/skipped, does not issue a same-block route `create_path(...)` for it, and advances planning toward the next waypoint on the current directed route walk instead.
5. `PathDispatcher` establishes controller authority by pushing the canonical **received_path_plan schema**. Its nested authority geometry uses the canonical **resource_sequence entry schema** and **path_tile entry schema**, and `controller.assigned_path_id` is read back as a derived view of that plan's `path_id`. `RouteExecutor` does not write `assigned_path_id`.
6. After `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)` succeeds, `RouteExecutor` may immediately advance only `target_waypoint_index` and attempt one more point-to-point concatenation on the same live `path_id` when the refreshed live authority actually reaches the waypoint target that was just armed. This means at most one waypoint beyond the immediate next waypoint on the current directed route walk; no separate used-attempt flag is stored. If best-effort growth remains short of that target, the same `target_waypoint_index` stays armed and the next retry keeps pursuing that same target. Longer authorities are therefore built one resolved waypoint segment at a time, but v1 same-tick growth stops after that one extra concatenation; it does not loop until the next stop waypoint. `current_waypoint_index` still does not advance until physical waypoint consumption or dispatcher-committed stop completion.
7. If the route uses `best_effort` and the current live path is still short of its current requested target, `RouteExecutor` keeps retrying `PathDispatcher.extend_path()` on that same `path_id` on later ticks whenever the train is not `OFF`, always passing a freshly re-resolved route-owned request contract for the same pending waypoint (`requested_destination_block_id` and `requested_destination_direction`). That request contract may change on a later retry as route-side target resolution advances to a new legal concrete platform/block target; dispatcher then attempts to continue the same live path from its current authority end toward that new request. If no concrete platform/block target can be resolved for that retry, the retry fails on the route-resolution side before any `extend_path(...)` call. If dispatcher cannot continue the existing live path from its current authority end toward that requested target, `RouteExecutor` must cancel and later recreate instead. The current authority stays live while `resource_sequence` grows in place; the controller may enter `RUNNING_WAITING` at the current authority boundary between successful extensions, but extension retries are not limited to `RUNNING_WAITING`.
8. Each simulation tick runs in setup, execute, and feedback phases:
   - setup: route/path planning
   - execute: controller lookahead, ATC, and ATO/manual command generation, followed by physics movement
   - feedback: `TrainPhysics.tick(...)` computes the next `span_update`, `TrainController.on_physics_updated(event_time, span_update)` applies controller span/speed storage and builds a controller progress report, and `PathDispatcher.on_controller_progress(report)` commits resource progress, release, cancellation, and completion
9. On path completion, `PathDispatcher.on_controller_progress(report)` has accepted `stop_complete == true` and verified that the active path authority end reaches its requested target; dispatcher clears controller authority by calling `controller.receive_path_plan(None)`, calls `controller.on_path_complete()`, marks the path completed, clears `active_path_id_by_train`, releases remaining not-yet-entered authority resources, and then calls `RouteExecutor.handle_path_completion()` directly with the completion context it needs (`train_id`, `path_id`, `authority_end_block_id`, `event_time`). This completion callback does not fire while EB is still latched. Any block or switch still physically occupied by the train remains held until its later tail-vacate report.
10. `RouteExecutor.handle_path_completion()` clears only route-owned bookkeeping and treats dispatcher-committed stop completion as a normal arrival trigger only for `Waypoint.kind == "stop"`. For stop waypoints it records arrival/progress/timing and does not call `TrainController.enter_station_dwell()` from the completion callback. `Waypoint.kind == "pass_through"` is advanced earlier by the route-owned head-entry progress rule instead; a later stop completion at or beyond that boundary is a safety-stop/truncated-authority event and must not advance `current_waypoint_index` by itself.
11. On the next route update after stop arrival is recorded, `RouteExecutor` enters `RUNNING_AT_STATION` before any new path/departure planning. Dwell then continues through `Waypoint.should_depart(arrived_at_time_sec, current_time_sec)`, using system-time Unix seconds.
12. When a stop dwell completes, `RouteExecutor` updates the route-run direction / next-leg state through the normal post-dwell helpers and the cycle repeats.

**End-to-end manual-arrival note**

- Manual trains use the same dispatcher-committed arrival and next-update `TrainController.enter_station_dwell()` path as ATO trains. The only difference is departure behavior: in manual mode `TrainController.depart()` marks the current authority ready to go and does not call `TrainController.ato_go()` or start movement by itself.

**End-to-end post-EB restart note**

- If EB interrupts a route leg, the old live path must not be reused. EB activation cancels that path through `PathDispatcher.cancel_path(path_id, cancellation_kind=PathCancellationKind.EB, reason=...)`; after `TrainController.release_emergency_cmd()` returns the controller to `IDLE` or `STANDBY` according to cab selection, it calls `RouteExecutor.continue_route_run_after_eb(train_id)` to let the route owner keep the current `RouteRun` alive for fresh replanning when one exists. `TrainController.post_eb_restart_pending` is latched from that route-executor continuation result and is the explicit gate that makes `Route.auto_depart_after_eb` apply to the fresh post-EB path recreation flow; once the fresh departure decision is made, clear that flag. There is no station/terminal exception to retain the old path. This ordinary EB restart flow is separate from `PathCancellationKind.ROUTE_DEVIATION`: when controller-reported deviation proves the head has already passed beyond the pending waypoint target, route logic skips the missed waypoint rather than retrying it; otherwise it clears stale planning state and replans from current physical progress.

**EB workflow state machine**

This is the single canonical step-by-step contract for EB activation, release, and post-EB restart in v1. Shared contracts must not invent separate EB-recovery state flags on `TrainController` or `RouteExecutor` beyond the ones listed below.

| Step | Trigger | Actor | Effect |
| --- | --- | --- | --- |
| 1. EB activation | ATC overspeed escalation, manual EB command, or no-authority insufficient-service-braking escalation | `TrainController.tick()` or operator command | Sets `eb_active = True`, forces handle to `EB`, clears `ato_running = False`, clears `departure_ready_path_id`, cancels any live dispatcher path through `PathDispatcher.cancel_path(path_id, cancellation_kind=PathCancellationKind.EB, reason=...)`, and enters the early-exit tick loop. Ordinary tick work is skipped until the train stops and EB is released. |
| 2. Rolling stop under EB | Physics integrates EB deceleration | `TrainPhysics.tick()` | Train decelerates according to `SpeedProfile.emergency_brake_rate`; `current_span` and `current_speed_kmh` continue to update normally. No additional path-release side effects fire during rolling beyond the EB activation cancellation. |
| 3. Full stop under EB | `TrainController.is_stopped()` returns `True` | `TrainController.tick()` | Controller remains in the EB early-exit loop with `eb_active == True`; no state transition yet. Dispatcher path completion is explicitly suppressed while `eb_active == True`. |
| 4. EB release | `TrainController.release_emergency_cmd()` called while stopped and powered | operator | Clears `eb_active = False`; transitions controller to `IDLE` (no cab) or `STANDBY` (cab selected). Calls `RouteExecutor.continue_route_run_after_eb(train_id)` through the runtime surface. `TrainController` latches `post_eb_restart_pending = True` iff that route-owned hook returns `True`; otherwise `post_eb_restart_pending` stays cleared. `release_emergency_cmd()` does not inspect or complete the cancelled pre-EB path. |
| 5. EB restart/replan | `post_eb_restart_pending == True` because `RouteExecutor.continue_route_run_after_eb(train_id)` kept an existing `RouteRun` active | `RouteExecutor._execute_route_for_train(...)` on the next tick | Re-runs the ordinary planning kernel (`_advance_past_covered_waypoints(...)` -> `_find_next_waypoint_target(...)` -> target resolution -> fresh `create_path(...)`). `Route.auto_depart_after_eb` gates whether `TrainController.depart()` is issued automatically once fresh authority exists. |
| 6. `post_eb_restart_pending` clear | Successful `TrainController.depart()` acceptance (ATO or manual) | `TrainController.depart()` | On success, `depart()` returns `(True, None)` and clears `post_eb_restart_pending = False` as part of the acceptance. Failed departure attempts leave the flag set. Only `TrainController.depart()` and `TrainController.power_off_cmd()` clear `post_eb_restart_pending`; `RouteExecutor` never writes it. |

- `eb_active` is controller-owned, but EB activation must cancel dispatcher authority through `PathDispatcher.cancel_path(path_id, cancellation_kind=PathCancellationKind.EB, reason=...)` immediately. The cancellation side effects still run only inside `PathDispatcher`; `TrainController` initiates them by calling the dispatcher API and never releases resources itself.
- `post_eb_restart_pending` is the only latched EB-recovery flag in v1. It survives across ticks until cleared; it is not re-derived from other state each tick.

## Logic Review Checklist

**Review checklist**

- Is the controller receiving the canonical **received_path_plan schema** when path-end stopping matters?
- Does each `resource_sequence` entry carry the ordered `path_tiles` slice using the canonical **path_tile entry schema**, with explicit `entry_edge` / `exit_edge` on both the resource entry and each nested tile entry, needed for controller lookahead and UI geometry after `Train.current_path` is removed?
- Is controller lookahead the only source of target speed and speed-limit reason?
- In manual mode, does ATC enforce the end of the assigned path as a hard stop through `_calculate_authority_boundary_limit()`?
- Can any path-complete event still fire while the train is braking or creeping toward the terminal authority end, instead of waiting for the pre-physics `TrainController.tick(...)` predicate to report `stop_complete == true` and `PathDispatcher.on_controller_progress(report)` to verify that the active authority reaches the requested target before committing completion?
- Does `_ato_calculate_handle()` read only the current tick's canonical lookahead payload, not stale scalar fields?
- Does `RouteExecutor` read controller state rather than mirrored runtime state on `Train`?
- Does `RouteExecutor` resolve waypoint-authored block-relative direction preferences into one concrete `requested_destination_direction` before calling `PathDispatcher.create_path()` or `PathDispatcher.extend_path()`, without relying on platform-level direction fields?
- Do `RouteExecutor` and `PathDispatcher` use the same shared pathfinder/current-span workflow, including the same deterministic tie-break, for start-side and platform-end selection?
- Do `RouteExecutor` and `PathDispatcher` obtain head/tail/current-span data only through `TrainController.get_current_span()`, with `TrainPhysics` remaining the movement-update producer and `TrainController` remaining the writer for controller-owned span state?
- For a waypoint whose resolved target block is already physically covered, does `RouteExecutor` skip that waypoint under covered-waypoint normalization rather than issuing a same-block route `create_path(...)`, while any explicit same-block repositioning remains a dispatcher-owned local/manual capability?
- For same-block / same-tile waypoint movement, does the request carry an explicit `requested_destination_direction`, and does dispatcher pathfinding reject ambiguous or wrong-direction candidates rather than guessing?
- Are repeated resources rejected during both `create_path()` and `extend_path()`?
- In `best_effort` mode, does the system keep one live `path_id`, extend `resource_sequence` in place, and avoid treating a truncated-but-live authority as a creation failure?
- Does `best_effort` creation fail instead of storing a live authority when the head is on a switch and no forward block can be acquired?
- Do dispatcher progress/completion/release callbacks all identify active authority by `train_id` rather than by caller-supplied `path_id`, with `PathDispatcher` resolving active progress from its own database rather than from physics or train mirrors, while delayed release of a still-occupied block or switch resolves from the resource itself after authority release?
- Are multi-train routes using per-train `RouteRun` objects (current-code class may still be `RouteExecutionState`) as the only canonical progress store, with no route-level runtime progress summary fields retained in the target model for now?
- Does `RouteExecutor._advance_past_covered_waypoints(...)` resolve station/platform targets as needed and skip any waypoint whose resolved target block is already physically covered, including `Waypoint.kind == "stop"`?
- On route edit, skip-to-waypoint, or other retarget reconciliation, does `RouteExecutor` clear affected route-owned scratch target state and replan from the train's current physical position without synthetic progress jumps?
- Does stop completion require the controller `stop_complete` predicate, and does `PathCancellationKind.ROUTE_DEVIATION` cover out-of-sequence resources, beyond-authority resources, and beyond-requested-terminal overshoot?
- Does the normal `CAUTION -> FREE` reevaluation require the forward neighbour (in `caution_direction`) to be non-occupied, while still allowing the explicit completion-time `force` exception in `release_path_block_reservations(..., completed=True)`? (`occupied_by` is always `None` in `CAUTION` — guaranteed by `on_block_tail_vacated()` clearing it — so a separate non-occupied check is vacuous. `reserved_by_path` is explicitly not a gating condition; if `_is_caution` has cleared but `reserved_by_path` remains set, the computed block state is `RESERVED`, not `FREE`.)
- Can any completion or cancellation path still unlock a block or switch that the train physically occupies at full stop?
- After `TrainController.release_emergency_cmd()`, does the system return to the state-machine-derived stopped ready state (`IDLE` with no cab selected, `STANDBY` with a cab selected), restart through fresh path creation after EB cancellation, and honor `departure_mode` plus `auto_depart_after_eb`?
- Do train-owned flank-protection claims record `source_switch_id` so tail-vacate can release only the protection created from the vacated main switch?

**Notes**

- In the desired model, ordinary switch release happens when the train tail vacates the switch tile, not on full path completion. `TrainController.on_physics_updated(event_time, span_update)` reports the vacated resource in `tail_vacated_resources`, and `PathDispatcher.on_controller_progress(report)` releases it according to `resource_type`: blocks go through `BlockManager.on_block_tail_vacated(...)`, while switches clear `Switch.occupied_by` and release train-owned protection sourced from that vacated switch through `Switch.release_train_protection_from(...)`. The neighbour-side `source_switch_id` filter protects claims created by other occupied main switches. Both completion and cancellation must respect physical occupancy: if a switch is still physically occupied, its train-owned protection stays in place until the later tail-vacate event.
- `assigned_path_id` moves from `Train` to `TrainController` as a read-only derived property of `received_path_plan.path_id`. `PathDispatcher` owns the underlying `received_path_plan`: it sets that plan when the active path is established, mirrors only the single active authority path referenced by `active_path_id_by_train[train_id]`, and clears it on path release by calling `controller.receive_path_plan(None)` before calling `RouteExecutor.handle_path_completion()`.
