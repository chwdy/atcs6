## Path And PathDispatcher

**Path model**

- The dispatcher path lifecycle has three states: `ACTIVE`, `COMPLETED`, and `CANCELLED`. The lifecycle value is stored on `Path` as `status: PathStatus`. `status` is initialized to `ACTIVE` on successful `create_path(...)` and is the field transitioned by completion and cancellation.
- Keep the core identity / routing fields on `Path`: `path_id`, `status`, `requested_destination_block_id`, `requested_destination_direction`, `train_id`, and `resource_sequence`. The reads `authority_end_block_id` and `path_tiles` are exposed as derived functions (`get_authority_end_block_id()`, `get_path_tiles()`) computed from `resource_sequence` on each call; see the **Path field schema** for the canonical contracts.
- `RouteExecutor` owns route scheduling priority through the current shared `Route.priority` once a run exists. Dispatcher path records do not carry a second copied `priority` field in v1; scheduling stays route-owned rather than becoming path-owned metadata.
- `Path.get_path_tiles()` returns the ordered physical tile list for the authority in train tail -> current authority end order, computed live from `resource_sequence[*].path_tiles`. Every `resource_sequence[*].path_tiles` slice uses the canonical **path_tile entry schema** below; shared contracts must not use bare `(x, y)` tuples.
- Resource acquisition is synchronous inside `create_path()`. Terminal-approach behavior is represented by progress/completion predicates, not a separate live status.
- `resource_sequence` is an ordered list of path-step records interleaving blocks and switches in traversal order. The per-entry schema is defined canonically in the **resource_sequence entry schema** subsection immediately below.
- `RouteExecutor` platform-end resolution, `PathDispatcher.create_path(...)` start-side selection, and `PathDispatcher.extend_path(...)` suffix search must all use the same shared backend pathfinding home/helper. The implementation may extend the existing backend pathfinding code in `PathDispatcher.find_paths()` / `PathDispatcher._bfs_find_paths(...)` or extract that code into a `RailwayPathfinder` class, but it must not create a second disconnected pathfinder with different comparison or direction rules. That shared helper must be callable before any live `Path.resource_sequence` exists, must return the ordered candidate walk it used for comparison, and must be the single source for candidate-length comparison, direction filtering, current-span end selection, and tie-breaking rather than letting different layers reimplement those rules independently.
- The dispatcher path-acquisition API surface is exactly `PathDispatcher.create_path(...)` for a new authority and `PathDispatcher.extend_path(...)` for growing an existing live authority. V1 must not introduce a third acquisition wrapper or route code path with a third acquisition contract.

**Path field schema**

This is the single canonical field set for the dispatcher-owned `Path` entity in v1.

**Why this shape.** `resource_sequence` is the single source of truth for path geometry; `authority_end_block_id` and `path_tiles` are derived functions over it so that any update to live authority is one mutation on one list, not multiple synchronized stores. `current_resource_index` is the head-progress anchor, separated from `requested_destination_*` because head progress and target identity are independent (the head can advance while the requested target is unchanged). Keeping `requested_destination_block_id` and `requested_destination_direction` on the dispatcher record (and out of the controller projection) lets only `PathDispatcher.try_complete_active_path(...)` enforce target-match completion.

| Field | Type | Meaning |
| --- | --- | --- |
| `path_id` | `str` | Unique dispatcher path identifier |
| `status` | `PathStatus` | One of `ACTIVE`, `COMPLETED`, `CANCELLED` |
| `train_id` | `str` | Assigned train |
| `path_tiles` | `function (read-only): get_path_tiles() -> List[path_tile]` | Function that returns the full ordered train-tail -> authority-end geometry by extracting and concatenating `resource_sequence[*].path_tiles` in `sequence_index` order on each call. Not a stored field; not a cache; no writers; no rebuild step. Shared contracts that previously read `Path.path_tiles` call `Path.get_path_tiles()` instead. |
| `resource_sequence` | `List[resource_sequence entry]` | Ordered interleaved block/switch resources. This is the single source of truth for path geometry. |
| `current_resource_index` | `int` | `sequence_index` of the current path-progress anchor resource. Initialized at `create_path(...)` time by walking the stored `resource_sequence` forward from index `0`: while `resource_sequence[i + 1]` is fully covered by the train's current physical span, advance to `i + 1`; stop at the first `i` where `resource_sequence[i + 1]` is not covered (or where `i + 1` is past the sequence). That stopping `i` is the initial value — it is the last covered resource on the directed walk, which is also the train's current physical head against the path frame regardless of cab selection. Once live head-advance progress fires through `PathDispatcher.on_controller_progress(report)`, this index is strictly head-based and advances only with each entered-resource update. |
| `requested_destination_block_id` | `str` | Caller's current requested block target carried by this live path |
| `requested_destination_direction` | `str` | Resolved block-relative traversal constraint at the requested target (`"forward"` or `"reverse"` only); used for compatibility/filtering, not exact terminal-frame geometry |
| `authority_end_block_id` | `function (read-only): get_authority_end_block_id() -> str` | Function that returns `resource_sequence[-1].resource_id` on each call (the **Path invariants** rule below requires the terminal `resource_sequence` entry to always be a `block` entry). Not a stored field; not a cache; no writers. Updates to live authority are made on `resource_sequence` itself, and the function reflects the new terminal block automatically. Shared contracts that previously read `Path.authority_end_block_id` call `Path.get_authority_end_block_id()` instead. |
| `last_status_updated_time` | `float` | System-time Unix timestamp when `status` last changed. The writer for each transition samples `time.time()` **exactly once at the top of the commit** (after preconditions pass, before any lower-layer teardown) and reuses that one value for every downstream write in the same commit (see **Time sampling** under the **Units contract**): `PathDispatcher.create_path(...)` samples once and writes `Path.status = ACTIVE` plus any same-transition notification `event_time`; `PathDispatcher.try_complete_active_path(...)` samples once and writes `Path.status = COMPLETED`, the route-side `task_runs[walk_position].finished_at`, and any `event_time`; `PathDispatcher.cancel_path(...)` samples once and writes `Path.status = CANCELLED`, the route-side cancellation callback diagnostic time (if any), and the `path_cancellation` notification `event_time`. The writer never re-samples `time.time()` partway through a single transition. |

- `Path` is the entity name for the dispatcher-owned resource-sequence authority record itself. Shared contracts must refer back to this table instead of rediscovering the field set from scattered prose.

**Path status state machine**

This is the single canonical state-machine contract for `Path.status` in v1. `status` is the lifecycle enum. Shared contracts must not invent extra path lifecycle states or path-owned pending cleanup flags.

| From `status` | Trigger | To `status` | Notes |
| --- | --- | --- | --- |
| (none) | `PathDispatcher.create_path(...)` succeeds | `ACTIVE` | Path record is inserted into `paths_by_id` and indexed as the train's active authority. Writes `last_status_updated_time` to the synchronous create-time system-time Unix timestamp. |
| `ACTIVE` | `PathDispatcher.try_complete_active_path(train_id)` is called from the post-physics Phase 3 completion check and the active path's live authority reaches the path's requested target block and direction | `COMPLETED` | The **Active-path completion procedure** owns ordering. Dispatcher commits the post-physics controller stop check plus the path-owned requested-target check; it does not infer completion from precise train position or require physical head occupancy in the requested block. |
| `ACTIVE` | `PathDispatcher.cancel_path(path_id, initiator=None, reason=None)` | `CANCELLED` | Not-yet-entered authority resources are released synchronously; controller authority is cleared; the `Path.status` transition to `CANCELLED` makes `active_path_id_by_train(train_id)` return `None` (or skip to a different `ACTIVE` path) by definition; `RouteExecutor.handle_path_cancellation(...)` is notified. |
| `COMPLETED` | any | `COMPLETED` | Terminal. `cancel_path(...)` on a `COMPLETED` path fails with reason `"already completed"`. |
| `CANCELLED` | any | `CANCELLED` | Terminal. `cancel_path(...)` on a `CANCELLED` path fails with reason `"already cancelled"`. |

- `status` is set once per lifecycle transition by the originating synchronous call. No later stopped cleanup pass re-transitions status or writes a pending field.
- Physical `occupied_by` (block or switch) is outside this state machine. It is cleared only by controller-reported tail-vacate observations committed through `PathDispatcher.on_controller_progress(report)` and never by `status` transitions.
- A train may have at most one `ACTIVE` path at a time; retained `COMPLETED` / `CANCELLED` rows do not block a fresh `create_path(...)`.
- In a stored live path, `resource_sequence[-1]` must always be a `block` entry. A v1 path may contain switch resources internally, but its live authority end is always expressed by `authority_end_block_id` on a block resource, never on a terminal switch.

**path_tile entry schema**

This is the single canonical definition of one tile step inside `Path.path_tiles` and inside each `resource_sequence[*].path_tiles` slice.

- Each `path_tile` entry carries exactly:
  - `x`
  - `y`
  - `entry_edge`
  - `exit_edge`
  - `resource_sequence_index` — the parent `Path.resource_sequence[*].sequence_index`.
- `entry_edge` and `exit_edge` are required on every tile entry; shared contracts must not infer them later from neighboring coordinates.
- For same-block synthetic movement, tile-entry `entry_edge` and `exit_edge` follow the directed traversal frame derived per the same-block rules in step 9: multi-tile moves use `requested_destination_direction` against `Block.ordered_tiles` (cab-independent); same-tile moves require a selected cab so the cab heading plus `requested_destination_direction` together define the frame. Dispatcher rejects same-tile no-cab requests rather than inventing a traversal frame.

**resource_sequence entry schema**

This is the single canonical definition of a `resource_sequence` entry. Every site that describes the `received_path_plan` projection, dispatcher/UI authority projections, the `to_dict()` exports, or any other projection of authority geometry refers back to this schema by name rather than restating it.

**Why this shape.** Each entry carries both the resource identity (`resource_type`, `resource_id`) and the directed traversal frame (`entry_edge`, `exit_edge`, plus the nested `path_tiles` slice). Storing the directed frame explicitly — rather than letting consumers infer it from tile coordinates — means same-block and same-tile traversals are unambiguous, and downstream lookahead/braking math has the geometry it needs without re-walking the tile graph. Storing `entry_edge` and `exit_edge` redundantly at both the resource and tile level lets resource-level consumers read the frame without unpacking the tile slice while still keeping per-tile detail available when needed.

- Each `resource_sequence` entry carries exactly:
  - `sequence_index` — position of the entry in the path's train-tail -> authority-end traversal order.
  - `resource_type` — `"block"` or `"switch"`.
  - `resource_id` — stable network resource ID for the block or switch.
  - `path_tiles` — the contiguous ordered slice of canonical `path_tile` entries belonging to that resource, in train-tail -> authority-end traversal order. Every nested tile entry in this slice has `resource_sequence_index == sequence_index`.
  - `entry_edge` — the directed traversal-frame entry edge for that resource in train-tail -> authority-end traversal order.
  - `exit_edge` — the directed traversal-frame exit edge for that resource in train-tail -> authority-end traversal order.
- No other fields are required in v1.
- Ordered tiles alone are not enough for same-block / same-tile movement because a single tile can be traversed in either direction and the stop frame changes with the chosen entry side; `entry_edge` and `exit_edge` are required fields on every entry.
- `entry_edge` must equal the first nested `path_tiles[0].entry_edge`, and `exit_edge` must equal the last nested `path_tiles[-1].exit_edge`; they are stored redundantly so resource-level consumers can read the traversal frame without unpacking the whole tile slice.
- For switch resources, the required switch state is not stored as a fixed field on the entry. It is derived at acquisition time from the planner-facing `TrackSegment.enumerate_traversals(entry_edge)` contract on the switch tile, using the `(entry_edge, exit_edge)` pair selected for that resource's `path_tiles` slice. This derivation replaces storing `switch_positions` as a separate dict on the path.
- These per-resource tile slices plus explicit resource/tile entry-exit edges are the geometry contract for controller/UI consumers after `Train.current_path` is removed.
- Replace `current_block_index` with `current_resource_index`, which should track the `sequence_index` of the current path-progress anchor resource, not the first matching raw resource ID. Initialization rule: walk the stored `resource_sequence` forward from index `0` and advance while `resource_sequence[i + 1]` is fully covered by the train's current physical span; stop at the first `i` whose successor is not covered (or whose successor is past the sequence end). That stopping `i` is the initial `current_resource_index` — the train's current physical head against the path frame, derived purely from coverage geometry and independent of cab selection. Once live head-advance progress fires, the index is strictly head-based.
- Flank protection lives on the switch entity (acquired automatically when the switch is locked); `Path` does not store its own flank-protection list.
- Add the requested target fields on `Path`: `requested_destination_block_id` and `requested_destination_direction`. `requested_destination_direction` is the caller's already-resolved block-relative traversal constraint for the requested target and is always `"forward"` or `"reverse"` by the time dispatcher stores it. It is used to filter compatible terminal candidates, to choose a legal terminal traversal frame, and as part of the dispatcher completion predicate; no stop-centimeter field is stored on the path.
- `Path.get_authority_end_block_id()` returns the live authority end block whose forward boundary the controller brakes toward using its safety-margin policy. The function is defined in the **Path field schema**; it has no setter and no stored backing field.
- The live terminal frame still comes from explicit directed geometry on the relevant terminal `resource_sequence` block entry (`path_tiles`, `entry_edge`, `exit_edge`). For a same-block / same-tile synthetic authority, that traversal frame must still be explicit in the path contract; the spec must not rely on readers inferring direction from tile coordinates alone or from `requested_destination_direction` alone.
- When the live authority already reaches the requested destination, `authority_end_block_id == requested_destination_block_id` and the terminal block entry's computed block-relative traversal direction equals `requested_destination_direction`. When the live authority is a best-effort truncated prefix, the requested target fields remain unchanged while `authority_end_block_id` describes the temporary current authority boundary.
- `Path` does not store a path-owned pending cleanup field. Physical `occupied_by` state and train-owned switch protection change only through controller-reported resource entry/tail-vacate observations committed by `PathDispatcher.on_controller_progress(report)`.
- `PathDispatcher` should treat each `Path` record as the authoritative dispatcher-owned database entry, keyed by `path_id` in `paths_by_id[path_id]`, with `active_path_id_by_train(train_id)` deriving the one active authority path for that train. The controller-facing authority is only a read-only projection of that current dispatcher record.
- Dispatcher-owned path records should remain available while active and, after termination, as retained `CANCELLED` or `COMPLETED` records for history/inspection. In v1, retain that history indefinitely rather than aging it out. Update `last_status_updated_time` on every `status` transition for recordkeeping, but authority release must not depend on any controller-side copy surviving.
- `PathDispatcher`'s retained path database should be the authoritative historical store for every path it has created. After `active_path_id_by_train(train_id)` has been cleared, controller progress reports resolve active authority only against the new active authority, while delayed release or occupancy reporting for a block or switch that remains under the train resolves from the resource itself (`BlockManager` state for blocks, `Switch.occupied_by` / `Switch.train_protection_claims` for switches). `PathDispatcher.create_path(...)` must reject while that train still has an `ACTIVE` path, but once the old path is no longer active retained history rows do not by themselves block creation; only ordinary live resource conflicts remain.
- In the desired model, `train_id` is mandatory for every dispatcher authority path, including ordinary route-driven paths and one-off operator routes. Frontend/API callers must be updated to supply it; anonymous authority paths are out of scope for this model. Future authority on reserved resources is tracked through `Block.reserved_by_path` (written by `BlockManager.reserve_blocks_for_path(...)`) and `Switch.locks` (keyed by `(path_id, source_switch_id)`, where main claims use `source_switch_id = None`, and each claim stores `path_id`, `source_switch_id`, `train_id`, and `locked_state`).

**Path API migration**

- The canonical write interfaces are `PathDispatcher.create_path(requested_destination_block_id, train_id, requested_destination_direction, acquisition_mode=...)`, `PathDispatcher.extend_path(path_id, requested_destination_block_id, requested_destination_direction, acquisition_mode=...)`, and `PathDispatcher.cancel_path(path_id, initiator=None, reason=None)`. `extend_path(...)` is the same request contract as `create_path(...)` plus the leading `path_id` that identifies which live path is being grown in place. `initiator` and free-form `reason` are diagnostic in v1, populated by the writer for the `path_cancellation` notification; callers must not branch on either when deciding planning or routing behavior. Create/extend branching uses the structured `result_kind` / `failure_kind` fields in the create/extend result object instead of parsing `reason`.
- The canonical replacement read interfaces are the controller-facing `received_path_plan` projection for active authority geometry, `TrainController.get_current_span()` for current physical span, `TrainController.get_lookahead()` for live speed/limit diagnostics, and a dispatcher-owned progress projection such as `PathDispatcher.get_active_path_progress(train_id) -> {path_id, status, current_resource_index}` when UI/debug consumers need live `current_resource_index`. That projection is resolved from dispatcher-owned path registries (for example `active_path_id_by_train` plus `paths_by_id`) and returns the currently active path bound to that `train_id`; it does not read train/controller mirror fields.
- Route-managed planning remains point-to-point per call. `RouteExecutor` never asks dispatcher/pathfinder to solve a whole multi-waypoint route in one search. Each `create_path(...)` or `extend_path(...)` request targets exactly one currently resolved waypoint block at a time, and longer waypoint chains are formed by concatenating repeated successful point-to-point segments onto the same live path.

**`create_path()` flow**

1. Before candidate search or any side effect, `PathDispatcher.create_path(...)` must reject the request if `active_path_id_by_train(train_id)` already returns an `ACTIVE` path, returning `success=False` with `failure_kind = train_already_has_active_path` per the **`create_path()` / `extend_path()` return contract**. A train can have only one active authority plan at a time. This failure happens with no path ID allocation, switch acquisition, block reservation, controller mutation, switch-state mutation, or `paths_by_id` record insertion. Callers must use `PathDispatcher.extend_path(...)` to grow that same live path, or wait until the old path has transitioned out of `ACTIVE` before calling `PathDispatcher.create_path(...)` again.
2. Candidate search should enumerate direction-compatible resource sequences from the train's current occupied span to `requested_destination_block_id`, reject any candidate that uses repeated resources, reject any candidate that traverses a disabled block or disabled switch, reject any candidate whose traversal violates a block's `Block.allowed_travel_directions`, and reject any candidate that reaches the terminal block in a way that does not satisfy `requested_destination_direction`. On a single `create_path(...)` call, dispatcher then selects exactly one candidate using the canonical candidate comparison defined in **`GraphWalkCandidate` payload**, applied across the remaining start-side choices, and applies `acquisition_mode` to that one candidate. There is no fall-through to a second candidate within the same call. (Higher-level alternative-target retry across distinct resolved `(block, direction)` pairs within one Phase 1 tick is a `RouteExecutor` concern; see the **Planning Kernel** section of 210-route-executor.md.)
3. Dispatcher must build and store the exact directed terminal frame for the requested target (`path_tiles`, `entry_edge`, `exit_edge`) as part of the terminal `resource_sequence` block entry. For an ordinary live path, dispatcher derives that frame from the chosen terminal block traversal. For same-block / same-tile normalization, dispatcher derives the needed local frame from the `train_id`'s current occupied blocks and, when the move stays inside a single tile, the currently selected cab direction. When the requested target was resolved from a multi-block platform, `RouteExecutor` must already have resolved one concrete terminal block for that run before calling dispatcher, and the terminal frame uses that already-resolved terminal block directly; dispatcher does not choose between platform blocks itself.
4. `PathDispatcher.create_path(...)` should take `requested_destination_block_id`, `train_id`, `requested_destination_direction`, and `acquisition_mode`; it should not require a caller-supplied `start_block_id`, a stop-centimeter value, or a second opaque waypoint/platform stop-context payload. Dispatcher derives the planning start side from `SimulationController.get_or_create_controller(train_id).get_current_span()` plus controller cab state by calling the same shared network-graph walk query that `RouteExecutor` uses. If a cab is selected, the only start-side candidate is the current head end implied by that cab. If no cab is selected, compare both physical ends of the train against the already resolved terminal block and use the end whose successful graph walk is shorter. If one physical end is currently on a switch resource, map that end to the one occupied block inward from that end of the current span before running the candidate comparison; if no such inward occupied block exists for that end, that end is not a valid start-side candidate. Use the canonical candidate comparison defined in **`GraphWalkCandidate` payload**, applied across the remaining start-side choices. Dispatcher must not introduce any other layer-local ad hoc tie-break. Depending on the caller, that shared graph query may return only distance metrics or the ordered tile/block walk used to build `resource_sequence`.
5. `PathDispatcher.create_path(...)` should also take an explicit `acquisition_mode` parameter of type `PathDispatcher.AcquisitionMode`, an enum owned by `PathDispatcher` with v1 values `all_or_nothing` and `best_effort`.
6. Candidate search must become direction-aware. The shared ordered-walk entry point (named `RailwayPathfinder.find_ordered_walk(...)` in this document if the implementation extracts a class from the existing dispatcher search) must reject candidates whose traversal uses a disabled block or disabled switch, reject candidates whose traversal violates `Block.allowed_travel_directions`, and reject candidates whose terminal traversal does not satisfy `requested_destination_direction`, and same-block / same-tile synthetic path construction must use `requested_destination_direction` only as a constraint while dispatcher still derives the exact local terminal frame from explicit geometry. For a direct `block_id` target, `requested_destination_direction` is interpreted against that block's immutable internal traversal order: `"forward"` means the increasing direction of that block-local order and `"reverse"` means the decreasing direction. `RouteExecutor` must resolve any waypoint-authored `"either"` into one concrete block-relative `"forward"` or `"reverse"` before calling `create_path(...)` or `extend_path(...)`; dispatcher never receives `"either"` in the v1 path contract. If dispatcher still cannot build one unique terminal frame for the chosen move, path creation must fail rather than guessing.
7. Stop-position centimeter inputs are not part of `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)` in v1. The controller computes the braking target from the authority boundary and its canonical safety margin.
8. Allow `create_path(...)` for same-block repositioning when the train's current occupied span already includes `requested_destination_block_id`, but treat that as a dispatcher capability for explicit one-off route workflows rather than as the normal route-side handling for an already covered stop waypoint. Argument naming is consistent throughout the desired model: `requested_destination_block_id` is the caller's current requested target passed into `create_path(...)` / `extend_path(...)`, and `Path.get_authority_end_block_id()` returns the current live-authority end derived from `Path.resource_sequence`.
9. For an explicit same-block repositioning request, `PathDispatcher.create_path(...)` owns deciding what tiles/resources must be assigned based on the train's current occupied span and the requested destination block/direction. It does not accept or store a separate centimeter stop target for that local move; the controller uses the ordinary safety-margin stop logic. Two sub-cases:
   - **Same-block, multi-tile (the move spans more than one tile inside the same block):** accepted with or without a selected cab. Dispatcher derives the local traversal frame from `requested_destination_direction` against `Block.ordered_tiles` (forward = increasing index direction; reverse = decreasing index direction) and the train's current covered tile range; this gives a unique frame purely from coverage geometry, so cab selection is not required. The synthetic local path has one block resource whose `path_tiles` slice covers the local movement.
   - **Same-tile (the move stays inside one tile):** requires a selected cab AND `requested_destination_direction` agreeing with the cab's heading; the two together are what define the local frame on a single tile. If no cab is selected, or if cab direction disagrees with `requested_destination_direction`, dispatcher must reject the request with a defined failure reason such as `"same-tile synthetic movement requires a selected cab direction"` rather than guessing.
10. In `all_or_nothing` mode, if the full chosen candidate path cannot be acquired, roll back and return failure; no live path is created. Dispatcher does not fall through to a second candidate inside the same call.
11. In `best_effort` mode, if the full chosen candidate cannot be acquired, `PathDispatcher` should truncate the authority to the furthest forward block-terminated resource prefix it can acquire on that candidate and still create one live path. Dispatcher does not fall through to a second candidate inside the same call; if that candidate cannot produce any storable live `resource_sequence` because the train has no usable occupied-span seed, because no block-terminated prefix can be acquired, or because of the head-on-switch failure below, the call fails. Same-tick alternative-target retry across distinct resolved `(block, direction)` pairs is a `RouteExecutor` concern; see the **Planning Kernel** section of 210-route-executor.md. That truncated live path keeps the same `path_id`, preserves the requested target fields, and stores a `resource_sequence` whose final block is the last block in the current authority (the derived `authority_end_block_id` reflects this automatically). The controller does not need a special "you are already at your authority end" branch: it enters the ordinary running flow, and ATC/lookahead handles the geometry using the current authority boundary plus safety margin. `PathDispatcher.create_path(...)` never returns `result_kind = blocked_no_growth` in v1. A successful create has created a brand-new path record with at least one block resource in its live `resource_sequence`; if the live authority reaches the requested target, return `result_kind = reached_requested_target`, otherwise return `result_kind = truncated_grew`. If no block-terminated live authority can be stored, return `success=False` with a structured `failure_kind` rather than storing a no-growth create result.
    - Special case: if the furthest acquirable prefix ends on a `switch` resource, dispatcher must truncate again to the previous `block` resource before storing the live path, so the stored live authority is always block-terminated.
    - The stored live authority's terminal block must not be the resolved target block of a `task_kind == "waypoint"` task on the requesting `RouteRun`'s current directed walk. If the block-terminated truncation point would land on a waypoint task's resolved target block, dispatcher must extend the storable prefix at least one block past it before storing the live authority. If no further forward block beyond the waypoint target can be acquired on this attempt, the create call fails with `failure_kind = blocked_before_target` and a `reason` such as `"cannot truncate authority at a waypoint target"`. This keeps the rule that waypoints are consumed by head-entry on a still-live authority, never by dispatcher path completion.
    - If the train's covered span itself is empty so no non-empty live `resource_sequence` can be formed for the new path, `PathDispatcher.create_path(..., acquisition_mode=best_effort)` must fail.
    - Exception: if the train head is currently on a switch resource and no forward block beyond that switch can be acquired, `PathDispatcher.create_path(..., acquisition_mode=best_effort)` must fail with `failure_kind = head_on_switch_no_block_authority` rather than storing a head-on-switch holding authority. A natural-language failure reason such as `"cannot create best-effort authority while head is on a switch"` is sufficient in v1.
12. Allocate the new `path_id` before switch acquisition so `Switch.locks` and flank-protection claims can be keyed by that same path ID. Once the chosen acquisition succeeds, create the dispatcher-owned path record directly in `ACTIVE` state; the controller observes the new movement-authority projection on its next `received_path_plan` read. There is no intermediate persisted lifecycle status.
13. `PathDispatcher.create_path(...)` seeds `resource_sequence` from the train's already-occupied resource span. Start-side selection uses the canonical rule already defined in the previous step: cab-selected -> head-side occupied block; no cab -> both end blocks compared by the canonical candidate comparison defined in **`GraphWalkCandidate` payload**. The stored sequence is `[already-occupied resources from the opposite span end through the chosen start side] + [forward candidate from start side to requested target]`. The already-occupied backward portion is not re-reserved; only the forward suffix is subject to `all_or_nothing` vs `best_effort` acquisition. `current_resource_index` is initialized per the canonical walk-forward rule in the **Path field schema**: start at sequence index `0` and advance while `resource_sequence[i + 1]` is fully covered by the train's current span; the stopping index is the initial value. This rule is identical for cab-selected and no-cab cases — coverage geometry, not cab, determines where the head sits in the path frame. On each seeded entry, the side toward the path direction is `exit_edge` and the opposite side is `entry_edge`. Covered-task index advance for already-covered `waypoint` tasks and same-block stopped-at-destination `stop` tasks is owned by Phase 1 (`RouteExecutor`) and runs before `create_path(...)` is even called; dispatcher does not run that reconciliation here.
14. Build `resource_sequence` in traversal order so both blocks and switches are tracked in one sequence.
15. Store the resolved requested target (`requested_destination_block_id`, `requested_destination_direction`) on the `Path`. The current authorized target read `authority_end_block_id` is derived from the stored `resource_sequence`'s terminal block entry, so storing the sequence is enough.
16. The active-path guard has already run before acquisition. A retained `CANCELLED` / `COMPLETED` row or retained history row does not by itself block `PathDispatcher.create_path(...)`; only ordinary resource conflicts still apply.
17. Store the new dispatcher-owned path record in `paths_by_id[path_id]` with `Path.status = ACTIVE` (which by definition makes `active_path_id_by_train(train_id)` return this `path_id`).
18. Do not copy reserved-block state onto `Train`; future reservations remain dispatcher-owned on resources and in the controller-facing authority projection until head-entry consumes them.
19. (No-op in v1.) The dispatcher's own `Path` record is updated atomically by `create_path(...)` / `extend_path(...)`; the controller's `received_path_plan` property automatically reflects that record. There is no separate controller write step. The `Path`'s nested authority geometry follows the canonical **resource_sequence entry schema** and **path_tile entry schema**.
20. The movement-authority projection must preserve an explicit traversal frame for every block and switch entry; readers must not try to recover that frame later from tile coordinates alone.

**`create_path()` / `extend_path()` return contract**

- `PathDispatcher.create_path(...)` and `PathDispatcher.extend_path(...)` return a small result object with exactly `success: bool`, `path_id: Optional[str]`, `resource_sequence: Optional[List[resource_sequence entry]]`, `requested_destination_block_id: Optional[str]`, `requested_destination_direction: Optional[str]`, `authority_end_block_id: Optional[str]`, `result_kind: Optional[PathAcquisitionResultKind]`, `failure_kind: Optional[PathAcquisitionFailureKind]`, and `reason: Optional[str]`.
- `PathAcquisitionResultKind` has v1 values:
  - `reached_requested_target` (`321a`): the live authority reaches the requested destination block/direction for this attempt.
  - `truncated_grew` (`33b1`): `best_effort` acquired at least one new forward resource but the live authority is still short of the requested target.
  - `blocked_no_growth` (`b003`): `best_effort` proved the current live path is still a valid prefix toward the requested target but could not acquire the next forward resource because of live occupancy/reservation/lock conflict on this tick; valid only for `extend_path(...)` against an existing live path. `PathDispatcher.create_path(...)` never returns this result kind.
- `PathAcquisitionFailureKind` has v1 values:
  - `no_viable_path` (`062a`): no topology-compatible, direction-compatible suffix exists to the requested target under disabled-resource and repeated-resource rules.
  - `blocked_before_target` (`d6e3`): a viable candidate exists but the requested authority could not be acquired to the requested target because of live occupancy/reservation/lock conflict on one or more required resources. In `all_or_nothing`, this means the full candidate could not be acquired due to that conflict. In `best_effort` create, this means no block-terminated live authority could be stored for the chosen candidate due to that conflict. Direction problems use `invalid_reverse`; topology/connectivity problems use `no_viable_path`; `extend_path(...)` precondition problems use `missing_or_inactive_path`.
  - `invalid_reverse` (`4d0e`): `extend_path(...)` would reverse at the current authority end.
  - `invalid_request` (`065a`): required request state is missing or ambiguous, such as same-tile synthetic movement without a selected cab.
  - `head_on_switch_no_block_authority` (`0f9b`): `best_effort` could not form a block-terminated authority because the train head is on a switch and no forward block beyond that switch can be acquired.
  - `missing_or_inactive_path` (`d76f`): `extend_path(...)` was called with a missing or non-`ACTIVE` path.
  - `train_already_has_active_path` (`a91c`): `create_path(...)` was called for a `train_id` that already has an `ACTIVE` path. Callers must use `extend_path(...)` to grow that same live path, or wait until the old path has transitioned out of `ACTIVE` before retrying `create_path(...)`.
- On success, `path_id`, `resource_sequence`, `authority_end_block_id`, and `result_kind` are required; `failure_kind = None`; `reason = None`; and `resource_sequence` is the full current live `resource_sequence` after that create/extend operation completes. `RouteExecutor` may inspect `result_kind` and geometry to see whether the armed pending-waypoint target is already contained in the live path, whether best-effort authority grew, or whether the live path remains a valid blocked prefix. It does not advance any route waypoint index from this return payload alone.
- Success means that `PathDispatcher.create_path(...)` created a new path record with a non-empty block-terminated live `resource_sequence`, or that `PathDispatcher.extend_path(...)` either appended at least one new resource to the existing live `resource_sequence` or returned `result_kind = blocked_no_growth` for an existing live path that remains a valid prefix toward the caller's requested target but is temporarily blocked by live occupancy/reservation/lock conflict. A create-path call never succeeds as `blocked_no_growth`; if it cannot store any block-terminated live authority for the chosen candidate, it fails. An extend-path call may succeed without appending only in the explicit `blocked_no_growth` case. Structural failures such as no legal forward suffix, invalid reverse, or missing/inactive path still return `success=False`.
- On failure, `success = False`, `path_id = None`, `resource_sequence = None`, all target fields are `None`, `result_kind = None`, `failure_kind` is required, and `reason` is required.
- `reason` is human-readable diagnostic text for create/extend failures. Callers may display or log it, but they must not branch on exact string equality in v1; control flow branches only on `success`, `result_kind`, and `failure_kind`.

**`cancel_path()` return contract**

- `PathDispatcher.cancel_path(path_id, initiator=None, reason=None)` returns a small result object with exactly `success: bool`, `path_id: Optional[str]`, `new_status: Optional[PathStatus]`, `failure_kind: Optional[CancelFailureKind]`, and `reason: Optional[str]`. `CancelFailureKind` is a v1 enum with values `path_not_found`, `already_completed`, and `already_cancelled`; `failure_kind is None` on success. Callers branch only on `success` and `failure_kind`; `reason` is plain-text diagnostic only and must not drive control flow. `initiator` is an `Optional[str]` free-form label (e.g., `"eb"`, `"operator_cancelled"`, `"power_off"`, `"deviation"`, `"revoked"`) that flows directly into the `path_cancellation` notification payload defined in the **Cancellation** subsection; v1 has no enum for it, and no planning or routing logic branches on it.
- On success, `success = True`, `path_id` is required, `new_status = CANCELLED`, and `reason` is optional plain-text diagnostic context.
- On failure, `success = False`, `path_id = None`, `new_status = None`, and `reason` is required.
- Failure cases are explicit in v1:
  - missing path -> failure with a plain-text reason such as `"path not found"`
  - already `COMPLETED` path -> failure with reason `"already completed"`
  - already `CANCELLED` path -> failure with reason `"already cancelled"`
- When the path is currently `ACTIVE`, `cancel_path(...)` performs the normal cancellation flow described below and returns success. Callers may display or log `reason`, but they must never branch on exact reason text.

**Resource acquisition**

- Dispatcher acquires future resources for one segment through the single coordinator entry `ResourceCoordinator.reserve_segment(future_block_ids, directions, switch_requests, path_id, train_id)`. The coordinator runs the block reservation phase first, then the switch-lock phase (via `SwitchManager.acquire_locks_for_segment(switch_requests, path_id, train_id)`); on any switch failure it rolls back the just-reserved blocks before returning. `PathDispatcher` does not call `BlockManager` or `SwitchManager` directly for acquisition and does not iterate switches per-entry. The single `resource_type` branch lives inside the coordinator per the **ResourceCoordinator** canonical home.
- Dispatcher builds the `directions` mapping (`{block_id -> ReservedBlockTraversal}`) and the `switch_requests` list (`List[SwitchLockRequest]`) from the chosen candidate's `resource_sequence`. `SwitchLockRequest` carries `switch_id`, `locked_state`, `claim_role` (`"primary"` or `"flank"`), and `source_switch_id` (`None` for primary; the originating main switch ID for flank claims) per the **SwitchManager** canonical home. For each switch in path order dispatcher emits one primary request plus one flank request per `(neighbour_switch_id, blocking_state)` entry in `switch.flank_protection`, with `locked_state = safe_state` (the opposite of the neighbour's stored `blocking_state` in v1's binary-switch model) and `source_switch_id = switch.switch_id`. Every flank claim's `source_switch_id` lets later switch head-entry convert only the flank claims sourced from that main switch into train-owned protection.
- In `best_effort` mode, dispatcher uses the same coordinator entry but selects the storable prefix first: dispatcher walks the chosen candidate's future switch resources in path order and probes acquirability per the coordinator's reserve+rollback contract, truncating the candidate to the last block-terminated prefix it can acquire. The final stored prefix is then acquired in one `ResourceCoordinator.reserve_segment(...)` call. If that final prefix contains no storable block authority, `create_path(...)` fails; for `extend_path(...)`, no appended prefix may still be reported as `success=True/result_kind=blocked_no_growth` when the existing path remains a valid blocked prefix.
- `Block.reserved_direction` is written by `BlockManager.reserve_blocks_for_path(...)` inside the coordinator; dispatcher does not write block fields directly. Tile-level traversal direction is carried by `resource_sequence[*].entry_edge` / `exit_edge` and nested `path_tiles[*].entry_edge` / `exit_edge`; there is no `TrackSegment.path_direction` field.
- Distinguish retained geometry, static allowed travel, and temporary reservation direction: v1 does not define a track-level `traffic_direction_policy` field. Static allowed travel direction lives on `Block.allowed_travel_directions`; `Block.reserved_direction` is only the dispatcher-owned temporary reservation direction for one path; and the path plan geometry carries the finer-grained per-tile traversal frame inside that block.
- On segment-level failure, the coordinator runs its own rollback via `ResourceCoordinator.rollback_segment(block_ids, switch_ids, path_id)`. Dispatcher does not iterate switches or blocks to roll back; it just trusts the coordinator's atomic contract. There is no separate tile-level `path_direction` assignment to clear.
- Rollback releases the acquired claims/reservations only; it does not restore an earlier physical `Switch.position`. The live switch alignment remains at the last successfully written value until some later switch command or path acquisition changes it again.
- Completion and cancellation release future resources through the single coordinator entry `ResourceCoordinator.release_path_resources(path_id, block_ids, completed=...)`, which composes `BlockManager.release_path_block_reservations(...)` and `SwitchManager.release_path_locks(path_id)` per the **ResourceCoordinator** canonical home.
- In v1, block reservations remain single-train/single-path resources even though `Switch.locks` can have multiple compatible owners. `Block.reserved_direction` therefore has at most one active value per reserved block and should be cleared when that block reservation is released.
- `create_path(..., acquisition_mode: PathDispatcher.AcquisitionMode)` and `extend_path(..., acquisition_mode: PathDispatcher.AcquisitionMode)` must share the same `PathDispatcher.AcquisitionMode` enum, with two v1 behaviors:
  - `AcquisitionMode.all_or_nothing`: dispatcher acquires only the full requested authority or returns failure after full rollback
  - `AcquisitionMode.best_effort`: dispatcher may truncate to the furthest forward acquirable resource prefix, but the acquisition of that chosen prefix is still atomic
- In `best_effort` mode, `PathDispatcher.create_path(...)` must either create a block-terminated live path record or fail; it never reports no-growth success. Same-block / local movement authorities may still create a one-block synthetic authority when the requested movement has a valid explicit traversal frame. `PathDispatcher.extend_path(...)` may report no-growth success only as `success=True/result_kind=blocked_no_growth`, and only when the existing live path remains a valid prefix toward the caller's current requested target while the next forward resource is temporarily blocked by live occupancy/reservation/lock conflict. That result updates the path's stored requested target contract; the controller projection reflects the same-path update on the next read. Any other extend attempt that appends no resource fails and leaves the existing path unchanged.
- The special head-on-switch case remains a failure because v1 does not allow storing a head-on-switch live authority end.
- In all acquisition modes, the stored live authority end must be block-terminated. A same-tick acquisition result that reaches a switch but no following block is not a valid stored live authority in v1; dispatcher must roll that trailing switch/flank acquisition back before storing the path.

**Controller-mediated progress**

- `TrainPhysics.tick(...)` should compute the next `TrainSpan`, next `current_speed_kmh`, and the ordered tile-level delta for that movement, then call `TrainController.on_physics_updated(span_update)` at least once every tick. `TrainPhysics` does not call dispatcher progress, completion, or release APIs directly and does not own the stored span.
- `TrainController.on_physics_updated(span_update)` should atomically write `span_update.new_span` and `span_update.current_speed_kmh` into controller-owned storage, then detect newly entered blocks, newly entered switches, tail-vacated blocks, and tail-vacated switches by converting `span_update.added_tiles` and `span_update.removed_tiles` through network tile/resource lookup, `received_path_plan.resource_sequence` when authority exists, and current traversal context. It then returns one ordered `ControllerProgressReport` to `SimulationController` for that train's same-transaction local progress buffer. Stop completion is not reported from this method; it is evaluated separately later in that same train's Phase 3 consume pass from the post-move controller state.
- The controller progress report payload follows the canonical **ControllerProgressReport schema** defined in the **Dispatcher progress/completion flow** section. `current_head_sequence_index` is the index of the train head's current position in `received_path_plan.resource_sequence`, or `None` when no active resource-sequence mapping is available. When live authority exists and the controller cannot map the head to that active `resource_sequence`, the report must set `deviation = true`, `deviation_kind = "out_of_sequence"`, and `current_head_sequence_index = None`; dispatcher treats that report as deviation/cancellation input rather than as ordinary active-path progress. For a single report, dispatcher processing order is entered resources first, then deviation cancellation if `report.deviation == true`, then tail-vacated resources.
- Phase 3 is the only normal consumer of these reports. It drains the `SimulationController` same-transaction local progress buffer in order and calls `PathDispatcher.on_controller_progress(report)` for each one. Within that same drain, each route head-advance callback compares its single reported block advance with the current next waypoint; if that callback consumes a waypoint, the following report in the local buffer is what may discover and test the next waypoint. After local progress reports have been consumed and any movement-derived deviation cancellation from them has already run, if an active path still exists for that train, `SimulationController` runs the post-physics usable-authority stop check against the controller's current state and, on success, calls `PathDispatcher.try_complete_active_path(train_id)`; timestamps for that transition (status timestamp, route-side `finished_at`, notification `event_time`) are sampled by the writer at the write site per **Time sampling** under the **Units contract**. Explicit latched teardown such as `phase_latches.path_cancel_request` or `phase_latches.power_off` is consumed only after that normal completion chance.
- The controller report carries `deviation_kind` as a structured diagnostic for the dispatcher / route callback chain, but v1 route progression does not branch on it. Once the active path has been cancelled in Phase 3, the next eligible Phase 1 always returns to the ordinary covered-task index advance plus `_find_next_task_target(train_id)` flow from the train's current physical position; already-covered pass-through handling and stop handling follow the normal task-kind rules.
- When physical movement crosses multiple resource boundaries within one simulation tick, `TrainPhysics` must fire multiple sequential `TrainController.on_physics_updated(span_update)` calls — one per resource boundary crossed, in physical traversal order — rather than batching them into a single multi-resource report. `TrainPhysics` computes each incremental `span_update` up to the next boundary, calls `TrainController.on_physics_updated(span_update)` for that boundary, collects that step's returned report into the ordered progress list returned to `SimulationController`, then computes the next boundary update and repeats. The boundary `event_time` on each returned `ControllerProgressReport` is sampled by `TrainController.on_physics_updated(...)` itself via `time.time()` at the write site (per **Time sampling** under the **Units contract**); `TrainPhysics` does not pass a timestamp in. After the last boundary in that tick, or on a tick with no boundary crossing, `TrainPhysics` must still emit one final callback for that tick. When no resource boundary was crossed, that final update carries `added_tiles=[]` and `removed_tiles=[]`; when nothing changed physically, it may be an explicit no-change callback. This guarantees that Phase 3 always runs, that latches such as `phase_latches.power_off` have a deterministic consume point, and that downstream side effects (lock consumption, tail-vacate release, route head-advance callbacks, switch state notifications) are later committed in the same physical order as the local progress reports. Within any single `TrainController.on_physics_updated(span_update)` call, `entered_resources` and `tail_vacated_resources` therefore typically carry one entry each at most; if a single call legitimately needs to carry more (for example simultaneous head entry and tail vacate at the same boundary), events within each list must still be ordered by physical traversal / vacate order, and dispatcher still processes the entered list before the vacated list.
- Entry ownership is resource-typed and routed entirely through `ResourceCoordinator.on_physical_entry(resource_type, resource_id, train_id, path_id)`. The coordinator routes to `BlockManager.occupy_blocks([block_id], train_id)` for blocks (the only normal runtime path that writes `Block.occupied_by`) and to `SwitchManager.on_physical_entry(switch_id, train_id, path_id)` for switches. `SwitchManager.on_physical_entry(...)` owns the clean-entry write of `Switch.occupied_by = train_id`, the main-lock consumption, and the per-neighbour conversion of flank locks sourced from that main switch into train-owned `train_protection_claims`. Conflict cases (another train already occupies the switch, disabled-resource entry) are reported through the **Fatal physical-entry conflict procedure** by the manager itself; dispatcher does not detect or repair conflicts. `PathDispatcher.on_controller_progress(report)` does not branch on `resource_type` for entry handoff.
- Dispatcher progress should update `Path.current_resource_index` using the reported path-step `sequence_index`, not by searching for the first matching raw `resource_id`. `Path.current_resource_index` is head-based progress only; it advances when the train head enters a new resource and does not wait for the later tail-based release of earlier resources.
- A live path should remain `ACTIVE` after creation, through intermediate resources, and after entering the final block/resource. Entering the terminal resource should not change lifecycle state by itself.
- Only Phase 3 may attempt dispatcher path completion. After local progress reports have been consumed and any movement-derived deviation handling from those reports has already run, if an active path still exists for that train, `SimulationController` runs the post-physics usable-authority stop check against the controller's current state. That check is the predicate defined in step `8df5` of the **Active-path completion procedure**. If it is true, Phase 3 calls `PathDispatcher.try_complete_active_path(train_id)`; the writer samples `time.time()` at the write site for any `Path.last_status_updated_time`, route-side `finished_at`, or notification `event_time` it records (see **Time sampling** under the **Units contract**). `PathDispatcher.try_complete_active_path(...)` still owns the path-level acceptance check: the path completes only when the active `Path.authority_end_block_id == Path.requested_destination_block_id` and the terminal authority block entry's computed block-relative traversal direction equals `Path.requested_destination_direction`; otherwise the path remains live and route-side extension/retry logic continues. The single canonical depart-acceptance signal is `controller.state == RUNNING_MOVING`, set by any canonical transition into that state listed in the Controller state machine table (either a successful `TrainController.depart()` call or the reactive speed-based evaluation observing motion under live authority). Manual driving input may command motion under live authority before Phase 1's `depart()` call lands; ATC still protects the train. The reactive transition into `RUNNING_MOVING` is treated as equally legitimate to depart-acceptance: stop-completion eligibility, `ato.running` setting (when `control_mode == "ato"` and `received_path_plan is not None`), and other readers all key on `state == RUNNING_MOVING` regardless of which transition fired. Head-entry route progress, including `task_kind == "waypoint"` consumption through `RouteExecutor.handle_train_advanced(...)`, is not state-gated. Explicit latched admin teardown such as `phase_latches.path_cancel_request` and `phase_latches.power_off` is consumed only after this normal completion chance.
- Raw `atc_limit == 0` is not enough for stop completion. No-cab, no-authority, EB, obstruction/conflict, wrong-direction cab, and truncated best-effort authority are not stop completion, even if the distance-0 ATC limit is zero.
- For a stop waypoint whose live authority already reaches its requested target block and direction, a post-physics controller stop at the safety-margin-adjusted usable authority stop completes the path normally. The head may be short of the physical requested block when the safety margin/ATC boundary requires that; ATC remains the higher-priority rule and there is no "go back and try again" prompt for a within-block or before-block safety-margin stop.
- EB activation records `phase_latches.path_cancel_request` with `initiator = "eb"` when a live path exists, and that request is committed by the same train's Phase 3 consume pass through `PathDispatcher.cancel_path(...)`. While EB is latched, the post-physics usable-authority stop check must fail; after EB release any route continuation uses a fresh path request.
- Controller-reported deviation produces `path_cancellation` with `initiator = "deviation"`; the structural distinction between wrong-resource (`"out_of_sequence"`) and beyond-authorized-target (`"beyond_authorized_target"`) flows on the event payload's `deviation_kind` field defined in the **Cancellation** subsection. Cancellation wins over any same-tick completion attempt. Recovery follows the canonical recovery table; both deviation flavors share the same recovery shell. A `task_kind == "waypoint"` target the train has entered, passed, or later covers counts as served and does not produce a separate overshot-waypoint deviation.
- **Movement-derived deviation cancels inline, not via `phase_latches.path_cancel_request`.** When `PathDispatcher.on_controller_progress(report)` observes `report.deviation == true` during the same-transaction Phase-3 local-progress drain, it commits the cancellation immediately by calling `PathDispatcher.cancel_path(path_id, initiator="deviation", ...)` from inside the drain — even while the train is still rolling. This is the only carve-out from the "Phase 3 must not call `PathDispatcher.cancel_path(...)` against a moving train" rule in the **Latch Table** preamble (the train's own ATC and EB protect the moving train under the no-authority empty payload after the inline cancel clears `Path.status`). The original `deviation_kind` value is preserved on the resulting `path_cancellation` notification payload for diagnostics. All other cancellation sources — operator cancel, route abort, EB activation, power-off, route deactivate, route reconciliation — route through the `phase_latches.path_cancel_request` latch and are committed by Phase 3 step (c) only after `TrainController.is_stopped() == True` per the Latch Table gating rule. See the **Physical progress / deviation procedure** step `389a` for the canonical ordering.
- A best-effort truncated path must not complete just because the train has stopped at the current authority boundary while the current authorized target is still short of the requested target. In that case the same path remains `ACTIVE`, the controller stays in `RUNNING_MOVING` (stopped under zero ATC clearance against the still-live authority), and `RouteExecutor` should keep trying `PathDispatcher.extend_path(...)` on that same `path_id`.
- Completed paths release not-yet-entered block reservations AND not-yet-entered switch / flank locks via the single coordinator entry `ResourceCoordinator.release_path_resources(path_id, block_ids, completed=True)`, which composes `BlockManager.release_path_block_reservations(..., completed=True)` and `SwitchManager.release_path_locks(path_id)` per the **Active-path completion procedure** step `09b0`. Already-entered block reservations were consumed on head entry; already-entered switch locks were converted into train-owned physical occupancy / protection on entry and are not released here. The block-reservation release may force-clear terminal `CAUTION` only for matching still-reserved owned blocks, but it must not force-clear any physical `OCCUPIED` block early. The retained record may remain in `paths_by_id` for history, but physical release of a switch or block still under the train resolves from the resource itself. When a later tail-vacate resource event arrives through `PathDispatcher.on_controller_progress(report)`, it clears `Switch.occupied_by` / block occupancy and any train-owned switch protection through the resource-specific release path. `RouteExecutor` treats the dispatcher callback as authoritative completion and does not re-check safety-margin projection itself.
- When creating or extending a path, resolve and store the requested target contract on the dispatcher-owned `Path` record first, then update `Path.path_id` and `Path.resource_sequence` on that same record. `Path.authority_end_block_id` is a derived read of `resource_sequence[-1].resource_id` and updates automatically. The controller's `received_path_plan` property reads these live on the next access; there is no separate controller write step:
  - if the live authority already reaches the requested target, the derived `authority_end_block_id == Path.requested_destination_block_id` and the terminal block entry's computed block-relative traversal direction equals `Path.requested_destination_direction`
  - if the live authority is still truncated, the derived `authority_end_block_id` is the current temporary end of `resource_sequence`; the requested target fields remain on the `Path` record only
- Drive resource release from controller-reported tail-vacate observations through the single coordinator entry `ResourceCoordinator.release_tail_vacated(resource_type, resource_id, train_id, direction)`. The coordinator routes blocks to `BlockManager.on_block_tail_vacated(block_id, train_id, direction)` (`OCCUPIED -> CAUTION -> FREE` stays a single-manager state machine) and switches to `SwitchManager.on_switch_tail_vacated(switch_id, train_id)`, which performs the `train_id == Switch.occupied_by` ordering check, clears `Switch.occupied_by`, and clears per-neighbour `train_protection_claims` sourced from that switch via `Switch.release_train_protection_from(...)`. `direction` is required for blocks and ignored for switches; `PathDispatcher.on_controller_progress(report)` does not branch on `resource_type` for tail-vacate handoff. Manual/admin reservation cleanup uses `BlockManager.release_path_block_reservations(...)` (the routine entry point) and never bypasses the coordinator for live tail-vacate.

**Path extension**

- The controller has no lookahead cache to invalidate (lookahead is computed live each read; see the lookahead section). Path updates therefore have no per-controller invalidation step.
- **Live-resource edit rule.** Operator/admin code must reject any static-config edit to a block or switch field while that resource is in use — i.e. when the block is physically occupied (`block.occupied_by is not None`), holds a path reservation (`block.reserved_by_path is not None`), is in `CAUTION` (`block.caution is not None`), or appears in any live (`status == ACTIVE`) path's `resource_sequence`. The covered fields include `Block.allowed_travel_directions`, `Block.length_cm`, `Block.speed_limit_kmh`, `Block.ordered_tiles`, `Block.disabled`, and the analogous switch-side static fields, plus geometry mutations routed through `BlockGeometryManager`. The admin handler returns failure with a diagnostic; it does not mutate the field, does not cancel the path, and does not clear the reservation. To change a live-resource field, the operator must first stop the train and cancel the holding path through the normal `phase_latches.path_cancel_request` workflow, then retry the edit. This rule supersedes any prose that suggests "the edit takes effect on the next reservation" — v1 does not accept the edit while the resource is in use.
- Truncated best-effort authority where the train physically stops at the temporary boundary while no resolved target is armed (the one-tick gap between task-completion and the next Phase 1 target arm) is permissible: the controller stays in `RUNNING_MOVING` against the still-live truncated authority with zero ATC clearance, and the next Phase 1 may extend authority once the next target resolves.
- Keep forward-only extension. **`RouteExecutor` must call `PathDispatcher.extend_path(...)` only with the same `(requested_destination_block_id, requested_destination_direction)` pair as the currently armed `RouteRun.task_runs[walk_position].resolved_target`, where `walk_position` is the index returned by the latest `_find_next_task_target(train_id)` call for the live planning chain.** Any other target is a route-side invariant violation and must be expressed via cancel-and-replan, never via extend with a different requested target.
- When the path model switches to `resource_sequence`, append new tiles and new resources while skipping duplicated connection/start entries.
- Reject any extension that would cause a resource to appear twice in the combined path.
- `PathDispatcher.extend_path(...)` should take the same argument contract as `create_path(...)`, except that it identifies the existing live path by `path_id`: `path_id`, `requested_destination_block_id`, `requested_destination_direction`, and `acquisition_mode`. The live path identified by `path_id` is the fixed already-acquired prefix; `extend_path(...)` grows that existing path forward from its current authority end toward the caller-supplied requested target for this extend attempt. Dispatcher does not run a separate shared-walk prefix-compatibility test. If the requested extension cannot continue forward from the existing live path without revisiting an already-held resource or otherwise violating the ordinary path rules, `extend_path(...)` fails and leaves the existing path unchanged.
- The shared request contract between `extend_path(...)` and `create_path(...)` is the same, but `extend_path(...)` adds extra constraints: it requires a live `path_id`, and the newly appended suffix must continue forward from that live path's current authority-end edge in the same travel direction the existing prefix was built in. The caller-supplied `requested_destination_direction` applies only to the new terminal block `requested_destination_block_id`; it is not a license to reverse at the current authority end. A `requested_destination_direction` that would require the train to reverse 180 degrees at the current authority end (for example, the requested new terminal block lies behind the current authority-end edge on the existing prefix's travel frame, or reaching it would require exiting the authority-end block backward out of its current `exit_edge`) is invalid for `extend_path(...)` and must be rejected with `success = False`, `failure_kind = invalid_reverse`, and a diagnostic `reason` such as `"extend would reverse at authority end"`. The existing live path must remain unchanged in that rejection. Callers that actually need the train to turn back at the current terminal must cancel the existing path and issue a fresh `create_path(...)` from the train's current span instead.
- `PathDispatcher.extend_path(...)` must return `success=False` with `failure_kind = missing_or_inactive_path` and a required `reason` when `path_id` does not exist or when the referenced path is not currently `ACTIVE`.
- In `all_or_nothing` mode, `extend_path(...)` should either acquire the full requested suffix to `requested_destination_block_id` or leave the existing path unchanged. Any outcome that cannot reach the requested target is `success=False`; use `failure_kind = blocked_before_target` when the suffix exists but cannot be fully acquired because of live occupancy/reservation/lock conflict, and `failure_kind = no_viable_path` when no legal suffix exists.
- In `best_effort` mode, `extend_path(...)` should keep the same `path_id` and append the furthest forward acquirable suffix it can add to the current path. The `resource_sequence` therefore grows in place on the same live path instead of creating a new path. When at least one resource is appended, update the stored requested target fields on that same `Path` to the caller-supplied contract for that attempt, even if the live authority remains truncated short of it, and return `result_kind = truncated_grew` or `reached_requested_target` as appropriate. The same waypoint-target exclusion as on `create_path(...)` applies to the appended suffix: the live authority's new terminal block after the extend must not be the resolved target block of a `task_kind == "waypoint"` task on the requesting `RouteRun`'s current directed walk. If the block-terminated truncation point would land on a waypoint target block, dispatcher must extend the storable suffix at least one block past it before committing the extend; if no further forward block beyond the waypoint target can be acquired on this attempt, the existing path is left unchanged and the call fails with `failure_kind = blocked_before_target` and a `reason` such as `"cannot truncate authority at a waypoint target"`. If no resource can be appended but the dispatcher can prove the existing path is still a legal prefix to the requested target and the next resource is blocked only by live occupancy/reservation/lock conflict, return `success=True` with `result_kind = blocked_no_growth`, update the existing path's stored requested target fields to the caller-supplied contract for that attempt, leave `resource_sequence` unchanged (the derived `authority_end_block_id` is therefore unchanged too), and let `RouteExecutor` retry later. The controller's `received_path_plan` property continues to return the same `path_id`, `resource_sequence`, and `authority_end_block_id` projection on its next read; refreshed requested-target fields remain dispatcher-internal. If no resource can be appended because no legal forward suffix exists, return `success=False` with `failure_kind = no_viable_path` and leave the existing path unchanged.
- While the path is still truncated short of the caller's current requested target, the stored `resource_sequence` terminates on the current last acquired block; the derived `authority_end_block_id` reflects that terminal automatically.
- Every successful `extend_path(...)` updates the dispatcher's `Path` record in place. `truncated_grew` / `reached_requested_target` carry the grown `resource_sequence`; `blocked_no_growth` carries the unchanged geometry but updates the requested-target fields. The controller's `received_path_plan` property reads these updates live on the next access. When the live authority finally reaches the requested target, the derived `authority_end_block_id` equals `Path.requested_destination_block_id`.
- In `best_effort` mode, a no-growth extend result is therefore branchable without parsing `reason`: `success=True/result_kind=blocked_no_growth` means "valid prefix, temporarily blocked; keep the live path and retry later," while `success=False/failure_kind=no_viable_path` or `invalid_reverse` means "the existing live path cannot continue to this requested target; RouteExecutor must latch cancellation before any fresh create-path attempt."

**Cancellation**

- `PathDispatcher.cancel_path(path_id, initiator=None, reason=None)` is the single canonical cancellation entry point in v1. `initiator` is a free-form label that flows directly into the `path_cancellation` notification payload for logs/UI; it must not be used as a condition by any planning or routing logic. `reason` is plain-text diagnostic context for logs/UI only and likewise must not be used for condition branching. Recovery branching is driven by controller state, runtime latches (`eb.active`, `phase_latches.power_off`, `received_path_plan`), current span coverage, and the normal waypoint-kind rules.
- Release owned blocks through `BlockManager.release_path_block_reservations(...)` instead of direct `block.release()` calls. In the desired v1 model, cancellation release clears future reservation ownership only; it never clears physical occupancy.
- Path cancellation or revocation effects are owned entirely by `PathDispatcher`, and the cancellation commit happens only in Phase 3. `RouteExecutor` or `TrainController` may request cancellation only by recording controller-owned Phase-3 handoff state such as `phase_latches.path_cancel_request`; they must not call `PathDispatcher.cancel_path(...)`, clear authority, or release resources directly from Phase 1 or Phase 2. If Phase 1 route logic decides that the current live path must be revoked, it records or refreshes that cancel request and then stops planning for that train for that tick; later eligible Phase 1 passes follow the same latch-only rule while the incompatible live path still exists. Only after the same train's later Phase 3 consumes that request, `PathDispatcher.cancel_path(...)` completes, and the ordinary cancellation callback clears route-side live-path correlation may a later eligible Phase 1 resume ordinary create/extend planning. When Phase 3 later commits the cancellation through `PathDispatcher.cancel_path(...)`, dispatcher transitions `Path.status` to `CANCELLED`, which by definition makes the controller's `received_path_plan` property return `None` on its next read.
- Power-off uses this same dispatcher cancellation workflow through the inclusive-latch fan-out: `TrainController.commands.power_off_cmd()` is a stopped-only controller command that validates acceptance during the tick-entry command drain inside `TrainController.tick(...)` and calls `TrainController._apply_power_off_request()`, which sets `phase_latches.power_off = True` and (when a live path exists at write time) writes the inclusive `phase_latches.path_cancel_request` with `initiator = "power_off"` per the **Writer-helper rule**; it does not run route/dispatcher teardown inline. On the same train's later eligible Phase 3, step (c) (the `phase_latches.path_cancel_request` consumer) commits the dispatcher cancel through `PathDispatcher.cancel_path(...)`, and the ordinary cancellation callback path runs (including `RouteExecutor.handle_path_cancellation(...)`). Step (e) (the `phase_latches.power_off` consumer) then calls `RouteExecutor.remove_train_route_run(train_id)`, and only after route/dispatcher teardown performs controller-local OFF cleanup such as clearing cab, EB latch, `phase_latches.power_off`, and `ato.running`. The power-off consumer never calls `PathDispatcher.cancel_path(...)`; if no live path was present at `_apply_power_off_request()` time, step (c) skips the dispatcher cancel mutation, still clears `phase_latches.path_cancel_request` on this same Phase 3 pass, and emits one `NotificationCenter` diagnostic such as `latched cancel for <train_id> initiator=<initiator> skipped: no active path` per the **Phase-3 latched-cancel consumption: stopped-train gating and no-active-path skip** rule in the Core Runtime Loop section; step (e) then proceeds straight to `RouteExecutor.remove_train_route_run(...)`.
- On the `ACTIVE -> CANCELLED` transition, `PathDispatcher.cancel_path(...)` runs synchronously and must finish lower-layer teardown before it makes the path externally non-active. Cancellation uses the same canonical terminal-teardown order as completion: release not-yet-entered block reservation ownership, release not-yet-entered switch/flank locks, then transition `Path.status` to `CANCELLED` (which by definition removes that path from `active_path_id_by_train(train_id)` and makes the controller's `received_path_plan` property return `None` on its next read). Only after that ordered teardown is complete may `cancel_path(...)` return success and deliver the route-side cancellation callback. Cancellation clears future reservation/authority only; it never clears `Block.occupied_by`, `Block.caution`, `Switch.occupied_by`, or train-owned switch protection. A block reservation may be cleared even when the train still physically occupies that block because reservation ownership and physical occupancy are independent, but in normal flow same-train reservations for entered blocks have already been consumed on head entry. A same-train new path is allowed once the old path is no longer `ACTIVE`, subject to ordinary live resource conflicts and train-owned physical protection.
- Future switch/flank release for both `PathDispatcher.cancel_path(...)` and `PathDispatcher.try_complete_active_path(...)` is routed through `ResourceCoordinator.release_path_resources(path_id, block_ids, completed=...)`, which composes `SwitchManager.release_path_locks(path_id)` per the **ResourceCoordinator** canonical home. `SwitchManager.release_path_locks(path_id)` iterates every switch owned by `path_id` and removes both main-usage claims (`(path_id, source_switch_id=None)`) and flank claims (`(path_id, source_switch_id=<main switch id>)`); the release is idempotent and is a no-op for claims already consumed into `Switch.occupied_by` / `train_protection_claims` by head entry. `PathDispatcher` does not iterate `Path.resource_sequence` to release switches itself, does not retain a separate path-level flank list, and does not branch on `Path.current_resource_index` for release. `SwitchManager.release_path_locks(...)` must not clear `Switch.occupied_by` or `Switch.train_protection_claims`; those remain physical/train-owned and are released only by later controller-reported switch tail-vacate.
- Reservation / physical state ownership in v1 should be read literally:
  - dispatcher-owned future reservation state: `Block.reserved_by_path`, `Block.reserved_for_train`, `Block.reserved_direction`, `Switch.locks`, flank-protection lock ownership for resources the train has not entered yet
  - block physical state owned by `BlockManager` and mutated only through `BlockManager` entry/tail-vacate APIs invoked by `PathDispatcher` on controller-reported observations: `Block.occupied_by`, `Block.caution`
  - dispatcher-mediated switch physical state, written by `PathDispatcher` on controller-reported resource-entry / tail-vacate observations rather than directly by `TrainPhysics`: `Switch.occupied_by` and `Switch.train_protection_claims`
  - a block or switch has at most one physical `occupied_by` train at a time (single-train physical ownership). A single train may hold multiple path records layered over that physical ownership; path membership is tracked separately by `PathDispatcher` on `Path` records, not by duplicating `occupied_by` per path.
  - cancellation / completion release clears only future block reservations and future switch locks that have not already been consumed by head entry
  - only controller-reported physical entry / tail-vacate observations may clear or set `BlockManager`-owned block physical state or dispatcher-mediated switch physical state
  - once a resource is physically occupied, later tail-vacate clears physical occupancy and train-owned protection rather than path-owned residue
- After cancellation transitions the dispatcher-owned path out of `ACTIVE`, the controller follows the no-authority braking path defined in step `826a` of the **Controller tick order**: the canonical lookahead becomes the no-authority empty payload, ATC sees overspeed at distance 0 (when the train is still rolling), and EB is engaged per the **canonical EB activation effects**. The operator clears EB through `eb.release()` once stopped, which transitions the controller to `READY`. Physics keeps integrating live network state during the EB brake; cancellation does not unlock a physically occupied switch.
- After cancelling a live path, the runtime should deliver the canonical cancellation context through `SimulationController.handle_path_cancellation(train_id, path_id, reason=None)` (which delegates to `RouteExecutor.handle_path_cancellation(...)`) only after `PathDispatcher.cancel_path(...)` has finished its own lower-layer mutation for that train. The diagnostic `initiator` and original `deviation_kind` (when the cancellation was deviation-driven) are surfaced only on the `path_cancellation` notification; they do not cross the dispatcher/route callback boundary. This notification is mandatory, but the free-form `reason` string is informational only. `RouteExecutor` should inspect whether that cancelled path actually affects its current waypoint / assigned route state, must not treat the old path as finished, and must defer all next-target selection / fresh authority assignment until the next eligible Phase 1 after the stopped no-authority or post-EB recovery point.
- **`path_cancellation` notification.** This is the canonical structured event surface for cancellation diagnostics. `PathDispatcher.cancel_path(...)` emits one `path_cancellation` notification through `NotificationCenter` as the last step of the canonical cancellation flow, after the dispatcher mutation has committed and the route-side `RouteExecutor.handle_path_cancellation(...)` callback has been invoked. UI/log consumers use this event as the canonical surface for cancellation diagnostics. The notification carries:
  - `notification_id` — assigned by `NotificationCenter` per the canonical notification rule
  - `event_time` — system-time Unix seconds. The writer reuses the single `time.time()` value it sampled at the top of `cancel_path(...)` (per the **`last_status_updated_time`** rule above and **Time sampling** under the **Units contract**). The same sampled value is stored into `Path.last_status_updated_time` for the `ACTIVE -> CANCELLED` transition.
  - `source` — `"PathDispatcher"`
  - `severity` — derived from the `initiator` actually committed by Phase 3: `"info"` for `"operator_cancelled"` / `"power_off"` / `"revoked"`; `"warning"` for `"deviation"`; `"error"` for `"eb"`; `"info"` when `initiator` is `None` or any other string. Because `initiator` is purely diagnostic (most recent same-tick payload wins), the recorded severity may not match the originating writer's intent in race cases.
  - `train_id`, `path_id`
  - `payload`:
    - `initiator: str` — required; free-form label populated by the writer (`"eb"`, `"operator_cancelled"`, `"power_off"`, `"deviation"`, `"revoked"`, or any other writer-supplied string for new origins)
    - `deviation_kind: Optional["out_of_sequence" | "beyond_authorized_target"]` — required when `initiator == "deviation"`; `None` otherwise
    - `reason: Optional[str]` — plain-text diagnostic context
**Path invariants**

- In the desired model, old `PENDING` and `SETTING` disappear entirely because acquisition is synchronous inside `create_path()`, and old `SET`, old `ACTIVE`, and old `CLEARING` collapse into a single live dispatcher state: `ACTIVE`. Whether the train has started moving, entered the terminal resource, or is stopped at the stop point should be represented by controller state, `current_resource_index`, and explicit completion predicates, not by separate path lifecycle values.
- `resource_sequence` replaces both `block_sequence` and `switch_positions`, so existing callers iterating those fields need updating.
- `current_resource_index` should track `sequence_index`, not the first occurrence of a raw resource ID.
- For v1, repeated resources in a single path are invalid and should be rejected during both `create_path()` and `extend_path()`.
- Switch resources contribute `0 cm` to forward-distance accumulation. Any helper that sums per-resource physical length should therefore add `0` for `resource_type == "switch"` and continue the cumulative axis across the surrounding block geometry.
- `FLANK_PROTECTION_DISTANCE_CM` should be a global config, not a per-path setting.
- In v1, switch locks are a multi-owner compatibility set: multiple paths may hold compatible same-state lock claims on the same switch, but conflicting required states are not allowed and physical occupancy stays single-owner.
- `PathDispatcher` does not run a behind-train release sweep; block release is fully owned by `BlockManager.on_block_tail_vacated()` triggered from physics.
