## Design Direction

**Ownership split**

- `TrainController` owns live operational state: ATC/ATO/manual mode, handle position, future manual `power_percent`-mode inputs, and the canonical live lookahead data series. "Target speed" and "speed-limit reason" MUST NOT be stored as standalone fields anywhere; they are the value and reason metadata at position 0 of the lookahead series.
- `TrainController` also owns live power/cab state: the canonical `state` machine (which includes `OFF` for power off), active cab selection, and any live direction-selection inputs tied to that active cab. The convenience read `power_on` is derived from `state != "OFF"`. After the runtime 1:1 `Train` <-> `TrainController` pairing is established, those values are not re-synced from `Train` on every tick.
- `Train` owns persistent/configuration state only: identity, consist, schedule/route assignment, and non-live train configuration. Live position/span, live speed, ATO/ATC/path-runtime state, power/cab state, and operational state are not mirrored on `Train`. Initial live placement comes through `SimulationController.add_train(...)`: it constructs the `Train`, creates or obtains the `TrainController`, derives the initial span from the placement payload, and writes the initial `TrainController.physics_sync.current_span` before the first simulation tick. The frontend/API input shape (`id`, optional `position: {x, y}`, `direction`, `max_speed`, `length`, and other train-configuration fields) is unchanged. Bootstrap data must enter through `add_train(...)` or explicit controller commands.
- The new manual model uses handle plus power-percentage; there is no `manual_target_speed` field.
- Manual control has two controller-owned submodes:
  - `simulation`: user drives with handle notches; the handle command flows to `TrainPhysics`, which integrates it into speed change over time.
  - `power_percent`: user drives with percentage power; the controller passes raw percentage power to `TrainPhysics`, which immediately converts it via train/profile calibration data such as `SpeedProfile.power_speed_curve` into both track voltage and the calibrated current speed when no braking override is active.
- `TrainPhysics` and `BlockPowerController` MUST NOT decide manual-mode policy. They execute whichever command the controller produces and perform command-to-speed conversion and voltage emission.
- Percentage-power mapping data lives in `SpeedProfile.power_speed_curve` as part of train calibration and is read by physics.

## Layered Architecture

**Layered responsibilities**

- `PathDispatcher` executes the route plan by acquiring future blocks, locking future switches, and managing movement authority. It plans for the controller by providing the dispatcher-owned authority geometry and current authority-end block; the controller projects the actual braking target from that boundary using its safety-margin policy.
- `PathDispatcher` is the sole owner of dispatcher path records. `TrainController.path_projection.received_path_plan` is a read-only property that returns the dispatcher's current movement-authority projection for that train; it is not controller-owned state, has no setter, and does not store its own copy.
- `PathDispatcher` keeps each path record keyed by `path_id` in a dispatcher-owned registry such as `paths_by_id[path_id]`.
- `PathDispatcher` exposes a derived read `active_path_id_by_train(train_id) -> Optional[str]` that scans `paths_by_id` for the one path whose `train_id` matches and `status == ACTIVE`. There is no separately stored registry to maintain; the index is a projection of `Path.status`. Each train has at most one `ACTIVE` path at a time, enforced by `PathDispatcher.create_path(...)` rejecting same-train requests when one already exists.
- Cancelled or completed paths may remain in `paths_by_id[path_id]` for history; they are not active authority (their `Path.status` is no longer `ACTIVE`, so `active_path_id_by_train(train_id)` skips them and the controller's `received_path_plan` property returns `None` or the next active path). In v1 there is no path-owned deferred-release flag. `PathDispatcher` owns only future authority resources: blocks and switches the train has not yet entered. When the train head enters a resource, that future reservation/lock is consumed and physical occupancy becomes resource-local physical state through dispatcher-mediated writes. Cancellation and completion release only not-yet-entered dispatcher-owned reservations and locks and transition `Path.status` synchronously; the active-path read switches to `None` (or to a different `ACTIVE` path) by definition because of that status transition. Physical train motion after completion/cancellation is not blocked by retained path rows: `TrainPhysics` keeps moving the train according to live network geometry/state, and physical `occupied_by` state is cleared only by later controller-reported tail-vacate release events. `PathDispatcher.create_path(...)` must reject a same-train request as its first step when that train already has an `ACTIVE` path, returning `success=False` with `failure_kind = train_already_has_active_path` per the **`create_path()` / `extend_path()` return contract**, and with no path ID allocation, switch acquisition, block reservation, controller mutation, or switch-state mutation. Once the old path is no longer `ACTIVE`, later creation is governed only by ordinary live resource conflicts.
- Controller progress reports identify the moving train by `train_id` only; they do not carry a caller-supplied `path_id`. `TrainController` owns the canonical stored span and speed. `TrainPhysics.tick()` computes the next physical span/speed plus the tile-level delta for that movement, then calls `TrainController.on_physics_updated(span_update)` once per crossed resource boundary and once more for the final no-boundary callback for that tick. `span_update` carries the new `TrainSpan`, the new `current_speed_kmh`, ordered `added_tiles`, ordered `removed_tiles`, and the traversal frame used for each added/removed tile. `TrainController.on_physics_updated(span_update)` atomically applies the new span/speed to controller-owned storage, runs the **Reactive speed-based state evaluation** synchronously (so any READY↔RUNNING_MOVING transition fires in the same tick that physics produced the speed change), interprets the tile delta against `TrainController.path_projection.received_path_plan.resource_sequence` when authority exists plus canonical lookahead, and returns one ordered `ControllerProgressReport` to `SimulationController` for that train's same-transaction progress buffer. Phase 3 is the only place that drains that local buffer by calling `PathDispatcher.on_controller_progress(report)`. The buffer is not retained controller state and is empty/discarded before the per-train transaction ends. `PathDispatcher` resolves any active path from `active_path_id_by_train(train_id)`, decides whether reported resources belong to that path, and then commits active progress. After authority has been cleared, later physical release must not depend on a retained path row surviving: block release is driven by `block_id` plus `direction` through `BlockManager`, and switch release is driven by the vacated switch resource's train-owned physical occupancy/protection state.
- `TrainController` executes the path plan by calculating ATC safety limits, ATO/manual commands, and an active handle or future power command. It plans for physics by producing the active control command for the current mode.
- `TrainPhysics` is an executor only; it MUST NOT decide manual-mode policy.
- `PathDispatcher` updates the `Path` record in its own registry whenever a path is created or extended. The controller's `received_path_plan` property reads a movement-authority projection of that record live, so the controller automatically observes any update on the next read. The controller brakes to the current authority boundary using its canonical safety margin and derives speed restrictions from lookahead over the network and dispatcher authority structure, not from per-block speed limits supplied as separate data. The requested target (`requested_destination_block_id`, `requested_destination_direction`) is stored on the dispatcher-owned `Path` record and is not included in the controller projection. Dispatcher completion enforces the requested-target rule internally: the active path completes only when the live authority end block equals `Path.requested_destination_block_id` and the terminal authority traversal direction equals `Path.requested_destination_direction`. The controller reads only the canonical **received_path_plan schema**; only stop-completion in `PathDispatcher.try_complete_active_path(...)` branches on the requested-target fields.
- The dispatcher-owned path record is the single source of truth for controller authority while it is active. Cancelling or replacing a path in `PathDispatcher` is sufficient to give the controller a clean slate.
