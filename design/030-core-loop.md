## Core Runtime Loop

**Phase structure**

### Per-train tick transaction

1. Advance `simulation_time`.
2. `RouteExecutor` owns the runnable-train ordering for the tick. `SimulationController.update(...)` advances time, calls `RouteExecutor.update(delta_seconds)` to refresh route-managed scheduling state, then passes the candidate train IDs to `RouteExecutor.order_runnable_trains(...)` and consumes the ordered list it returns. Route-managed trains are ordered by descending current shared `Route.priority`; priority values are integers where `9` is highest, `0` is lowest, and default priority is `5`. Trains with no current route-managed Phase 1 work, including one-off/manual trains, participate in the same ordering at effective priority `5`; a train that is powered off at the start of its transaction uses the same effective priority it would use when powered but skips Phase 1 because route planning cannot run before the command drain has had a chance to accept `TrainController.commands.power_on_cmd()`. Ties use stable existing iteration order. `SimulationController` still owns executing each train transaction in that returned order. During each train transaction, `SimulationController.update(...)` calls `RouteExecutor.tick_train_phase1(train_id, delta_seconds)` as the entire Phase 1 route-executor tick for that train before it calls `SimulationController._update_train(train, delta_seconds)`.
3. For each train in that order, run one full three-phase transaction to completion before starting the next train:
  - **Phase 1 - Setup (top-down planning for that train)**: `RouteExecutor` runs the canonical Planning Kernel steps `9c4f`–`66aa` defined in the **Planning Kernel** section. The full ordering and gating rules are canonical there; this list is a cross-reference, not a restatement: (`9c4f`) RouteRun (re)allocation — when the train is assigned to a `Route` with `is_active == True` but has no currently-`RUNNING` `RouteRun`, allocate a fresh `RouteRun` with `current_route_status.state = RUNNING` and continue; otherwise continue with the existing `RUNNING` run; (`5fc7`) route-deviation cleanup; (`70c3`) dwell-complete timer check (calls `TrainController.finish_dwell()`); (`c481`) helper lookup via `_find_next_task_target(train_id)` — if the projection's `task_kind == "dwell"`, skip directly to step `3a37`; (`a5c6`) covered-task index advance for already-covered `waypoint` tasks and for same-block stopped-at-destination `stop` tasks (train is stopped, no active path, current block equals the task's destination block); (`3a37`) dwell-entry transition (calls `TrainController.enter_station_dwell()`) — when this step fires, Phase 1 returns for that tick with no path creation; (`592a`) re-resolve the next target via `_find_next_task_target(train_id)` after any cursor-changing step; (`66aa`) authority acquisition via `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)`. After successful path creation, authority growth, or a successful `blocked_no_growth` target refresh, `PathDispatcher` has updated its own `Path` registry; the controller's `received_path_plan` property automatically returns that updated record on its next read. There is no separate controller write step. Phase 1 may retry or loop locally in the same tick only while it stays inside Phase-1-owned procedures such as covered-task index advance, target resolution, candidate selection, and `create_path(...)` / `extend_path(...)` acquisition-and-rollback. In v1, if shared-route reconciliation or a route/controller invariant check concludes that the current live path must be replaced, Phase 1 must not call `PathDispatcher.cancel_path(...)` directly and must not keep a hidden desired-target override attached to the still-live path. Instead it latches `phase_latches.path_cancel_request` for Phase 3, stops planning for that train for that tick, and waits for the ordinary Phase 3 cancel → callback → route deviation cleanup flow. Operator retargeting and explicit route swap take a different path entirely: they go through "abort current run + create new run" (see **Route Edit And Reconciliation**), driven by `phase_latches.route_abort` plus its inclusive cancel. After authority cancellation has committed and the train reaches the stopped state, the next eligible Phase 1 reruns ordinary covered-task index advance plus `_find_next_task_target(train_id)` from current physical progress and requests a brand-new path; for this fresh create/replan branch, eligibility uses the canonical Phase-1 eligibility predicate defined in the **Planning Kernel** section.
  - **Phase 2 - Execute (controller + physics for that train)**: `TrainController.tick(...)` begins by draining that controller's queued operator commands. That command-drain substep runs after Phase 1 has completed for the train and before any power check, ATC/ATO/manual decision, or physics movement. The controller reads `lookahead` live whenever it needs it (each read recomputes from current inputs); there is no separate "pre-physics consume" or "post-physics refresh" step. The command-drain substep may set `phase_latches.power_off`, write `phase_latches.path_cancel_request`, and immediately clear `ato.running` for accepted stopped power/cab/mode/EB commands, but it does not commit path completion or dispatcher cancellation directly. `TrainPhysics.tick(...)` then computes movement for that same train and must call `TrainController.on_physics_updated(...)` at least once for that tick. Phase 2 must not call `_find_next_task_target(train_id)`, must not read `RouteRun` task-walk state directly, and must not write any `RouteRun` field. Dwell entry, dwell exit, route-deviation cleanup, and all `RouteTaskRun` timing writes are owned by `RouteExecutor` in Phase 1 and Phase 3; the controller transitions to `RUNNING_AT_STATION` only when `RouteExecutor` calls `TrainController.enter_station_dwell()` from Phase 1, and to the `READY` state only when `RouteExecutor` calls `TrainController.finish_dwell()` from Phase 1.
  - **Phase 3 - Feedback and cleanup for that train**: `SimulationController` runs one general feedback/cleanup pass for that train. The canonical step ordering (a)–(f) is defined in the **Phase ownership in v1 is strict** bullet immediately below; this prose cross-references that list rather than restating it. Notes specific to Phase 3 behavior: each `RouteExecutor.handle_train_advanced(...)` call consumes at most one task per call as defined in the **Physical progress / deviation procedure**. If a local progress report cancels the active path, that movement-derived cancellation wins immediately, inline during step (a). Phase 3 owns `PathDispatcher.on_controller_progress(report)`, `PathDispatcher.try_complete_active_path(...)`, and `PathDispatcher.cancel_path(...)`. Dwell entry, dwell-complete timing, and route-deviation cleanup are owned by `RouteExecutor` in Phase 1 (see the Phase 1 description above); Phase 3 does not run a dwell-complete check.
4. After all trains have completed their per-train transactions, update signals from blocks once for the tick.

- The three phases are therefore interleaved per train, not as three world-wide passes. One train's Phase 1/2/3 transaction fully commits before the next train's Phase 1 begins.
- Phase ownership in v1 is strict:
  - Phase 1 owns downward resolution, all `RouteRun` mutation, and same-phase retries: route-deviation cleanup (clear `RouteRun.path_cancelled`), dwell-complete timer check (when `TrainController.ops.state == RUNNING_AT_STATION`: write `task_runs[walk_position].finished_at` — the derived `current_waypoint_index` advances with that write — and call `TrainController.finish_dwell()`), covered-task index advance (write `task_runs[i].finished_at` for skipped already-covered `waypoint` tasks, and for `stop` tasks where the train is stopped with no active path and its current block is the task's destination block), dwell-entry transition (call `TrainController.enter_station_dwell()`), route reconciliation, next-target resolution via `_find_next_task_target(train_id)`, `create_path(...)`, `extend_path(...)`, and ordinary departure decisions that do not require cross-phase cleanup. Every Phase 1 step that needs the resolved next target must invoke `_find_next_task_target(train_id)` afresh after any cursor-changing step (deviation cleanup, dwell-complete, covered-task advance) — the helper's last result is not reused across cursor changes.
  - Phase 2 owns controller-side observation and execution for that same train: the operator-command drain at the start of `TrainController.tick(...)`, ATC/manual/ATO command generation (each consumer reads `lookahead` live as needed), physics integration, and the controller-owned span/speed update triggered by `TrainController.on_physics_updated(...)`. The **operator-command processing slot** is the first substep of `TrainController.tick(...)`; it is not a separate `SimulationController` drain method. Phase 2 does not call `_find_next_task_target(train_id)`, does not read `RouteRun` task-walk state directly, does not write any `RouteRun` field, and does not run any dwell-entry, dwell-complete, or route-deviation step.
  - Phase 3 owns commit/cleanup of dispatcher and physical state, in this canonical order: (a) same-transaction progress-report consumption from the `SimulationController` local buffer, including all movement-derived deviation handling, physical entry/tail-vacate writes, callback-by-callback route-progress checks against the current task (each `RouteExecutor.handle_train_advanced(...)` callback writes `task_runs[i].finished_at` for the consumed task); (b) normal stop-arrival/completion evaluation (`PathDispatcher.try_complete_active_path(...)` callback writes `task_runs[walk_position].finished_at` for the just-served stop); (c) explicit `phase_latches.path_cancel_request` consumption (gated by `TrainController.is_stopped() == True` per the Latch table; latch survives across ticks while the train is rolling); (d) explicit `phase_latches.route_abort` consumption (gated by `phase_latches.path_cancel_request is None` per the Latch table — i.e. the inclusive cancel has either committed earlier in this same Phase 3 pass or was never written because no live path existed at write time); (e) explicit `phase_latches.power_off` consumption (gated by `phase_latches.path_cancel_request is None` per the Latch table); (f) `phase_latches.route_deactivate` consumption (gated by `phase_latches.path_cancel_request is None` per the Latch table). Terminal route completion is not on this list: when Phase 1 detects the terminal walk, it calls `RouteExecutor.finish_route_run(train_id)` directly inside `tick_train_phase1(...)` rather than handing off through Phase 3. Latches written *during* this Phase 3 pass (e.g. by the cancellation callback in step c) are not consumed in the same pass; they wait for the next tick's Phase 1 (route-deviation cleanup) or next tick's Phase 3 (dispatcher cleanup). Phase 3 must not arm a fresh planning target, create fresh authority, run dwell entry/exit, or perform route-deviation cleanup; those wait for the next eligible Phase 1 for that train.

**Operator-command processing slot**

- Operator commands targeted at a train (`TrainController.commands.power_on_cmd()`, `TrainController.commands.set_cab(...)`, `TrainController.commands.set_mode(...)`, `TrainController.commands.set_manual_mode_type(...)`, `TrainController.commands.set_handle(...)`, `TrainController.commands.set_manual_power_percent(...)`, `TrainController.eb.activate()`, `TrainController.eb.release()`, `TrainController.commands.power_off_cmd()`) are queued onto the targeted train's `TrainController` as they arrive from the API/UI layer. They are drained by `TrainController.tick(...)` as its first substep for that train, before any controller decision. For powered-on trains this substep runs after Phase 1 has completed planning; for powered-off trains Phase 1 is skipped and this Phase-2 tick entry still runs so `TrainController.commands.power_on_cmd()` can be accepted. Operator intent is therefore reflected in the same tick's controller commands and physics step when a train is powered, while route planning after power-on waits for a later Phase 1 tick.
- Within that drain slot, queued commands run in the canonical order below so lower-urgency configuration is observed by higher-urgency commands on the same tick:
  1. `power_on_cmd()`
  2. `set_cab(...)`
  3. `set_mode(...)`
  4. `set_manual_mode_type(...)`
  5. `set_handle(...)` / `set_manual_power_percent(...)`
  6. `eb.activate()`
  7. `eb.release()`
  8. `power_off_cmd()`

  `set_mode(...)` (slot 3) always runs before `set_manual_mode_type(...)` (slot 4) because the latter requires `control_mode == "manual"` to accept.
- Each command's stopped-only / power-on / EB-not-latched / cab-selected preconditions are re-checked at the moment it is drained, against the controller state established by earlier commands in the same drain. A command that fails its preconditions is rejected (`success=False`) and does not block later commands in the same queue.
- Commands that write Phase-3 latches (`phase_latches.path_cancel_request` from operator-issued and ATC-derived EB paths, `phase_latches.route_abort` from explicit route-abort requests, `phase_latches.power_off` from `power_off_cmd()`) write those latches during this tick-entry command drain or, for ATC-derived EB activation, from later inside the same `TrainController.tick()` call; the same train's later Phase 3 consumes them in the canonical Phase-3 latch-consumption order. External API/UI/admin operations must honor this same internal workflow: they enqueue controller commands or set the controller-owned Phase-3 handoff payloads and then let the per-train phase loop commit dispatcher/route/resource mutations. They must not call `PathDispatcher.cancel_path(...)`, clear controller authority, remove route runs, or release resources inline from the request handler. `TrainController.eb.activate()` is the canonical operator-issued EB command; ATC overspeed escalation — including the no-authority overspeed branch in step `826a` where the canonical lookahead has dropped to `atc_limit = 0` because `received_path_plan` is `None` — can also raise EB from inside `TrainController.tick()`. Both paths perform the **canonical EB activation effects** defined in the **EB workflow state machine** so Phase 3 commits any resulting cancellation through the same dispatcher cancel-and-release path used by every other cancellation kind.
- API/UI command submission has a separate result from command execution. A request handler returns success once the command has been appended to the targeted controller's command queue, or once a direct Phase-3 handoff such as `phase_latches.path_cancel_request` has been written; it does not block waiting for the later tick-entry drain. The real command result is produced when `TrainController.tick(...)` drains the command: each drained command emits one `command_result` notification through the runtime `NotificationCenter` (`command_id`, command name, `train_id`, `success`, optional `reason`, and `event_time`) for UI/API consumers. If a command fails its stopped-only, power, EB, cab, or mode preconditions at drain time, that later result is `success=False` with the diagnostic reason; the original enqueue response remains an accepted/pending submission. `TrainController.commands.power_off_cmd()` is the exception to any generic EB-not-latched guard: it may be accepted with EB latched when the stopped-only shutdown precondition is satisfied.
- `TrainController.eb.release()` is also latch-based. It may clear `eb.active` only after the EB-triggered path cancellation has already committed and live authority has been cleared. The acceptance check reads its own `received_path_plan` (must be `None`) and its own `phase_latches.path_cancel_request` (must not still contain an EB payload). If either condition fails, `TrainController.eb.release()` rejects with a diagnostic command-result notification. On acceptance it transitions to the **`READY` state**. It must not call `RouteExecutor` directly and must not mutate `RouteRun` directly; route continuation/replanning is discovered by the normal Phase 1 route-deviation cleanup (which fires from `path_cancelled`, set by the EB cancellation callback) and the next eligible Phase 1 planning pass.

**Runtime notifications**

- `NotificationCenter` is the only runtime notification owner in v1. It is exposed through `SimulationController.notification_center` and is responsible for storing, sequencing, and projecting runtime notifications to frontend/API consumers. Controllers, dispatcher, route executor, and admin surfaces emit notifications by calling this class; they do not keep component-local frontend notification queues.
- Every notification carries at minimum `notification_id`, `event_time`, `source`, `kind`, `severity`, optional `train_id`, optional `path_id`, and a structured `payload`. `NotificationCenter` assigns monotonically increasing `notification_id` values in emission order and is the only component that decides retention, read/ack state, and frontend delivery mechanics such as polling, streaming, or websocket fanout.
- Command execution results are notifications with `kind = "command_result"` and payload `{command_id, command_name, success, reason}`. Path cancellation/completion diagnostics, fatal runtime failures, route-run errors, and operator-visible planning failures also flow through `NotificationCenter`; the originating component still owns the underlying state mutation, while `NotificationCenter` owns only the user-facing event record and delivery surface. Runtime warnings emitted from skipped no-op release paths and from any other component-side runtime diagnostic also flow through this same `NotificationCenter` surface as `kind = "diagnostic"` notifications; component code does not log these to a parallel sink. The canonical structured cancellation event is `path_cancellation`, defined in the **Cancellation** subsection.
- Request handlers must not read controller internals to discover later semantic command failures. They return accepted/pending for enqueue or latch writes, then frontend/API consumers observe later results through `NotificationCenter`.

**Phase 1 departure-request writes (manual + ATO)**

- For both manual and ATO modes, Phase 1 calls `TrainController.depart()` directly on the first eligible Phase 1 pass that observes live authority, regardless of whether the driver has already started rolling manually. This guarantees that route-managed manual operation also goes through the canonical depart-acceptance path; manual driver pre-depart movement is allowed (and protected by ATC) but the route-side "depart accepted, route progress can complete a stop" gate (`controller.state == RUNNING_MOVING`) is not skipped just because the train moved early. If `TrainController.depart()` rejects (e.g. EB latched, no cab in manual mode, `phase_latches.power_off` set; see the **`TrainController.depart()` canonical contract** for the full precondition list), Phase 1 may retry on the next eligible tick.

**Phase handoff rule**

- A phase may retry immediately only when every operation stays inside that same phase.
- If logic in one phase needs a later tick/pass to mutate live runtime state, it must write a per-train retained latch instead of calling across phases directly. The only v1 same-transaction Phase-2-to-Phase-3 data handoff is `ControllerProgressReport`, which uses the `SimulationController` local progress buffer described below and is not retained controller state.
- **Same-transaction commit-callback exception.** Within one train's per-tick transaction, Phase 1, 2, and 3 run sequentially and Phase 2 does not run again before the next tick. Phase 3 commit code may therefore synchronously call controller and route reaction hooks that mutate Phase-2-owned and Phase-1-owned fields, because there is no live Phase 1 or Phase 2 reader for that train left to observe a partial state. The closed list of allowed same-transaction cross-phase calls is: `PathDispatcher.try_complete_active_path(...)` calling `TrainController.on_path_complete()` and then `SimulationController.handle_path_completion(...)` (which delegates to `RouteExecutor.handle_path_completion(...)`); `PathDispatcher.cancel_path(...)` calling `SimulationController.handle_path_cancellation(...)` (which delegates to `RouteExecutor.handle_path_cancellation(...)`); `PathDispatcher.on_controller_progress(report)` calling `RouteExecutor.handle_train_advanced(...)` and `ResourceCoordinator.on_physical_entry(...)` / `ResourceCoordinator.release_tail_vacated(...)` (which fan out to `BlockManager.occupy_blocks(...)` / `BlockManager.on_block_tail_vacated(...)` and `SwitchManager.on_physical_entry(...)` / `SwitchManager.on_switch_tail_vacated(...)`); `RouteExecutor.remove_train_route_run(...)` calling `TrainController.finish_dwell()`; the Phase 3 `phase_latches.route_deactivate` consumer (and Phase 1 dwell-complete step) calling `TrainController.finish_dwell()` per the **`current_route_status` write contract**. Cross-train and cross-tick mutations remain latch-only.
- The per-train Phase 3 retained latch / flag table is controller-owned in v1. Its canonical home is `TrainController.phase3_latches` (or equivalent controller-owned fields when implemented without a nested object).
- The v1 retained latch table contains:
  - `phase_latches.path_cancel_request`
  - `phase_latches.route_abort`
  - `phase_latches.power_off` (controller-owned latch consumed by Phase 3)
  - `phase_latches.route_deactivate` (controller-owned latch written by `route.deactivate()` admin handler per assigned train; consumed by Phase 3)
- `ControllerProgressReport` values are intentionally excluded from this retained latch table. They are same-transaction outputs returned by Phase 2 into a `SimulationController`-owned local progress buffer and are drained immediately by that train's Phase 3 pass.
- `phase_latches.path_cancel_request` is an optional payload, not a bare boolean. It is the **canonical owner** of "cancel my path" — the only latch that ever drives `PathDispatcher.cancel_path(...)`. Every cancel-needing writer (EB activation, route-edit/replan revocation, operator/admin path cancellation, route-abort, power-off, route-deactivate) routes through `controller.route_hooks.phase_latches.set_path_cancel_request(...)` directly, or through one of the higher-level helpers (`set_route_abort`, `set_power_off` via `_apply_power_off_request`, `set_route_deactivate`) that fans out to it per the **Writer-helper rule**; once written, the writer walks away. Phase 3 commits exactly one cancellation per pass for that train. Ordinary movement-derived deviation does not use this latch; it is committed inline while Phase 3 drains the same-transaction progress buffer. The payload's canonical fields are `initiator: str` (one of the latch-writer values `"eb"`, `"operator_cancelled"`, `"power_off"`, or `"revoked"`, populated by the writer for the `path_cancellation` notification) and `reason: Optional[str]`. The `"deviation"` initiator string is reserved for the inline movement-derived cancellation path — `PathDispatcher.on_controller_progress(report)` calls `cancel_path(path_id, initiator="deviation", ...)` directly and never writes this latch — so `"deviation"` is a notification-payload value but not a `phase_latches.path_cancel_request` value. It does not decide whether the `RouteRun` should be removed. If multiple same-tick writers set `phase_latches.path_cancel_request`, the most recent payload wins; Phase 3 still resolves the actual live path from `PathDispatcher.active_path_id_by_train(train_id)` and commits at most one explicit latched cancellation for that train on that tick. Functional behavior is identical regardless of which `initiator` ends up in the slot — the path is cancelled. Consumers must not depend on a particular `initiator` being present after a multi-writer same-tick race. Because v1 allows at most one active path per train, this payload does not need a required `path_id` routing key.
- `phase_latches.route_abort` is a separate Phase-3 bare-bool latch for explicit route-run teardown. API/UI/admin "abort route" requests call `controller.route_hooks.phase_latches.set_route_abort(...)`, which sets `phase_latches.route_abort = True` and (when a live path exists) fans out to `set_path_cancel_request(...)` with `initiator = "operator_cancelled"` so Phase 3 cancels authority before removing the run. Route edit, retarget, reconciliation, EB, and ordinary path revocation that should continue the same `RouteRun` write only `phase_latches.path_cancel_request` and must not set `phase_latches.route_abort`.
- Phase 1 calls `TrainController.depart()` directly when route conditions are met. `RouteExecutor.tick_train_phase1(...)` invokes `depart()` with no intervening latch; the call may fail (e.g. EB latched, no cab in manual mode, power off; see the **`TrainController.depart()` canonical contract**) and Phase 1 retries on a later tick. There is no `departure_requested` latch in v1. Dwell entry and dwell exit are also direct calls: `RouteExecutor.tick_train_phase1(...)` calls `TrainController.enter_station_dwell()` directly when the dwell-entry preconditions are met (the dwell row's `started_at` is the derived read of the predecessor stop's `finished_at`), and calls `TrainController.finish_dwell()` directly (after writing `task_runs[walk_position].finished_at`) when `RouteTask.should_depart(...)` is satisfied. The controller never reads `RouteRun` to decide either transition.

**Phase-3 latched-cancel consumption: stopped-train gating and no-active-path skip**

- The `phase_latches.path_cancel_request` consumer is the **canonical owner** of "is there a live path to cancel?" branching. All other latches (`phase_latches.route_abort`, `phase_latches.power_off`, `phase_latches.route_deactivate`) "assign and forget": their writers wrote `phase_latches.path_cancel_request` through the inclusive-latch helpers, and Phase 3 commits that cancel before reaching their consumer steps. They themselves do not branch on active-path emptiness.
- When Phase 3 reaches the `phase_latches.path_cancel_request` consumption step, it first checks `TrainController.is_stopped()`. If the train is still rolling, the latch is preserved and reconsidered on the next eligible Phase 3 pass — Phase 3 must NOT call `PathDispatcher.cancel_path(...)` against a moving train, because that would release future block reservations and switch locks ahead of the still-rolling train. Cancellation that needs to commit while a train is rolling is the EB workflow: EB itself stops the train, and once `is_stopped()` is true the same `phase_latches.path_cancel_request(EB)` latch is consumed on the next Phase 3 pass. Multiple writers in the rolling window overwrite the same single payload slot (most-recent payload wins per the latch table); no extra blocking is needed.
- When Phase 3 reaches the `phase_latches.path_cancel_request` consumption step and the train IS stopped, but `PathDispatcher.active_path_id_by_train(train_id)` is already empty (because a movement-derived deviation cancellation already ran inline during local progress drain, because the path completed normally earlier in the same Phase 3, or because no path ever existed for that train), the dispatcher cancel mutation step is skipped with a single `NotificationCenter` diagnostic such as `latched cancel for <train_id> initiator=<initiator> skipped: no active path`. The latch is still consumed on that same Phase 3 pass. Route-run teardown occurs only from `phase_latches.route_abort`, `phase_latches.power_off`, `phase_latches.route_deactivate`, the Phase-1 terminal-walk direct call to `RouteExecutor.finish_route_run(train_id)`, or train removal.
- When the `phase_latches.path_cancel_request` latch survives across ticks because the train was rolling at inline-deviation-cancel time, no cross-phase coordination is needed: the train's own ATC sees `received_path_plan is None` (the inline cancel cleared authority) and brakes the train under the no-authority limit. Once `is_stopped() == True`, the next eligible Phase 3 step (c) consumes the latch through the same no-active-path skip rule above. The train protects itself; `PathDispatcher` does not reach across phases to clear the latch early.
- Phase 3 must not call `PathDispatcher.cancel_path(...)` on a `COMPLETED` or `CANCELLED` retained path row. That call would return failure with `"already completed"` / `"already cancelled"` and is unnecessary because the latch's intent has already been satisfied by the earlier inline mutation or by normal completion.
- When Phase 3 reaches the `phase_latches.route_abort` consumption step, the inclusive `phase_latches.path_cancel_request` has already been processed earlier in the same pass (or correctly skipped when no live path existed). The abort step performs only its own teardown: call `RouteExecutor.remove_train_route_run(train_id)` so the route assignment is fully removed; the helper writes `state = DEACTIVATED` and (when the controller is `RUNNING_AT_STATION`) calls `TrainController.finish_dwell()` itself before tearing down the run. Clear `phase_latches.route_abort` after `remove_train_route_run(...)` returns. The abort step does not branch on active-path emptiness — that decision was already owned by the `phase_latches.path_cancel_request` consumer.
- `phase_latches.power_off` is a separate Phase-3 latch. `TrainController.commands.power_off_cmd()` is allowed while EB is latched if the train is stopped; EB release is not a prerequisite for shutdown. `power_off_cmd()` is stopped-only at acceptance, so the `is_stopped()` gate on the inclusive `phase_latches.path_cancel_request` is trivially satisfied at the same Phase 3. When Phase 3 reaches the `phase_latches.power_off` consumption step, the inclusive `phase_latches.path_cancel_request` has already been processed; this step performs only its own teardown: call `RouteExecutor.remove_train_route_run(train_id)` followed by the controller-local OFF cleanup (clear cab, EB latch, `phase_latches.power_off`, `ato.running`). The power-off step does not branch on active-path emptiness.
- Terminal route completion is handled by a direct call from Phase 1, not by a Phase 3 latch consumption step. **Same-tick chain.** Within one Phase 1 invocation, when step `70c3` (dwell-complete) finishes the final `dwell` task (or, for routes ending in a `stop`, when the prior Phase 3 stop-completion already finished the final task), the same Phase 1 continues into step `c481` and re-invokes `_find_next_task_target(train_id)`. If that helper returns `None`, the kernel falls into terminal-walk handling instead of step `a5c6`: `RouteExecutor.tick_train_phase1(...)` calls `RouteExecutor.finish_route_run(train_id)` directly inside that same Phase 1 invocation. The terminal-walk path therefore commits in the same tick as the final task's `finished_at` write — no extra tick is required. By that point, the matching live path has already been cleared by the normal stop-completion path during the prior Phase 3 pass (terminal completion only fires after the last stop or stop+dwell pair finishes), so this direct call does not need a dispatcher cancel. `RouteExecutor.finish_route_run(train_id)` performs the canonical terminal teardown: set `RouteRun.current_route_status.state = FINISHED`, and leave the run as a historical `FINISHED` row in the route registry. `RouteExecutor.assigned_route_id_for(train_id)` automatically returns `None` once the run's `state` flips out of `RUNNING`. If the route is `RouteMode.ONE_OFF` and has no remaining assigned trains, `route.deactivate()` may be invoked here; that triggers the `phase_latches.route_deactivate` workflow for any other still-assigned trains, but since this branch only fires when no other trains remain it is effectively a no-op beyond setting `Route.is_active = False`.
- When Phase 3 reaches the `phase_latches.route_deactivate` consumption step, the inclusive `phase_latches.path_cancel_request` has already been processed earlier in the same pass. The deactivate step performs only its own teardown: call `RouteExecutor.remove_train_route_run(train_id)` (the helper writes `state = DEACTIVATED` and — when the controller is `RUNNING_AT_STATION` — calls `TrainController.finish_dwell()` first), then clear `phase_latches.route_deactivate`. `RouteExecutor.assigned_route_id_for(train_id)` automatically returns `None`. The deactivate step does not branch on active-path emptiness.

**Phase Table**

Each phase is a strict execution boundary within one train's per-tick transaction. Code must not cross into another phase's entity chain. Retained cross-phase communication uses only the latches defined in the Latch Table below; same-transaction movement progress uses the `SimulationController` local progress buffer and is drained before the train transaction ends.

**Why this shape.** Phases are interleaved per train, not run as three world-wide passes, so one train's full Phase 1/2/3 transaction commits before the next train's Phase 1 begins. That gives each transaction a single coherent view of network state at the moment it runs and keeps cross-train reads always-current. The strict ownership split — Phase 1 owns route planning and `RouteRun` mutation, Phase 2 owns controller and physics, Phase 3 owns dispatcher and resource commit — means each phase has exactly one writer for the fields it touches, which is what makes "always recompute live" reads safe across the rest of the document.

**Latch table**

**Why latches exist.** Latches model hardware constraints. The underlying real-world action — releasing track resources, cancelling authority, powering off — cannot always commit when requested. The train may still be rolling, hardware may be busy, or another condition may need to clear first. A latch persists the *intent* of the action in controller-owned state and waits for its gating predicate to allow commit. A latch is therefore a deferred command, not a flag. Adding a new latch is only correct when there is a gating predicate that defers the action across one or more ticks. If the action can always commit immediately, do not add a latch — write a flag or call the action directly.

**Naming convention.** The four controller-owned Phase-3 latches live nested under `TrainController.route_hooks.phase_latches: PhaseLatches`, with the field names `path_cancel_request`, `route_abort`, `power_off`, and `route_deactivate`. The aggregate keeps the four together so the latch discipline (canonical writers, fan-out, consumers) lives in a single class. The exception is `path_cancelled`, which is `RouteRun`-owned rather than controller-owned and uses past-tense form. New controller-owned Phase-3 latches must be added to `PhaseLatches`.

Rule: each latch is consumed by its canonical consumer in its canonical phase, and the last entity that uses a latch in the same 3-phase period is the one that clears it. Within one phase, steps run in canonical order, so a latch written by an earlier step in that phase may be consumed by a later step in the same phase (this is what step ordering is for). Cross-phase handoffs always wait for the next eligible run of the consumer phase. Gating predicates may further defer consumption to a later tick's run of the consumer phase. v1 defines no Phase-1-to-Phase-2 retained latch — Phase 1 either commits its work in Phase 1 itself or writes a Phase-3 latch, and Phase 2 reads only operator-command queue entries plus controller-owned state.

**Writer-helper rule.** Every latch has exactly one canonical writer helper. That helper is the only assignment site for the latch field; all other code routes through it and never assigns the field directly. Each helper is also the canonical site that declares its sub-latch fan-out — i.e. when a higher-level latch implies a lower-level latch, the helper applies that fan-out from inside itself. The helpers are:

| Helper | Latch written | Sub-latch fan-out applied inside the helper |
| --- | --- | --- |
| `RouteExecutor.handle_path_cancellation(...)` | `RouteRun.path_cancelled = True` | none — leaf latch |
| `controller.route_hooks.phase_latches.set_path_cancel_request(initiator, reason=None)` | `phase_latches.path_cancel_request` | none — leaf latch |
| `controller.route_hooks.phase_latches.set_route_abort(reason, has_active_path=...)` | `phase_latches.route_abort = True` | calls `set_path_cancel_request(...)` with `initiator = "operator_cancelled"` when `has_active_path` is true |
| `controller.route_hooks.phase_latches.set_power_off(reason, has_active_path=...)` | `phase_latches.power_off = True` | calls `set_path_cancel_request(...)` with `initiator = "power_off"` when `has_active_path` is true |
| `controller.route_hooks.phase_latches.set_route_deactivate(reason, has_active_path=...)` | `phase_latches.route_deactivate = True` | calls `set_path_cancel_request(...)` with `initiator = "revoked"` when `has_active_path` is true |

Callers pass `has_active_path = controller.received_path_plan is not None` so the data class itself stays free of controller dependencies. The `power_off` setter does not clear `controller.ato.running` (that cross-field side effect lives on `TrainController._apply_power_off_request(...)`, which wraps the latch setter so every power-off path stays consistent). **One-caller rule for `phase_latches.set_power_off(...)`:** the only caller is `TrainController._apply_power_off_request(...)`. Any new power-off-needing code path must route through `_apply_power_off_request(...)` (not the helper directly) so the `ato.running` clear is never skipped.

**Consumer-helper rule.** Symmetric to the writer-helper rule: each latch has exactly one canonical consumer helper on `PhaseLatches`, and that helper is the only assignment site that clears the latch field. Phase 3 consume steps call these helpers; no code clears a `phase_latches.X` field directly. The four helpers are:

| Helper | Latch cleared | Effect |
| --- | --- | --- |
| `controller.route_hooks.phase_latches.consume_path_cancel_request()` | `phase_latches.path_cancel_request = None` | Called by Phase 3 step (c) after `PathDispatcher.cancel_path(...)` commits or the no-active-path skip diagnostic emits. |
| `controller.route_hooks.phase_latches.consume_route_abort()` | `phase_latches.route_abort = False` | Called by Phase 3 step (d) after `RouteExecutor.remove_train_route_run(train_id)` returns. |
| `controller.route_hooks.phase_latches.consume_power_off()` | `phase_latches.power_off = False` | Called by Phase 3 step (e) as part of controller-local OFF cleanup, after `RouteExecutor.remove_train_route_run(train_id)` returns. |
| `controller.route_hooks.phase_latches.consume_route_deactivate()` | `phase_latches.route_deactivate = False` | Called by Phase 3 step (f) after `RouteExecutor.remove_train_route_run(train_id)` returns. |

Each consumer helper is idempotent against a same-pass no-op (calling it when the field is already cleared is allowed and writes nothing).

Public callers route through these helpers — they never assign latch fields directly:

- API/UI/admin handlers call `controller.route_hooks.phase_latches.set_route_abort(...)` directly between ticks. There is no separate `TrainController.request_route_abort()` wrapper in v1; every caller routes through the same writer-helper on `phase_latches`.
- `TrainController.commands.power_off_cmd()` calls `_apply_power_off_request()`, which clears `ato.running` and forwards to `phase_latches.set_power_off(...)`.
- The `route.deactivate()` admin handler calls `controller.route_hooks.phase_latches.set_route_deactivate(...)` per assigned train.
- EB activation calls `controller.route_hooks.phase_latches.set_path_cancel_request(...)` with `initiator = "eb"` when a live path exists (skipped during dwell where there is no path to cancel — see the **EB workflow state machine**).
- Operator-driven Phase 1 cancel-and-replan calls `controller.route_hooks.phase_latches.set_path_cancel_request(...)` with `initiator = "operator_cancelled"`.
- System Phase 1 cancel-and-replan (route reconciliation, structural extend failure) calls `controller.route_hooks.phase_latches.set_path_cancel_request(...)` with `initiator = "revoked"`.

Terminal route completion is not a latch and is not part of this rule: when Phase 1 detects the terminal walk, the matching live path has already been cleared by normal stop-completion in the prior Phase 3, so Phase 1's direct `RouteExecutor.finish_route_run(train_id)` call has no inclusive cancel to write.

**`SimulationController.update()` calls**

- `self.route_executor.update(delta_seconds)` becomes a pure per-tick scheduling / Phase 1 preparation call. It advances route-executor bookkeeping time and prepares only the route-managed scheduling state that `SimulationController` consumes for this tick; it does not own the outer train loop and does not call `SimulationController._update_train(...)` itself.
- `SimulationController._update_train(train, delta_seconds)` remains the per-train Phase 2 execute step plus the immediate Phase 3 consume pass for that same train.
- `SimulationController` is the sole owner of executing the per-tick loop, while `RouteExecutor` owns the train ordering. `SimulationController.update(...)` advances time, calls `RouteExecutor.update(delta_seconds)` to refresh route-managed scheduling state, asks `RouteExecutor.order_runnable_trains(candidate_train_ids)` for the final ordered runnable-train list by effective priority (`Route.priority` for route-managed trains, default `5` for non-route/one-off trains; `9` highest, `0` lowest, stable order for ties), calls `RouteExecutor.tick_train_phase1(train_id, delta_seconds)` as that train's complete Phase 1 route-executor tick immediately before that same train's `SimulationController._update_train(train, delta_seconds)` transaction, and then updates signals. `RouteExecutor.order_runnable_trains(candidate_train_ids: Iterable[str]) -> List[str]` takes only the candidate train IDs; it does not take `delta_seconds` (time advancement happens in `RouteExecutor.update(delta_seconds)`). The runnable list includes ALL trains (powered and powered-off). For powered-off trains, route Phase 1 is skipped but the per-train transaction still runs Phase 2 (operator-command drain so `TrainController.commands.power_on_cmd()` can be accepted; `TrainPhysics.tick(...)` integration; `TrainController.on_physics_updated(...)` storage callback). If the controller remains `OFF` after the command drain, Phase 3 is skipped for that transaction but Phase 2 still ran. If the command drain turns power on, continue the normal powered Phase 2 controller/physics flow and run the normal Phase 3 feedback/cleanup pass in that same transaction; fresh route planning still waits for the next eligible Phase 1 tick. For trains with no current route-managed Phase 1 work, `RouteExecutor.tick_train_phase1(...)` is a no-op. `SimulationController` must not forward resource-entry or tail-vacate events itself.
- `SimulationController` owns one shared `PathDispatcher` instance for all trains. `TrainPhysics.tick(delta_seconds)` computes the next span/speed plus tile delta and invokes `TrainController.on_physics_updated(span_update)` for that train on every tick, including ticks where the controller remains `OFF`. At the start of each per-train transaction, `SimulationController` creates an empty local `progress_reports` buffer. For powered transactions, `TrainController.on_physics_updated(span_update)` applies the update to controller-owned span/speed and returns ordered resource-entry, typed tail-vacate, and deviation observations as `ControllerProgressReport` values that `SimulationController` appends to that same-transaction buffer; it does not call `PathDispatcher` directly. For a transaction where the controller remains `OFF`, the same callback still applies the controller-owned span/speed update, but returns no dispatcher/route Phase 3 progress reports because Phase 3 is skipped for that transaction. `TrainController.tick(...)` may also set `phase_latches.power_off`, but it does not latch path completion. After Phase 2, `SimulationController` runs one Phase 3 consume pass for powered trains; for a controller that remains `OFF`, Phase 3 is skipped for that transaction even though Phase 2 physics ran. The Phase 3 drain consumes the local progress buffer in order; that same drain is the only place movement-derived deviation is committed, and each route head-advance callback may consume at most the current next waypoint for that callback's reported block advance. If a tick crossed multiple boundaries, later reports in the same local buffer may then discover and consume later waypoints one callback at a time. After the drain, if an active path still exists for that train, `SimulationController` runs the post-physics usable-authority stop check against the controller's just-updated state and, on success, calls `PathDispatcher.try_complete_active_path(train_id)`; the writer inside `PathDispatcher.try_complete_active_path(...)` samples `time.time()` at the write site for any `Path.last_status_updated_time` and notification `event_time` it records (see **Time sampling** under the **Units contract**). After that normal completion chance, Phase 3 consumes `phase_latches.path_cancel_request`, `phase_latches.route_abort`, `phase_latches.power_off`, and `phase_latches.route_deactivate` in that order. `phase_latches.path_cancel_request` consumption is gated by `TrainController.is_stopped() == True`: while the train is still rolling, that latch (and the inclusive higher-level latches that depend on it — `phase_latches.route_abort` and `phase_latches.route_deactivate`) survive across ticks and are reconsidered on the next eligible Phase 3 pass. When the gate is satisfied, each consumer clears its own latch on the pass that runs the consumer step, even when the underlying action is a no-op (e.g. `phase_latches.path_cancel_request` consumed when no active path exists still clears the latch on this pass; `phase_latches.power_off` always clears once acceptance has been confirmed). `phase_latches.power_off` has no rolling-train defer because its writer requires the train already stopped (`power_off_cmd()`). Path completion is therefore committed before explicit admin cancel/OFF cleanup, while movement-derived deviation cancellation still wins inline during local progress consumption. Phase 3 never runs dwell-complete or route-deviation cleanup; both are Phase 1 steps consumed on the next eligible tick. `PathDispatcher` resolves active authority from its own registries while resolving post-authority physical release from the resource itself rather than by reading a stale controller-side path copy.
- `self.network.update_signals_from_blocks()` runs after dispatcher feedback so signals reflect all block-state changes, including path completion.

**SimulationController runtime surface**

- `SimulationController` is the registered runtime surface shared by `TrainController`, `PathDispatcher`, `RouteExecutor`, and `TrainPhysics` whenever any simulation runtime is active. It is the canonical home for runtime services and is the only owner of the public `add_train(...)` API surface. When a `SimulationController` instance exists for a network, it must finish initializing and registering this surface before any `TrainController` instance is constructed.
- `SimulationController` is optional in editor mode. Pure map-editor sessions (geometry placement, connectivity wiring, static field edits that do not affect runtime occupancy or locks) run with no `SimulationController`, no `BlockManager` runtime, no dispatcher, and no controllers; entities that hold a reference to `SimulationController` MUST type it as `Optional[SimulationController]` and tolerate `None`. An editor session that wants live track/switch testing MAY instantiate a lightweight `SimulationController` (with `BlockManager` wired but no runtime route/dispatcher trains) so that switch state changes route through the canonical mutation workflow normally. The choice is binary at the editor session level — there is no partial wiring.
- The v1 surface exposes exactly the shared services and registries needed by those components: `network`, `block_manager`, `path_dispatcher`, `route_executor`, `notification_center`, the controller registry keyed by `train_id`, the physics registry keyed by `train_id`, `get_train(train_id)`, `get_controller(train_id) -> Optional[TrainController]` (read-only registry lookup; returns `None` if no controller is registered for that `train_id`; never side-effects construct one), `get_or_create_controller(train_id)`, `get_or_create_physics(train_id)`, route-event delivery methods using the canonical `handle_` prefix (`SimulationController.handle_path_completion(...)`, `SimulationController.handle_path_cancellation(...)`) which delegate to `RouteExecutor.handle_path_completion(...)` and `RouteExecutor.handle_path_cancellation(...)` respectively, and the public train-addition API `add_train(...)`. Callers that need the route's currently armed target call `RouteExecutor._find_next_task_target(train_id)` directly through the route-executor surface; there is no separate runtime-services projection for it. `PathDispatcher.active_path_id_by_train(train_id) -> Optional[str]` remains the canonical dispatcher projection for the train's active path id, and `PathDispatcher.get_active_path(train_id) -> Optional[Path]` is the canonical accessor that returns the active `Path` record itself (composed as `paths_by_id[active_path_id_by_train(train_id)]` when a path is active, else `None`). `add_train(...)` is owned by `SimulationController` because the train-addition API is invoked from the frontend/client layer to introduce a new train into the running simulation; it constructs the `Train`, ensures the controller exists, and writes the initial `TrainController.physics_sync.current_span` from placement input before any simulation tick. **Threading model**: All API/UI/admin requests that mutate runtime state (including `add_train(...)`, controller-command queueing, latch writes) run on the same single execution thread as the per-tick phase loop. The runtime processes API requests strictly between ticks; if a tick is in progress when a request arrives, the request is queued and processed only after the tick's post-tick signal update completes. (Multi-threaded execution is Out of Scope; see the **Out of Scope** section.) Because all API requests run between ticks, the system can also rely on always-recompute-live reads: API actions may have changed shared state, so consumers must recompute live (e.g. via `_find_next_task_target`) instead of trusting cached values from a prior tick. `add_train(...)` is therefore synchronous and all-or-nothing inside that single-threaded model: if any sub-step fails (validation, span derivation, controller registration), the partial state must be rolled back and the call must return failure rather than registering a partially wired train. A request whose `train_id` already exists must fail without mutating state.
- External operation surfaces exposed through routes/API/UI/admin code honor the same phase workflow as internal code. A request that wants to cancel/revoke a live path resolves the target train/controller, calls `controller.route_hooks.phase_latches.set_path_cancel_request(initiator, reason=None)`, and returns success once that accepted/pending payload has been written. A request that wants to abort the whole route run calls `controller.route_hooks.phase_latches.set_route_abort(...)` per the **Writer-helper rule** in the **Latch Table** preamble; route-run removal is driven by the abort latch. A request that sends an operator command returns success once the command has been queued. Any later semantic failure is emitted by the real command or dispatcher operation when the command queue or Phase-3 handoff is actually consumed, through `NotificationCenter`. The later per-train Phase 3 pass is the only place that calls `PathDispatcher.cancel_path(...)`, clears authority, releases future resources, removes route runs, and invokes route callbacks. Request handlers must not mutate dispatcher path records, controller authority, route-run state, block reservations, or switch locks directly.
- When a `SimulationController` instance is created for a runtime session, it is the first runtime object initialized for that network run. `SimulationController.__init__` constructs/registers `BlockManager`, `SwitchManager`, `ResourceCoordinator`, `PathDispatcher`, and `RouteExecutor`, wires them and every already-loaded network entity (including each `Switch`) to the same `SimulationController` reference so that cross-entity callbacks such as `Switch` → `BlockManager.on_switch_position_changed(switch_id)` resolve through `self.simulation_controller.block_manager` rather than requiring direct injected back-references, and only then allows `SimulationController.get_or_create_controller(train_id)` to create a `TrainController`. Any later-created or later-loaded entity must be registered with this same `SimulationController` before it is allowed to mutate cross-entity runtime state. If that surface is not registered yet, `SimulationController.get_or_create_controller(...)` must fail rather than constructing a partially wired controller.
- Every `TrainController` stores only a reference to `SimulationController`, not separate dispatcher or route-executor references. Controller-owned release/removal commands do not call dispatcher or route teardown inline anymore; they only write the appropriate Phase 3 handoff (`phase_latches.path_cancel_request`, `phase_latches.route_abort`, and/or `phase_latches.power_off`). That same train's later Phase 3 consume pass then performs `PathDispatcher.cancel_path(...)`, any required `RouteExecutor.remove_train_route_run(train_id)` call, and controller-local cleanup in canonical order. Route-deviation cleanup itself is a Phase 1 step that runs on the next eligible tick after the train has reached the stopped recovery state.
- `PathDispatcher` and `RouteExecutor` also resolve controllers through `SimulationController.get_or_create_controller(train_id)` and must not keep private controller registries or construct controllers directly.

**Canonical runtime procedures**

These named procedures are the canonical home for ordering-sensitive cross-component workflows. Later sections may restate local consequences, but they should cross-reference these procedures rather than inventing a second order.

- **Physical progress / deviation procedure**:
  1. `e3e6` — `TrainPhysics.tick(...)` emits one ordered `PhysicsSpanUpdate` per crossed resource boundary, plus one final no-boundary callback every tick so Phase 3 always has a deterministic consume point.
  2. `35d0` — `TrainController.on_physics_updated(span_update)` writes the new controller-owned span/speed, converts the tile delta into one typed `ControllerProgressReport`, and returns that report to `SimulationController` for the train's same-transaction local progress buffer. It does not call `PathDispatcher` directly.
  3. `908c` — During that same train's Phase 3 consume pass, `SimulationController` drains that local progress buffer in FIFO order by calling `PathDispatcher.on_controller_progress(report)` for each report.
  4. `83a2` — `PathDispatcher.on_controller_progress(report)` handles entered resources before any path bookkeeping by calling `ResourceCoordinator.on_physical_entry(resource_type, resource_id, train_id, path_id)` for each one. The coordinator routes block events to `BlockManager.occupy_blocks(...)` and switch events to `SwitchManager.on_physical_entry(...)`, which compares the incoming `train_id` with the current `Switch.occupied_by`, and only on a clean entry sets `Switch.occupied_by = train_id` and converts applicable same-path switch/flank locks into train-owned physical protection. Physical occupancy is the top-priority truth: if a train physically enters a resource and recording that entry would not overwrite another owner's live claim, the resource state must record it even if the software authority state is already wrong.
  5. `018a` — If recording that physical entry would overwrite another train's current physical/reservation owner, `PathDispatcher` enters the canonical fatal physical-entry conflict procedure below immediately, leaves the prior owner intact, and stops processing the report.
  6. `389a` — If `report.deviation == true`, dispatcher commits the cancellation immediately, inline during local progress drain, by calling `cancel_path(path_id, initiator="deviation", ...)`. The original `deviation_kind` value (`"out_of_sequence"` or `"beyond_authorized_target"`) flows into the `path_cancellation` event payload defined in the **Cancellation** subsection. It does not run normal `Path.current_resource_index` advancement or `RouteExecutor.handle_train_advanced(...)` for that report. The canonical cancellation context is delivered upward only after the dispatcher cancel mutation has committed for that train on that same tick. The next eligible Phase 1 reruns ordinary covered-task index advance plus `_find_next_task_target(train_id)` from the train's current physical position. Both deviation flavors share the same recovery path.
  7. `640a` — If `report.deviation == false`, dispatcher applies ordinary active-path head progress and route head-advance callbacks. For each entered block advance, after `Path.current_resource_index` is updated, the route side compares that single reported block/direction with the current next task on the `RouteRun` directed walk. If that task is finished or passed, the callback records `task_runs[i].finished_at` (the derived `current_waypoint_index` advances with that write) and returns. If the same physics tick crossed another boundary, the next report in the local progress buffer discovers the next task via a fresh `_find_next_task_target(train_id)` call. The callback must not call `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)`, must not arm a future planning cursor, and must not consume more than one task. Fresh target resolution for a new authority waits for the next eligible Phase 1.
  8. `02bb` — Dispatcher processes `tail_vacated_resources` after all entered-resource handling above.
- **Active-path completion procedure**:
  1. `e564` — Stop-completion observation is post-physics in v1. `TrainController.tick(...)` maintains lookahead and stopped-only command handling, but it does not latch or emit path completion.
  2. `e4ad` — `TrainPhysics.tick(...)` moves the train for that tick, and `TrainController.on_physics_updated(...)` writes the post-move span/speed plus any resource/deviation observations returned into the `SimulationController` same-transaction local progress buffer.
  3. `4e0e` — Later in that same train's Phase 3 consume pass, `SimulationController` drains local progress reports first by calling `PathDispatcher.on_controller_progress(report)` for each report.
  4. `9d8b` — After local progress has been fully consumed, including any movement-derived deviation handling from those reports, if an active dispatcher path still exists for that train, `SimulationController` asks the controller's post-move state whether the train is now stopped at the usable end of that live authority. Plain English: this means "the train has already moved for this tick and is now fully stopped at the controller's usable authority stop boundary." Explicit latched admin teardown such as `phase_latches.path_cancel_request` and `phase_latches.power_off` is processed only after this normal completion chance.
  5. `8df5` — The usable-authority stop check is true only when all of the following are true: the controller still has live authority, depart has been accepted for the current authority (`controller.state == RUNNING_MOVING`, which is set only by a successful `TrainController.depart()`), the selected cab/travel frame is heading in the active authority frame toward the current authority end, `TrainController.is_stopped()` is true, `TrainController.eb.active == False`, and the distance-0 lookahead has `atc_limit == 0` with `atc_limit_reason_code == "authority_stop"`. The train may satisfy this check either because it physically progressed through the final `resource_sequence` entry or because the remaining projected authority distance is too short to grant additional positive clearance after applying the controller safety margin. The check does not require physical head occupancy in the requested destination block, a route-authored centimeter stop target, or a second exact-position test.
  6. `f8c6` — If that post-physics controller check is false, Phase 3 does not attempt path completion for that train on that tick.
  7. `bc55` — If the post-physics controller check is true, Phase 3 calls `PathDispatcher.try_complete_active_path(train_id)` directly rather than routing completion back through `PathDispatcher.on_controller_progress(report)`. Timestamps that record this transition (`Path.last_status_updated_time`, the route-side stop's `task_runs[walk_position].finished_at`, the next directed-walk task's `started_at`, and any related notification `event_time`) are sampled by the writer at the moment of the write per **Time sampling** under the **Units contract**.
  8. `790a` — `PathDispatcher.try_complete_active_path(...)` accepts completion only when the active path still exists, `Path.authority_end_block_id == Path.requested_destination_block_id`, and the terminal authority block entry's block-relative traversal direction equals `Path.requested_destination_direction`. Dispatcher computes that terminal traversal direction from the final block `resource_sequence` entry's explicit directed frame and the block's canonical ordered tiles. Dispatcher does not require the train head to physically occupy the requested destination block; the controller safety margin / ATC stop boundary is the higher-priority stopping rule. By construction of the create/extend acquisition rules (the waypoint-target exclusion in **`create_path()` flow** and the matching rule in **Path extension**), the live authority's terminal block is never the resolved target block of a `task_kind == "waypoint"` task on the train's `RouteRun`, so dispatcher path completion always lands on a `stop` target.
  9. `09b0` — On accepted completion, `PathDispatcher` follows the canonical terminal-teardown order: release not-yet-entered block reservations and switch/flank locks through `ResourceCoordinator.release_path_resources(path_id, block_ids, completed=True)` (which composes `BlockManager.release_path_block_reservations(..., completed=True)` and `SwitchManager.release_path_locks(path_id)`), transition `Path.status` to `COMPLETED` (which by definition makes `active_path_id_by_train(train_id)` return `None` for this train and makes the controller's `received_path_plan` property return `None` on its next read), call `TrainController.on_path_complete()` so the controller transitions to the **`READY` state**, then call `RouteExecutor.handle_path_completion(...)`.
  10. `29c5` — `RouteExecutor.handle_path_completion(...)` records the matching stop as finished by setting `task_runs[walk_position].finished_at = time.time()` via `_enter_task_arrival(...)` (the derived `current_waypoint_index` advances to `walk_position` with that write, and the next task's derived `started_at` automatically reflects this `finished_at`). The callback then clears the route-owned active-path correlation. The `stop` task and any following `dwell` task are independent rows. The completion callback does not call `TrainController.enter_station_dwell()`; dwell entry is performed by the next eligible `RouteExecutor.tick_train_phase1(...)` after this callback returns.
  11. `d843` — On the next eligible tick, `RouteExecutor.tick_train_phase1(...)` runs its dwell-entry step: when the route's next non-finished task has `task_kind == "dwell"`, the predecessor task's `finished_at` is set, and `controller.is_recovery_clean` is true, `RouteExecutor` calls `TrainController.enter_station_dwell()`. The dwell row's `started_at` is the derived read of the predecessor stop's `finished_at` written in step `29c5`; the dwell-entry step does not need to write it. While the controller is `RUNNING_AT_STATION` (or the next task is `dwell` and the controller is about to enter dwell), Phase 1 must not create or extend authority. The same train's later Phase 1 dwell-complete step checks `RouteTask.should_depart(task_runs[walk_position].started_at, current_time)`; when the dwell timer is satisfied, `RouteExecutor` sets `task_runs[walk_position].finished_at = current_time` (the derived `current_waypoint_index` advances with that write), calls `TrainController.finish_dwell()`, and continues into target resolution for the next task in the same Phase 1.
- **Power-off procedure**: The `phase_latches.power_off` latch coordinates a four-step teardown across `PathDispatcher`, `RouteExecutor`, and `TrainController`. The dispatcher cancel for an in-flight live path is committed by Phase 3 step (c) (the `phase_latches.path_cancel_request` consumer that the inclusive-latch fan-out wrote), not by the `phase_latches.power_off` consumer itself.
  1. `98d3` — `TrainController.commands.power_off_cmd()` is processed in the tick-entry **operator-command processing slot** inside `TrainController.tick(...)`. It validates only the stopped-only shutdown precondition for acceptance; it is valid while `eb.active == True` as long as the train is stopped. On acceptance it immediately disengages any active ATO run by setting `ato.running = False` and calls `TrainController._apply_power_off_request()`, which sets `phase_latches.power_off = True` and (when a live path exists at write time) writes the inclusive `phase_latches.path_cancel_request` with `initiator = "power_off"` per the **Writer-helper rule**. It does not cancel dispatcher authority, clear EB, or remove route state inline.
  2. `278a` — On the same train's later eligible Phase 3, step (c) (the `phase_latches.path_cancel_request` consumer) commits the inclusive `phase_latches.path_cancel_request(POWER_OFF)` through `PathDispatcher.cancel_path(...)`, gated by `is_stopped() == True` per the **Latch table**. Because `power_off_cmd()` is stopped-only at acceptance, that gate is trivially satisfied on the same Phase 3 pass. The ordinary cancellation callback (`RouteExecutor.handle_path_cancellation(...)`) runs as part of that commit. If no live path was present at `_apply_power_off_request()` time, no inclusive cancel was written and step (c) is a no-op for this train.
  3. `534f` — After step (c) has run (or no-opped), Phase 3 reaches the `phase_latches.power_off` consumer in step (e). That step calls `RouteExecutor.remove_train_route_run(train_id)` through `SimulationController.route_executor`. The power-off consumer never calls `PathDispatcher.cancel_path(...)` itself.
  4. `886a` — Finally that same Phase 3 cleanup performs controller-local OFF cleanup: transition to `OFF`, clear the active cab selection, clear any EB latch, and set `phase_latches.power_off = False`. Note: between `RouteExecutor.remove_train_route_run(...)` invoking `finish_dwell()` (which transitions the controller to `READY`) and this OFF cleanup step clearing `eb.active`, the controller is briefly in the transient combination `(state == READY, eb.active == True)` when the operator powered off while EB was latched and the train was dwelling. This transient is permitted only inside this Phase-3 power-off cleanup sequence and is cleared in the same Phase-3 pass before any other consumer observes it; `is_recovery_clean` correctly reads false during that window because `EB_LATCHED ∈ active_conditions`, but no consumer needs `is_recovery_clean` between these two writes.
- **Fatal physical-entry conflict procedure**:
  1. `cd5e` — `SimulationController` owns the unrecoverable failed-runtime flag and fatal diagnostic payload.
  2. `16e0` — `BlockManager` (for block conflicts) or `SwitchManager` (for switch conflicts) reports a typed `FatalPhysicalEntryConflict` to `SimulationController.enter_failed_runtime(...)` when a physical entry would overwrite another train's `occupied_by`, another train's `reserved_for_train`, another train's `Switch.occupied_by`, or enter a disabled block/switch. Both reports flow through the same `ResourceCoordinator.on_physical_entry(...)` entry point that `PathDispatcher.on_controller_progress(report)` calls. The payload is intentionally small and branchable: `resource_type`, `resource_id`, `incoming_train_id`, `prior_owner_train_id: Optional[str]`, `conflict_kind: FatalConflictKind`, and active path IDs when known. `prior_owner_train_id` is populated for conflicting train ownership and is `None` for `conflict_kind == FatalConflictKind.DISABLED_RESOURCE_ENTRY`.
  2a. `6e4a` — **`FatalConflictKind` canonical home.** Define `FatalConflictKind` here once as the diagnostic enum for fatal physical-entry conflicts with v1 values:
    - `OCCUPIED_BY_OTHER_TRAIN` (`bc14`)
    - `RESERVED_FOR_OTHER_TRAIN` (`f3f2`)
    - `SWITCH_OCCUPIED_BY_OTHER_TRAIN` (`c0bf`)
    - `DISABLED_RESOURCE_ENTRY` (`b0f5`)

    `FatalConflictKind` describes an unrecoverable physical-entry conflict and is consumed only by `enter_failed_runtime(...)` diagnostics; cancellation diagnostics are carried by the free-form `initiator` string on the `path_cancellation` notification (defined in the **Cancellation** subsection) rather than by a parallel enum.
  3. `b9a2` — `SimulationController.enter_failed_runtime(...)`, not the reporting entity, is the only writer of `SimulationController.failed_runtime = True`. It records the fatal payload, emits a `fatal_runtime_failure` notification through `NotificationCenter`, aborts the current simulation transaction immediately, and leaves all controller state, path rows, route runs, block states, switch states, and physical occupancy exactly as they were at the moment of detection for inspection.
  4. `525b` — Fatal conflict is not an ordinary cancellation/recovery branch. `SimulationController.enter_failed_runtime(...)` must not call `PathDispatcher.cancel_path(...)`, `RouteExecutor.handle_path_cancellation(...)`, or `RouteExecutor.remove_train_route_run(...)`, because those APIs are recoverable workflow callbacks and would incorrectly clear state or replan while the runtime is failed.
  5. `ee19` — `SimulationController.update(...)` refuses further simulation advancement while the failed-runtime flag is set. V1 defines no automatic software resume. The UI/admin "release runtime failure" button is only an acknowledgement/resume gate after the operator has manually removed the problematic train or otherwise repaired the conflicting resource state. That release action calls a runtime-owned helper such as `SimulationController.release_failed_runtime_after_manual_cleanup()`, verifies that the fatal resource no longer has the conflicting physical owner / disabled-entry condition reported in the stored fatal payload, clears `failed_runtime` and the fatal payload, and emits a resume notification. It must not cancel paths, remove route runs, clear controller authority, or mutate resource ownership itself; those cleanup actions happen only through the explicit manual/admin repair workflow before the release button is accepted.

**Path completion notification flow**

- `PathDispatcher.try_complete_active_path(train_id)` should commit completion only when the post-physics controller stop check has already passed for that train and the active path's authority end has reached the path's requested target block and direction. Completion ordering is exactly the **Active-path completion procedure**: release not-yet-entered resources, transition the path to `COMPLETED` (the active-path read switches to `None` for this train by definition), call `TrainController.on_path_complete()`, then call `RouteExecutor.handle_path_completion(...)` using the canonical completion payload from the **route path-event callback schema**. Completion release may drop not-yet-entered reservation ownership and may force-clear `CAUTION` for matching still-reserved blocks, but it must not force-clear any `OCCUPIED` resource the train still physically occupies.
- `PathDispatcher.try_complete_active_path(train_id)` returns a `PathCompletionResult` with this exact shape:

  | Field | Type | Meaning |
  | --- | --- | --- |
  | `success` | `bool` | `True` only when dispatcher accepted and committed completion. `False` means no completion mutation was committed. |
  | `path_id` | `Optional[str]` | The active path ID that was completed or considered. `None` only when no active path existed for `train_id`. |
  | `new_status` | `Optional[PathStatus]` | `PathStatus.COMPLETED` on success; the unchanged current status such as `PathStatus.ACTIVE` on a failed predicate; `None` when no path row exists. |
  | `reason` | `Optional[str]` | `None` on success. Required diagnostic string on failure, such as `"no active path"`, `"active path missing"`, or `"authority end has not reached requested destination block/direction"`. |

  On `success=False`, `PathDispatcher.try_complete_active_path(...)` leaves the path, controller authority, route state, and resources unchanged except for optional diagnostics. `SimulationController` may log or surface the failure result, but it must not synthesize a fallback completion or cancellation from that failure.
- `PathDispatcher`, `RouteExecutor`, `TrainController`, `Switch`, `BlockManager`, and any other runtime component access cross-component services exclusively through the single `self.simulation_controller` back-reference. There is no separate "runtime services interface" object; the access shape is direct named-attribute access on the `SimulationController` instance: `self.simulation_controller.block_manager`, `self.simulation_controller.path_dispatcher`, `self.simulation_controller.route_executor`, `self.simulation_controller.notification_center`, `self.simulation_controller.network`, `self.simulation_controller.get_or_create_controller(train_id)`, `self.simulation_controller.handle_path_completion(...)`, and `self.simulation_controller.handle_path_cancellation(...)`. `PathDispatcher` calls the route-event methods through this surface, not through a concrete `RouteExecutor` reference; `TrainController` writes latches and calls only controller/`simulation_controller` methods, not route planning helpers directly.
- Wiring pattern: `SimulationController` is initialized first and is the canonical shared runtime owner. It then constructs `PathDispatcher` and `RouteExecutor` and wires every entity (including each `Switch`) to itself by setting `entity.simulation_controller = self` so all cross-entity callbacks resolve through that single attribute. Components may keep that `simulation_controller` reference, but they must not keep direct concrete references to each other when the same access can go through `self.simulation_controller.<named attribute>`.
- `TrainController` instances are created on demand through `SimulationController.get_or_create_controller(train_id)`, which runs only after the **SimulationController runtime surface** above is fully registered. Every new `TrainController` is constructed with the same `simulation_controller` reference, and controller-owned release/removal commands (e.g. `TrainController.commands.power_off_cmd()`) write the appropriate Phase 3 handoff latches through controller-owned state rather than reaching directly into `PathDispatcher` or `RouteExecutor`. This keeps `SimulationController` the single registry of shared runtime components and removes any temporal concern about `TrainController` being constructed before `PathDispatcher` / `RouteExecutor`.
- Path completion should only be recognized after the train has already moved for that tick, Phase 3 has already committed any resource entry/deviation/tail-vacate effects, the controller's post-move stop check says the train is fully stopped at the usable authority stop boundary, and the live authority reaches the requested destination block in the requested destination direction. The controller safety margin is a braking/diagnostic target used by lookahead and is higher priority than trying to force the head to the physical edge or physical interior of the requested destination block. No completion callback should run while the train is still braking or creeping toward that usable authority stop.
- After dispatcher-owned completion release, route-level waypoint and dwell logic should follow the **Active-path completion procedure**: the completion callback records route-owned arrival/progress, and the next eligible `RouteExecutor.tick_train_phase1(train_id, delta_seconds)` call decides whether the train enters dwell (`RUNNING_AT_STATION`) or remains in the **`READY` state** (per the predicate defined in the Controller state machine subsection).

**`SimulationController._update_train(...)` flow**

1. Get or create a `TrainController`.
2. Get or create a `TrainPhysics`.
3. On first pairing only, initialize any controller-owned bootstrap values that still come from persisted train data, then establish the runtime 1:1 `Train` <-> `TrainController` pairing for that `train_id`.
4. Tick controller.
5. Tick physics.
6. Sync only train-owned persistent/configuration state back to `Train`. Do not sync live position/span, speed, path authority, power/cab state, or operational state back to `Train`.
7. Do not add a separate simulation-owned dispatcher feedback pass. `TrainPhysics.tick()` should compute a `span_update` and call `TrainController.on_physics_updated(span_update)`, and that controller method should apply the controller-owned span/speed update and return one ordered `ControllerProgressReport` with any typed tail-vacate observations into `SimulationController`'s same-transaction local progress buffer. That same train's Phase 3 consume pass later delivers those reports to `PathDispatcher.on_controller_progress(report)`.

**`SimulationController._update_train(...)` calls**

- Keep `get_or_create_controller(train_id)` (the public `SimulationController` accessor that owns the controller registry), `_get_or_create_physics(train)`, `controller.tick(delta_seconds)`, and `physics.tick(delta_seconds)`. `RouteExecutor` and `PathDispatcher` both reach the registry through the same public train-ID-based accessor rather than keeping private `_get_or_create_controller` helpers.
- A newly created controller may bind only to train-owned persistent/configuration data needed for that 1:1 pairing. It does NOT seed `TrainController.physics_sync.current_span` itself; initial span placement is owned by the application train-addition path. The API `SimulationController.add_train(...)` flow must create or obtain the controller and write `TrainController.physics_sync.current_span` before any simulation tick. In the desired model `Train` does not carry live runtime authority or live position/span fields, so this constructor path does not need to seed `received_path_plan` (it is a read-only property that resolves the dispatcher's active `Path` into the canonical projection whenever read; before any path is created it returns `None`). The derived reads `assigned_path_id`, `ato_path_id`, and `ato_destination_block_id` are never written directly on the controller — they only surface when `PathDispatcher` has an active path. Runtime authority is always route-backed in v1: `RouteExecutor` creates the path in Phase 1 through `PathDispatcher.create_path(train_id=..., ...)`, using either the train's ordinary assigned route or a dedicated one-off operator route for ad hoc/local movement. The controller's `received_path_plan` property automatically reflects that path on the next read; there is no separate `receive_path_plan(...)` setter. In v1 there is no normal standalone non-route dispatcher-authority mode. `RouteExecutor` should already have ensured the controller exists before any Phase 1 path creation; `SimulationController.get_or_create_controller(train_id)` in `SimulationController._update_train(...)` remains only a controller-registry accessor/fallback, not a separate non-route authority path.
- In v1 there is no late-controller recovery hook. Controller existence is a hard precondition for authority assignment: `RouteExecutor` or any other caller must ensure `SimulationController.get_or_create_controller(train_id)` has already established the 1:1 `train_id -> controller` binding before `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)` runs (the controller's `received_path_plan` property needs the controller object to exist before any reader can call it). If persisted/bootstrap train data is needed to initialize that controller, `SimulationController` resolves the `Train` entity internally from `train_id`; callers still use the train-ID-based accessor. Controller bootstrap must not recreate authority from train-side runtime mirrors, and `PathDispatcher` does not expose `on_controller_available(train_id)` or any post-bind authority refresh — the property always returns the live dispatcher state.
- Stop writing `train.target_speed`, `train.speed_limit_reason`, `train.ato_destination_block_id`, and `train.state` here. Consumers that want live target-speed data should read controller lookahead at distance 0 instead; consumers that want live operational state should read `TrainController.ops.state` directly.
- Do not re-sync live power/cab state from `Train` on every tick. V1 does not import old train-side live power/cab mirrors into the controller; initial power/cab runtime state comes from the v1 controller defaults and later explicit `TrainController` commands only.
- Dispatcher feedback comes through controller progress reports triggered by `TrainPhysics.tick()`, so it can consume both blocks and switches in `resource_sequence` order.
- In the same controller-mediated reporting path, emit typed tail-vacated resource-release observations so `PathDispatcher` can release a vacated resource according to its resource type (`block` vs `switch`).

**`PathDispatcher.on_controller_progress(report)` signature**

- `report: ControllerProgressReport` — payload schema defined immediately below.
- Returns `None`. Side effects only; ordering follows the **Physical progress / deviation procedure**.
- Fatal physical-entry conflicts escalate through `SimulationController.enter_failed_runtime(...)`; the call does not return a failure code.

**Dispatcher progress/completion flow**

**ControllerProgressReport schema**: The canonical field set for `ControllerProgressReport` is defined here. Every producer (`TrainController.on_physics_updated(...)`) and consumer (`PathDispatcher.on_controller_progress(report)`) refers back to this heading by name. Fields: `train_id` (`str`), `event_time` (`float`, system-time Unix seconds sampled at the write site), `entered_resources` (ordered list of resource-entry events), `tail_vacated_resources` (ordered list of tail-vacate events), `current_head_sequence_index` (`Optional[int]`, index of the train head in the active `resource_sequence`), `deviation` (`bool`), `deviation_kind` (`"out_of_sequence" | "beyond_authorized_target"` — these are the only two values in v1), `deviation_reason` (`Optional[str]`, diagnostic plain text only, must not be used for branching). The report does not carry `path_id`; `PathDispatcher` resolves the active path from `active_path_id_by_train(train_id)`. Each resource event in `entered_resources` and `tail_vacated_resources` carries `sequence_index` (when known), `resource_type`, and `resource_id`; block tail-vacate events additionally carry `direction` (the vacated block's forward `exit_edge` `N`/`E`/`S`/`W` for the traversal by which the train left that block).

- `PathDispatcher.on_controller_progress(report)` is the runtime progress API. The report payload follows the **ControllerProgressReport schema** above. It does not carry `path_id`; `PathDispatcher` resolves the active path from `active_path_id_by_train(train_id)`. `current_head_sequence_index` is the index of the train head's current position in the active `resource_sequence`, or `None` when the controller cannot map the head to the active resource sequence. When live authority exists and the controller cannot map the head to that active `resource_sequence`, the report must set `deviation = true`, `deviation_kind = "out_of_sequence"`, and `current_head_sequence_index = None`; dispatcher treats that report as deviation/cancellation input rather than as ordinary active-path progress. `deviation_kind` is the structured controller deviation enum (`"out_of_sequence"` or `"beyond_authorized_target"`); `deviation_reason` is optional plain-text diagnostics only and must not be used for branching. Each resource event in `entered_resources` and `tail_vacated_resources` carries `sequence_index` when known, `resource_type`, and `resource_id`; block tail-vacate events additionally carry `direction`, where `direction` is the vacated block's forward `exit_edge` (`N`/`E`/`S`/`W`) for the traversal by which the train left that block. For a single report, `PathDispatcher.on_controller_progress(report)` follows the **Physical progress / deviation procedure**: entered physical resources are recorded first, deviation cancellation is handled after clean physical entry, and tail-vacated resources are processed last.
- `PathDispatcher` uses `deviation` plus `deviation_kind` to decide whether to cancel the active path in Phase 3. On a deviation report, dispatcher calls `cancel_path(path_id, initiator="deviation", ...)`; the original `deviation_kind` value (`"out_of_sequence"` or `"beyond_authorized_target"`) is preserved on the `path_cancellation` notification payload (defined in the **Cancellation** subsection) for diagnostics. EB recovery timing is gated by controller state (Phase 1 cannot replan until the controller has reached `READY` after `eb.release()`); power-off teardown is driven by `phase_latches.power_off` / the controller transitioning to `OFF`. Planning and routing logic do not read `initiator`.
- The structured deviation predicates are:

  | `deviation_kind` | Predicate |
  | --- | --- |
  | `"out_of_sequence"` | Live authority exists, but the train head cannot be mapped to the active `received_path_plan.resource_sequence`, or maps to a resource that is not the current/next legal head resource for that active path. |
  | `"beyond_authorized_target"` | The head is physically beyond `Path.authority_end_block_id` in the path's directed traversal frame. This is an overshoot of the authorized clearance, including a truncated best-effort authority whose track ahead was not yet ready. |

- `TrainController` owns progress interpretation and canonical span storage. It applies the `span_update` from `TrainPhysics`, converts ordered `added_tiles` and `removed_tiles` into entered/tail-vacated block and switch resource observations, and compares the updated `current_span` with `received_path_plan.resource_sequence` when live authority exists. Stop completion is evaluated separately later in that same train's Phase 3 consume pass from the controller's post-move state after same-transaction progress reports have already been drained. When no live authority exists, the report may still carry physical entry/release observations but `current_head_sequence_index` is `None` and no active-path progress can be inferred by the controller. `PathDispatcher` still owns `Path.current_resource_index`, path status, reservation/lock consumption, resource release, path cancellation/completion, and route callbacks.
- For entered resources, `PathDispatcher.on_controller_progress(report)` must first record clean physical entry exactly as defined in the **Physical progress / deviation procedure** above. Only after those physical writes succeed, and only when `report.deviation == false` and an active path still exists for `train_id`, may dispatcher resolve the relevant dispatcher-owned path record and update `Path.current_resource_index` from the reported `sequence_index` when the train head enters a resource in that live `Path.resource_sequence`. The globally-unique-ID-namespace alternative is not adopted.
- After dispatcher has recorded clean physical entry and updated `Path.current_resource_index` for the entered resource, `PathDispatcher.on_controller_progress(report)` must call the single route-facing head-advance callback `RouteExecutor.handle_train_advanced(train_id, path_id, resource_event)` for the path's active route execution, if any. The `path_id` argument is the dispatcher-resolved active path ID. `resource_event` is a structured payload carrying `resource_type`, `resource_id`, and `traversal_direction: Optional`. For block resources, `resource_event.traversal_direction` is the block-relative `"forward"` / `"reverse"` traversal direction computed by the canonical block-direction helper from the entered `resource_sequence` block entry against `Block.ordered_tiles`. For switch resources it is `None`. `RouteExecutor` must not poll `TrainController.get_current_span()` or `TrainController.get_lookahead()` inside `RouteExecutor.update(...)` to discover head movement. `RouteExecutor.handle_train_advanced(...)` is a Phase-3 route-progress callback that consumes at most one task per call:
  - If `resource_type != "block"`, return; switches are no-ops on the route side.
  - Call `_find_next_task_target(train_id)` to live-resolve the next non-finished task on the directed walk. The helper is read-only and does not write `task_runs[i].resolved_target`.
  - If the resolved next task's `task_kind == "waypoint"` and its resolved-target block and direction match the callback's reported block and direction, the callback consumes that task: set `task_runs[i].finished_at = current_time` (the derived `current_waypoint_index` advances to `i` with that write); update `direction` if needed; return. The next report in the same local progress drain discovers the next task via the same live recompute.
  - If the resolved next task's `task_kind == "stop"`, the callback is a no-op on the route side regardless of whether the reported block matches: stops are served only by dispatcher-committed completion through `PathDispatcher.try_complete_active_path(...)` → `RouteExecutor.handle_path_completion(...)` → `_enter_task_arrival(...)`. The head-advance callback must not record `finished_at` for a `stop` task.
  - If the reported block does not match the next task's target block, the callback is a no-op on the route side. Coverage of an intermediate task that the train physically passed through without entering is reconciled by the next Phase 1's covered-task index advance — Phase 3 does not run that reconciliation.
  - The callback must not call `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)`, must not arm a future planning cursor, and must not call `TrainController.enter_station_dwell()`.

  Head-entry route progress is not gated by depart-acceptance: if the head enters a `waypoint` task's resolved block before departure acceptance, the callback still consumes that task.
- When the entered resource is a block, that same dispatcher-owned entry handoff calls `ResourceCoordinator.on_physical_entry("block", block_id, train_id, path_id)`, which routes to `BlockManager.occupy_blocks(block_id, train_id)`. In the desired model this is the only normal runtime path that marks a block physically `OCCUPIED`, and it consumes any same-train dispatcher reservation for that block because the resource has moved from future authority into train-owned physical occupancy.
- When the entered resource is a switch, the same dispatcher-owned entry handoff calls `ResourceCoordinator.on_physical_entry("switch", switch_id, train_id, path_id)`, which routes to `SwitchManager.on_physical_entry(...)`. That manager method first verifies that the switch is not already physically occupied by another train; on clean entry it sets `Switch.occupied_by = train_id`, consumes the path-owned primary switch lock for the entered switch, and converts any required flank protection for that occupied switch into train-owned physical protection that will be cleared on tail-vacate. If another train already owns `Switch.occupied_by`, the hard-failure rule below applies and the handoff must not overwrite it. Switch physical occupancy is separate from future reservation/lock ownership.
- Physical occupancy updates still happen even when no `ACTIVE` path remains for that train. If `active_path_id_by_train(train_id)` is already clear because the old authority was completed or cancelled, `PathDispatcher.on_controller_progress(report)` must still apply the resource-typed physical entry update via `ResourceCoordinator.on_physical_entry(...)` and simply skip path-progress / completion bookkeeping because there is no active authority row left to update. Clean physical entry records the reported block or switch as occupied by this `train_id` and consumes same-train future claims. A conflicting physical entry is not a normal workflow: if the target block's prior `occupied_by` is another train, or its `reserved_for_train` is another train, or the target switch's prior `Switch.occupied_by` is another train, the dispatcher/manager must enter the canonical unrecoverable hard-failure path: emit a fatal conflict diagnostic identifying the resource, the incoming `train_id`, and the prior owner; stop further simulation advancement immediately; and freeze controller state, dispatcher path rows, route runs, block states, switch states, and physical occupancy exactly as they were at the moment of detection for inspection. V1 must not automatically cancel live paths, remove route runs, or repair resource ownership during fatal conflict handling. The operator/admin must manually remove the problematic train or repair the conflicting resource state, then use the runtime failure release action defined in the **Fatal physical-entry conflict procedure** before simulation advancement can resume. It must not silently overwrite the prior `occupied_by` / `Switch.occupied_by`, must not treat the conflict as recoverable cancellation, and must not continue route or dispatcher bookkeeping as though the entry succeeded.
- In the desired model there should be no separate `CLEARING` lifecycle state. A live dispatcher-owned authority path stays `ACTIVE` until it is either `COMPLETED` or `CANCELLED`; entering the final block/resource only updates progress and completion predicates.
- Tail-vacate release remains resource-local and dispatcher-mediated. `TrainController.on_physics_updated(span_update)` reports vacated resources in `tail_vacated_resources`, and `PathDispatcher.on_controller_progress(report)` releases each vacated resource by calling `ResourceCoordinator.release_tail_vacated(resource_type, resource_id, train_id, direction)` after it has processed any `entered_resources` in that same report. The coordinator routes the release to `BlockManager.on_block_tail_vacated(block_id, train_id, direction)` for blocks and to `SwitchManager.on_switch_tail_vacated(switch_id, train_id)` for switches. `direction` is required for blocks (the vacated block's forward `exit_edge`) and ignored for switches. The single `resource_type` string branch lives inside the coordinator method; `PathDispatcher` does not branch on it. Active progress continues to resolve through `PathDispatcher`'s registries rather than from `TrainController.path_projection.received_path_plan`, but tail-release logic after authority release must resolve from the resource itself so it still works after there is no active dispatcher authority. The switch release path clears `Switch.occupied_by` and clears any train-owned physical protection for that switch; neighbour flank protection associated with the vacated switch is released by the same tail-vacate operation, not by a retained path claim.
- `PathDispatcher.on_controller_progress(report)` is not a deferred-release hook. Once a path is no longer `ACTIVE`, any later physical release is resource-local and triggered by controller-reported tail-vacate observations.
- Explicit local/manual reposition authorities that do not cross a new resource, if retained, do not introduce a route-authored centimeter target. The controller uses the same safety-margin authority-boundary logic as every other stop, and completion still comes only through the same post-physics controller stop check plus `PathDispatcher.try_complete_active_path(train_id)` flow. Dispatcher must not run a separate precise-position detector for those stationary local moves.
- Switch release should be driven by tail-vacate detection in `TrainPhysics`, not by dispatcher tile-index checks.
- Implementation note: every old physics-named dispatcher progress or tail-release caller must be migrated to `TrainController.on_physics_updated(span_update)` plus `PathDispatcher.on_controller_progress(report)`. Active progress commit belongs to `PathDispatcher`, but delayed release of a resource that is still physically occupied after authority release must resolve from the resource itself (`BlockManager` for blocks, `Switch.occupied_by` plus train-owned protection for switches) rather than requiring a retained path row just to rediscover ownership.

**Controller/train sync**

- `TrainController.tick(delta_seconds)` should continue to own ATC, ATO, and manual-control runtime calculations, but target speed and speed-limit reason should move into the canonical controller lookahead payload instead of standalone scalars.
- `Train` should keep only persistent/configuration state in sync from the simulation loop.
- `PathDispatcher.create_path()` should store or update the dispatcher-owned `Path` record only. `TrainController.path_projection.received_path_plan` reads the active movement-authority projection live from that record; path cancellation or completion changes `Path.status`, which makes the next controller read return no active authority without any controller-side clear step.

**Tick-order dependency**

- For one train's transaction, Phase 1 must run before Phase 2 because the controller should read path tiles that already exist.
- For one train's transaction, Phase 2 must run before Phase 3 because the dispatcher should read positions that physics has just produced.
- Physics progress and route-level reactions are synchronous within the same per-train transaction: a boundary crossing reported through `TrainController.on_physics_updated(span_update)` is committed by `PathDispatcher.on_controller_progress(report)` and any route callback before the next train's transaction starts.
