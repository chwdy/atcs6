## Logic Review Checklist

**Review checklist**

- Is the controller reading the canonical **received_path_plan schema** projection when path-end stopping matters?
- Does each `resource_sequence` entry carry the ordered `path_tiles` slice using the canonical **path_tile entry schema**, with explicit `entry_edge` / `exit_edge` on both the resource entry and each nested tile entry, needed for controller lookahead and UI geometry after `Train.current_path` is removed?
- Is controller lookahead the only source of target speed and speed-limit reason?
- In manual mode, does ATC enforce the end of the assigned path as a hard stop through `_calculate_authority_boundary_limit()`?
- Can any path-complete event still fire while the train is braking or creeping toward the terminal authority end, instead of waiting for the post-physics controller stop check to say the train is stopped at the usable end of live authority and `PathDispatcher.try_complete_active_path(...)` to verify that the active authority reaches the requested target before committing completion?
- Does `_ato_calculate_handle()` read only the current tick's canonical lookahead payload, not stale scalar fields?
- Does `RouteExecutor` read controller state rather than mirrored runtime state on `Train`?
- Does `RouteExecutor` resolve waypoint-authored block-relative direction preferences into one concrete `requested_destination_direction` before calling `PathDispatcher.create_path()` or `PathDispatcher.extend_path()`, without relying on platform-level direction fields?
- Do `RouteExecutor` and `PathDispatcher` use the same shared pathfinder/current-span workflow, including the same deterministic tie-break, for start-side and platform-end selection?
- Do `RouteExecutor` and `PathDispatcher` obtain head/tail/current-span data only through `TrainController.get_current_span()`, with `TrainPhysics` remaining the movement-update producer and `TrainController` remaining the writer for controller-owned span state?
- For a pass-through waypoint whose resolved target block is already physically covered, does Phase 1's covered-task index advance skip it, while a stop task whose block is already covered remains the current target and uses ordinary same-block stop authority/completion plus dwell exit?
- For explicit local/manual same-block or same-tile dispatcher movement, does the request carry an explicit `requested_destination_direction`, and does dispatcher pathfinding reject ambiguous or wrong-direction candidates rather than guessing?
- Are repeated resources rejected during both `create_path()` and `extend_path()`?
- In `best_effort` mode, does the system keep one live `path_id`, extend `resource_sequence` in place, and avoid treating a truncated-but-live authority as a creation failure?
- Does `best_effort` creation fail instead of storing a live authority when the head is on a switch and no forward block can be acquired?
- Do dispatcher progress/completion/release callbacks all identify active authority by `train_id` rather than by caller-supplied `path_id`, with `PathDispatcher` resolving active progress from its own database rather than from physics or train mirrors, while delayed release of a still-occupied block or switch resolves from the resource itself after authority release?
- Are multi-train routes using per-train `RouteRun` objects (current-code class may still be `RouteExecutionState`) as the only canonical progress store, with no route-level runtime progress summary fields retained in the target model for now?
- Does Phase 1's covered-task index advance loop resolve `PlatformTarget` and `StationTarget` task targets as needed, advance past already-covered `task_kind == "waypoint"` tasks, and avoid advancing past `task_kind == "stop"` tasks solely because the target block is covered?
- On active-run plan replacement (operator retargeting and route swap follow abort + new assignment, never a `route_id` rewrite) and on shared-route reconciliation, does `RouteExecutor` clear the affected `path_cancelled` handoff state through the canonical write contract and replan from the train's current physical position without synthetic progress jumps, while keeping target identity in `task_runs[i].resolved_target` rather than in `current_route_status`, and without keeping any stored planning cursor outside `_find_next_task_target(train_id)`?
- Does stop completion require the post-physics usable-authority stop check, and do controller deviation cases produce `path_cancellation` with `initiator = "deviation"` and the structural distinction carried on the event payload's `deviation_kind` field?
- Does the normal `CAUTION -> FREE` reevaluation require either (a) the forward neighbour (in `block.caution.direction`) to be non-`OCCUPIED`, or (b) the `OCCUPIED` forward neighbour to hold a train whose current `travel_direction` is the opposite of `block.caution.direction` (cab-flip case), while still allowing the explicit completion-time `force` exception in `release_path_block_reservations(..., completed=True)`? (`occupied_by` is always `None` in `CAUTION` — guaranteed by `on_block_tail_vacated()` clearing it — so a separate non-occupied check on the CAUTION block itself is vacuous. `reserved_by_path` is explicitly not a gating condition; if `block.caution` has cleared but `reserved_by_path` remains set, the computed block state is `RESERVED`, not `FREE`.)
- Can any completion or cancellation path still unlock a block or switch that the train physically occupies at full stop?
- After `TrainController.eb.release()`, does the system return to the **`READY` state** (per the predicate defined in the Controller state machine subsection) and restart through fresh path creation followed by a Phase 1 `TrainController.depart()` call per the canonical depart contract?
- Do train-owned flank-protection claims record `source_switch_id` so tail-vacate can release only the protection created from the vacated main switch?

**Notes**

- In the desired model, ordinary switch release happens when the train tail vacates the switch tile, not on full path completion. `TrainController.on_physics_updated(span_update)` reports the vacated resource in `tail_vacated_resources`, and `PathDispatcher.on_controller_progress(report)` releases it according to `resource_type`: blocks go through `BlockManager.on_block_tail_vacated(...)`, while switches clear `Switch.occupied_by` and release train-owned protection sourced from that vacated switch through `Switch.release_train_protection_from(...)`. The neighbour-side `source_switch_id` filter protects claims created by other occupied main switches. Both completion and cancellation must respect physical occupancy: if a switch is still physically occupied, its train-owned protection stays in place until the later tail-vacate event.
- `assigned_path_id` moves from `Train` to `TrainController` as a read-only derived property of `received_path_plan.path_id`. The underlying `received_path_plan` is itself a read-only projection over `self.simulation_controller.path_dispatcher.get_active_path(train_id)` (which derives over `Path.status == ACTIVE`), so updates and releases surface automatically without any controller-side write step.
