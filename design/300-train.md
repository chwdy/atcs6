## Train Entity

**Train ownership**

- `Train` is the persistent/configuration entity. Persistent/configuration fields kept on `Train` in v1 are identity, consist (including length), `max_speed`, and other non-live train-configuration data already on the entity. `assigned_route_id` is no longer carried on `Train` at all (no field, no property, no back-reference to the network). Consumers ask `RouteExecutor.assigned_route_id_for(train_id)` instead, which prefers the live `execution_states[train_id].route_id` and falls back to scanning `Route.assigned_train_ids` in the route registry. The active route is structurally encoded by the `RouteRun` registry, so no per-train sync is needed.
- All live runtime state lives on `TrainController`: `current_span` (live physical span, including end locators and ordered occupied tiles), `current_speed_kmh`, operational `state`, power/cab, ATO/path projections, and operational diagnostics. `TrainPhysics` computes movement and sends `span_update` deltas to the controller; the controller applies those updates to its own storage. Live target speed and speed-limit reason are reads from controller lookahead at distance 0; there is no `manual_target_speed`, `train.state`, `train.assigned_path_id`, `train.ato_destination_block_id`, `train.current_path`, `train.path_index`, or `train.reserved_blocks` field.
- Initial placement of `TrainController.physics_sync.current_span` is owned by `SimulationController.add_train(...)`. It constructs the train, builds its initial physical span from placement input (reusing the existing repo placement-to-position derivation that produces precise `end_a` / `end_b` locators plus `occupied_tiles`), obtains the controller, and writes the span directly into `TrainController.physics_sync.current_span` before any simulation tick runs. `SimulationController.get_or_create_controller(train_id)` does NOT seed the span — it only ensures the controller object exists and is registered.
- Persistence-loading code also calls `add_train(...)` with the saved placement payload for each restored train; there is no parallel `seed_train_span(...)` helper.
- After initial placement, `TrainPhysics` is the only normal producer of movement `span_update` values and `TrainController.on_physics_updated(span_update)` is the only normal writer for `TrainController.physics_sync.current_span`. Live movement updates never write back to `Train`.
