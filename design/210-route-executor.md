## Route And RouteExecutor

**Route data**

| Field | Type | Meaning |
| --- | --- | --- |
| `route_id` | `str` | Unique route identifier |
| `name` | `str` | Display name |
| `tasks` | `List[RouteTask]` | Ordered route definition — see **RouteTask data** |
| `mode` | `RouteMode` | One of `ONE_OFF`, `CIRCULAR`, `ROUND_TRIP` |
| `assigned_train_ids` | `List[str]` | Stored list of train IDs assigned to the route. Canonical mutators are `Route.assign_train(train_id)` (appends if not already present) and `Route.unassign_train(train_id)` (removes if present); both are idempotent. The field is written from these canonical entry points only — see **Route assignment writers** below. |
| `is_active` | `bool` | Route execution enabled |
| `started_at` | `Optional[float]` | System-time Unix timestamp when activated |
| `created_at` | `float` | System-time Unix timestamp when the Route record was constructed. Sampled by `Route.__post_init__` via `time.time()` at the write site (see **Time sampling** under the **Units contract**). Written exactly once at construction; never mutated by edit, assignment, activation, deactivation, or any other handler. |
| `last_edited_at` | `Optional[float]` | System-time Unix timestamp of the most recent route-definition edit. `None` for a freshly-constructed Route that has never been edited after creation. Written only by the canonical route-definition edit writers — see **Route edit timestamps** below. Not touched by `Route.assign_train` / `Route.unassign_train` (assignment) or `Route.activate` / `Route.deactivate` (lifecycle). |

**Route assignment writers**

`Route.assigned_train_ids` is mutated only through these canonical writers:

- `Route.assign_train(train_id)` and `Route.unassign_train(train_id)` are the two helper methods; both are idempotent.
- HTTP/UI/admin entry points that ultimately call those helpers (existing v1 routes; their exact paths and payload shapes are unchanged from current code unless this document overrides them):
  - `POST /api/train-routes` accepts an `assigned_train_ids` list in its body and calls `Route.assign_train(train_id)` for each.
  - `PUT /api/train-routes/<route_id>` diffs the existing list against the requested list and calls `Route.assign_train(train_id)` / `Route.unassign_train(train_id)` per change.
  - `PUT /api/trains/<train_id>/assign-route` calls `Route.assign_train(train_id)` (with optional unassign of any previous route).
- Internal teardown writers that call `Route.unassign_train(train_id)`:
  - `RouteExecutor.remove_train_route_run(train_id)` (called by Phase 3 abort, power-off, and deactivate consumers).
  - `RouteExecutor.finish_route_run(train_id)` (called by Phase 1 terminal-walk completion).
- Operator retargeting / route swap handlers also call `Route.unassign_train(train_id)` on the old route and `Route.assign_train(train_id)` on the new route as part of the atomic two-step retarget flow defined in **Route Edit And Reconciliation**.

`RouteExecutor.assigned_route_id_for(train_id)` (derived read) is kept in sync with `Route.assigned_train_ids` (stored) by construction: the only sites that flip a `RouteRun.state` out of `RUNNING` are also the sites that call `unassign_train(...)` on the matching `Route`. New assignments writing `Route.assign_train(train_id)` create a fresh `RUNNING` `RouteRun` only at the next eligible Phase 1 RouteRun (re)allocation step, so a brief window between the assign call and Phase 1 may show the train in `Route.assigned_train_ids` with no `RUNNING` `RouteRun` — that is the canonical signal Phase 1 step `9c4f` keys on to allocate a fresh run.

**Route edit timestamps**

`Route.created_at` is sampled exactly once via `time.time()` inside `Route.__post_init__`. No other writer touches it.

`Route.last_edited_at` is sampled via `time.time()` only by edit handlers that mutate the route definition. The set of fields whose mutation bumps `last_edited_at` is exactly: `name`, `tasks`, `mode`, `priority`, `acquisition_mode`. Mutations to `is_active`, `started_at`, and `assigned_train_ids` do NOT bump `last_edited_at` — those are lifecycle / assignment events and are timestamped through `Route.started_at` (activation) and the per-train `RouteRun` registry respectively.

The canonical route-definition edit entry points are:

- `POST /api/train-routes` — when the new Route is created with at least one of the five edit fields supplied in the request body, the handler writes `last_edited_at = time.time()` once at the end of the handler before persisting. A bare create with no edit fields leaves `last_edited_at = None`.
- `PUT /api/train-routes/<route_id>` — the handler writes `last_edited_at = time.time()` once at the end of the handler if and only if at least one of the five edit fields was actually written on this request. A request that touches only `assigned_train_ids` does not bump `last_edited_at`.

`Route.priority` and `Route.acquisition_mode` edits bump `last_edited_at` even though they do not trigger the structural-edit teardown described in **Route Edit And Reconciliation**: `last_edited_at` records the time of the last definition write, not the time of the last structural change. UI/log consumers that need to distinguish structural from non-structural edits cannot do so from `last_edited_at` alone in v1; they observe the teardown side effects instead.

**Canonical ownership split**

- `Route` is the shared plan definition only: ordered tasks plus route-level policy such as mode and acquisition mode. It does not own per-train mutable execution cursors.
- A route may be assigned to multiple trains in v1, but each train may execute at most one route task at a time. Each assigned train has at most one `RUNNING` `RouteRun` at any moment; the live read is `RouteExecutor.execution_state_for(train_id)` (computed by searching the registry for the `RUNNING` `RouteRun`). Historical `RouteRun` rows for the same train (state `FINISHED` or `DEACTIVATED`) are preserved indefinitely in the route registry as a parallel history; only the active-state predicate is single-instance. The run's `route_id` identifies which shared `Route` definition that train is currently following. That `RouteRun` is the per-train runtime instance of the shared plan and owns only per-train mutable execution state: task cursor, current traversal direction, per-task timing and resolved-target state (`task_runs`), route-version reconciliation state, and current route status. Shared route execution state across trains is not allowed.
- `Route` is live shared execution input in v1, not a snapshot source that is copied into each run. Active runs read the current shared `Route` through `RouteRun.route_id`, and later structural route edits trigger immediate teardown of every assigned train's currently-`RUNNING` `RouteRun` followed by fresh `RouteRun` allocation; see **Route Edit And Reconciliation**.
- In helper prose below, when an active-run helper still shows a `route` parameter, read that as the current shared `Route` resolved from `RouteRun.route_id` unless the paragraph explicitly says a new dedicated route assignment is being created.
- Because multi-train assignment is supported, `RouteRun` is the only canonical runtime progress store. Remove route-level runtime summary fields such as `Route.current_waypoint_index` and `Route.direction` from the target model for now; the future UI summary shape is intentionally left open rather than being baked into the refactor contract.
- Per-train route/path errors belong to `RouteRun.last_error` (an `Optional[ErrorRecord]` carrying both `text` and `time`); `Route` does not keep a shared last-writer-wins error summary in v1.
- Departure is not a route-level policy in v1. Phase 1 calls `TrainController.depart()` directly for every successful create/extend on the first eligible Phase 1 pass; the ATO-vs-manual behavioral difference is owned inside that call per the **`TrainController.depart()` canonical contract**. The driver in manual mode sees that depart has been accepted (state == `RUNNING_MOVING`) and starts moving the train; there is no separate operator-confirmation button.
- Add `acquisition_mode` at route level as the policy for how this route wants dispatcher authority to be acquired (`all_or_nothing` or `best_effort`), with default `AcquisitionMode.best_effort` when the route definition omits it. `RouteExecutor` reads the current shared `Route.acquisition_mode` for both `create_path(...)` and later `extend_path(...)` retries on the same planning chain.
- Add `priority` at route level as the canonical route-executor scheduling priority, with default `5`. Priority values are integers in `0..9`, where `9` is highest and `0` is lowest. `RouteExecutor` sorts runnable route runs by the current shared `Route.priority`; later shared-route edits may therefore legitimately reshuffle later tick order for active runs. Non-route and one-off/manual train work uses effective priority `5` when `SimulationController` merges it into the per-tick runnable-train order.
- `ResolvedRouteTarget` carries exactly `requested_destination_block_id` and `requested_destination_direction`. `requested_destination_direction` in this structure is always the block-relative direction for `requested_destination_block_id`. `Platform` has no direction field, no platform-frame direction, and no direction-conversion helper in v1; `PlatformTarget` and `StationTarget` resolution chooses a concrete platform-end block, then derives the resolved direction from `Block.ordered_tiles`, validates it against `Block.allowed_travel_directions`, and stores that block-relative result. There is no persistent per-task resolved-target cache outside `task_runs`: every new route-side path attempt resolves a transient candidate live from the current shared `Route`, current platform availability, train span, and task policy via `_find_next_task_target(train_id)`. That helper is read-only and returns one candidate per call. Phase 1's authority-acquisition step is the only canonical writer of `RouteRun.task_runs[i].resolved_target`, after a successful `PathDispatcher.create_path(...)` / `PathDispatcher.extend_path(...)` for that candidate. For a `StationTarget` task, `_find_next_task_target` returns one candidate per call; Phase 1 retries with successive candidates by re-invoking the helper after a failed `create_path(...)` / `extend_path(...)` attempt within the same tick. A `PlatformTarget` or `BlockTarget` task has only one candidate per tick. If a path request succeeds, the path record's `requested_destination_block_id`, `requested_destination_direction`, and `authority_end_block_id` become the dispatcher-owned stored target contract for that successful live segment, while `RouteRun.task_runs[i].resolved_target` records the candidate actually accepted for that segment. Operator/admin edits to platform/block target-resolution inputs (for example platform block membership/order, target block disablement, or `Block.allowed_travel_directions` changes) do not rewrite an already-successful live segment; they take effect the next time Phase 1 commits a new successful create/extend attempt.

**Canonical Next-Target Selection**

- **`ResolvedNextTaskProjection` schema.** The return type of `_find_next_task_target(train_id, exclude=None)` is `Optional[ResolvedNextTaskProjection]`. The optional `exclude` argument is a caller-owned set of already-attempted `ResolvedRouteTarget` values for the current planning problem; the helper itself stores no per-tick state. `None` means no next task on the current directed walk (terminal). Otherwise the projection carries:

  | Field | Type | Meaning |
  | --- | --- | --- |
  | `walk_position` | `int` | Walk-position index in `RouteRun.task_runs` of the next non-finished walk-position on the directed walk. The underlying `RouteTask` is `Route.tasks[task_runs[walk_position].task_index]`. |
  | `task_kind` | `"waypoint" \| "stop" \| "dwell"` | The task's kind, copied from the underlying `RouteTask.task_kind` for caller convenience. |
  | `direction` | `"forward" \| "reverse"` | The route walk direction at this task (may have flipped at a `ROUND_TRIP` reflection). |
  | `resolved_target` | `Optional[ResolvedRouteTarget]` | The resolved block + direction for `waypoint` and `stop` tasks. `None` for `dwell` tasks (which carry no dispatcher target) and for tasks whose target cannot be resolved in the current attempt (e.g. all station candidates have been tried). |

  The helper is **read-only**: it does not write `task_runs[walk_position].resolved_target` and has no other side effect on `RouteRun` state. The canonical writer of `task_runs[walk_position].resolved_target` is Phase 1's authority-acquisition step, after a successful `PathDispatcher.create_path(...)` / `PathDispatcher.extend_path(...)` for that task. All other callers (head-advance callback, dwell-complete step, UI projection) consume the helper's return value only.

- **Index-driven, live-recompute model.** The "armed next task" is reflected by `current_waypoint_index` and `direction`, not by a separate flag. The "armed target" is whatever `_find_next_task_target(train_id)` returns when called. Whenever any phase needs the current next-task projection — Phase 1's planning step, Phase 1's dwell-complete check, the head-advance callback's next-task pointer, or a UI projection — call `_find_next_task_target(train_id)`. The helper computes fresh from current shared `Route` + current physical progress + current span coverage. It does not arm authority, does not write `current_route_status.state`, does not advance `current_waypoint_index`, does not write `task_runs[i].resolved_target`, and does not call `PathDispatcher`.
- `_find_next_task_target(train_id)` is read-only with respect to `RouteRun` storage. For `RouteMode.ROUND_TRIP`, the helper resolves the direction flip at route ends and returns the flipped `direction` in the projection; the caller commits that direction to `RouteRun.signed_direction`.
- For a station task with multiple compatible platform-end candidates on the current tick, `_find_next_task_target(train_id, exclude=...)` picks one candidate per call. The helper itself does not maintain any per-tick state: the caller (Phase 1's per-tick retry loop) owns the `exclude` set of already-attempted resolved targets for this planning problem and passes it on each call. The helper enumerates the current candidate ordering, skips any candidate present in `exclude`, and returns the next untried one (or `None` when exhausted). For a `PlatformTarget` or `BlockTarget` task, only one candidate exists per tick. Non-Phase-1 callers (Phase 1 dwell-complete step, head-advance callback) pass `exclude=None` and receive the first candidate under the canonical ordering; that candidate is deterministic for the same shared `Route` + physical-progress + platform-availability inputs.
- If `_find_next_task_target(train_id)` returns no next task on the current directed walk, the current walk is terminal: Phase 1 calls `RouteExecutor.finish_route_run(train_id)` directly inside `tick_train_phase1(...)`, which sets `current_route_status.state = FINISHED` (`RouteExecutor.assigned_route_id_for(train_id)` automatically returns `None`) and (for `RouteMode.ONE_OFF` routes with no remaining assigned trains) calls `route.deactivate()` for any other still-assigned trains. The `RouteRun` is preserved as a historical `FINISHED` row in the route registry. Phase 1 then returns for that tick. By the time Phase 1 reaches this step, the matching live path has already been cleared by stop-completion in the prior Phase 3 pass, so no dispatcher cancel is needed. For `RouteMode.CIRCULAR` and `RouteMode.ROUND_TRIP`, `_find_next_task_target` never returns `None` (it wraps or reflects), so this terminal-walk branch never fires for those modes.
- If a next task exists but no legal concrete platform/block target can be resolved under the task's targeting policy on this attempt, the helper returns a `ResolvedNextTaskProjection` whose `walk_position`, `task_kind`, and `direction` describe that walk-position and whose `resolved_target` is `None`. The helper returns overall `None` only for the terminal-walk condition (line 919). If no live authority exists and Phase 1 has exhausted all same-tick candidates, Phase 1 stops for that train for that tick. If live authority exists, leave the live path and route status unchanged unless a later `extend_path(...)` result proves structural incompatibility.
- Callers must not rewrite `direction` or `task_runs[i].resolved_target` through raw increment/decrement index arithmetic or by indexing `Route.tasks` outside the helper. Next-task selection comes from `_find_next_task_target(...)`; committed progress advances through the head-advance callback recording `finished_at`, through Phase 1 dwell-complete step recording `finished_at`, and through Phase 1's covered-task index advance for already-passed `waypoint` tasks and same-block stopped-at-destination `stop` tasks.
- `Route.mode` is consumed inside `_find_next_task_target(train_id)`:
  - `RouteMode.ONE_OFF`: if no next task exists, return `None` (terminal).
  - `RouteMode.CIRCULAR`: wrap from the last task to the first task.
  - `RouteMode.ROUND_TRIP`: reflect at the route ends and flip `direction` together with the next task.
- The canonical `ROUND_TRIP` truth table for a three-waypoint route `[A, B, C]` is:
  - `714a`: `(-1, forward) -> (0, forward)`
  - `a91b`: `(0, forward) -> (1, forward)`
  - `1f41`: `(1, forward) -> (2, forward)`
  - `c733`: `(2, forward) -> (1, reverse)`
  - `79a9`: `(1, reverse) -> (0, reverse)`
  - `7db6`: `(0, reverse) -> (1, forward)`

**RouteTask data**

Retained current-code enums used by route data:

- `RouteMode`: `ONE_OFF`, `CIRCULAR`, `ROUND_TRIP`

`RouteTask` is the unified route-task schema in v1. Every entry in `Route.tasks` is a `RouteTask`.

| Field | Type | Applies | Meaning |
| --- | --- | --- | --- |
| `task_kind` | `"waypoint" \| "stop" \| "dwell"` | all | Required task behavior discriminator. `waypoint` is a pass-through traversal (no stop, no dwell). `stop` is a platform stop that enters dispatcher-committed completion. `dwell` is a hold at a location after a stop. |
| `task_location` | `BlockTarget \| PlatformTarget \| StationTarget` (tagged union) | all | The concrete target for this task. `BlockTarget(block_id: str)` for direct block targets, `PlatformTarget(platform_id: str)` for fixed concrete platforms, `StationTarget(station_id: str)` for logical stations resolved at runtime. The tagged union enforces that exactly one targeting mode is present. |
| `task_time` | `Optional[float]` | all | Semantics depend on `task_kind`. For `waypoint`/`stop`: expected travel time in seconds from the previous task's location to this task's location; used to classify arrival as early/on-time/late when the `RouteTaskRun` timing data is available; omit when no timing classification is needed. For `dwell`: how long in seconds to remain at the location; omit to allow departure immediately (equivalent to `dwell_time_sec = 0` in the old model). |
| `task_direction` | `Optional["forward" \| "reverse" \| "either"]` | all | Route-level block-relative traversal preference. `RouteExecutor` resolves `"either"` to a concrete direction before any dispatcher call; the dispatcher never receives `"either"`. Defaults to `"either"` when omitted. |
| `target_time` | `Optional[float]` | `stop` | Optional absolute system-time Unix departure timestamp. When present and the train arrives late (`current_time >= target_time`), departure is granted immediately. |

Route-task authoring rules:

- A typical platform stop with a hold is authored as two consecutive tasks: `stop(task_location=PlatformTarget(platform_X), task_time=expected_travel_seconds)` followed by `dwell(task_location=PlatformTarget(platform_X), task_time=hold_seconds)`. The `stop` enters dispatcher-committed completion; the `dwell` holds the train in `RUNNING_AT_STATION` until the dwell timer elapses.
- A terminal stop with no hold is authored as a single `stop` task with no following `dwell` task (or with `task_time` omitted on the implied dwell). There is no `dwell_time_sec = 0` field equivalent; a missing `dwell` task is the correct encoding.
- A pass-through is a single `waypoint` task. It resolves to a concrete `ResolvedRouteTarget` for authority planning, is completed by head entry into the resolved block, and does not invoke dwell logic or `TrainController.enter_station_dwell()`.
- `task_kind` is required. Missing, null, or unrecognized `task_kind` is a validation error at task creation time; `RouteExecutor` must never infer a default kind.
- A terminal task must not be `waypoint`. If the train must stop and reverse immediately with no dwell, the terminal task is `stop`.
- For target resolution and path acquisition, `waypoint` and `stop` tasks use the same resolution chain and the same dispatcher target contract. Both resolve to a `ResolvedRouteTarget` for authority planning. The behavioral difference: a `stop` arrival is dispatcher-committed completion from the post-physics controller stop check, and the route's `RouteTaskRun` records `finished_at` at stop completion; a `waypoint` is completed by head entry with no stop, no dwell, and no `TrainController.enter_station_dwell()`.
- A `dwell` task does not create or require new dispatcher authority. While a `dwell` task is the current active task, Phase 1 does not create or extend authority. The `dwell` task is complete when its `task_time` has elapsed since `task_runs[walk_position].started_at` (the derived read of the predecessor stop's `finished_at`, i.e. the moment the stop completed), at which point Phase 1 dwell-complete step inside `RouteExecutor.tick_train_phase1(...)` sets `finished_at`, calls `TrainController.finish_dwell()`, and leaves the next task to a later Phase 1.
- Station/platform distinction is explicit:
  - `Station` is a logical grouping of platforms used by route planning and platform selection.
  - `Platform` is the concrete physical stop. When a waypoint's task_location is a `PlatformTarget` or `StationTarget`, dispatcher path requests, block IDs, and directions are always derived from one resolved concrete platform, never from a station group directly.
  - The current attempt may resolve one concrete `platform_id` when resolution goes through a platform. For a `BlockTarget` waypoint, no platform resolution is needed.
- `Platform.ordered_blocks` is the canonical ordered list of block IDs in the platform, used to identify the two platform-end blocks and preserve edit stability. `Platform` carries no direction, no platform-local forward/reverse semantics, no per-block alignment mapping, and no user-facing directional option. It is initialized from the block order supplied to backend platform-creation/edit logic; backend validation must verify the supplied list is one connected switch-free walk in that exact order. Platform edits may only insert or remove linked blocks at the ends while preserving relative order; middle insertions, reorders, or reversals are rejected.
- `Platform` carries no direction or platform-side helper. If a platform should serve only one direction, the user must configure the underlying end block's `Block.allowed_travel_directions` so only that traversal is allowed.
- `requested_destination_direction` is the resolved traversal constraint at the requested target. Task authors express the route-level preference as `forward`, `reverse`, or `either` on `RouteTask.task_direction`, but those values are block-relative preferences, not platform-relative preferences. By the time `RouteExecutor` builds `ResolvedRouteTarget`, it must have resolved that preference into one concrete block-relative `"forward"` or `"reverse"` for the chosen `requested_destination_block_id`. For a task that resolves through a concrete platform, the candidate comparison defined in the platform resolution subsection below evaluates terminal traversals through the platform end block(s); `task_direction == "forward"` or `"reverse"` filters out candidates whose terminal traversal does not match that authored block-relative direction or is not allowed by `Block.allowed_travel_directions`. `task_direction == "either"` applies no route-authored direction filter, but every candidate must still satisfy `Block.allowed_travel_directions`, and `RouteExecutor` still stores the chosen block-relative concrete direction. When the task_location is a `BlockTarget`, `"forward"` / `"reverse"` are interpreted directly in that block's immutable internal traversal order, and `"either"` means `RouteExecutor` picks whichever block-relative direction is reachable under the same current-span comparison and allowed by `Block.allowed_travel_directions`. Dispatcher never receives `"either"` in the v1 path contract; route resolution must always eliminate it before calling `create_path(...)` or `extend_path(...)`. These are deliberately two distinct types: `RouteTask.task_direction` is the route-author input (may be `"either"`); `ResolvedRouteTarget.requested_destination_direction` is the strict subtype `"forward" | "reverse"` passed to dispatcher. Implementations must reflect this difference in their static types so that handing an unresolved `RouteTask.task_direction` to `PathDispatcher.create_path()` / `PathDispatcher.extend_path()` is a type error rather than a runtime branch.
- Define the exact dispatcher terminal frame separately. The terminal frame is the explicit directed geometry used for controller braking and diagnostics: `path_tiles`, `entry_edge`, and `exit_edge` for the relevant terminal block. When a live path exists, dispatcher derives that frame from the chosen terminal `resource_sequence` block entry. Boundary/safety-margin projection must never infer that frame from `requested_destination_direction` alone.
- Resolve waypoint targets through one canonical chain: `station -> platform -> block`. If the task_location is a `PlatformTarget`, resolution starts at `platform`. If it is a `BlockTarget`, resolution skips station/platform lookup and targets that block directly.
- When a task_location is a `StationTarget` rather than a `PlatformTarget`, `RouteExecutor` must resolve one concrete platform before path creation. In v1, platform availability is evaluated relative to the train for this route attempt. A platform is unavailable when any linked block is held by another train's physical occupancy or another train/path's live reservation. `CAUTION` by itself does not make a platform unavailable: a caution block may still be reserved/acquired when ordinary reservation rules allow it, and the caution state is consumed by `TrainController` lookahead as a lower ATC speed cap. The current train's own physical occupancy or current live authority must not make that platform unavailable to itself; same-train coverage is handled by Phase 1's covered-task index advance and same-train path conflicts are handled by the shared pathfinder/acquisition rules. Deterministic tie-breaking is required and follows the canonical candidate-order rule below.
- Platform/station target selection in v1 is:
  - if the task_location is a `PlatformTarget`, resolve exactly that platform for this tick. Pick its single best compatible platform-end candidate by the canonical graph comparison. If that create/extend attempt fails without creating or growing authority, wait until the next eligible tick rather than trying another platform or another platform end in the same Phase 1 pass.
  - if the task_location is a `StationTarget`, build the complete ordered transient candidate list of all compatible available platform-end candidates across every platform in `Station.platform_ids`, sorted by the canonical graph comparison (`tile_count`, then `walk_length_cm`, then `candidate_rank`, then final `end_a` dead-heat only across current-span end choices). In that same Phase 1 pass, `RouteExecutor` may try each distinct resolved `(requested_destination_block_id, requested_destination_direction)` pair from that station candidate list at most once, stopping as soon as one create/extend attempt creates or grows authority.
  - if the task_location is a `BlockTarget`, resolve exactly that block/direction for this tick. If the create/extend attempt fails without creating or growing authority, wait until the next eligible tick rather than inventing alternatives.
- A waypoint that wants "try any platform in this station" should use a `StationTarget`; a waypoint that uses a `PlatformTarget` targets that one concrete platform.
- Station candidate enumeration preserves the route-specified `requested_direction` literally as a block-relative traversal preference. If the waypoint specified `forward` or `reverse`, candidate platform ends are compatible only when their terminal traversal satisfies that direction under the candidate block's `Block.allowed_travel_directions`. If the waypoint specified `either` (or omitted the field, which is treated as `either`), any `Block.allowed_travel_directions`-compatible terminal traversal may be used.
- Later retries follow the same route-side selection policy. A concrete platform retry keeps the same platform and recomputes its current best compatible end on the later tick. A station retry may re-enumerate all compatible available platform-end candidates for that station on the later tick. If no concrete platform/block candidate can be resolved for the retry under that policy, `RouteExecutor` fails target resolution for that retry and must not treat it as an `extend_path(...)`-side retarget problem.
- For covered normalization and subsequent task service on the current directed route walk, a `PlatformTarget` or `StationTarget` task with `task_kind == "waypoint"` counts as satisfied when the train covers any compatible concrete platform in that task's allowed platform set; a `PlatformTarget` or `StationTarget` task with `task_kind == "stop"` counts as satisfied only after the stop has been served by dispatcher-committed stop completion and dwell exit. When either satisfaction rule applies, `RouteExecutor` uses the actually covered or served compatible block/platform only to decide satisfaction and to report diagnostics; it must not force resolution to some other platform, must not write a persistent served-platform choice for later route-control decisions, and must not depend on a persistent per-task cache to remember that choice later.
- For each concrete platform being considered, `RouteExecutor` must gather the terminal candidate block at each end of that platform by calling the same shared network-graph walk query that `PathDispatcher.create_path(...)` uses. For a multi-block platform, the candidate end blocks are the first and last entries of `Platform.ordered_blocks`; for a single-block platform, both platform ends collapse to the same block, so only that one block participates. If a cab is selected, only the current head-side start locator participates in this stop-planning comparison. If no cab is selected, both physical train ends may participate, and a switch-side end is first mapped inward to the occupied block at that end of the current span; if no such inward occupied block exists, that end is dropped from the comparison set. Each candidate graph-query result carries the terminal block-relative direction derived from the canonical block-direction helper through `Block.ordered_tiles`; that direction must pass the task direction filter and `Block.allowed_travel_directions`. For a `PlatformTarget` task, pick the shortest successful candidate using the canonical candidate comparison defined in **`GraphWalkCandidate` payload**, applied across the remaining current-span end choices. For a `StationTarget` task, keep the full sorted list of compatible successful platform-end candidates as transient same-Phase-1 retry state, and try each distinct resolved `(requested_destination_block_id, requested_destination_direction)` pair at most once in that pass. The chosen or currently attempted block becomes `requested_destination_block_id`, and the chosen block-relative direction becomes `requested_destination_direction`. This is how task-authored `"either"` is converted into one concrete `"forward"` or `"reverse"` for `PlatformTarget` and `StationTarget` tasks. If no candidate succeeds, fail the task attempt. The chosen/current candidate block is the dispatcher-facing target block for both `stop` and `waypoint` tasks that resolve through a `PlatformTarget` or `StationTarget` task_location.
- For a task-authored `task_direction == "forward"` or `"reverse"`, the same candidate comparison is used, but pairs whose resulting block-relative direction does not match the authored direction are dropped from the comparison before selection. For `task_direction == "either"`, no route-authored direction filter is applied and the shortest allowed candidate wins.
- After resolution, `RouteExecutor` derives the per-attempt `ResolvedRouteTarget` (`requested_destination_block_id`, block-relative `requested_destination_direction`) for the current task and passes only that transient route-owned request contract into `PathDispatcher`. There is no platform-frame direction to convert. Phase 1's authority-acquisition step, after a successful `PathDispatcher.create_path(...)` / `PathDispatcher.extend_path(...)` for that task, writes the actually-attempted candidate into `RouteRun.task_runs[walk_position].resolved_target`, where `walk_position` is the index returned by the same Phase 1 pass's `_find_next_task_target(train_id)` projection. `_find_next_task_target(train_id)` itself never writes that field. Callback-time code may call the helper to recompute live without disturbing `task_runs[i].resolved_target`; the stored value remains whatever Phase 1's last successful create/extend wrote and is the authoritative match key for later stop-completion lookup. Later planning retries call `_find_next_task_target(train_id)` again whenever Phase 1 needs a fresh resolve, and Phase 1's next successful create/extend overwrites the bookkeeping value.
- A task with `task_kind == "stop"` may therefore use a `task_location` that is:
  - a `PlatformTarget`, or
  - a `StationTarget`, in which case `RouteExecutor` resolves a concrete `platform_id` for the current attempt before path creation, or
  - a `BlockTarget`, in which case no platform resolution is required.
- Keep platform targeting, dwell/timing rules, platform-selection flexibility, and block-relative direction policy.
- Direction compatibility depends only on block-level `Block.allowed_travel_directions` plus current availability — there is no `required_platform_side` or platform-side direction helper.
- Add explicit stop-policy data used by route arrival and same-block repositioning for tasks with `task_kind == "stop"`:
  - the resolved destination block for the task attempt
  - the block-relative traversal direction for that attempt
- Add an explicit route-owned traversal-constraint field, `requested_destination_direction`, on the per-attempt `ResolvedRouteTarget` for every task. Same-block / same-tile repositioning must not guess direction from geometry alone; before path creation, `RouteExecutor` must resolve the task-authored `task_direction` into one concrete block-relative `"forward"` or `"reverse"` for `requested_destination_block_id` and store that value on `ResolvedRouteTarget`. Dispatcher still derives the exact terminal frame from explicit terminal geometry, but it does so after route resolution has already eliminated `"either"` from the request contract.
- If the task_location is a `StationTarget` or `PlatformTarget`, `requested_destination_block_id` is resolved only after `RouteExecutor` has picked a concrete platform for that train's current attempt and then applied the canonical shorter-path platform-end selection rule above. If the task_location is a `BlockTarget`, that block becomes `requested_destination_block_id` directly, but a disabled block is not a valid direct target. In all cases, the stored `requested_destination_direction` is the block-relative direction for that resolved block; there is no raw platform-level direction token in the route definition or resolved runtime state.
- Do not define a separate stop-window tolerance or route-authored stop-position field in v1. The controller safety margin is used by controller lookahead and ATO braking to shape the train's stop, but route completion does not manually verify a centimeter tolerance around any route value.
- For tasks with `task_kind == "stop"`, task arrival is not simply "the train is in the task block", but it is also not gated by an exact-stop tolerance check in v1. A stop task enters dwell only after dispatcher completion caused by the post-physics controller stop check for the active authority that reaches the resolved target, and that stop task is marked finished only when the following dwell task exits (or immediately if no dwell task follows). `task_kind == "waypoint"` is reached by train-head entry / physical pass of its resolved block. Controller deviation cases produce `path_cancellation` with `initiator = "deviation"`; the structural distinction between out-of-sequence and beyond-authorized-target flows on the event payload's `deviation_kind` field.
- Add one shared boundary projection helper such as `RailwayNetwork.project_authority_boundary_delta(head_locator, authority_end, safety_margin_cm) -> delta_cm`. `head_locator` is a `GraphLocator` carrying `tile`, `edge`, and `distance_cm` for the live train head. `authority_end` carries `block_id` and `terminal_frame: DirectedBlockFrame` (whose `path_tiles`, `entry_edge`, and `exit_edge` describe the directed terminal frame for the authority-end block). The helper uses tile lengths and traversal geometry to project the live train head and the safety-margin-adjusted authority boundary onto the same forward axis, then returns their signed separation in centimeters on that shared axis: positive means the train head is past the safety-margin boundary in the forward axis, negative means it is still short of it, and zero is on-target. In v1 this helper is for braking/diagnostic projection only; it is not the authoritative path-completion gate, and `RouteExecutor` must not compare live train position against it itself.

**Task time semantics**

- All stored route/task timestamps use system-time Unix seconds.
- `RouteTask.target_time`, when present on a `stop` task, is the absolute system-time Unix departure timestamp. If the train arrives late (`current_time_sec >= target_time` at dwell entry), `RouteTask.should_depart(...)` returns `True` immediately with no extra wait.
- `RouteTask.should_depart(started_at_time_sec, current_time_sec)` uses only system-time Unix seconds in v1:
  - if `target_time` is present, depart when `current_time_sec >= target_time`
  - otherwise, for a `dwell` task, depart when `current_time_sec - started_at_time_sec >= task_time` (where `task_time` is the dwell task's hold duration and `started_at_time_sec` is the dwell row's `started_at`)
  - if neither `target_time` nor `task_time` is set on the dwell task, depart immediately
- A `stop` task is independent of its neighbors. It records `finished_at` at dispatcher-committed stop completion and the route progress cursor advances with that write. A following `dwell` task (when present) is a separate row with its own `started_at` / `finished_at` lifecycle. The presence or absence of a following `dwell` does not change stop-task behavior. `should_depart(...)` is only evaluated against `dwell` rows.

**Route-definition validation**

- A valid route definition must contain at least one `task_kind == "stop"` task in total. Single-stop routes are valid (e.g. one-off reposition or single-destination delivery); the single stop is both the first and final stop.
- Consecutive stop tasks that resolve to the same concrete target are valid. Route validation must not reject or collapse them merely because their resolved `requested_destination_block_id` / `requested_destination_direction` pair is identical; runtime stop handling decides whether the next stop is completed through the ordinary stop-completion/dwell path or used as an explicit local reposition destination. A stop task is not skipped solely because its block is already covered.
- Every task must provide `task_kind` explicitly as `"waypoint"`, `"stop"`, or `"dwell"`. Missing `task_kind`, null `task_kind`, or any other value is a validation error at task creation/update time.
- A route made only of `waypoint` tasks is invalid.
- The stored `Route.tasks` list must end in `task_kind == "stop"` (or a `dwell` task immediately following a `stop`) before a `RouteRun` may be created. The schedule editor/API must validate that terminal stop requirement before sending the route to route-run activation. `RouteMode.CIRCULAR` changes how the stored task list is interpreted during execution, but it does not remove the requirement that the authored list itself ends at a stop or dwell. The terminal task sequence is part of the route: the route is not complete until any terminal `dwell` task's timer has elapsed, or the terminal `stop` task has completed when no `dwell` follows it. A terminal `stop` with no following `dwell` is the canonical "stop and end immediately" shape; a terminal `stop` followed by a `dwell` with `task_time > 0` or `target_time` is the canonical "end after holding at the platform" shape. Both are valid.
- A bulb loop or other turnaround that returns to the same stop must be modeled explicitly in the task list (for example `A(stop) -> bulb(waypoint) -> dwell(A) -> A(stop)`). `RouteMode.ROUND_TRIP` does not infer that geometry from one terminal stop.
- Every `task_kind == "stop"` task must identify a valid stop target through `task_location`: a `BlockTarget`, a `PlatformTarget`, or a `StationTarget` that can be resolved to a platform at runtime.
- `Route.priority` must be an integer in `0..9` (`9` highest, `0` lowest); out-of-range values are a route-definition validation error rejected at activation time.
- `RouteExecutor` should reject or refuse to activate any route definition that violates these rules rather than trying to infer missing stop semantics at runtime.

**Route-run state**

This is the canonical field set for `RouteRun` in v1. The canonical store for every `RouteRun` is the per-route `RouteRegistryEntry.runs` map under `RouteExecutor.route_registry[route_id]`; a `RouteRun` is filed there by its `run_number` at creation time and stays there indefinitely as either a live `RUNNING` row or a historical `FINISHED` / `DEACTIVATED` row. A train may have many historical `RouteRun` rows in the registry over time; the live invariant is that at most one `RouteRun` per `train_id` has `current_route_status.state == RUNNING` at any moment. `RouteExecutor.execution_state_for(train_id)` is a derived read, not a stored dict: it scans the registry for the one `RouteRun` whose `train_id` matches and `current_route_status.state == RUNNING`, returning that one or `None`. The parallel history accessor `RouteExecutor.history_for_train(train_id)` returns every `RouteRun` (any state: `RUNNING`, `FINISHED`, `DEACTIVATED`) for that train across all routes, ordered by `run_number` ascending. Return type: `List[RouteRun]`. The accessor flattens across all `RouteRegistryEntry.runs` maps in the registry, selects only rows where `run.train_id == train_id`, and sorts the result by `run_number` ascending. Throughout the rest of this section the name `exec_state` is used as a short alias for the train's currently `RUNNING` `RouteRun` (i.e. the result of `RouteExecutor.execution_state_for(train_id)`); when that read returns `None`, no helper that names `exec_state` runs.

`RouteExecutor.route_registry` is in-memory only; it is not persisted across process restart (persistence is Out of Scope for v1 per the Out of Scope table).

- Operator/manual same-block or same-tile reposition is modeled through the ordinary one-off `Route` + `RouteRun` flow, with no special run-level flag. - `text` — `str`, the diagnostic error message
- `time` — `float`, system-time Unix seconds when the error was recorded

This is the canonical field set for `RouteRun.current_route_status` in v1.

**RouteTaskRun schema**

`RouteTaskRun` is the per-run task-state entry. `RouteRun.task_runs` is a `List[RouteTaskRun]` parallel to `Route.tasks` — one entry per task index, allocated when the `RouteRun` is created and indexed by the same integer index as `Route.tasks`. `RouteTaskRun` is the canonical owner of per-task timing, resolved dispatcher target, and per-task error context.

For `dwell` walk-positions, set when the dwell timer is satisfied and the controller transitions out. `None` until the walk-position ends. Every `finished_at` write triggers `RouteRun._append_next_walk_task()` per the canonical append rule. |
| `delay_class` | `Optional["early" \| "on_time" \| "late"]` | Timing classification computed when `finished_at` is recorded, by comparing the underlying `Route.tasks[task_index].task_time` (expected travel time from the previous task's location to this task's location) with the actual elapsed time since the predecessor walk-position's `finished_at` (use `RouteRun.started_at` for walk-position `0`). `None` when `task_time` is absent on the shared task or when the walk-position has not yet finished. Not computed for `dwell` walk-positions. |
| `last_error` | `Optional[ErrorRecord]` | Most recent per-task error recorded during a failed planning or completion attempt for this task. Diagnostic only. `None` when no error has been recorded; otherwise an `ErrorRecord(text: str, time: float)` (system-time Unix seconds). |

`ResolvedRouteTarget` is the resolved dispatcher request contract for one task attempt: `requested_destination_block_id: str` and `requested_destination_direction: "forward" | "reverse"`. It supersedes `ResolvedWaypointTarget`.

The "armed next task" is reflected by the directed-walk projection, not by a separate flag: it is the next `task_runs[i]` returned by `_find_next_task_target(train_id)` for the current directed walk. There is no `_arm_next_target(...)` step. `task_runs[i].resolved_target` is the historical record of what Phase 1's last successful create/extend used for that task, not a gate that says "this task is armed."

For predecessor timestamp lookup (used by `delay_class`, dwell timer, and any other "elapsed since predecessor" computation): the predecessor is the directly-preceding walk-position. For walk-position `0` on a newly created `RouteRun`, the predecessor is the synthetic route-start sentinel `RouteRun.started_at`. The derived `task_runs[i].started_at` returns `RouteRun.started_at` for `i == 0` and `task_runs[i - 1].finished_at` otherwise, so any "elapsed since predecessor" computation reads `task_runs[i].started_at` directly. That predecessor `finished_at` always exists by the time walk-position `i` becomes active, because tasks finish in walk-position order and each new walk-position is appended only after its predecessor's `finished_at` is written.

**`RouteRun._append_next_walk_task()`** is the canonical helper that grows `task_runs` on every `finished_at` write. It is called by every site that writes `task_runs[i].finished_at` (head-advance callback, stop-completion callback via `_enter_task_arrival(...)`, Phase 1 dwell-complete step, Phase 1 covered-task index advance) immediately after the write commits. It selects the next `task_index` to append per `Route.mode`:

- `RouteMode.ONE_OFF`: do not append. After the terminal task finishes, `task_runs` stops growing.
- `RouteMode.CIRCULAR`: append a new `RouteTaskRun` whose `task_index` is the next-in-cycle index (i.e. `(task_runs[i].task_index + 1) mod len(Route.tasks)`).
- `RouteMode.ROUND_TRIP`: append a new `RouteTaskRun` whose `task_index` follows the canonical ROUND_TRIP truth table: forward direction past the last task reflects to the second-to-last task with reverse direction; reverse direction past the first task reflects to the second task with forward direction. The appended walk-position carries the reflected `direction` on the run side via `RouteRun.signed_direction` updates owned by `_find_next_task_target(...)`; the appended `RouteTaskRun` itself carries no `direction` field — direction lives on the `RouteRun`.

The appended `RouteTaskRun` initializes with `finished_at = None`, `resolved_target = None`, `delay_class = None`, `last_error = None`. Its derived `started_at` reads `task_runs[i - 1].finished_at` (the value just written by the caller). The helper never re-reads or mutates older walk-positions.

- `RouteRun` is the canonical per-train runtime object for one assigned route. Current-code implementation may still name the class `RouteExecutionState`, but every changed contract in this section refers to that object as the train's `RouteRun`.
- Keep `current_waypoint_index`, `direction`, and `task_runs`.
- `RouteRun.current_route_status` is route-owned temporary per-run status, not a shared route-definition cache. `RouteExecutor.handle_path_completion(...)` reads this object and the dispatcher-passed completion context. `RouteExecutor.handle_train_advanced(...)` also reads it. Both callbacks identify the current task by index; whenever they need a fresh `ResolvedRouteTarget`, they call `_find_next_task_target(train_id)`.
- `task_runs[i].resolved_target` is the historical record of Phase 1's last successful create/extend for task `i`. The only writer is Phase 1's authority-acquisition step, on a successful `PathDispatcher.create_path(...)` / `PathDispatcher.extend_path(...)` for that task. `_find_next_task_target(train_id)` is read-only; head-advance, dwell-complete, and UI consumers consume the helper's return value and do not write `task_runs[i].resolved_target`. No callback ever clears it; it is overwritten only by the next successful create/extend that targets the same task.
- `RouteExecutor` owns a scheduling registry over these `RouteRun` entries. On each Phase 1 tick it iterates runnable runs in descending current shared `Route.priority` order rather than arbitrary per-train order. Among equal priorities, stable existing iteration order is acceptable in v1.
- `RouteExecutor.remove_train_route_run(train_id)` is the route-owned removal entry point used by Phase 3 abort, power-off, and deactivate consumers (per the **`current_route_status` write contract**). All three Phase-3 latch consumers call it with the same single argument; the originating cause is recorded only on the `path_cancellation` and `command_result` notifications, not on any helper parameter or any field on the `RouteRun`. Natural terminal completion uses Phase 1's direct `RouteExecutor.finish_route_run(train_id)` call instead and writes `FINISHED`. When `remove_train_route_run(...)` is invoked, it first looks up the train's currently-`RUNNING` `RouteRun` via `RouteExecutor.execution_state_for(train_id)`. If no `RUNNING` run exists (e.g. a powered-off train without a route, or a train whose run was already torn down by an earlier consumer in the same Phase 3 pass), the call is a no-op success and returns immediately. Otherwise it performs the active-run teardown sequence:
  - if a live dispatcher path still exists for this train (`active_path_id_by_train(train_id)` is set), the caller must already have cancelled it through `PathDispatcher.cancel_path(...)` before invoking this method (the canonical caller is the same Phase-3 cleanup pass that already runs the inclusive-cancel step, so the latch-cancel-then-callback flow handles this naturally),
  - if the controller is currently in `RUNNING_AT_STATION` (the `RouteRun` is dwelling), the method calls `TrainController.finish_dwell()` to exit dwell into the **`READY` state** before clearing route-run state,
  - it calls `Route.unassign_train(train_id)` on the run's `route_id` (idempotent if the train has already been unassigned by an earlier handler step) and flips the run's active-state predicate by setting `current_route_status.state = DEACTIVATED`, so the derived `RouteExecutor.execution_state_for(train_id)` read no longer returns it. Historical rows from finish/deactivate that already exist in the registry are NOT touched. The `RouteRun` itself is NOT removed from the registry; only the active-state predicate flips, and the run remains as a historical row (visible to `RouteExecutor.history_for_train(train_id)`).

  An explicit operator/admin "abort route" request — including operator retargeting and explicit route swap — is delivered through the controller-owned Phase-3 latch `pending_route_abort` per the inclusive-latch rule defined in the **Latch Table** preamble. That same Phase 3 cleanup calls `remove_train_route_run(train_id)` only when the abort latch is consumed after the dispatcher cancel step (or the dispatcher-cancel-skipped no-active-path branch) has run. Aborting a dwelling train therefore takes that same path: Phase 3 cancels any live path (or skips the dispatcher cancel when none exists), then `remove_train_route_run(...)` exits dwell via `finish_dwell()` and flips the run's active-state predicate.

- **`RouteRun.last_error` and `RouteTaskRun.last_error` clearing rule.** Both fields are overwrite-only diagnostic records and are never cleared during a `RUNNING` run; later writers replace the prior `ErrorRecord` with the most recent failure context. Both initialize to `None` at run creation. They are not cleared by a successful create/extend, by stop completion, or by route-deviation cleanup. Run-terminal writes (`RouteExecutor.finish_route_run(train_id)`, `RouteExecutor.remove_train_route_run(...)`) leave whatever record was last written in place as part of the historical row.
- **`RouteTaskRun.last_error` canonical writer.** Phase 1 step `66aa` records per-task error context on `task_runs[walk_position].last_error` (where `walk_position` is the index returned by `_find_next_task_target(...)` for that attempt) on a failed `PathDispatcher.create_path(...)` / `PathDispatcher.extend_path(...)` for that task. The value is one `ErrorRecord(text=..., time=time.time())`. Same-task subsequent failures overwrite the field. No other writer touches it. Phase 1 step `66aa` also writes `RouteRun.last_error` on the same failure (so the run-level "most recent error" reflects the latest task-level error).
- Do not add a synchronous `RouteExecutor.continue_route_run_after_eb(...)` hook. EB release is handled through latches: the EB activation has already written `pending_path_cancel_request` with `initiator = "eb"`, which Phase 3 commits and which sets `RouteRun.path_cancelled = True` via the cancellation callback. The same train's later Phase 1 route-deviation-cleanup step consumes `path_cancelled` once the controller has reached `READY` with no live path. The next `RouteExecutor.tick_train_phase1(...)` tick reruns the ordinary planning kernel from the current physical position: covered-task index advance for already-passed `waypoint` tasks, `_find_next_task_target(train_id)` to resolve the next task, and a brand-new `PathDispatcher.create_path(...)`. This flow does not reuse, complete, or preserve the cancelled pre-EB path chain.
- The derived `current_waypoint_index` reads `None` when no task has finished yet (no `task_runs[i].finished_at` is set). There is no "synthetic current-location start stop" branch: a one-off reposition route is authored as a single-task `stop` route; `current_waypoint_index is None` means "no task has been completed yet" and `Route.tasks[0]` is the first planning target.
- `current_waypoint_index` is the route-progress cursor: derived from `task_runs[i].finished_at`, it always marks the last task the train has actually finished. There is no separate stored planning cursor in v1; whenever any phase needs the next-task index, it calls `_find_next_task_target(train_id)` afresh.
- The initial `RouteRun.signed_direction` is `"forward"` through the stored route order. The route plan remains an ordered list in v1. Reversible round-trip behavior comes only from `RouteRun.signed_direction` flipping between `"forward"` and `"reverse"` inside `_find_next_task_target(train_id)`, not from building a second linked or reversed route structure.
- When a new target is resolved, `_find_next_task_target(train_id)` returns the next-task projection and resolved target candidate. Phase 1 sets `direction` to the resolved direction, and after a successful create/extend writes `task_runs[walk_position].resolved_target` (where `walk_position` is the helper's returned index) to the accepted candidate. Route planning must not look beyond the resolved task in one pathfinder request.
- A failed `PathDispatcher.extend_path(...)` without growing authority while a live path still exists, and a `RouteExecutor.handle_path_cancellation(...)` for the matching live path, both leave physical progress unchanged. There is no separate planning-cursor rollback; later Phase 1 calls `_find_next_task_target(train_id)` from the current shared route, current physical progress, and the current live authority end or no-authority stopped position as applicable, and that helper resolves the next task fresh. `PathDispatcher.create_path(...)` failure follows the same rule: the next Phase 1 simply re-invokes `_find_next_task_target(train_id)`.
- `RouteExecutor` reads the live path id via `PathDispatcher.active_path_id_by_train(train_id)`. A single live path may remain active across multiple task segments. After `waypoint` consumption, `dwell` completion, or `stop` completion, `task_runs[i].finished_at` is recorded for the consumed task (the derived `current_waypoint_index` advances to that index automatically), and only a later progress callback or later Phase 1 may discover the next task on the same `path_id` when authority is still live. A single `RouteExecutor.handle_train_advanced(...)` callback never consumes more than one task.
- UI consumers wanting "why does the train have no live authority?" read `RouteRun.last_error` (the most recent path/route failure recorded by Phase 1) plus the controller's live `lookahead` diagnostics. (Watchdogs and alert notifications are Out of Scope; see the **Out of Scope** section.)
- Do not add a separate controller operational sub-state for cancellation recovery in v1. When a live path is cancelled, `PathDispatcher` still clears controller authority and the controller enters the no-authority EB protocol per step `826a` (lookahead becomes the no-authority empty payload; ATC overspeed at distance 0 escalates to EB). The deferred recovery gate is the `path_cancelled` latch (see Latch Table); `RouteExecutor.handle_path_cancellation(...)` sets it and records diagnostic context immediately in Phase 3, but does not choose a new target or create fresh authority there. Once the train reaches the stopped no-authority state (after EB has brought it to rest and `eb.release()` has cleared EB to `READY`), the same train's Phase 1 route-deviation-cleanup step consumes `path_cancelled`. A later eligible Phase 1 then re-enters ordinary planning: covered-task index advance for already-passed `waypoint` tasks, then `_find_next_task_target(train_id)` to resolve the next task.
- Phase 1's covered-task index advance: at the start of each Phase 1 tick, `RouteExecutor.tick_train_phase1(...)` reads the train's current span via `SimulationController.get_or_create_controller(train_id).get_current_span()` and walks the current directed route from `current_waypoint_index` (the derived read of "last finished task"). For each next non-finished task on the directed walk: if `task_kind == "waypoint"` and the task's resolved target block (resolved live for this purpose) is already inside the current span, set `task_runs[i].finished_at = current_time` (the derived `current_waypoint_index` advances with that write) and continue. If the next task is `task_kind == "stop"`, block coverage alone never finishes it — stops are served only by dispatcher-committed completion. If the next task is `task_kind == "dwell"`, return without advancing — dwell is handled by the Phase 1 dwell-entry step inside `RouteExecutor.tick_train_phase1(...)`. There is no separate `_advance_past_covered_waypoints(...)` helper or `_skip_waypoint(...)` helper in v1; the index advance is just a small loop inside `tick_train_phase1`.

**Canonical Route-Progress Events**

- `current_waypoint_index` advances automatically (it is a derived read) when any of these route-owned events writes `task_runs[i].finished_at` in v1:
  - head-based `task_kind == "waypoint"` consumption in `RouteExecutor.handle_train_advanced(...)`, at most one task per head-advance callback
  - `task_kind == "dwell"` completion after the dwell timer elapses following a dispatcher-committed stop arrival
  - Phase 1's covered-task index advance for already-covered `waypoint` tasks (including post-cancellation reconciliation)
  - route edit / reconciliation that explicitly declares one or more pending tasks skipped
- Head-based `task_kind == "waypoint"` consumption is a route-owned in-motion progress event, not a dispatcher stop-completion event. The canonical trigger chain is `TrainPhysics.tick(...)` → `TrainController.on_physics_updated(span_update)` → `PathDispatcher.on_controller_progress(report)` → `RouteExecutor.handle_train_advanced(...)`. The callback contract is fully defined once in the **Dispatcher progress/completion flow** section; consult that section. Summary: each callback consumes at most one task. If the reported block matches the next non-finished task's resolved target, the callback records `task_runs[i].finished_at` (the derived `current_waypoint_index` advances with that write) and returns. Non-matching block reports are no-ops on the route side; intermediate tasks the train physically passed are reconciled by the next Phase 1's covered-task index advance.
- Already-covered `waypoint` normalization is a Phase 1 step: it records `task_runs[i].finished_at = current_time` (so the derived `current_waypoint_index` advances) for any next-on-walk `waypoint` task whose resolved target block is already inside the train's current span. `task_kind == "stop"` tasks are not skipped this way: they are served only by dispatcher-committed stop completion. Phase 1 may run this index advance on multiple consecutive tasks in one pass before requesting authority. Route edits, operator skip requests, and post-cancellation covered-task reconciliation use this same index-advance mechanism. There is no separate `_skip_waypoint(...)` helper.
- There is no stored planning cursor in v1. The "next task to plan against" is always the index returned by the latest `_find_next_task_target(train_id)` call. `current_waypoint_index` (derived from `task_runs[i].finished_at`) is the only stored route-progress cursor, and it advances only through physical consumption (head entry, stop completion, dwell exit, or covered-task index advance, all of which write `task_runs[i].finished_at`). A successful `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)` writes `task_runs[walk_position].resolved_target` for the helper-returned `walk_position` but does not by itself advance `current_waypoint_index`.

**Route-executor state reads**

- `RouteExecutor` should read live operational state from `TrainController`, not from mirrored runtime fields on `Train`.
- Departure, retry, arrival, dwell, and waiting decisions should use controller state as the operational source of truth.
- `Train` may still expose persisted or UI-facing state, but route-control decisions should not depend on it being a live mirror.
- In the desired model, manual driving is `control_mode == manual`, not a separate operational state. A route-managed manual train still uses ordinary `READY` / `RUNNING_*` states and dispatcher authority; the difference from ATO is how movement begins and is driven, not whether `RouteExecutor` owns the waypoint plan. In particular, manual `READY` must not block route-side path creation. It changes only what `depart()` means after authority exists.

**Planning Kernel**

- Phase 1 is a state-machine: each canonical step has explicit preconditions and is a no-op when those preconditions are not met. The kernel never creates fresh authority while the train has not yet reached a stopped recovery point, while any teardown/recovery latch is still dirty, while the controller is `OFF`, or while the `RouteRun` is pending/inside a dwell step.
- Eligibility precondition for the planning kernel's authority-acquisition step (step `66aa`) and the re-resolve step (step `592a` when it would lead to acquisition): `RouteExecutor` may run those steps only when one of the following is true:
  - the train has live authority (`PathDispatcher.active_path_id_by_train(train_id) is not None`) AND `controller.active_conditions ∩ {PATH_CANCEL_PENDING, ROUTE_ABORT_PENDING, ROUTE_DEACTIVATE_PENDING} == ∅`, in which case only step `66aa`'s `extend_path(...)` branch is allowed. The latch exclusion prevents Phase 1 from extending a live path that Phase 3 is about to cancel; or
  - `RouteExecutor.is_clean_for_create(train_id)` is true per the **`ControllerCondition` set** canonical home, in which case the create branch is allowed.
- Steps `5fc7`–`3a37` (deviation cleanup, dwell-complete, helper lookup, covered-task advance, dwell-entry) run unconditionally on every Phase 1 entry — they make no `PathDispatcher` mutation and only mutate `RouteRun` state per their own gating predicates. When `pending_route_deactivate` is set, these steps still run unconditionally. The interactions with Phase 3's deactivation teardown are safe by construction: (a) if step `70c3` calls `finish_dwell()` on the deactivation tick, Phase 1 runs before Phase 3 and the controller has already exited `RUNNING_AT_STATION` by the time Phase 3's deactivate consumer runs `remove_train_route_run(...)`; that helper checks `state == RUNNING_AT_STATION` before calling `finish_dwell()` and correctly skips it; (b) if step `3a37` calls `enter_station_dwell()` on the deactivation tick, the same-tick Phase 3 deactivate consumer calls `finish_dwell()` through `remove_train_route_run(...)` before archiving the run. Do not add a guard to skip steps `70c3` or `3a37` when `pending_route_deactivate` is set; doing so would leave the controller stuck in `RUNNING_AT_STATION` when the deactivation teardown relies on the Phase-1-first ordering.
- The derived `display_state == "DEVIATED"` projection is not itself a gate; it clears automatically when `path_cancelled` is consumed by the same Phase 1 route-deviation-cleanup step (step `5fc7`).
- If the controller is `OFF`, Phase 1 is skipped. If eligibility preconditions are otherwise unmet (still braking, dirty handoff), Phase 1 returns and waits for a later tick.
- For the EB case, the same eligibility rule applies: while `eb.active == True`, `controller.is_recovery_clean` is false (because `EB_LATCHED ∈ active_conditions`) and Phase 1 produces no authority. After `eb.release()` returns the controller to `READY`, the next eligible Phase 1 runs the planning kernel normally.
- One Phase 1 pass owns all `RouteRun` mutation in this canonical order. `RouteExecutor` is the canonical owner of every step; `SimulationController` invokes the kernel through `RouteExecutor.tick_train_phase1(train_id, delta_seconds)` and `RouteExecutor` reaches the controller through its top-level `SimulationController` reference (`self.simulation_controller.get_or_create_controller(train_id)`). Steps:
  0. `9c4f` — **RouteRun (re)allocation.** Look up the train's currently-`RUNNING` `RouteRun` (`RouteExecutor.execution_state_for(train_id)`). If one exists, continue to step `5fc7`. Otherwise, scan the route registry for any `Route` with `train_id ∈ Route.assigned_train_ids` and `Route.is_active == True`; if none is found, Phase 1 returns (no work). If one is found, allocate a new `RouteRun` against that `route_id`: write `route_id`, sample `RouteRun.started_at = time.time()`, set `direction = "forward"`, allocate `task_runs` with `len(Route.tasks)` entries (one per task with `task_index = 0..N-1`, all other fields `None`), set `current_route_status.state = "RUNNING"`. The newly-allocated run is the canonical home of all subsequent Phase 1 mutation for that train this tick. Continue to step `5fc7`.
  1. `5fc7` — **Route-deviation cleanup** (multi-tick latch). When `RouteRun.path_cancelled == True` AND `controller.is_recovery_clean` is true, clear `path_cancelled` (the derived `display_state == "DEVIATED"` projection clears with it).
  2. `70c3` — **Dwell-complete timer check.** When `TrainController.ops.state == RUNNING_AT_STATION` and `RouteTask.should_depart(task_runs[walk_position].started_at, current_time)` is satisfied: write `task_runs[walk_position].finished_at = current_time` (the derived `current_waypoint_index` advances to `walk_position` with that write, and the next task's derived `started_at` automatically reflects this `finished_at`); call `TrainController.finish_dwell()` (resolved through the top-level reference); then continue into step `c481`.
  3. `c481` — **Look up the next non-finished task** on the directed walk by calling `_find_next_task_target(train_id)`. If the projection's `task_kind == "dwell"`, skip to step `3a37` (dwell-entry); otherwise continue to step `a5c6` with the result discarded — every step that needs the resolved target re-invokes the helper after any cursor change.
  4. `a5c6` — **Covered-task index advance.** While the next non-finished task is `task_kind == "waypoint"` and its (live-resolved) target block is inside the current span, set `task_runs[i].finished_at = current_time` (the derived `current_waypoint_index` advances with that write, and the next task's derived `started_at` automatically reflects this `finished_at`). Stop when the next task is `task_kind == "stop"` (block coverage never finishes a stop) or `task_kind == "dwell"` (continue to step `3a37`) or no further task fits coverage.
  5. `3a37` — **Dwell-entry transition.** When the next non-finished task has `task_kind == "dwell"`, the predecessor task's `finished_at` is set, and `controller.is_recovery_clean` is true: call `TrainController.enter_station_dwell()`. The dwell row's `started_at` is the derived read of the predecessor's `finished_at`; this step does not need to write it. Return for that tick — no path creation while dwell is pending or active. (If the controller is already `RUNNING_AT_STATION` at step `3a37`, also return.)
  6. `592a` — **Re-resolve the next target.** Call `_find_next_task_target(train_id)` afresh now that any cursor-changing step has run. Use the returned projection's `walk_position`, `direction`, and `resolved_target` as the candidate for this authority attempt, and set `direction` from that projection. Do not write `task_runs[i].resolved_target` yet.
  7. `66aa` — **Authority acquisition.** Call `PathDispatcher.create_path(...)` or `PathDispatcher.extend_path(...)` for that one resolved target only. On a successful create/extend, write `RouteRun.task_runs[walk_position].resolved_target` (where `walk_position` is the helper-returned index) to the candidate that the dispatcher actually targeted (this is the only canonical writer of that field in v1). When this Phase 1 has live authority for the current target, also call `TrainController.depart()` directly for the current authority. On a failed create/extend, record per-task error context on `task_runs[walk_position].last_error` and run-level error on `RouteRun.last_error` per the canonical writer rule.
- A single Phase 1 pass may loop locally through these steps. For one planning problem, Phase 1 may try multiple distinct same-tick resolved targets only when the current task is a `StationTarget` task: Phase 1 owns a local `tried` set of already-attempted resolved targets for this planning problem and calls `_find_next_task_target(train_id, exclude=tried)` repeatedly, appending each returned `resolved_target` to `tried` after a failed `create_path(...)` / `extend_path(...)` attempt. The helper itself stores no per-tick state; Phase 1 has all the information needed to decide which candidates have been attempted. The helper returns the next compatible candidate each time (or `None` when exhausted). A `PlatformTarget` task, `BlockTarget` task, or explicit local-reposition task has only one resolved pair for that tick; if that create/extend attempt fails without creating or growing authority, the run waits until a later eligible tick rather than trying alternatives in the same pass. If every same-tick candidate is exhausted without authority creation or growth and no live path exists for that run, `RouteExecutor` stops Phase 1 for that train for that tick. If a live path still exists and `extend_path(...)` returns `success=True/result_kind=blocked_no_growth`, keep `current_route_status.state = RUNNING`, preserve the live path, and retry on later eligible ticks. If `extend_path(...)` returns `success=False/failure_kind=no_viable_path`, `invalid_reverse`, or another non-temporary structural failure for that live path, `RouteExecutor` must latch cancellation and wait for the ordinary Phase 3 cancel/recovery flow before any fresh create-path attempt.
- `RouteExecutor` never asks dispatcher/pathfinder to solve a whole multi-task route in one search. Longer authorities are formed only by repeated point-to-point segments appended onto the same live path identified by `path_id`.
- In normal route-managed execution, v1 does not concatenate beyond the currently armed task on the same tick. Route planning arms exactly one task at a time. If the current armed task is `task_kind == "waypoint"`, that task is still consumed only by the head-entry callback chain; after that physical consumption, the next Phase 1 tick may resolve the next task and extend or recreate authority from the train's then-current physical state.
- A waypoint-terminated authority before that next planning tick is a degraded but valid v1 authority boundary. If the train later brakes there, that is a safety stop caused by lack of further authority, not a planned stop for the `waypoint` task itself.
- `task_kind == "stop"` versus `task_kind == "waypoint"` changes only what happens when the resolved target is reached: `stop` enters dwell (or the `dwell` task that follows it) through dispatcher-committed completion from the post-physics controller stop check, while `waypoint` advances immediately without dwell. It does not change the dispatcher path API shape.

**Route Edit And Reconciliation**

- Active runs reference the current shared `Route` through `RouteRun.route_id`. Any edit to `Route.tasks` that changes the waypoint set, ordering, or task-kind composition triggers immediate teardown of every assigned train's currently-`RUNNING` `RouteRun` for that `route_id`, followed by fresh `RouteRun` allocation against the edited `Route` on the next eligible Phase 1. There is no in-place reconciliation in v1, no version stamp on the run, and no policy that changes how the fresh run picks its starting walk-position. `Route.priority` and `Route.acquisition_mode` edits are the exception — they take effect live without a teardown because they do not change the walk structure. All edits in this paragraph (structural and non-structural) bump `Route.last_edited_at` per the **Route edit timestamps** subsection.
- A `RouteRun`'s `route_id` is established at run creation and never mutated.
- **Shared-route edit teardown.** When the shared-route edit handler accepts a structural edit, it walks `Route.assigned_train_ids` and per assigned train calls `controller.route_hooks.phase_latches.set_route_deactivate(...)`, which sets `pending_route_deactivate = True` and writes the inclusive `pending_path_cancel_request(REVOKED)` when a live path exists. Each train's later eligible Phase 3 commits the inclusive cancel and the deactivate teardown through the standard latch consumption flow: the deactivate consumer calls `RouteExecutor.remove_train_route_run(train_id)`, which writes `current_route_status.state = DEACTIVATED` on the old run and (when `state == RUNNING_AT_STATION`) calls `finish_dwell()` first. The historical row stays in the registry. The handler that performed the edit is also responsible for re-adding each train to the (now-edited) `Route.assigned_train_ids` (or to a different `Route.assigned_train_ids` for a swap workflow) immediately after writing the deactivate latches; the next eligible Phase 1 then sees the train assigned to a route with no `RUNNING` `RouteRun` and allocates a fresh `RouteRun` against the edited `Route.tasks` per Phase 1's RouteRun (re)allocation step.
- The fresh `RouteRun` starts cleanly with `current_waypoint_index == None`, `direction == "forward"`, and `task_runs` initialized from the edited `Route.tasks`. Phase 1 then runs the ordinary planning kernel: the covered-task index advance walks past any `task_kind == "waypoint"` tasks the train already covers, and `_find_next_task_target(train_id)` returns the first non-finished walk-position for the next planning step. Stops are not skipped by coverage, so the fresh run lands on the first non-covered stop or waypoint after the train's current physical position automatically.
- Operator retargeting and explicit route swap follow the same teardown workflow with one variation: the API/UI/admin handler for the retarget/swap request atomically (a) calls `controller.route_hooks.phase_latches.set_route_abort(...)` on the targeted train (which fans out to inclusive `pending_path_cancel_request(OPERATOR_CANCELLED)` when a live path exists) and (b) updates assignment — `Route.unassign_train(train_id)` on the old route and `Route.assign_train(train_id)` on the new (or newly-created one-off `RouteMode.ONE_OFF`) route. The handler returns success immediately. The same train's later Phase 3 consumes the inclusive cancel and then the abort latch through `RouteExecutor.remove_train_route_run(train_id)`; the next eligible Phase 1 sees the train assigned to the new route with no `RUNNING` `RouteRun` and allocates a fresh `RouteRun` against the new `route_id`.

**Concrete `RouteExecutor` tick calls**

- `RouteExecutor.update(delta_seconds)` refreshes route-managed scheduling inputs for this tick. `delta_seconds` is the per-tick movement-window length (the gap between consecutive ticks at the simulation's current playback rate); it is used by physics integration and by callers that need a per-tick delta, but `RouteExecutor` does NOT maintain a separate `simulation_time` accumulator. All stored route/run timestamps use system-time Unix seconds (`time.time()`); there is no v1 `RouteExecutor.simulation_time` field. `RouteExecutor` owns the final runnable-train ordering through `RouteExecutor.order_runnable_trains(candidate_train_ids)`: every candidate train resolves to one effective priority (route-managed trains use the current shared `Route.priority`; trains without a current `RouteRun` use effective priority `5`), and the merged set is sorted strictly by effective priority descending (`9` highest, `0` lowest) with stable existing iteration order as the only tie-break. Route-managed and non-route trains at the same effective priority interleave in stable iteration order; route management does not bump priority within a tier. `SimulationController.update(...)` owns executing the returned train IDs, but it must not apply a second priority sort. `RouteExecutor.update(delta_seconds)` prepares the route-managed Phase 1 work that `SimulationController` will invoke by train; it must not itself call `RouteExecutor.tick_train_phase1(...)` for every train in a world-wide pass. Trains without a current `RouteRun` still remain in the `SimulationController` loop and simply have no route-managed Phase 1 work for that tick. Stored route/run timestamps such as `Route.started_at`, `RouteRun.task_runs[i].started_at`, `RouteRun.task_runs[i].finished_at`, `RouteRun.last_error.time` (when present), and `RouteTask.target_time` use system-time Unix seconds.
- `RouteExecutor.tick_train_phase1(train_id, delta_seconds)` is the canonical public Phase-1 surface and is the entire Phase 1 route-executor tick for one train. `SimulationController.update(...)` calls it immediately before that same train's `SimulationController._update_train(train, delta_seconds)` transaction. Dwell handling, covered-task index advance, live target resolution, station candidate iteration, and `PathDispatcher.create_path(...)` / `PathDispatcher.extend_path(...)` attempts all live here. `tick_train_phase1` creates or reuses the train's `RouteRun` (current-code class may still be named `RouteExecutionState`). If the controller is `OFF`, Phase 1 route work is skipped and power-on is handled by the Phase-2 command slot. If the next non-finished task on the directed walk has `task_kind == "dwell"`, dwell is the active route step: Phase 1 returns for that tick (Phase 1 dwell-entry step inside `RouteExecutor.tick_train_phase1(...)` handles the transition into `RUNNING_AT_STATION`).
- Before any create/extend decision, `RouteExecutor.tick_train_phase1(...)` must call `_find_next_task_target(train_id)` and receive a legal `ResolvedNextTaskProjection` for the current shared route and current physical progress. The returned `resolved_target` is the transient request candidate for this attempt. If the helper cannot currently resolve a legal concrete platform/block target under the task's fixed/flexible platform policy, the retry fails at target resolution and `RouteExecutor` must not call `PathDispatcher.extend_path(...)` for that tick.
- Before any create/extend decision, the current attempt's resolved target is the route-owned request contract for the `walk_position` returned by `_find_next_task_target(train_id)`: the task target block and the route-owned `requested_destination_direction` constraint. It must not resolve or pass any stop-position centimeter field. Dispatcher and controller use the chosen terminal frame plus controller safety margin for braking/boundary projection.
- Route-managed path building is always segment-by-segment along the current directed route walk. On each create/extend attempt, the resolved target represents exactly one resolved task target, never a bundled multi-task search request. After one segment is successfully created or appended, route planning stops for that train on that tick; if the armed target is `task_kind == "waypoint"`, the next task is not armed until that `waypoint` is physically consumed and the next planning tick runs.
- `RouteExecutor.tick_train_phase1(...)` should ensure the train's `TrainController` exists before it reads controller state or calls `PathDispatcher.create_path(...)`. In the desired model a route-managed train should already have a controller by the time authority is assigned in Phase 1. `SimulationController` owns only the 1:1 binding between `train_id` and `TrainController`; it does not construct or write authority projections.
- Before resolving a new task or retrying the current one, `RouteExecutor.tick_train_phase1(...)` runs the covered-task index advance (a small loop inside the method) so the route does not keep targeting a task the train already physically covers.
- The operational state checks inside `RouteExecutor.tick_train_phase1(...)` should read controller state rather than `train.state`.
- If controller state is `OFF`, `RouteExecutor.tick_train_phase1(...)` is not invoked for normal Phase 1 planning. A powered-off train must not create, extend, or rely on dispatcher authority, and the system must not auto-power-on it. `TrainController.commands.power_on_cmd()` is accepted only through the Phase-2 command slot; route planning resumes on a later tick after the controller is powered and in an eligible state. The canonical power-off release/removal order follows the standard phase workflow per the **Power-off procedure**: `TrainController.commands.power_off_cmd()` calls `_apply_power_off_request()` during the Phase-2 operator-command slot (which immediately clears `ato.running`, sets `pending_power_off = True`, and writes the inclusive `pending_path_cancel_request` with `initiator = "power_off"` when a live path exists); the later eligible Phase 3 step (c) commits the dispatcher cancel through `PathDispatcher.cancel_path(...)` and lets the ordinary cancellation callback run while route execution is still registered; step (e) then calls `RouteExecutor.remove_train_route_run(train_id)` and clears controller-local OFF state.
- If the next route task is `task_kind == "dwell"`, `RouteExecutor.tick_train_phase1(...)` must treat dwell as the active route step before any departure/path planning and return for that tick. The Phase 1 dwell-entry step inside `RouteExecutor.tick_train_phase1(...)` transitions the controller to `RUNNING_AT_STATION` automatically when its preconditions are met (`controller.is_recovery_clean` is true and the predecessor task's `finished_at` is set). Phase 1 must not advance past the dwell task or request authority until the Phase 1 dwell-complete step inside `RouteExecutor.tick_train_phase1(...)` marks the `dwell` task finished.
- If controller state is `READY` and there is no pending/active dwell task, `RouteExecutor.tick_train_phase1(...)` should call `RouteExecutor._try_depart_to_waypoint(train, route, exec_state)`. Path creation/retry is allowed from `READY` regardless of cab selection. The behavioral difference between ATO and manual is only departure execution after authority exists: ATO may auto-select/start, while manual mode leaves actual movement to the driver.
- If controller state is `RUNNING_MOVING`, `RouteExecutor.tick_train_phase1(...)` should not poll for `stop` task arrival; normal stop arrival comes only from dispatcher-committed path completion after the post-physics controller stop check has passed. `task_kind == "waypoint"` consumption is also not polled inside `RouteExecutor.tick_train_phase1(...)`; it is driven by the head-advance callback chain `TrainPhysics.tick(...)` -> `TrainController.on_physics_updated(span_update)` -> `PathDispatcher.on_controller_progress(report)` -> `RouteExecutor.handle_train_advanced(...)`. Each `RouteExecutor.handle_train_advanced(...)` callback compares one reported block advance with the current route task pointer and may consume at most that one task; it must not arm the next planning target or create/extend authority. `waypoint` consumption is head-based route progress only; the later physical release of earlier path resources still waits for tail-vacate callbacks. `RouteExecutor.tick_train_phase1(...)` in `RUNNING_MOVING` is therefore limited to best-effort `PathDispatcher.extend_path(...)` retries toward the currently armed target; it does not re-implement head-entry detection.
- If controller state is `RUNNING_AT_STATION`, `RouteExecutor.tick_train_phase1(...)` should run its Phase 1 dwell-complete step (which may call a helper such as `RouteExecutor._check_dwell_complete(train, route, exec_state)`) before any covered-task or planning work; if dwell does not complete on this pass, the run is dwelling/on hold and the rest of Phase 1 returns without new path or departure planning. The dwell-complete helper is owned by Phase 1 only and is never invoked from Phase 3 or from `RouteExecutor.update(...)`.
- If a still-live path's `authority_end_block_id` is still short of the route-owned `task_runs[walk_position].resolved_target.requested_destination_block_id` (where `walk_position` is the index returned by `_find_next_task_target(train_id)` for the live planning chain), `RouteExecutor.tick_train_phase1(...)` should keep retrying `PathDispatcher.extend_path(...)` on that same path using the stored `task_runs[walk_position].resolved_target` as the armed requested target. If reconciliation would produce a different `walk_position` or different requested target for the live path, Phase 1 must latch cancel-and-replan instead of extending the live path with a different pair. It must not request a brand-new path while `received_path_plan` is still present.
- More generally, dynamic best-effort extension is allowed in any controller state except `OFF`. The common zero-clearance retry case is when ATC is holding the train at the live-authority boundary, but if a still-live path remains short of its requested target while the train is still moving or otherwise stopped under authority, `RouteExecutor.tick_train_phase1(...)` may proactively retry `PathDispatcher.extend_path(...)` on later ticks without waiting for a state change, as long as it does not create a second live path.
- `RouteExecutor` does not call any stop-position resolver and does not pass stop centimeters into dispatcher. Route callers pass only the resolved block/direction request contract.
- `RouteExecutor._try_depart_to_waypoint(...)` is the route executor's normal "make progress toward the current task" entry point. The same function is used for the initial departure attempt and for retries after `PathDispatcher` has cancelled/revoked the previous path once the train has reached a fresh stopped no-authority state. If the cancellation stop escalated into EB, that retry point occurs only after `TrainController.eb.release()` has returned the controller to `READY` according to cab selection; active-path completion still comes back from `PathDispatcher`, not from `RouteExecutor.tick_train_phase1(...)` polling for end-of-path.
- `RouteExecutor` calls `TrainController.depart()` directly whenever live authority exists for the current route target, regardless of `control_mode`. There is no route-level `departure_mode` policy and no `departure_requested` latch in v1; the ATO-vs-manual behavioral difference is owned inside `TrainController.depart()` itself per the **`TrainController.depart()` canonical contract**.
- After EB release, the EB-interrupted path has already been cancelled by the EB activation flow. `RouteExecutor` must wait for EB release, then make a fresh `create_path(...)` or `extend_path(...)` decision from the current route state; it must not try to reuse that cancelled path. Once fresh authority exists, the next eligible Phase 1 calls `TrainController.depart()` directly per the same rule.

- **Departure-to-waypoint flow**

- The canonical step ordering and gating for one Phase 1 pass live in the **Planning Kernel** subsection (steps `5fc7`–`66aa`). This subsection only states the manual-vs-ATO behaviour at depart-acceptance time and the per-controller-state guards on `RouteExecutor._try_depart_to_waypoint(...)`; it does not redefine the kernel's step order, eligibility precondition, latch checks, or per-step writes. Where this subsection's prose appears to differ from the kernel, the kernel wins.
- `RouteExecutor` owns task targeting; `PathDispatcher` owns authority acquisition and terminal authority geometry; `TrainController` owns stop/braking behavior from that authority geometry using the controller safety margin. The departure flow is: resolve task block/direction, request or extend dispatcher authority as needed, and call `TrainController.depart()` directly once live authority exists.
- The stop, same-block, and dwell-entry rules in this subsection apply only to tasks with `task_kind == "stop"`. Tasks with `task_kind == "waypoint"` do not call arrival/dwell helpers; they constrain route geometry only.
- A `task_kind == "waypoint"` task uses the same block/direction resolution rules and the same point-to-point create/extend contract as a `stop` task. The difference is route behavior only: when that task's resolved target is reached, `RouteExecutor` advances immediately without dwell and leaves the next target to the next planning tick.
- A longer multi-task route is implemented as repeated point-to-point segments across later planning ticks. A pathfinder call never receives "go through all remaining tasks"; after one task target has been resolved and physical route progress actually consumes that target, a later `create_path(...)` / `extend_path(...)` request is made from the then-current live authority end to the next resolved task. Physical route progress still waits for `waypoint` head entry or `stop` dispatcher completion.
- `RouteExecutor` owns task-chain progression on the route side. `PathDispatcher` grows authority geometry; it does not own task progression. A `waypoint` task is consumed only when the train head first enters that task's resolved block. Live `resource_sequence` coverage may be inspected for diagnostics or extension planning, but coverage alone does not advance `current_waypoint_index` and does not retarget dispatcher authority away from the currently armed task. Tail-based resource release is a separate physical-lifecycle concern owned by controller-reported tail-vacate observations and dispatcher-mediated resource release.
- For a train departing from rest under route control, `RouteExecutor` does not try to grow authority past the currently armed task inside the same departure call. Departure uses the current live authority only; later ticks may extend or recreate authority after physical route progress advances and the next task becomes the armed target.
- There is a route-side already-covered skip in v1 only for `task_kind == "waypoint"` targets. If the resolved target block for the current `waypoint` task is already physically covered by the train's current span, `RouteExecutor` treats that task as already missed/skipped, does not request a same-block `create_path(...)`, and immediately advances route planning toward the next task on the current directed route walk. For `task_kind == "stop"`, the block-coverage test is insufficient: a stop is served only by dispatcher-committed stop completion. If a stop's resolved destination block is already covered, the run keeps that stop as the armed target and requests or keeps same-block stop authority as needed; the controller's ordinary safety-margin authority-stop predicate decides completion. Operator/manual same-block reposition uses the ordinary one-off route flow as a `stop` task and is not converted into a covered-task skip.
- `RouteExecutor` does not resolve or compare stop-position targets at all. For any `stop` task that still needs authority, it passes only `requested_destination_block_id` and `requested_destination_direction`. Dispatcher stores authority geometry and the controller owns safety-margin braking from that geometry. The route/task resolution step must still provide `requested_destination_direction` as a route-level constraint; dispatcher must not guess it from same-block geometry, and must not treat it as the exact terminal frame by itself.
- `RouteExecutor` uses `Route.acquisition_mode` for both `create_path(...)` and any later `extend_path(...)` retries while it is still pursuing that same planning chain. `AcquisitionMode.best_effort` is therefore a route policy choice, not a one-off branch invented mid-chain.
- For a `waypoint` task, the create/extend chain is still block-based: the current per-attempt resolved target still carries `requested_destination_block_id` and `requested_destination_direction` just like a `stop` task. The difference is not the path API shape; the difference is that once the train head enters that task's resolved block, `RouteExecutor` consumes the `waypoint` immediately, advances the route cursor, and leaves the next create/extend step to a later planning tick.
- The canonical create-vs-extend decision for `RouteExecutor` is driven by `TrainController.path_projection.received_path_plan` presence, not by any route-side re-evaluation of whether the current waypoint is reachable on an empty map. For the currently armed waypoint:
  - if `controller.received_path_plan is None`, the train has no live authority, so `RouteExecutor` must call `PathDispatcher.create_path(train_id=..., ...)`
  - if `controller.received_path_plan is not None`, the train is already on a live path, so `RouteExecutor` must call `PathDispatcher.extend_path(path_id=received_path_plan.path_id, ...)` on that same `path_id` rather than synthesizing a second path
  Because `received_path_plan` is derived from the dispatcher-owned active path, this rule is well-defined in v1: a cancelled/completed path transitions out of `ACTIVE`, so the next controller read returns no live plan and the next planning tick naturally falls into the `create_path(...)` branch. A pass-through waypoint at which the train happens to be stopped with no live plan is therefore a `create_path(...)` case, not an `extend_path(...)` case.
- When live authority exists for this train (`PathDispatcher.active_path_id_by_train(train_id) is not None`), `RouteExecutor._try_depart_to_waypoint(...)` must treat that live authority as the current route path for this attempt and must not request a second `PathDispatcher.create_path(...)` on top of it. `RouteExecutor` reads the live path id from `PathDispatcher.active_path_id_by_train(train_id)`. If the next route decision wants a subsequent waypoint target on the current directed route walk, `RouteExecutor` calls `PathDispatcher.extend_path(active_path_id, ...)`. If `PathDispatcher.extend_path(...)` returns `success=True/result_kind=blocked_no_growth`, the existing live path is still a valid prefix and `RouteExecutor` keeps it, stops Phase 1 for that train, and retries later. If `PathDispatcher.extend_path(...)` returns `success=False` with a structural `failure_kind` such as `no_viable_path` or `invalid_reverse`, dispatcher cannot continue the existing live path from its current authority end toward that requested target; `RouteExecutor` must latch `pending_path_cancel_request` for that same live path, stop Phase 1 for that train, and wait for the ordinary Phase 3 cancel → callback → route deviation cleanup flow. Later eligible Phase 1 passes keep using that latch-only behavior while the incompatible live path still exists. Only after that cancellation flow has completed may a later eligible Phase 1 request a fresh path.
- If `PathDispatcher.create_path(..., acquisition_mode=best_effort)` returns a live path whose current authorized target is still short of the route's current planning target, that is not a failure. It is a degraded but valid live authority: let the controller treat it as normal movement authority toward the current authorized end, and let `RouteExecutor` keep retrying `PathDispatcher.extend_path(...)` on the same `path_id` toward that same pending waypoint, re-resolving its current request contract on each retry, on later ticks in any controller state except `OFF`. A best-effort create request counts as success whenever it creates one new path record with a non-empty block-terminated live `resource_sequence`; a best-effort extend request counts as success when it grows authority or returns `result_kind=blocked_no_growth` because the live path is still a valid prefix but temporarily blocked by live resource ownership.
- Once such a live path exists, `RouteExecutor` calls `TrainController.depart()` directly when this target is otherwise route-ready. Any immediate zero-clearance hold is controller-owned and comes from lookahead/ATC against that live authority rather than from a special route-side suppression rule.
- On successful path, do not write train-side path cache fields from `RouteExecutor`. `PathDispatcher` owns the authoritative path-progress view; any controller/UI-facing path tiles or path-progress reads should be read as a projection of dispatcher state rather than as a train mirror.
- Do not set destination-block fields directly on `Train` or `TrainController` from `RouteExecutor`; controller authority comes only from the live `received_path_plan` projection.
- `PathDispatcher` owns the `Path` record underlying `controller.received_path_plan`; `controller.assigned_path_id` should be only a derived read of `received_path_plan.path_id`, so `RouteExecutor` does not write that field.
- On successful path creation, authority growth, or `blocked_no_growth` target refresh, `RouteExecutor` should update route-owned state for the immediate live task carried by that path: set/keep `current_route_status.state = RUNNING`, set `direction` from the accepted projection, and write `task_runs[walk_position].resolved_target` (where `walk_position` is the index returned by `_find_next_task_target(...)` for this attempt) to the accepted candidate per the **`current_route_status` write contract**. Later planning retries against the same live path call `_find_next_task_target(train_id)` again and use the returned `walk_position` plus its stored `resolved_target`. If reconciliation would change the target while authority is live, Phase 1 uses cancel-and-replan rather than rewriting the live target under the existing path. Returned `resource_sequence` geometry alone does not advance `current_waypoint_index`, which remains physical route progress, and v1 does not arm a second waypoint target on the same tick.
- After any successful `PathDispatcher.extend_path(...)` that returns a grown `resource_sequence`, `RouteExecutor` keeps the same currently armed waypoint/stop because `_find_next_task_target(train_id)` keeps returning the same `walk_position` until physical progress consumes that task. If the grown path is still short of that target, later retries continue toward the stored `task_runs[walk_position].resolved_target`. If the grown path now reaches that target, the next call to `_find_next_task_target(train_id)` still returns that same `walk_position` until physical route progress consumes the waypoint through head-entry callback, dispatcher-committed stop completion, or explicit skip. The result payload by itself does not advance physical route progress; `current_waypoint_index` still advances only when the train actually reaches/consumes that waypoint.
- Keep `TrainController.depart()` as the controller's departure-acceptance command once a valid path plan exists. `RouteExecutor` calls it directly on every eligible Phase 1 pass with live authority, regardless of `control_mode`. ATO vs manual effects on acceptance are owned per the **`TrainController.depart()` canonical contract**.
- When `TrainController.depart()` returns `success == False`, the caller must treat that as a failed departure attempt, not as movement. The controller leaves itself in its current stopped state, records or emits the diagnostic `reason` through `NotificationCenter`, and the next planning tick re-evaluates from current controller state and `received_path_plan` presence. If authority was cleared before the call, the normal create-path branch handles recovery on that later tick; if EB or power/state made departure invalid, the existing EB/power/stopped-state rules decide when retry is allowed.

**Concrete departure calls**

- Every `RouteExecutor` access to a train's controller goes through `SimulationController.get_or_create_controller(train.train_id)` (the shared public accessor) rather than a private `_get_controller` helper or any direct dictionary lookup.
- If the resolved target block for a `task_kind == "waypoint"` task is already physically covered by the train's current span, `RouteExecutor._try_depart_to_waypoint(...)` must not call `PathDispatcher.create_path(...)` for that `waypoint` task. Phase 1's covered-task index advance has already advanced past it by recording `task_runs[i].finished_at` (which makes the derived `current_waypoint_index` advance) before the depart helper is reached, so the helper continues planning toward the next task on the current directed route walk. If the resolved target block for a `task_kind == "stop"` task is already physically covered, `RouteExecutor._try_depart_to_waypoint(...)` must still treat the stop as the current target and may request same-block stop authority; the stop is not finished until the normal post-physics usable-authority stop check and dispatcher completion have run.
- For any `stop` task that still needs authority, `RouteExecutor` does not compute or compare a centimeter-level local stopping target. It passes only the task's `requested_destination_block_id` and `requested_destination_direction` into `PathDispatcher.create_path(...)`.
- Explicit same-block/zero-movement authorities are route-backed in v1 through the ordinary one-off `Route` flow with no special run-level flag. A direct operator/API local-reposition request constructs a `RouteMode.ONE_OFF` route with a single `task_kind == "stop"` task whose `task_location` is a `BlockTarget`, `PlatformTarget`, or `StationTarget` for the destination. Because `current_waypoint_index` initializes to `None` for every run, `Route.tasks[0]` is the first executable target. `RouteTask.task_direction` for the destination follows the same task-authoring rule as any other route; the operator/API construction step is responsible for resolving "current cab/running direction" into a concrete `"forward"` / `"reverse"` value before the route is stored, because dispatcher never receives `"either"`. If that direction cannot be derived at construction time, the operator/API request fails before any route is stored. The run is executed through the ordinary Phase 1 / `PathDispatcher.create_path(...)` flow. If the destination stop block is already covered when planning runs, the run still targets that stop and uses same-block stop authority or immediate usable-authority stop completion under the ordinary stop predicate; it does not skip the destination merely because the block is covered. These authorities carry no separate target-position field; the controller uses the standard safety-margin stop logic.
- When the current attempt uses `AcquisitionMode.best_effort`, compare the live path's current authorized target against the live path's stored requested target each tick (`Path.authority_end_block_id` versus `Path.requested_destination_block_id`). If the live path is still short of that requested target, keep calling `PathDispatcher.extend_path(...)` on that same `path_id` using the newly re-resolved request contract for the same pending waypoint; do not synthesize a new path.
- If `RouteExecutor._try_depart_to_waypoint(...)` sees current live authority already present on the controller (`TrainController.path_projection.received_path_plan is not None`), do not call `PathDispatcher.create_path(...)` again. First perform any eligible `PathDispatcher.extend_path(...)` retry for the currently armed target; after that create/extend decision is complete for this Phase 1 pass, call `TrainController.depart()` directly for that current live authority. ATO vs manual effects are owned per the **`TrainController.depart()` canonical contract**.
- `RouteExecutor` does not write `current_path`, `path_index`, `train.assigned_path_id`, `controller.ato_path_id`, or any destination field. `PathDispatcher` owns path-progress; `controller.assigned_path_id` is derived from the live `received_path_plan` projection.
- Route-driven movement requires a dispatcher path plan and reaches departure acceptance only through a direct `TrainController.depart()` call by `RouteExecutor`. The controller infers "no path authority" from an empty `received_path_plan`.
- If initial path creation fails before departure in `all_or_nothing` mode, `RouteExecutor` should record that route/path error on `exec_state.last_error` as one `ErrorRecord(text=..., time=current_time)` and keep the train in `READY`; the train never had authority, so no special controller waiting command is needed.
- In `best_effort` mode, only "no authority at all could be created" is a creation failure. A truncated but live path is not a failure path; the train may run under that current authority and later wait at the current authority boundary while `RouteExecutor` keeps retrying `PathDispatcher.extend_path(...)` on the same `path_id`.
- On cancel/revoke, `PathDispatcher` transitions `Path.status` to `CANCELLED` (the controller's `received_path_plan` property then returns `None` on its next read), the controller follows the no-authority EB protocol defined in step `826a`, and recovery follows the canonical recovery table. Phase 1 is gated by `controller.is_recovery_clean`; it never reads the cancellation `initiator`. If the next planning attempt fails, fall through to the ordinary pre-departure route/path error path — no recovery-only state machine.

**Arrival detection**

- Stop using `RouteExecutor._is_train_at_platform()` as the normal arrival gate after dispatcher-owned path completion. In the desired model, the post-physics controller stop check owns stop-complete observation and `PathDispatcher.try_complete_active_path(train_id)` owns the completion commit; dispatcher-committed completion is the authoritative arrival trigger for that `stop` task.
- `RouteExecutor._enter_task_arrival(exec_state, walk_position)` is the route-owned arrival-recording helper. `walk_position` is the walk-position in `task_runs` of the `stop` walk-position that just completed. The helper samples `time.time()` at the write site (per **Time sampling** under the **Units contract**) and sets `exec_state.task_runs[walk_position].finished_at` to that sampled value (the derived `current_waypoint_index` advances to `walk_position` with that write, and the next task's derived `started_at` automatically reflects this `finished_at`). It does not call `TrainController.enter_station_dwell()`; that transition happens in the next eligible `RouteExecutor.tick_train_phase1(...)` dwell-entry step.
- `TrainController.enter_station_dwell()` is the controller-side dwell-entry transition called by `RouteExecutor.tick_train_phase1(...)` (Phase 1). The controller does not detect dwell entry on its own; it never reads `RouteRun`. The transition is valid only from the dispatcher-completed `READY` state (`READY`). The dwell row's `started_at` is the derived read of the predecessor stop's `finished_at`, which `_enter_task_arrival(...)` recorded before this controller call runs.
- On the next eligible tick after `_enter_task_arrival(...)` records the stop's `finished_at`, `RouteExecutor.tick_train_phase1(...)` performs the dwell-entry step: when `controller.is_recovery_clean` is true, the route's next non-finished task has `task_kind == "dwell"`, and the predecessor task's `finished_at` is set, `RouteExecutor` calls `TrainController.enter_station_dwell()`. The dwell row's `started_at` is the derived read of that predecessor `finished_at`; the dwell-entry step does not need to write it. The train does not plan a new target while dwell is pending or active.
- The dwell-complete check is a Phase 1 step inside `RouteExecutor.tick_train_phase1(...)`, invoked before covered-task index advance. It runs only while controller state is `RUNNING_AT_STATION`. It calls `_find_next_task_target(train_id)` to live-resolve `walk_position` (the walk-position of the next non-finished task on the directed walk), then calls `RouteTask.should_depart(exec_state.task_runs[walk_position].started_at, current_time_sec)`, where both timestamps are system-time Unix seconds.
- Stop arrival sets `finished_at` for that stop directly in `_enter_task_arrival(...)`, which makes the derived `current_waypoint_index` advance. The stop task is independent of its neighbors: a following `dwell` task (when present) is a separate row with its own `started_at` / `finished_at` lifecycle; a `stop` with no following `dwell` simply has no dwell-entry / dwell-complete steps to run, and the next eligible Phase 1 either plans the next task or calls `RouteExecutor.finish_route_run(train_id)` for terminal completion.
- A route is complete only after the terminal task sequence (stop + any following dwell) has finished. Route completion handling never fires before the terminal dwell (if any) exits.
- If dwell/timing says depart, the Phase 1 dwell-complete step sets `exec_state.task_runs[walk_position].finished_at = current_time` (the derived `current_waypoint_index` advances to `walk_position` with that write, and the next task's derived `started_at` automatically reflects this `finished_at`), sets `exec_state.signed_direction` from the route walk, and calls `SimulationController.get_or_create_controller(train.train_id).finish_dwell()`. The same Phase 1 then continues into target resolution for the next task via a fresh `_find_next_task_target(train_id)` call.
- If no task remains after the completed stop+dwell pair, that Phase 1 dwell-complete step calls `RouteExecutor.finish_route_run(train_id)` directly inside `tick_train_phase1(...)` and returns for that tick. `RouteExecutor.finish_route_run(train_id)` performs the route-completion teardown (set `current_route_status.state = FINISHED`, possibly trigger `route.deactivate()` for one-off routes with no remaining assigned trains) per the **`current_route_status` write contract**. `RouteExecutor.assigned_route_id_for(train_id)` automatically returns `None`. Dwell exit (`finish_dwell()`) has already run before this call; the `RouteRun` is preserved with `state = FINISHED` indefinitely as a historical record.
- `route.deactivate()` is the admin-driven entry point for switching off a shared `Route` while one or more assigned `RouteRun`s have not yet finished. It sets `Route.is_active = False` and walks every assigned train, writing `pending_route_deactivate` on each train's controller per the inclusive-latch rule defined in the **Latch Table** preamble. `route.deactivate()` is idempotent; calling it on an already-inactive route with no assigned trains is a no-op. The actual per-train teardown happens in each train's later Phase 3 `pending_route_deactivate` consumer, which calls `RouteExecutor.remove_train_route_run(train_id)` after the inclusive cancel has committed; the helper writes `state = DEACTIVATED` and (when applicable) calls `TrainController.finish_dwell()` first. There is no separate `RouteRun.deactivate()` method, and `route.deactivate()` does not delete any `RouteRun` — the runs are kept as historical `DEACTIVATED` records.
- `finish_dwell()` is a **dwell-exit state-transition command only**, named `finish_dwell` rather than `depart_from_station` because it does not start movement. It transitions the controller out of `RUNNING_AT_STATION` to the **`READY` state**. The normal caller is `RouteExecutor.tick_train_phase1(...)` dwell-complete step. `RouteExecutor` is still responsible for deciding whether more route work remains, clearing route assignment when complete, and removing the execution-state entry; those are route-level bookkeeping, not controller state.
  `TrainController.finish_dwell()` must not touch `received_path_plan` (the property is derived from the dispatcher-owned active path; authority for the completed target already transitioned out of `ACTIVE` in `PathDispatcher.try_complete_active_path(...)` before dwell began), must not call `TrainController.depart()` / `TrainController.ato.go()`, and must not initiate physics movement. The next target's route-side restart happens in the same Phase 1 (after dwell exit) or on a later tick through `RouteExecutor._try_depart_to_waypoint(...)` -> `PathDispatcher.create_path(...)` and then `RouteExecutor` calls `TrainController.depart()` directly once live authority exists. ATO vs manual effects are owned per the **`TrainController.depart()` canonical contract**.

**Dispatcher completion handling**

**route path-event callback schema**

- This is the single canonical callback contract for `PathDispatcher -> RouteExecutor` path-terminal notifications.
- The canonical callback signatures are exactly:
  - `RouteExecutor.handle_path_completion(train_id, path_id, completion_target)`
  - `RouteExecutor.handle_path_cancellation(train_id, path_id, reason=None)`
  Parameters are listed positionally above; callers may pass them by name. No other parameter is accepted in v1. Neither callback carries a timestamp parameter — the callback writer samples `time.time()` at the write site for any `task_runs[i].finished_at`, `task_runs[i].started_at` (when first-written here), or `last_error.time` it records, per **Time sampling** under the **Units contract**. `completion_target` is a structured payload carrying `authority_end_block_id` and `requested_destination_direction`.
- The callback payloads are exactly:
  - completion context: `train_id`, `path_id`, `completion_target` (carrying `authority_end_block_id` and `requested_destination_direction`)
  - cancellation context: `train_id`, `path_id`, `reason`
  These callbacks are invoked synchronously by `PathDispatcher` immediately after committing the path-status transition, so the callback's `path_id` always identifies the just-terminated path. There is no path-id correlation step.
- In that completion context:
  - `completion_target.requested_destination_direction` is the active path's stored block-relative requested target direction (`"forward"` or `"reverse"`) at completion time
  - the callback does not carry a route-owned target block. `RouteExecutor.handle_path_completion(...)` resolves the matching route task by iterating the remaining task indexes in directed-walk order from the current route progress and selecting the first non-finished `task_kind == "stop"` task whose stored `resolved_target.requested_destination_block_id` equals `completion_target.authority_end_block_id` and whose stored `resolved_target.requested_destination_direction` equals `completion_target.requested_destination_direction`. For a `PlatformTarget` or `StationTarget` task whose live recompute could pick a different platform under the canonical helper ordering, the comparison is anchored by `task_runs[i].resolved_target` (the most recent platform actually targeted for this stop), not by a fresh `_find_next_task_target(train_id)` call: the train physically completed at the platform whose block was stored, and that stored value is the authoritative match. The dispatcher payload carries only path-completion facts.
- In that cancellation context:
  - `reason` is optional plain-text diagnostic context only and must not be used for branching. UI/log consumers that need the originating kind subscribe to the `path_cancellation` event on `NotificationCenter` (its `initiator` field carries the writer-supplied label). v1 route-side recovery does not branch on the originating kind. EB recovery timing is gated by controller state (Phase 1 cannot run until `eb.release()` has returned the controller to `READY`); power-off teardown is driven by `pending_power_off` and the controller transitioning to `OFF`; every other case shares the same recovery shell.
- The single v1 recovery table for cancellation / mismatch cases is:

  | Case | Detection point | Immediate effect | Next eligible Phase 1 |
  | --- | --- | --- | --- |
  | any cancellation (movement-derived deviation, or explicit operator cancel / revoke / EB) (`7fa0`) | `RouteExecutor.handle_path_cancellation(...)` | preserve only confirmed physical progress, set `RouteRun.path_cancelled = True` (the derived `current_route_status.display_state == "DEVIATED"` projection follows automatically) | rerun covered-task index advance plus `_find_next_task_target(train_id)` from current physical position once `controller.is_recovery_clean` is true; the next task's behavior follows normal task-kind rules |
  | shared-route reconciliation invalidates a live path (`162a`) | Phase 1 latch + Phase 3 cancel / replan flow | let the cancel callback set `path_cancelled` per the cancellation row of the **`current_route_status` write contract** | rerun ordinary planning under the same `route_id`; later Phase 1 calls `_find_next_task_target(train_id)` afresh |
  | EB interruption (`eddc`) | EB cancellation plus release flow | clear live path | the `RUNNING_MOVING` → stop → `eb.release()` chain naturally returns the controller to `READY`, at which point Phase 1 replans normally |
  | power off (`dc91`) | power-off cleanup flow | cancel live path if any, remove `RouteRun`, perform OFF cleanup | the `RouteRun` no longer exists and the controller is `OFF`; Phase 1 has nothing to do |

- `PathDispatcher.try_complete_active_path(train_id)` should follow the **Active-path completion procedure** when the post-physics controller stop check has already passed and the active path requested-target check succeeds: release not-yet-entered block reservations, release not-yet-entered switch/flank locks, transition the `Path` to `COMPLETED` (which by definition makes `active_path_id_by_train(train_id)` return `None` for this train and makes the controller's `received_path_plan` property return `None`), call `TrainController.on_path_complete()`, and then call `SimulationController.handle_path_completion(train_id, path_id, completion_target)` where `completion_target` carries `authority_end_block_id` and `requested_destination_direction` (the `SimulationController` surface delegates to `RouteExecutor.handle_path_completion(...)` per the canonical route-event delivery contract in the SimulationController section).
- `handle_path_completion()` should treat dispatcher completion as authoritative and should not perform a second exact-stop or live-controller-state check. The callback is invoked synchronously by `PathDispatcher` immediately after dispatcher transitions `Path.status` to `COMPLETED` and clears authority, so the callback's `path_id` always identifies the just-terminated path. There is no path-id correlation step.
- Every live authority path has a matching `RouteRun` in v1 (including one-off operator routes). The callback can rely on `RouteRun` existing.
- The callback does not write `Train` fields — authority residue lives on dispatcher records and controller-facing projections.
- `PathDispatcher` clears controller authority by transitioning `Path.status` to `COMPLETED` before `controller.on_path_complete()` and before calling `handle_path_completion()`. The controller's `received_path_plan` property then returns `None` on its next read, and the derived reads `controller.assigned_path_id`, `controller.ato_path_id`, and `controller.ato_destination_block_id` disappear automatically.
- `TrainController.on_path_complete()` owns the post-path stop transition and lands in the **`READY` state**; `handle_path_completion()` does not call any `transition_to_standby()`-style helper.
- Controller destination-block/path release should remain dispatcher-owned: dispatcher transitions `Path.status` (the controller's `received_path_plan` property automatically reads the new state); `TrainController.on_path_complete()` reacts to that completion while `RouteExecutor` records the completed stop. `RouteExecutor` remains responsible for entering dwell (`RUNNING_AT_STATION`) on the next eligible Phase 1 and for marking the dwell task finished in the same Phase 1 dwell-complete step.
- `handle_path_completion()` must not need to query live train/controller path state after dispatcher release. It should use the completion context passed in by `PathDispatcher` plus route-executor-owned state only.
- `RouteExecutor.handle_path_completion(...)` must not read `PathDispatcher.paths_by_id[path_id]` or any other dispatcher path record. It uses only the completion context and `exec_state.task_runs`.
- Iterate the remaining task indexes in directed-walk order from current route progress and pick the first non-finished `task_kind == "stop"` task whose stored `task_runs[i].resolved_target.requested_destination_block_id` and `requested_destination_direction` match the callback's `authority_end_block_id` and `requested_destination_direction`. The callback does NOT call `_find_next_task_target(train_id)` — `task_runs[i].resolved_target` is the authoritative record of which platform/block this stop targeted, and a station task that previously resolved to platform B must not silently match against a different platform A on completion. On a match, call `RouteExecutor._enter_task_arrival(exec_state, walk_position=walk_position)` to record `task_runs[walk_position].finished_at` (the helper samples `time.time()` at the write site per **Time sampling** under the **Units contract**). The next eligible Phase 1 dwell-entry step handles the transition into `RUNNING_AT_STATION` when the route's next task is `dwell`. The callback always matches a `stop` task: by construction of the create/extend acquisition rules (the waypoint-target exclusion in **`create_path()` flow** and the matching rule in **Path extension**), the live authority's terminal block is never a `task_kind == "waypoint"` target, so dispatcher path completion cannot land on a waypoint task. If no non-finished `stop` task in the remaining directed walk has a matching `resolved_target`, that is a contract violation; raise a fatal diagnostic through `SimulationController.enter_failed_runtime(...)` rather than silently advancing or retrying.
- Add `RouteExecutor.handle_path_cancellation(train_id, path_id, reason=None)` as the cancellation-side counterpart. The lower-to-upper ordering is canonical: `PathDispatcher.cancel_path(...)` finishes its own path/resource/controller mutation first, and only after that commit may the canonical cancellation context be handed upward to this route callback. Movement-driven cancellations detected after physics are initiated and committed in Phase 3 while the same-transaction local progress buffer is being drained. Explicit authority cancellations and EB-triggered cancellations are latched earlier through `pending_path_cancel_request`; the same train's later Phase 3 consume pass calls `PathDispatcher.cancel_path(...)` only after the normal local-progress and completion opportunity has already been processed. Explicit route abort is a separate `pending_route_abort` latch consumed after authority cancellation. Phase 1 shared-route reconciliation that invalidates a live path uses the latch-cancel-and-replan workflow described in the Route Edit And Reconciliation section. In all cases, the callback is bookkeeping only: it must not choose a fresh target or create fresh authority. The callback writes: record route/path error context on `exec_state.last_error` as one `ErrorRecord(text=..., time=...)` when relevant, and set `RouteRun.path_cancelled = True` (the derived `current_route_status.display_state == "DEVIATED"` projection follows automatically). UI/log consumers that need the originating kind read it from the canonical `path_cancellation` event on `NotificationCenter` (defined in the **Cancellation** subsection). When the train later reaches the stopped recovery state, the same train's later Phase 1 route-deviation-cleanup step consumes `path_cancelled`. A later Phase 1 planning attempt reruns ordinary covered-task index advance plus `_find_next_task_target(train_id)` from the train's current physical position and creates a brand-new path. The callback must NOT advance `current_waypoint_index`, synthesize arrival, choose the next task, or create authority while the train is still braking.
- Every cancellation source (movement-derived deviation, operator cancel, revoke, EB, power-off) shares the same `handle_path_cancellation(...)` body. There is no per-source branch inside the callback. The recovery timing differences observed at the system level emerge from runtime gates that exist independently of any enum:
  - the Phase 1 eligibility precondition only allows replanning when the controller is in `READY`, which naturally defers EB recovery until `eb.release()` has run;
  - the power-off Phase 3 cleanup separately calls `RouteExecutor.remove_train_route_run(train_id)`, which flips the run to its historical `DEACTIVATED` row so no later Phase 1 has anything to replan; `handle_path_cancellation(...)` still records the same diagnostic state, but the run is unassigned moments later by the same Phase 3 cleanup.
  Planning and routing logic rely on these runtime gates (controller state, latches, presence of `RouteRun`, current span coverage, and task-kind rules).
- Route reconciliation uses this same temporary-status-clear model only after the current live path has already left `ACTIVE`. When a shared-route reconciliation changes the active target chain, the current live path must be treated as potentially stale because the system cannot prove that the already-acquired authority is still correct for the edited route. Phase 1 therefore latches `pending_path_cancel_request` with `initiator = "revoked"` (system/non-operator-driven), stops planning for that train, and waits for the ordinary Phase 3 cancel/callback/route-deviation-cleanup flow. Operator-driven retargeting and explicit route swap take a different path entirely (abort current run + create new run, see **Route Edit And Reconciliation**); the inclusive cancel for that workflow uses `initiator = "operator_cancelled"` per the **Latch Table** preamble. Only after the live path is no longer active may `RouteExecutor` clear or rewrite the affected route-owned temporary target state and restart ordinary planning from the train's current position under the reconciled route.
- Completion handling may observe a train still physically occupying the terminal block or switch footprint. That is not a contradiction: `RouteExecutor` treats dispatcher completion as authoritative arrival, while physical resource release still waits for the later tail-vacate callbacks.
