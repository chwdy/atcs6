## Platform And Station

**Platform and station model**

- `Platform` and `Station` are canonical first-class entities in v1. Unchanged local fields, helper internals, and serialization details may continue to follow current code unless this document overrides them; the changed contracts below are the canonical ownership and lookup rules.
- `Station.platform_ids` is the canonical ordered grouping list of concrete `Platform` IDs belonging to that logical station. Route planning that resolves a `StationTarget` task_location reads only through that list; it does not inspect tile-level station membership fields.
- `Platform.ordered_blocks` is the canonical ordered physical extent of that concrete platform. Route target resolution, platform-end selection, and platform availability checks all read platform membership from this ordered block list rather than from `TrackSegment.station_id`, `TrackSegment.block_section_id`, or ad hoc tile scans.
- `RailwayNetwork` owns the reverse indices required by the desired model: at minimum block -> platform, tile -> block, tile -> platform, and tile -> station-group lookups derived from the canonical `Station.platform_ids`, `Platform.ordered_blocks`, and `Block.ordered_tiles` ownership chain. Callers that need membership or reverse ownership resolve it through `RailwayNetwork`; lower-level entities do not keep back-reference membership fields in v1.
- Route resolution, platform availability, current-span coverage checks, and UI/export helpers that need platform/station membership use those `RailwayNetwork`-owned indices plus the canonical `Platform` / `Station` ownership fields. They do not consult tile-level membership.
- **Resolution ownership.** `Platform` and `Station` are pure data containers and have no `resolve(...)` methods. Resolution of a `RouteTask` whose `task_location` is a `StationTarget` or `PlatformTarget` into one concrete `(platform_id, block_id, requested_destination_direction)` is owned entirely by `RouteExecutor._find_next_task_target(train_id)` (see [210-route-executor.md](210-route-executor.md)). That helper reads `Station.platform_ids`, `Platform.ordered_blocks`, and the `RailwayNetwork` reverse indices defined above; it does not delegate to platform/station-owned helpers.
- `RailwayNetwork.add_station / add_platform / delete_station / delete_platform / extend_station / extend_platform / get_station / get_platform / create_station_group / delete_station_group / add_platform_to_station_group / remove_platform_from_station_group / tile_to_platform_id / tile_to_station_id` are doc-canonical method names but are now implemented as forwarders to `StationRegistry`. The actual platform/station CRUD logic lives in `station_registry.py`. The `platforms`, `station_groups`, and `_tile_to_platform` registries remain stored on `RailwayNetwork` itself; `StationRegistry` reads and writes them via a back-reference. External callers (UI, scenario setup, tests) keep using the network surface unchanged.
