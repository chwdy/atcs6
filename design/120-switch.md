## Switch Entity

**Switch entity**

- `Switch` is a `TrackResource` subclass; the shared identity surface (`resource_id`, `resource_type == "switch"`, `name`, `occupied_by`, `disabled`) comes from the **TrackResource** canonical home. Switch-only fields below extend that base.
- `Switch` should become a first-class resource entity at the same level as a block.
- The retained `Switch` schema in v1 is explicit:
  - identity/location: `switch_id`, `x`, `y` (and the `name` / `occupied_by` / `disabled` fields inherited from `TrackResource`)
  - retained physical/configuration fields from current code: `main_length_cm`, `diverge_length_cm`, `main_radius_cm`, `diverge_radius_cm`, `switch_type`, `notes`
  - new authoritative live/runtime fields: `position`, `locks`, `flank_protection`, `train_protection_claims`, `simulation_controller: Optional[SimulationController]` (Optional because editor mode may instantiate a `Switch` before any `SimulationController` exists; runtime mutations require it to be wired)
  - `simulation_controller: Optional[SimulationController]` is the runtime back-reference to the owning `SimulationController`. It is wired by `SimulationController.__init__` for already-loaded switches and by registration on later-loaded switches, and is required for any `Switch.acquire_lock(...)`, `Switch.release_lock(...)`, or `Switch.position` mutation that must notify `BlockManager`. The dispatcher-facing entry points for path-driven multi-switch acquisition / release / clean physical entry / tail-vacate now live on **SwitchManager** (which calls these `Switch` primitives); `PathDispatcher` reaches `SwitchManager` through the **ResourceCoordinator** facade.
- `disabled` means the switch behaves like missing track / an open circuit. A disabled switch cannot be traversed, locked, or used by pathfinding/wayfinding, and callers should treat it as absent connectivity until it is re-enabled. Live traversal helpers return no usable traversal through a disabled switch, so normal physics cannot enter it through live geometry.
- Runtime physical entry into a disabled switch is not a normal recoverable workflow. Because a disabled switch is an open circuit, `TrainPhysics` should stop at the last reachable live edge; if a controller progress report nevertheless says the train entered that disabled switch, `PathDispatcher.on_controller_progress(report)` routes the entry to `ResourceCoordinator.on_physical_entry(...)` → `SwitchManager.on_physical_entry(...)`, which must treat it as a fatal physical-entry conflict and report `conflict_kind = FatalConflictKind.DISABLED_RESOURCE_ENTRY` to `SimulationController.enter_failed_runtime(...)`; it must not silently set `Switch.occupied_by`. Operator/admin code must reject disabling a switch that is physically occupied, has future locks, or has train-owned protection. v1 has no force-cleanup workflow that bypasses these claims; the operator/admin must remove the conflicting train, cancel the holding path, or release the train-owned protection through the ordinary runtime workflows before the disable request is accepted. Any runtime enable/disable mutation changes connectivity and must notify `BlockManager.on_switch_position_changed(switch_id)` (or an equivalent topology-availability callback) so directional `CAUTION` reevaluation sees the open circuit immediately.
- Add `position: int` as the authoritative physical switch alignment. In the desired model the code-defined values are retained explicitly: `0 = MAIN`, `1 = DIVERGE`. When traversal code needs the active switch segment, it should resolve that alignment from the `Switch` entity rather than keeping a second authoritative live copy on `TrackSegment`.
- `occupied_by: Optional[str]` (inherited from `TrackResource`) is the switch resource's physical-occupancy field. `occupied_by` means a train is physically spanning the switch tile right now; it is set on switch-resource entry and cleared on tail-vacate. Reservation/lock ownership remains separate.
- Replace single-owner `locked_by_path` / `locked_state` fields with future-authority `locks`, keyed canonically by `(path_id, source_switch_id)` where `source_switch_id` is `None` for a main-usage claim and the originating main switch ID for a flank-protection claim. Each future-authority lock claim stores exactly `path_id`, `source_switch_id: Optional[str]`, `train_id`, and `locked_state`. The convenience read `claim_role` (= `"main"` if `source_switch_id is None` else `"flank"`) may still be referenced by name in this document. Path locks do not carry a deferred-release flag in v1.
- `train_protection_claims` is the train-owned physical protection set used after the train head has entered a switch and consumed the path lock. Each claim stores exactly `train_id`, `source_switch_id`, and `locked_state`; it blocks conflicting switch state changes until the source switch tail-vacate event clears it.

**Return-contract principle for `BlockManager` / `Switch` mutators.** Every method returns either `bool` (single success/failure) or a structured `<Method>Result` object (multiple distinguishable failure modes that callers branch on). When the result's "kind" or "reason" field is purely diagnostic (no caller branches on it), it is a free-form `str`, not a new enum. New enums require a caller that actually branches on the values; otherwise they are diagnostic-only and belong as strings.

- `Switch.acquire_lock(claim)` takes a structured `claim` payload carrying `path_id`, `train_id`, `locked_state`, and optional `source_switch_id` (`None` for a main-usage claim, originating main switch ID for a flank-protection claim). The input field name `locked_state` matches the stored claim field, so the same name is used everywhere — there is no input-vs-stored renaming inside the helper. It must first check `Switch.locks`, `Switch.occupied_by`, and `Switch.train_protection_claims`. Compatible future switch locks may be shared only when no switch throw is required and only within the cross-train rule defined two bullets below: if `Switch.position` already equals `claim.locked_state` and all existing future locks / train-owned protection are compatible with `claim.locked_state` and the new claim is not a cross-train primary collision, `acquire_lock(claim)` may record another future lock claim without moving the switch. If the current state differs, `acquire_lock(claim)` may throw the switch only when no physical occupancy or train-owned protection exists and no future lock requires another state. Physically occupied switches are not acquirable for future authority except for same-train already-covered span entries that are seeded into `Path.resource_sequence` and are not newly locked. Returns `LockAcquireResult(success: bool, reason: Optional[str])`. On failure, `reason` is a free-form diagnostic string (e.g., `"disabled switch"`, `"locked state conflicts with existing claim"`, `"physical occupancy by other train"`, `"cross-train primary lock conflict"`, `"protection conflict"`).
- `Switch.acquire_lock(...)` must fail immediately when `Switch.disabled == True`.
- Every successful `Switch.position` mutation path, whether it came from dispatcher lock acquisition or from a manual/API switch-state command, must use the same canonical mutation workflow: validate that no future lock, physical occupancy, or train-owned protection requires a different state; write `Switch.position`; then notify `BlockManager.on_switch_position_changed(switch_id)`. The validate-and-write step is `Switch.apply_position_change(new_position)` (a pure data operation that does not notify any external entity). The cross-resource notification to `BlockManager` is paired with that write inside `SwitchManager.request_position_change(switch_id, new_position)`, which is the single public entry point for position-change requests; admin / API / UI handlers route through the manager so the notification is never skipped. `Switch` holds the standard `simulation_controller` back-reference per the canonical entity-wiring rule in **SimulationController runtime surface**, but the only public position-mutation entry point is `SwitchManager.request_position_change(...)`; admin / API / UI handlers must not assign `Switch.position` directly. Pure geometric editor writes (placement, connectivity wiring, static field edits that do not affect occupancy or locks) do not invoke runtime methods and remain safe without any runtime surface.
- A non-dispatcher/manual/API switch-state command follows that same canonical workflow and may change `Switch.position` only when no lock, physical occupancy, or train-owned protection blocks the requested state. If any such claim exists, the state-change request must fail rather than bypassing the workflow. Such a manual/API command is a runtime mutation and therefore also requires `simulation_controller` to be wired; it must raise in pure editor mode and is available only when the editor session has instantiated a runtime surface.
- Manual/API switch-state command result delivery follows the canonical `NotificationCenter` contract. The API/UI request handler returns accepted/pending once the request has been validated and forwarded to the targeted `Switch`. The actual command result — success or failure — surfaces through `NotificationCenter` as a `command_result` notification with `source = "Switch"`, `severity = "info"` on success or `"warning"` on failure, payload `{command_id, command_name, switch_id, success, reason}`. This matches the operator-command notification contract under **Runtime notifications**; request handlers must not synthesize a synchronous error response that bypasses this surface.
- A disabled switch cannot be targeted by a manual/API switch-state command in v1; the request must fail through that same `command_result` notification rather than mutating the disabled switch.
- `Switch.acquire_lock(claim)` should be idempotent only for an already-recorded claim on that same canonical claim key with the same `locked_state`, and succeed immediately in that case.
- `Switch.acquire_lock(claim)` should allow multiple paths to hold future lock claims on the same switch when those claims all require the same physical `claim.locked_state` and the switch is already in that state. This same-state co-locking is restricted to same-train multi-path use and to flank claims (any `source_switch_id != None`): a new primary claim (`source_switch_id is None`) from a different `train_id` than an existing primary claim is rejected even when the requested `locked_state` matches. Two trains' primary claims would both authorize physical traversal, but `Switch.occupied_by` is single-owner — the second train to arrive would otherwise hit the `SWITCH_OCCUPIED_BY_OTHER_TRAIN` fatal conflict on physical entry. The blocked train's path acquisition falls through the ordinary `SWITCH_LOCKED` failure into `PathDispatcher`'s BEST_EFFORT truncation, which lands the live authority on the block before the contested switch; the holding train's tail-vacate clears the lock and the blocked train extends past on a later tick.
- `Switch.acquire_lock(claim)` must fail if any existing future lock or train-owned protection on that switch requires a different physical state, or if satisfying the request would require throwing a physically occupied switch.
- When the train head enters a switch, `PathDispatcher.on_controller_progress(report)` routes the entry through `ResourceCoordinator.on_physical_entry(...)` to `SwitchManager.on_physical_entry(...)`. That manager consumes that path's main switch lock for the entered switch and converts any path-owned flank locks sourced from that main switch into `train_protection_claims`. From that point onward the occupied switch and its active flank protection are train-owned physical state, not path-owned cleanup.
- `release_lock(path_id, source_switch_id=None)` removes that future-authority claim immediately. It must not inspect train physical occupancy or set a pending flag; an occupied switch is protected by `Switch.occupied_by` and any `train_protection_claims`, not by a retained path lock. Returns `bool`: `True` if a matching claim was found and removed; `False` if no matching claim existed. Idempotent; no exception raised.
- Releasing or rolling back a switch lock claim does **not** restore a previous physical `Switch.position` in v1. `Switch.position` stays at the last successfully written alignment; a later compatible or conflicting path acquisition sets it again if needed.
- Add `release_train_protection_from(source_switch_id, train_id)` on `Switch` for neighbour-side tail-vacate cleanup. It removes only train-owned physical protection claims where `claim.train_id == train_id` and `claim.source_switch_id == source_switch_id`. This helper manages train-protection claims only; it does not read or mutate `occupied_by`. It is called when the source switch's tail-vacate event clears `Switch.occupied_by`; it is not a path-release trigger. Returns `bool`: `True` if at least one matching claim was removed; `False` if none. Idempotent.
- `Switch.release_train_protection_from(source_switch_id, train_id)` does **not** inspect `Switch.occupied_by`; the caller is responsible for the `train_id == Switch.occupied_by` ordering check before invoking it. The helper purely removes train-owned protection claims matching `(source_switch_id, train_id)`.
- Candidate `end_a` dead-heat tie-break source: `start_locator.physical_end` carries the `end_a` / `end_b` label; the caller passes that field as the dead-heat key, not a `GraphWalkCandidate` field.
- Tail-vacate switch release must compare the releasing `train_id` with the current `Switch.occupied_by` before clearing anything. If they match, clear `Switch.occupied_by` and then release neighbour-side train protection sourced from that switch. If they do not match, leave switch occupancy and train protection unchanged and emit a `NotificationCenter` diagnostic such as `switch <switch_id> release for train <train_id> skipped: currently occupied by <other_train_id>`.
- `Switch.locks` is a multi-owner lock collection in the sense that it can carry multiple compatible entries from the same train (different paths, flank claims sourced from different neighbour switches), but it does not carry primary claims from different trains: those serialize through the same-state cross-train rule defined for `acquire_lock(claim)` above. Physical occupancy is always single-owner: only one train may have `Switch.occupied_by` at a time.
- Add `flank_protection: List[Tuple[str, int]]` on the switch entity. In v1 each tuple is exactly `(neighbour_switch_id, blocking_state)`, where `blocking_state` is the neighbour state that would create the flank conflict if that neighbour were set toward this switch.

**Switch invariants**

- `is_locked()` and `can_lock(state)` should check the canonical `(path_id, source_switch_id)`-keyed future lock collection plus train-owned physical protection, not a single field. `can_lock(state)` means "is there a compatible lock/protection state for this switch right now," not "is there only one owner." Train-owned protection continues to block a conflicting acquisition until the later tail-vacate callback removes it.

## Flank Protection Computation

**Flank protection computation**

- Compute flank-protection relationships at the network level and store them on each switch entity instead of on individual paths.
- Use one canonical global setting `FLANK_PROTECTION_DISTANCE_CM = 5.0` when searching for nearby switches that require mutual locking.
- At switch placement time, search the network graph outward from the switch tile, determine which neighbour states would create a flank conflict, and append `(neighbour_switch_id, blocking_state)` to `flank_protection`.
- Recompute nearby flank-protection relationships whenever topology changes.
- In v1, future flank protection uses the same `Switch.locks` compatibility rule as ordinary future switch use: multiple paths may hold compatible same-state lock claims, but physical occupancy is still single-owner and no lock or protection set may demand conflicting physical states. Future flank-protection claims follow the same `(path_id, source_switch_id, train_id, locked_state)` contract as primary switch claims; flank claims set `source_switch_id` to the main switch whose acquisition created that claim, while main claims have `source_switch_id = None`. When the train head enters the source switch, those future flank claims are consumed into `train_protection_claims` until source-switch tail-vacate clears them. Stored flank-protection data remains `(neighbour_switch_id, blocking_state)`; the acquisition-time `safe_state` is derived from it as `1 - blocking_state` because v1 switches are binary.

## SwitchManager

**Switch-manager model**

- `SwitchManager` is the database-style lock manager for switch resources and the single serialization point for atomic multi-switch lock acquisition, whether the dispatcher is attempting a full-route all-or-nothing acquisition or a best-effort prefix. It mirrors `BlockManager`'s contract on the switch side.
- `SwitchManager` holds the owning `RailwayNetwork` reference and an `Optional[SimulationController]` runtime back-reference. It uses the network for the switch registry; it uses the runtime surface only to report fatal physical-entry conflicts through `SimulationController.enter_failed_runtime(...)`. In editor mode (no `SimulationController`) the manager exists but its runtime entry points are not exercised.
- `SwitchLockRequest` is the canonical value type for one requested switch lock. It carries exactly `switch_id`, `locked_state`, `claim_role` (`"primary" | "flank" | "overlap"`), and optional `source_switch_id` (`None` for primary; the originating switch_id for flank claims).
- `SwitchManager.acquire_locks_for_segment(requests, path_id, train_id)` attempts every requested switch lock atomically. On any failure it rolls back the locks recorded in this call and returns `LockAcquireResult(success: bool, failed_switch_id: Optional[str], reason: Optional[str], locked_switch_ids: List[str])`. Same all-or-nothing rule as `BlockManager.reserve_blocks_for_path(...)`.
- `SwitchManager.release_path_locks(path_id)` releases every lock owned by `path_id` across every switch. `SwitchManager.release_path_locks_for_switches(switch_ids, path_id)` is the segment-rollback variant scoped to a passed switch_id list.
- `SwitchManager.on_switch_tail_vacated(switch_id, train_id)` is the canonical switch tail-vacate entry, called by `PathDispatcher.on_controller_progress(report)` for switch tail-vacate events through the `ResourceCoordinator` facade. The manager performs the `train_id == Switch.occupied_by` ordering check first, then clears `Switch.occupied_by` and calls `Switch.release_train_protection_from(switch_id, train_id)` to release train-owned protection sourced from this switch on every neighbour. If the ordering check fails, the manager leaves `Switch.occupied_by` and train protection unchanged and emits a `NotificationCenter` diagnostic per the switch-entity tail-vacate rule. There is no `Switch.on_train_tail_vacated(...)` entity helper; the per-switch primitives are `Switch.release_train_protection_from(source_switch_id, train_id)` plus the direct `Switch.occupied_by` clear, both already declared above.
- `SwitchManager.on_physical_entry(switch_id, train_id, path_id)` is the canonical clean-physical-entry entry. It owns the flank-lock conversion: on clean entry it sets `Switch.occupied_by = train_id`, consumes the path-owned primary lock for that switch, and converts every required flank-protection claim on neighbours into train-owned `train_protection_claims` per the **Switch entity** flank-protection contract. Conflict cases (occupied-by-other-train, disabled switch entry) are reported through the **Fatal physical-entry conflict procedure** and return `False`.
- The actual `Switch.position` write still goes through the canonical mutation workflow on `Switch` per the **Switch entity** section; `SwitchManager` calls into that workflow rather than mutating `Switch.position` directly.
