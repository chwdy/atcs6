## TrainPhysics

**Movement-authority input in `TrainPhysics`**

- `TrainPhysics` should continue to execute physical integration (speed update, span/end-locator update, occupancy tracing, and tail tracing), but the canonical live storage is `TrainController.physics_sync.current_span` and `TrainController.physics_sync.current_speed_kmh`. `TrainPhysics.tick(delta_seconds) -> List[ControllerProgressReport]` computes each `span_update` (`new_span`, `current_speed_kmh`, ordered `added_tiles`, ordered `removed_tiles`, and traversal frame metadata), passes it to `TrainController.on_physics_updated(span_update)` once per crossed resource boundary plus a final no-boundary callback per tick, and returns the ordered list of `ControllerProgressReport` values that each callback produced. `SimulationController` consumes that return value into the per-train same-transaction local progress buffer drained in Phase 3. `TrainPhysics` must not call `PathDispatcher`, `RouteExecutor`, `BlockManager`, or `SwitchManager` directly; the controller callback is the only outbound channel. `TrainPhysics` should not own path identity, dispatcher authority state, progress interpretation, completion, or a separate canonical position store on `Train`.
- To choose exits on ambiguous geometry, `TrainPhysics` normally needs a controller-provided, read-only authority-geometry projection derived from `TrainController.path_projection.received_path_plan.resource_sequence`. The minimum movement data is the ordered `resource_sequence` / `path_tiles` geometry from that active plan, plus enough local direction context to choose the correct next edge through the current tile.
- `TrainPhysics` does **not** need dispatcher ownership fields such as `path_id` to step the train, and it does not need requested/authorized centimeter stop targets for physical integration. Centimeter stop-target fields are not part of the v1 path/controller contract; controller braking logic uses authority-boundary geometry plus the controller safety margin.
- `TrainPhysics` should obtain that geometry projection from `TrainController.path_projection.received_path_plan`. `Train.current_path` should not remain a movement input.
- `TrainPhysics` should read the current live position through the controller-owned span and should write movement only by sending `span_update` to `TrainController.on_physics_updated(span_update)`, not through any train-entity position field. Initial placement is established by the API `SimulationController.add_train(...)` flow writing `TrainController.physics_sync.current_span` before the first tick. (Persistence and save-data migration are Out of Scope; see the **Out of Scope** section.)
- Exception for cancellation/revocation braking: if the dispatcher-owned path has already transitioned out of `ACTIVE` while the train is still rolling, `TrainPhysics` must still keep moving the train according to speed and the current live network state. That post-revocation movement relies on the physical `Switch.position` / live track geometry that exists in the network at that moment, not on retained authority locks or a second copy of path ownership surviving in the controller.
- Once live switch state ownership moves to `Switch`, `TrainPhysics._advance_end()` and tail tracing must call the updated `TrackSegment` traversal helpers using the resolver input defined by the `TrackSegment` helper contract above.

**Block occupancy**

- Route normal tail-vacated transitions through `TrainController.on_physics_updated(span_update)` and `PathDispatcher.on_controller_progress(report)`, which routes block releases through `BlockManager.on_block_tail_vacated()` so `OCCUPIED -> CAUTION -> FREE` stays in one state machine.
- `TrainPhysics` must not write `Block` fields directly and must not call block-state mutators for normal occupancy, CAUTION, or release. It computes movement `span_update` values, and the controller/dispatcher feedback chain performs all block writes through `BlockManager`.
- `TrainController.on_physics_updated(span_update)` must not include a block in `tail_vacated_resources` just because the tail left one tile of that block. `PathDispatcher` may call `BlockManager.on_block_tail_vacated()` only after the controller report proves the train no longer occupies **any** tile in that block.
- Normal CAUTION clearing happens inside `on_block_tail_vacated()` via `_reevaluate_caution_blocks()`. There is no separate `clear_block()` / `release_block()` step.

**Tail-vacate flow in `TrainPhysics`**

- `TrainPhysics` does not call `BlockManager` mutators directly; CAUTION transitions go through `on_block_tail_vacated()` via the controller-reported tail-vacate path.
- On tail-vacate, `TrainController.on_physics_updated(span_update)` includes a typed resource-release observation in `tail_vacated_resources`, packages it into the same `ControllerProgressReport`, and returns that report for the train's same-transaction Phase 3 consume pass. For blocks, the controller must report the vacate only after the updated `current_span` proves the train no longer occupies any tile in that block; tile-level vacate is not enough. For switches, tile-level vacate of the switch resource is sufficient. The resource event obtains `resource_id` from the same tile-lookup mechanism already used for entry detection: block IDs come from the `RailwayNetwork` tile-to-block reverse index computed from `Block.ordered_tiles`, and switch IDs come from `TrackSegment.switch_id` on switch tiles. The controller report carries block tail-vacate `direction` as the vacated block's forward `exit_edge` for the traversal by which the train left that block. During Phase 3, `PathDispatcher` routes the release according to `resource_type`: blocks go through `BlockManager.on_block_tail_vacated(block_id, train_id, direction)` so `OCCUPIED -> CAUTION -> FREE` stays in one state machine; switches go through the `Switch` entity by clearing `Switch.occupied_by` and then clearing train-owned protection sourced from that vacated switch.
- `TrainPhysics` does not track its own `_caution_blocks`; `BlockManager` owns the full release lifecycle.

**Voltage behavior**

- Keep the terminology explicit and simple: `track_voltage`, `power_percent`, and `speed_kmh` are three different values. **Canonical home for `track_voltage` is `TrainPhysics`**: it is computed each tick from the authoritative source for the active mode (controller/physics speed solution in ATO/manual-simulation; `manual.manual_power_percent` mapped through `SpeedProfile.power_speed_curve` in manual `power_percent` mode). `track_voltage` is not a stored field on `TrainController` or persisted on `Train`; it is per-tick derived state owned by `TrainPhysics` and emitted to `BlockPowerController` as that tick's hardware output.
- `TrainPhysics` should pass the current `track_voltage` value to `BlockPowerController` as the software-to-hardware output layer for block voltage emission.
- The active mode determines which value is authoritative. In ATO and manual `simulation` mode, `speed_kmh` is the controller/physics source of truth and `power_percent` / `track_voltage` are derived from that current operating point. In manual `power_percent` mode, `manual.manual_power_percent` is the source of truth and `speed_kmh` / `track_voltage` are derived from that commanded power level in the same movement update; the manual power command sets the absolute calibrated voltage/speed point instead of being integrated through the normal service acceleration/deceleration rates.
- In manual `power_percent` mode, that authority applies only while no controller braking override is active. There is no handle-based speed-up/speed-down integration in this submode: without a braking override, `TrainPhysics` uses the calibrated `power_percent -> speed_kmh` result directly as the movement speed for that tick. If ATC/service braking or EB is active, the controller forces `manual_power_percent = 0` for that tick (with EB additionally engaging `eb.active`), and `TrainPhysics` uses the calibrated zero-power / zero-speed outcome for that tick rather than a handle-based braking command.
- In `power_percent` manual mode, `TrainPhysics` should use the profile's voltage/power/speed calibration directly rather than reading removed scalar target-speed fields or applying the service acceleration/deceleration rates to the manual-power command. The calibration must be usable in both directions so physics can convert between the authoritative value for the active mode and the derived outputs it needs to maintain. These mappings are owned by `SpeedProfile` and should be documented exactly this way:
  - `track_voltage <-> power_percent`
  - `power_percent <-> speed_kmh`
- When `TrainPhysics` needs `track_voltage`, it derives it from the current authoritative mode input: `speed_kmh -> power_percent -> track_voltage` in ATO and manual `simulation` mode, or `manual_power_percent -> track_voltage` plus the calibrated absolute `speed_kmh` command in manual `power_percent` mode. In manual `power_percent` mode without a braking override, that calibrated `speed_kmh` is written into the same `PhysicsSpanUpdate.current_speed_kmh` that carries the movement result.
- Do not introduce extra names for these concepts. Keep the doc wording in terms of voltage, power percent, and speed, and keep the mappings distinct.

**Physics invariants**

- `TrainPhysics` should not own manual-mode policy; it should execute controller commands and maintain physical state only.
- `TrainPhysics` no longer relies on a separate track-level path-lock field. The future-authority role is now played by `Block.reserved_by_path` / `Block.reserved_for_train` on the block side and `Switch.locks` on the switch side. Movement remains geometry-driven; once the train enters a resource, switch integrity during traversal is enforced by `Switch.occupied_by` plus any `Switch.train_protection_claims` rather than by a global track-level path lock or retained path claim. This is not a transitional/migrated version of the old field — the mechanism is different, so no transitional phase is needed.
